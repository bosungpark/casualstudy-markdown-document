## AI 요약

### 1. 한 줄 요약

> LLM은 코드를 엄청나게 빨리 만든다. 문제는 **의도한 것만** 만들게 하는 것이고,
> 그 경계선 역할을 하는 것이 **도메인 추상화와 DSL**이다.

저자는 이를 "harness(구속구)"라고 부른다. 프롬프트를 정교하게 다듬어 LLM을 설득하는 게 아니라, **LLM이 틀릴 수 있는 공간 자체를 좁히는** 접근이다.

### 2. 출발점 — 왜 "명세를 잘 쓰면 된다"가 안 되는가

저자는 두 가지 전제에서 출발한다.

**(a) 사전 명세의 한계 (The Limits of Upfront Specification)**

큰 시스템을 만드는 일은 수많은 작은 설계 결정으로 이루어지는데, 이건 미리 다 알 수 없다. 실제 제약·트레이드오프·엣지 케이스는 **구현하면서 반복적으로 발견된다.**

> 명세는 잘해봐야 **출발 가설(starting hypothesis)** 이지, 완성된 청사진이 아니다.

(저자는 이전 글에서 이를 *Upfront Specification Impossibility*라고 불렀다.)

**(b) 설계는 구현을 통해 드러난다 (Design Is Discovered Through Implementation)**

여기가 이 글의 가장 날카로운 지점이다.

| | 코드를 **리뷰**할 때 | 코드를 **작성**할 때 |
|---|---|---|
| 하는 일 | 청크 단위로 "내 의도와 맞나" 확인, 함정 찾기 | 책임이 어디에 속하는지, 경계를 어디까지 노출할지 결정 |
| 설계와의 관계 | 설계 결정과 **씨름하게 만들지 않는다** | 구체적 결정을 강제한다 |

즉 "LLM이 짜고 내가 리뷰한다"는 루프는 **설계가 아직 발견되지 않은 단계에서는 작동하지 않는다.** 리뷰는 설계를 드러내주지 않기 때문이다.

여기서 저자는 코드의 이중성을 강조한다 — 코드는 **기계를 위한 명령어**이자 동시에 **도메인의 개념 모델**이다. 잘 설계된 코드베이스는 그 도메인의 어휘(vocabulary)를 표현한다.

### 3. 그래서 LLM의 자리는 어디인가

저자는 LLM의 역할을 도메인 모델의 존재 여부로 나눈다. DDD의 **Ubiquitous Language** 개념을 빌려온다.

```
도메인 모델이 아직 없다  →  LLM = 브레인스토밍 파트너 (설계 공간 탐색, 어휘 발견)
도메인 모델이 이미 있다  →  LLM = 그 어휘에 대한 자연어 인터페이스
```

이 구분이 글 전체를 관통하고, 마지막 절에서 "두 단계(Two phases)"로 다시 정리된다.

### 4. 왜 DSL이 LLM과 유난히 잘 맞는가

이미 우리가 체감하고 있는 사실부터 짚는다. LLM은 **PlantUML, Mermaid, Graphviz, SQL, 쿠버네티스 YAML**을 놀랍도록 잘 만든다. 이들은 전부 범용 언어가 아니라 **의도적으로 제약된 DSL**이다.

이유는 두 가지다.

**(1) 표현의 변주가 제거된다**

> Java 같은 범용 언어는 같은 의도를 표현하는 유효한 방법이 너무 많다.
> **DSL은 그 변주를 걷어낸다.** 그래서 few-shot 예시 몇 개면 문법을 안정적으로 생성한다.

(저자는 단서를 단다 — 최신 모델은 PlantUML이나 Java fluent interface를 학습 때 이미 많이 봤다. **진짜 새로운 DSL**을 작은 모델에 물렸을 때 어떨지는 아직 지켜볼 일이라고.)

**(2) DSL에는 거의 항상 결정론적 검증기가 딸려온다** ← 에이전트 관점에서 핵심

파서, JSON 스키마, 타입 체커, 컴파일러. 에이전트는 **생성 → 검증기 통과 → 에러로부터 수리**를 사람 개입 없이 돌릴 수 있다. 게다가 결정적으로:

> 에러가 **도메인 수준의 언어로** 나온다.
> *"클라이언트를 고르기 전에 액션을 선택할 수 없습니다"* ← 이렇게.
> 생성된 코드 깊숙이 묻힌 스택트레이스가 아니라.

**단, 만능이 아니다.** 저자가 명시한 조건:
- 이점은 **DSL이 작고 제약적으로 유지되는 동안만** 성립한다 (few-shot으로 사용법이 전달될 정도).
- 언어와 시맨틱 모델을 설계·유지하는 **선행 비용이 실재한다.**
- 따라서 보상은 **검증기가 뒷받침하는, 잘 factoring된 진짜 제약적인 DSL**에 집중된다.

### 5. 예시 A — 가벼운 DSL: 슬라이드 YAML

저자는 분산 시스템을 가르치면서 시퀀스 다이어그램을 **단계별로** 보여주는 슬라이드가 필요했다. 그래서 PlantUML에 `'[step]` 마커를 얹고, 그걸 참조하는 작은 YAML 스펙을 만들었다.

```yaml
- slide:
    title: "Quorum Write Example"
    diagram: "quorum-write"
```

프롬프트는 그냥 *"'quorum-write' 다이어그램을 참조하는 'Quorum Write Example' 제목의 슬라이드 YAML을 만들어줘"* 수준이다.

여기서 저자가 짚는 포인트: **"아무 YAML이나"가 아니다.** 도구가 이해하는 YAML 스펙이 프롬프트의 컨텍스트로 들어가 있기 때문에, LLM이 **곧바로 도구에 투입 가능한** 올바른 스펙을 만든다.

그리고 이 단순한 예시 안에 이미 두 역할이 다 들어있다 — 먼저 **공동 설계자**(step 마커 확장과 슬라이드 YAML을 함께 다듬음), 그다음 **자연어 인터페이스**.

### 6. Semantic Model — Tickloom 사례

YAML 예시는 구문 트리를 그대로 시맨틱 모델로 썼다(구문과 실행 의미가 결합되는 단점이 있다). 분산 시스템처럼 복잡한 도메인에서는 제대로 된 **시맨틱 모델**이 필요하다.

**문제 정의가 인상적이다.** 저자는 분산 시스템 구현의 난점을 코드 생성 복잡도가 아니라 **검증 복잡도**로 규정한다.

> 스레드 스케줄링 × 네트워크 지연 × 프로세스 정지 × 클럭 스큐의 가능한 인터리빙이 만드는 상태 공간이 너무 커서, 모든 상호작용 동작의 정확성을 체계적으로 리뷰·검증하는 게 거의 불가능하다.
> **그래서 Jepsen 테스트가 가장 검증된 분산 시스템에서도 버그를 찾아낸다.**

Tickloom은 이 상태 공간을 **설계 결정으로 미리 닫아버린** 프레임워크다.

| 축 | Tickloom의 결정 |
|---|---|
| 스레딩 | 모든 노드가 **단일 스레드 tick loop**. `tick()` 호출이 논리 시계를 1 진행 |
| 실행 순서 | 고정된 결정론적 순서 (network → message bus → process → storage) |
| 시간 | 밀리초가 아니라 **tick** |
| 메시지 | 평범한 Java record |
| 조정 | `Replica` 베이스 클래스가 peer·브로드캐스트·쿼럼을 이미 알고 있음 |

핵심 효과:

> 스레딩·타이밍·네트워크 전달이 **매 프롬프트마다 다시 결정될 열린 질문이 아니게 된다.**
> 알고리즘 작성자에게 남는 건 실제 프로토콜 로직뿐이다.

그래서 프롬프트가 배관(plumbing)이 아니라 **프로토콜 수준**에 머물 수 있다:

> *"Tickloom Replica 추상화를 써서 쿼럼 기반 key-value 스토어를 구현해줘. 클라이언트 GET은 과반에서 값을 모아 타임스탬프가 가장 큰 것을 반환(last-writer-wins). 쓰기는 저장된 것보다 타임스탬프가 최신일 때만 로컬 적용."*

생성된 코드는 `quorumRequest(...)`, `countResponseIf(...)`, `initialiseHandlers()` 같은 **프레임워크 어휘 안에서만** 움직인다.

> 시맨틱 모델 자체가 컨텍스트로 작동한다. 프롬프트가 부르는 개념이 코드베이스에 **구체적인 타입으로 실재**하므로, LLM은 스레딩 모델이나 네트워크 레이어를 발명하지 않는다.

### 7. DSL이 없어도 — 좋은 추상화만으로도 효과가 있다

이 절이 실무적으로 제일 유용하다. 저자는 DSL을 스펙트럼의 한쪽 끝으로 놓고, **자기만의 언어를 만들기 전에 깨끗한 추상화부터** 보라고 한다.

> 라이브러리의 **이름 붙은 타입과 메서드 자체가 이미 모델을 그라운딩할 수 있는 어휘**다.

Tickloom의 시맨틱 모델도 결국 네 개의 seam일 뿐이다:

```
Process / Replica  →  연산과 메시지 처리
Network            →  통신
Storage            →  영속성
Clock (logical)    →  시간
```

**새로운 문법 하나 없이** 이 분해가 대부분의 일을 한다. "Raft를 Tickloom Replica로 구현해줘"라는 프롬프트는 탐색할 상태 공간이 제한적이고, 기존 `QuorumReplica`를 worked example로 컨텍스트에 넣을 수 있다.

### 8. 예시 B — 시나리오 테스트 DSL (before / after)

알고리즘 구현과 **그걸 시험하는 것**은 다른 문제다. 분산 시스템의 미묘한 버그는 특정 **순서(ordering)** 에 산다 — 리더의 쿼럼이 옮겨가기 직전에 한 노드에만 복제된 쓰기, 하필 그 순간 치유되는 파티션, 어긋난 두 코디네이터의 시계.

**Before — 테스트킷 직접 사용 (클럭 스큐 시나리오)**

```java
Cluster cluster = new Cluster()
    .withProcessIds(Arrays.asList(ATHENS, BYZANTIUM, CYRENE))
    .useSimulatedNetwork()
    .build(QuorumReplica::new);
cluster.start();
try {
    cluster.tickUntil(cluster::areAllNodesInitialized);
    cluster.setTimeForProcess(ATHENS, 1000L);
    cluster.setTimeForProcess(BYZANTIUM, 2000L);
    QuorumReplicaClient alice = cluster.newClientConnectedTo(ALICE, ATHENS, QuorumReplicaClient::new);
    // ... 바이트 인코딩, tickUntilComplete, 팩토리 오버로드 선택 ...
} finally { cluster.close(); }
```

저자의 진단:

> 의도 — *"Bob이 Byzantium을 통해 쓰고, Alice가 Athens를 통해 쓰고, Byzantium의 시계가 앞서 있었기 때문에 리더가 Bob의 값을 본다"* — 가 **기계적 절차 아래 파묻혀 있다.**
> 그리고 **검증하기 어려운 코드**다. LLM이 미묘하게 틀릴 수 있는 부수적 결정(언제 tick할지, 바이트를 어떻게 인코딩할지, 어떤 팩토리 오버로드를 부를지)이 수십 개고, 리뷰어는 그걸 전부 확인해야 한다.

**After — 시나리오 DSL**

```java
Scenario<QuorumReplicaClient> scenario =
  QuorumStepBuilder.scenario("LWW lost update via server clock skew")
    .servers(ATHENS, BYZANTIUM, CYRENE)
    .clients(ALICE, BOB, READER)
    .client(ALICE).connectedTo(ATHENS)
    .client(BOB).connectedTo(BYZANTIUM)
    .given(g -> g.serverTimeAt(ATHENS, 1_000L)
                 .serverTimeAt(BYZANTIUM, 2_000L))
    .steps(s -> {
        s.client(BOB).writes(KEY, "B").expectSuccess();
        s.client(ALICE).writes(KEY, "A").expectSuccess();
        s.client(READER).reads(KEY).expectResponse(v -> "B".equals(v));
    });
```

설계 포인트:

- DSL은 **얇은 선언적 표면**이고, 순수한 중간 표현(`Scenario` = `Step`들, 각 Step은 `Action` + 선택적 `ClusterEvent`)으로 컴파일된다.
- 장애 주입도 영어처럼 읽힌다: `partition(BYZANTIUM).from(CYRENE)`, `reconnect(BYZANTIUM)`, `delay(INTERNAL_SET_REQUEST).from(ATHENS).to(BYZANTIUM, CYRENE).byTicks(100)`
- **문법을 타입 시스템이 강제한다.** progressive interface로 토폴로지 전에 step을 선언하거나, 클라이언트를 고르기 전에 액션을 쓸 수 없다 → **잘못된 시나리오는 애초에 컴파일이 안 된다.**
- **internal DSL(호스트 언어 Java 내부)** 이라 호스트 컴파일러가 문법 검증을 공짜로 해준다. 잘못 생성되면 런타임 서프라이즈가 아니라 **정확히 그 불법 step에 핀이 꽂힌 컴파일 에러**로 돌아온다.

효과:

> 표면이 아주 작기 때문에 — 생성 가능한 유효 코드의 공간이 유효한 Java 프로그램의 공간보다 훨씬 작기 때문에 — **LLM이 환각을 부릴 여지가 거의 없다.**
> 그리고 리뷰어는 결과물을 *한 줄씩 감사해야 할 코드*가 아니라 **하나의 실험에 대한 서술**로 읽을 수 있다.

### 9. LLM과 일하는 두 단계

모든 예시에서 반복된 패턴을 저자가 정리한다.

| | **1단계: 추상화/DSL을 설계** | **2단계: DSL이 존재하는 상태** |
|---|---|---|
| LLM의 역할 | **브레인스토밍 파트너** (코드 생성기 아님) | **자연어 인터페이스** |
| 운전대 | **사람이 확실히 쥔다** | LLM에 넘겨도 됨 |
| 성격 | 본질적으로 반복적·피드백 주도 | 영어 → 어휘로 거의 직역 |
| LLM이 하는 일 | 대안 스케치, 설계 비평, 다른 언어의 아이디어 이식 | 신뢰 가능한 생성 |

1단계에서 사람이 운전대를 쥐어야 하는 이유가 명확하다 — **이건 당신이 이해하고 소유해야 하는 결정들**이기 때문이다. 그리고 DSL을 쓸 만하게 만드는 구조(불법 시나리오가 컴파일 실패하게 하는 progressive interface, 빌더와 분리된 시맨틱 모델)는 **명세를 쓰고 코드를 생성해서가 아니라 반복하면서 수렴하는** 종류의 것이다.

2단계에서 LLM이 믿을 만한 생성기가 되는 이유:

> 추상화가 **프롬프트를 그라운딩하는 컨텍스트**와 **결과를 검사하는 harness**를 **동시에** 제공하기 때문이다.

### 10. 결론 — 영속하는 자산은 프롬프트가 아니라 DSL이다

저자가 마지막에 던지는 반론이 이 글의 하이라이트다.

> **프롬프트를 source of truth로 취급하는 흐름이 커지고 있다. 잘 설계된 DSL은 이 역학을 근본적으로 바꾼다.**

이유:

- DSL은 밀도가 높고, 표현력이 있고, 부수적 보일러플레이트가 없다. 그래서 **생성된 프로그램 자체가 사람이 유지보수하는 산출물**이 된다.
- 생성 결과가 이미 **도메인의 어휘로** 표현되어 있다. 다음 달에 시나리오를 바꿔야 하면, **원래 프롬프트를 복원해서 전부 재생성할 필요가 없다.**
- DSL 안에 LLM이 의도를 파악하고 작업할 만한 컨텍스트가 충분히 들어있다.

> **영속하는 자산은 프롬프트가 아니라, DSL과 시맨틱 모델이다.**

## 내가 얻은 인사이트

### 설계 관점

1. **"프롬프트 엔지니어링"의 상위 개념이 여기 있다**
   - 이 글의 진짜 주장은 "DSL 쓰세요"가 아니라 **"LLM의 신뢰성은 프롬프트가 아니라 출력 공간의 크기로 결정된다"** 는 것이다.
   - 유효한 Java 프로그램의 공간 vs 유효한 시나리오 DSL의 공간. 후자가 압도적으로 작으니 환각이 들어갈 자리가 없다. **환각을 설득으로 줄인 게 아니라 기하학적으로 없앤 것.**
   - 그래서 "모델이 더 좋아지면 해결된다"는 기대와 방향이 다르다. 이 접근은 **모델 성능에 의존하지 않는 개선**이다.

2. **검증기가 딸려오느냐가 DSL 채택의 진짜 기준이다**
   - 저자가 "DSL은 거의 항상 결정론적 검증기와 함께 온다"고 한 부분이 에이전트 관점에서 제일 중요하다. 파서/타입체커/컴파일러가 있어야 **사람 없는 generate → validate → repair 루프**가 성립한다.
   - 뒤집으면 **검증기 없는 DSL은 이 글의 이점을 거의 못 받는다.** 새 포맷을 만들 때 "문법이 예쁜가"보다 **"틀렸을 때 도메인 언어로 에러를 뱉는가"** 를 먼저 물어야 한다.
   - internal DSL(호스트 언어 내부 fluent interface)을 고른 게 영리하다. 파서를 직접 안 만들고도 **컴파일러를 검증기로 공짜로 얻는다.**

3. **progressive interface = "불법 상태를 표현 불가능하게 만들기"의 LLM 버전**
   - "토폴로지 전에 step 선언 불가, 클라이언트 선택 전에 액션 불가"는 타입 설계의 고전 원칙인데, LLM 시대에 **의미가 하나 더 붙었다.**
   - 예전엔 사람 실수를 막는 장치였다면, 이제는 **에이전트 자기수정 루프의 피드백 채널**이다. 컴파일 에러가 곧 학습 신호다.

4. **"설계는 리뷰가 아니라 작성에서 드러난다"는 AI 코딩의 가장 불편한 진실**
   - 이 문장이 "AI가 짜고 내가 리뷰한다"는 지배적 워크플로의 한계를 정확히 찌른다. 리뷰는 **의도와의 일치**를 확인할 뿐, 책임의 소재나 경계 같은 **설계 결정과 씨름하게 만들지 않는다.**
   - 실무 함의: **설계가 아직 안 정해진 영역에서는 AI에게 코드를 맡기면 안 된다.** 어휘가 잡힌 다음에 맡겨야 한다. 순서를 뒤집으면 "리뷰는 다 통과했는데 설계는 없는" 코드베이스가 남는다.
   - 이건 앞서 정리한 Spec-Driven Development 계열 글들에 대한 **가장 강한 반론**이기도 하다. SDD는 명세를 청사진으로 보는데, 이 글은 **출발 가설**로 본다.

### 운영 관점

5. **WebTestPilot이 이 글의 실증 사례다 — 같은 구조가 독립적으로 나왔다**
   - Fowler 사이트의 이 글과 FSE 2026의 WebTestPilot이 동일한 처방을 내린다. **LLM은 DSL을 *작성*하고, 판정/실행은 결정론적 도구가 한다.**
   - 심지어 실패 양상까지 일치한다. WebTestPilot의 로컬 모델 실패 원인 91%가 "심볼 선언 오류 + DSL 문법 오류"였는데, 이 글의 처방(검증기로 repair, few-shot 예시, 제약 디코딩)이 정확히 그 지점을 겨냥한다.
   - 두 자료가 서로 인용 없이 같은 결론에 도달했다는 게 이 패턴의 신뢰도를 높인다. (실제로 WebTestPilot 리포 README가 이 글을 링크해두고 있다.)

6. **"DSL 없이 좋은 추상화만으로도"가 실무 도입의 현실적 출발점**
   - DSL 설계는 선행 비용이 크고, 저자도 "작고 제약적으로 유지될 때만" 이점이 있다고 못 박았다. 대부분의 팀에 DSL은 과하다.
   - 대신 **Tickloom의 네 seam(Process/Network/Storage/Clock) 같은 분해**는 새 문법 없이 오늘 당장 가능하다. 우리 코드베이스에서 "AI에게 맡길 때 매번 다시 결정되는 열린 질문"이 뭔지 목록화하고, 그걸 **이름 붙은 타입으로 닫아버리는 것**이 첫 단계다.
   - 체크리스트: 에이전트가 매 프롬프트마다 재발명하는 게 있나? (에러 처리 방식, 트랜잭션 경계, 재시도 정책, 로깅 규약) → 그게 추상화 후보다.

7. **"프롬프트가 아니라 DSL이 source of truth"는 프롬프트 저장소 유행에 대한 반박**
   - 프롬프트를 버전관리하고 재생성하는 워크플로가 유행인데, 저자는 이를 정면으로 반박한다. **생성된 DSL 코드가 이미 도메인 어휘로 쓰여 있으면, 프롬프트는 폐기해도 된다.**
   - 판단 기준이 나온다: **생성 결과물이 프롬프트보다 읽기 쉬운가?** 그렇다면 결과물이 자산이고, 그렇지 않다면(= 보일러플레이트 범벅이면) 추상화가 부족한 것이다.
   - 이 기준으로 보면 "AI가 짜준 500줄"은 대부분 자산이 아니라 부채다. 프롬프트도 코드도 유지보수 대상이 되어버리기 때문.

8. **아직 열린 질문 — 진짜 새로운 DSL에서도 성립하는가**
   - 저자가 스스로 단 단서가 정직하다. LLM이 PlantUML·SQL·K8s YAML을 잘하는 건 **학습 데이터에 대량으로 있었기 때문**일 수 있다.
   - 사내에서 새로 만든 DSL은 그 이점이 없다. 그럼 남는 건 (a) few-shot 예시의 질, (b) 검증기의 에러 메시지 품질, (c) 표면의 작음 — 이 세 가지뿐이다.
   - 그래서 새 DSL을 설계할 때는 **worked example 몇 개를 스킬/컨텍스트에 넣는 것이 문법 설계만큼 중요**하다. 이건 CLAUDE.md나 skill 파일 운영과 직접 연결되는 이야기다.
