## AI 요약

### 1. agent-browser란?

**AI 에이전트 전용으로 설계된 브라우저 자동화 CLI**다. Rust 네이티브 바이너리이며, Playwright/Puppeteer 의존성 없이 CDP로 Chrome을 직접 제어한다.

저장소 실측 메타데이터 (2026-09-02 확인):

| 항목 | 값 |
|---|---|
| 저장소 생성 | **2026-01-11** |
| 최신 릴리스 | **v0.36.0** (2026-09-01) |
| 스타 / 포크 | 41,744 / 2,782 |
| 열린 이슈 | 677 |
| 라이선스 | Apache-2.0 |
| 구성 | Rust 3.19MB, TypeScript 342KB |

> 여러 3자 블로그가 "2026년 7월 공개", "2개월 만에 22,000 스타"로 소개하는데 **둘 다 사실과 다르다.** 저장소는 1월에 생성됐다.

### 2. 핵심 설계 — snapshot + refs

에이전트가 페이지를 다루는 방식이 기존 자동화 도구와 다르다.

```bash
agent-browser snapshot
# - heading "Example Domain" [level=1, ref=e1]
# - link "Learn more" [ref=e2]

agent-browser click @e2          # 스냅샷의 ref로 바로 조작
agent-browser fill @e3 "a@b.com"
```

README가 밝히는 refs의 이점은 셋이다. **결정론적**(스냅샷의 정확한 요소를 가리킴), **빠름**(DOM 재질의 불필요), **AI 친화적**.

ref 클릭이 오버레이에 막히면 에러에 가린 요소를 담아 돌려준다 — `covered by <div#consent-banner>`. 에이전트가 다음 행동을 스스로 정할 수 있는 형태다.

### 3. 컨텍스트를 줄이기 위한 장치들

공식 문서에서 컨텍스트 관리와 직접 연결되는 부분:

| 장치 | 내용 |
|---|---|
| `snapshot` 필터 | `-i` 상호작용 요소만 / `-c` 빈 구조 요소 제거 / `-d N` 깊이 제한 / `-s <sel>` 선택자로 스코핑 |
| `--max-output` | "context flooding 방지"라고 명시된 출력 길이 제한 |
| MCP `--tools core` | MCP 서버 모드의 기본 프로파일. "일상 자동화에서 MCP 컨텍스트를 작게 유지하기 위해" |
| 명령 체이닝 | 데몬이 상태를 유지하므로 `&&`로 여러 액션을 셸 호출 한 번에 |
| 스킬 stub | `SKILL.md`는 52줄짜리 발견용 스텁일 뿐, 실제 사용법은 `agent-browser skills get core`로 CLI가 **설치된 버전에 맞는 내용을 서빙** |

마지막 항목의 이유를 README가 직접 밝힌다. 스텁은 릴리스 사이에 바뀔 수 없으므로 `skills get core`를 가리키기만 하고, **CLI가 서빙하는 내용은 설치된 버전과 항상 일치하므로 지침이 낡지 않는다.** `node_modules`의 `SKILL.md`를 복사하지 말라고 명시적으로 경고한다.

### 4. 아키텍처

**클라이언트-데몬 구조**다. Rust CLI가 명령을 파싱하고, Node.js 없는 순수 Rust 데몬이 CDP로 직접 통신한다. 데몬은 첫 명령에 자동 기동해 명령 사이에 유지되고, **1시간 무입력이면** 설정된 복원 상태를 저장한 뒤 브라우저를 닫고 종료한다. `close`를 부르지 않고 죽은 통합이 데몬과 브라우저를 무한정 누수시키지 못하게 하는 장치다.

### 5. 공식 벤치마크가 재는 것

저장소의 [`benchmarks/`](https://github.com/vercel-labs/agent-browser/blob/main/benchmarks/README.md)는 **Node.js 데몬 vs Rust 네이티브 데몬**을 Vercel Sandbox microVM 안에서 비교한다. 측정 항목은 명령 지연, 콜드 스타트, 데몬 RSS, 배포 크기다.

주목할 점은 문서가 스스로 한계를 밝힌다는 것이다.

> 명령 지연은 데몬이 아니라 **Chrome(CDP 왕복)이 지배한다.** 두 데몬 모두 CLI와 Chrome 사이의 얇은 릴레이이므로 명령당 속도 향상은 대체로 작다.

네이티브 데몬이 실제로 이기는 곳은 콜드 스타트, 데몬 메모리(**V8 오버헤드 ~140MB vs Rust ~7MB**), 배포 크기다.

**이 벤치마크는 토큰을 재지 않는다.**

## 직접 실험 — "컨텍스트 절감" 주장 검증

### 검증 대상

공식 랜딩 페이지 [agent-browser.dev](https://agent-browser.dev)의 문구:

> 텍스트 출력이 컨텍스트 사용을 최소화한다 — **~200–400 토큰 vs 전체 DOM ~3,000–5,000 토큰**

주의할 점: **비교 대상이 raw DOM이지 Playwright MCP가 아니다.** 랜딩 페이지는 Playwright MCP를 언급조차 하지 않는다. "Playwright MCP 대비 93% 절감"이라는 3자 블로그들의 표현은 비교 대상을 바꿔치기한 것이고, Playwright MCP 역시 접근성 트리 스냅샷을 쓴다.

### 환경

- agent-browser **v0.36.0** (로컬 설치), Chrome for Testing 152.0.7977.75, macOS ARM64
- 토큰 계수: `tiktoken` `o200k_base`
- `eval`이 반환하는 raw DOM은 JSON 문자열이므로 **이스케이프를 풀어** 공정 비교
- 재현 스크립트: 이 디렉터리의 `bench.sh`, `count.py`

### 결과 1 — 표현별 토큰 (raw DOM 대비 절감률)

| 페이지 | raw DOM | `read` | `snapshot` | `snapshot -c` | `snapshot -i` |
|---|---:|---:|---:|---:|---:|
| example.com | 159 | 23 (85.5%↓) | 55 (65.4%↓) | 30 (81.1%↓) | 26 (83.6%↓) |
| news.ycombinator.com | 11,527 | 1,124 (90.2%↓) | 7,281 (**36.8%↓**) | 5,687 (50.7%↓) | 4,711 (59.1%↓) |
| github.com/vercel-labs/agent-browser | 453,878 | 20,439 (95.5%↓) | 47,751 (89.5%↓) | 42,313 (90.7%↓) | 14,628 (**96.8%↓**) |
| wikipedia.org/wiki/Web_browser | 197,907 | 9,435 (95.2%↓) | 19,907 (89.9%↓) | 19,547 (90.1%↓) | 6,923 (96.5%↓) |

**판정: 상대 절감은 사실, 절대 수치는 거짓.**

- "~200–400 토큰"에 해당하는 페이지는 **example.com뿐**이다. 실제 페이지의 스냅샷은 HN 7,281 / 위키백과 19,907 / GitHub 47,751 토큰이다. 랜딩 페이지 숫자는 자기들이 고른 단순 페이지 기준으로 보인다.
- 반면 **절감률은 주장보다 오히려 크다.** GitHub은 45.4만 → 4.8만 토큰(89.5%↓), `-i`까지 쓰면 1.5만(96.8%↓)이다.

### 결과 2 — 절감률은 페이지 복잡도가 아니라 DOM 비대에 비례한다

가장 반직관적인 결과다. **HN의 절감률이 36.8%로 가장 낮다.**

```
raw DOM 대비 snapshot 절감률
  example.com   ████████████▌         65.4%   (DOM 159 토큰, 잴 게 없음)
  HN            ███████▎              36.8%   (테이블 기반, DOM이 이미 얇음)
  Wikipedia     █████████████████▉    89.9%
  GitHub        █████████████████▉    89.5%   (React/Turbo, DOM이 매우 비대)
```

HN은 링크가 빽빽하지만 마크업이 옛날식 테이블이라 DOM 자체가 얇다. 접근성 트리가 DOM만큼 크므로 줄일 여지가 없다. 반대로 GitHub은 프레임워크가 만든 래퍼·속성이 DOM을 45만 토큰까지 부풀려 놨고, 그래서 접근성 트리로 바꾸는 효과가 극적이다.

**즉 이 도구의 이득은 "페이지가 얼마나 복잡한가"가 아니라 "DOM에 에이전트가 쓸모없어하는 마크업이 얼마나 끼어 있는가"에 비례한다.**

### 결과 3 — 읽기와 조작은 다른 명령을 써야 한다

위키백과에서 `read`(9,435)가 `snapshot`(19,907)의 절반이다. 본문을 이해하는 게 목적이면 접근성 트리는 낭비다. 반대로 `read`에는 ref가 없어 조작할 수 없다.

| 목적 | 명령 | GitHub 기준 |
|---|---|---|
| 페이지 내용을 **읽기** | `read` | 20,439 토큰 |
| 요소를 **조작하기** | `snapshot -i` | 14,628 토큰 |
| 구조까지 **파악하기** | `snapshot` | 47,751 토큰 |

### 결과 4 — README가 권장하는 `--json`이 토큰을 2배로 만든다

README의 "Optimal AI Workflow"는 `agent-browser snapshot -i --json`을 제시한다. 그런데 GitHub 페이지에서:

| 명령 | 토큰 |
|---|---:|
| `snapshot -i` | 14,628 |
| `snapshot -i --json` | **30,778 (2.1배)** |
| `snapshot -i -u` (URL 포함) | 20,441 (1.4배) |
| `snapshot -i -d 8` | 14,628 (변화 없음 — `-i` 출력은 평평해서 깊이 제한이 무의미) |

기계 파싱이 필요 없다면 `--json`은 켜지 않는 게 낫다. 컨텍스트 효율이 이 도구의 존재 이유인데 권장 워크플로가 그걸 절반으로 깎는다.

### 결과 5 — `-s` 스코핑에 재현되는 버그가 있다 (v0.36.0)

컨텍스트를 줄이라고 만든 `-s <selector>` 옵션이 **출력을 오히려 2~4배 늘린다.**

| 페이지 | 페이지 내 `main` 개수 | `snapshot` | `snapshot -s main` |
|---|---:|---:|---:|
| wikipedia.org/wiki/Web_browser | 1 | 19,908 | **38,824 (1.95배)** |
| github.com/vercel-labs/agent-browser | 1 | 47,752 | **212,341 (4.45배)** |
| news.ycombinator.com | 0 | 7,281 | 12 (정상 — 빈 결과) |

원인은 **노드 중복 방출**이다. 위키백과에서:

- ref를 가진 줄이 **1,045개인데 고유 ref는 504개** — 평균 2배 중복
- 최상위 노드가 `- main` 하나여야 하는데 **64개**
- 동일한 라디오 버튼 줄이 4회씩 반복
- 반면 기본 `snapshot`은 **중복이 정확히 0**이다 (모든 ref 줄이 1회)

GitHub에서는 더 심해서 ref 줄 4,430개 / 고유 913개(최대 ref 번호는 양쪽 다 909)로 약 4.85배 중복이다. 선택자가 여러 요소에 매칭돼서가 아니다 — `document.querySelectorAll("main").length`가 양쪽 다 **1**이었다.

정리하면 **문서화된 컨텍스트 절감 수단 중 하나가 정반대로 동작한다.** 스코핑이 필요하면 현재 버전에서는 `-i`로 대체하는 편이 안전하다.

### 결과 6 — 설치 과정에서 확인한 것들

- README는 "기존 Chrome, Brave, Playwright, Puppeteer 설치를 자동 감지한다"고 하지만, Chrome과 Playwright 캐시가 이미 있는 머신에서도 `agent-browser install`은 **179MB Chrome for Testing을 새로 받았다.** 감지는 실행 시점에 적용되는 것으로 보이고, `install`은 무조건 받는다.
- **Volta 환경에서는 전역 설치가 동작하지 않는다.** `npm i -g` / `volta install` 모두 등록은 되지만 실행 시 `Volta error: Could not execute command`로 실패한다. 네이티브 Rust 바이너리를 Volta 심이 처리하지 못하는 것으로 보인다. 프로젝트 로컬 설치(`npm i agent-browser` + `./node_modules/.bin/agent-browser`)로 우회했다.

## 내가 얻은 인사이트

### 검증 관점

1. **"93% 절감"은 세 단계를 거치며 왜곡됐다**
   - 공식: "snapshot ~200–400 vs 전체 DOM ~3,000–5,000" → 3자 블로그: "Playwright MCP 대비 93% 절감" → 재인용: "82%", "5.7배 더 많은 테스트 사이클".
   - **비교 대상이 raw DOM에서 Playwright MCP로 바뀐 것**이 핵심 왜곡이다. Playwright MCP도 접근성 트리를 쓰므로 사실 같은 편에 서 있는 도구다. 벤더가 하지도 않은 비교를 3자가 만들어 붙였고, 그게 검색 결과 상단을 차지한다.
   - 교훈은 단순하다. **성능 주장을 인용하기 전에 벤더의 1차 문구를 직접 확인한다.** 이번에는 저장소·랜딩 페이지·벤치마크 코드가 전부 공개돼 있어서 30분이면 확인됐다.

2. **절대 수치와 상대 수치는 따로 판정해야 한다**
   - "~200–400 토큰"은 실제 페이지에서 20~120배 틀렸지만, "raw DOM 대비 크게 줄인다"는 주장은 맞고 오히려 과소평가였다. 하나가 틀렸다고 도구를 버릴 이유도, 하나가 맞았다고 숫자를 그대로 인용할 이유도 없다.
   - 실무에서 이 구분이 중요한 이유는 **용량 산정** 때문이다. "스냅샷 한 번에 400토큰"으로 예산을 짜면 GitHub 같은 페이지에서 100배 넘게 빗나간다. 50스텝짜리 작업이면 컨텍스트가 그냥 터진다.

### 아키텍처 관점

3. **이 도구는 Manus의 "레이어드 액션 공간"을 그대로 구현한 물건이다**
   - [Context Engineering in Manus](../Context%20Engineering%20in%20Manus%20-%20%EC%A4%84%EC%9D%B4%EA%B3%A0%20%EB%B0%96%EC%9C%BC%EB%A1%9C%20%EB%B9%BC%EA%B3%A0%20%EA%B2%A9%EB%A6%AC%ED%95%98%EB%8A%94%20%EC%84%B8%20%EA%B0%80%EC%A7%80%20%EC%A0%84%EB%9E%B5.md)에서 Manus는 함수 호출 층을 20개 미만으로 고정하고 나머지를 CLI로 샌드박스에 내렸다. agent-browser는 **MCP 서버가 아니라 CLI가 기본**이고, MCP 모드조차 기본 프로파일이 `core`다. 같은 결론에 독립적으로 도달했다.
   - `&&` 체이닝이 이 설계의 숨은 이점이다. `fill @e1 ... && fill @e2 ... && click @e3`을 **Bash 호출 한 번**에 넣으면 도구 호출 3회가 1회가 된다. MCP 도구로 노출됐다면 불가능했을 절약이고, Manus가 todo.md를 버린 이유(액션 횟수 자체가 비용)와 정확히 같은 축이다.

4. **스킬을 CLI가 서빙한다는 발상이 가장 이식할 만하다**
   - `SKILL.md`를 52줄 스텁으로 두고 실제 내용은 `agent-browser skills get core`로 받게 한 것. 문서와 구현의 버전 불일치를 **구조적으로** 없앤다.
   - 이 저장소의 [Browser Agent Harness](../Browser%20Agent%20Harness%20-%20%EC%8B%A4%EC%A0%9C%20%EC%9B%B9%EC%97%90%EC%84%9C%20%EC%82%B4%EC%95%84%EB%82%A8%EB%8A%94%20%EB%B8%8C%EB%9D%BC%EC%9A%B0%EC%A0%80%20%EC%97%90%EC%9D%B4%EC%A0%84%ED%8A%B8%20%ED%95%98%EB%84%A4%EC%8A%A4%206%EA%B0%9C%20%EB%A0%88%EC%9D%B4%EC%96%B4.md) 문서의 "스킬 = 하네스의 장기 기억"과 이어지는데, 여기서는 한 걸음 더 나가 **스킬의 신선도까지 런타임이 보장**한다. 사내 도구에 그대로 적용할 수 있는 패턴이다.

5. **`read`와 `snapshot`이 갈라져 있다는 게 설계의 정답에 가깝다**
   - 하나의 "페이지를 달라" API로 통합하지 않고, **읽기용 표현과 조작용 표현을 분리**했다. 결과 3에서 봤듯 목적에 따라 토큰이 2~3배 차이 난다.
   - 브라우저 에이전트를 직접 만든다면 이 분리를 먼저 설계해야 한다. 하나의 표현으로 두 목적을 다 커버하려 하면 항상 한쪽이 낭비다.

### 운영 관점

6. **0.x 버전에 열린 이슈 677개다 — 핀 고정이 필수다**
   - 릴리스가 거의 매주 나오고(v0.33~v0.36이 한 달), 문서화된 옵션(`-s`)에 재현되는 버그가 있다. 스타 4만이라는 숫자가 성숙도를 뜻하지 않는다.
   - 프로덕션에 넣는다면 **버전을 고정하고, 쓰는 플래그 조합만 골라 회귀 테스트를 붙이는 것**이 최소 조건이라고 본다. 이번에 만든 `bench.sh`가 그대로 그 회귀 테스트의 골격이 된다.

7. **`-s` 버그는 "문서를 믿지 말고 재라"의 교과서적 사례다**
   - `-s`는 README 표에 "선택자로 스코핑"이라고 정상 문서화돼 있고, 이름만 보면 당연히 줄어들 것 같다. 실제로는 4배 늘어난다. **컨텍스트를 줄이려고 켠 옵션이 컨텍스트를 터뜨리는** 최악의 실패 모드다.
   - 에이전트 도구에서 이 종류의 버그가 특히 위험한 이유는 **조용히 실패하기 때문**이다. 에러가 나지 않고 그냥 비싸진다. 토큰 사용량을 측정하지 않으면 청구서를 받고서야 안다 — Manus 문서의 "KV 캐시 적중률을 대시보드 지표로 올려라"와 같은 교훈이 여기서도 반복된다.

### 한계

8. **이 실험이 재지 않은 것**
   - **태스크 성공률.** 토큰만 쟀고 "그래서 에이전트가 일을 더 잘 끝내는가"는 확인하지 않았다. `-i`는 96.8% 절감하지만 본문 텍스트를 전부 버리므로, 읽고 판단해야 하는 작업에서는 오히려 실패할 수 있다. 절감률과 성공률은 트레이드오프 관계일 가능성이 높다.
   - **Playwright MCP와의 실제 비교.** 3자 블로그의 주장이 틀렸다는 것만 확인했지, 두 도구를 같은 태스크에서 직접 비교하지는 않았다. 그게 실제로 궁금한 숫자다.
   - **4개 페이지, 각 1회 측정**이다. 페이지는 시점에 따라 바뀌고 통계적 신뢰구간이 없다. 절감률의 자릿수는 믿을 만하지만 소수점은 아니다.
