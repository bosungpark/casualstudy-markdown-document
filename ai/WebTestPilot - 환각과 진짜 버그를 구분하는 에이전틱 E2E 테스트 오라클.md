## AI 요약

### 1. 이 논문이 푸는 문제 — "이거 진짜 버그야, 아니면 네가 헛본 거야?"

VLM(Visual Language Model) 에이전트에게 자연어 요구사항을 주고 웹 앱을 돌려보게 하는 건 이미 된다. 문제는 그다음이다.

> 에이전트가 "요구사항과 앱 동작이 불일치합니다"라고 말했을 때,
> 그게 **진짜 버그**인지 **모델의 환각**인지 구분할 방법이 없다.

E2E QA 관점에서 이건 치명적이다. 오탐(false positive)이 섞인 리포트는 결국 사람이 전부 다시 확인해야 하므로, **자동화했는데 검증 부담이 그대로거나 오히려 늘어난다.**

논문은 이를 두 가지 기술 과제로 쪼갠다.

| 과제 | 내용 |
|---|---|
| **암묵적 오라클 추론 (implicit oracle inference)** | 에이전트가 스스로 오라클이 되어, 아무 가이드 없이 "이 동작이 맞는가"를 판정해야 함 |
| **확률적 추론 (probabilistic inference)** | LLM의 추론이 매번 흔들리므로, 오라클로서의 신뢰성이 무너짐 |

### 2. 기존 접근이 왜 실패하는가

논문이 지적하는 기존 LLM 기반 E2E 테스트의 두 가지 실패 방식:

1. **"크래시 안 나면 성공"** — 페이지 이동이 되기만 하면 통과 처리. 사실상 아무것도 검증하지 않음.
2. **각 상태를 독립적으로 검사** — 현재 화면만 보고 판정하기 때문에, **이전 단계의 맥락에 의존하는 버그를 놓친다.**

두 번째가 특히 중요하다. 실제 E2E 버그의 상당수는 "이 화면이 이상하다"가 아니라 **"이전 화면에서 한 일이 이 화면에 반영되지 않았다"** 형태이기 때문이다. 장바구니에 담았는데 소계가 안 바뀌는 것 같은.

### 3. 해법 A — 심볼화 레이어 (Symbolization Layer)

화면의 중요한 GUI 요소를 **타입이 있는 변수(symbol)로 추상화**한다. Pydantic 스키마로 정의한다.

```python
class Product(BaseModel):
    title: str = Field(...)
    price: float = Field(..., ge=0)
    quantity: Optional[int] = Field(None, gt=0)
```

핵심 설계 결정:

- **온디맨드 추출** — 모든 요소를 미리 심볼화하지 않는다. 필요할 때만 꺼낸다.
- **Session history 유지** — 구조화된 상태 이력을 들고 다니며 페이지 재식별(page reidentification)로 이전 상태의 심볼을 다시 찾는다.
- 이 조합으로 **"심볼은 적게(focused), 상태는 많이(scalable)"** 라는 균형을 얻는다.

픽셀/DOM을 직접 다루는 대신 타입 있는 변수로 바꾸는 게 왜 중요하냐면, **비교와 단정(assertion)이 결정론적으로 가능해지기 때문**이다. LLM이 "장바구니가 맞는 것 같습니다"라고 말하는 대신, `cart.subtotal == prev.subtotal + product.price * qty` 라는 식이 실제로 실행된다.

### 4. 해법 B — 사전/사후 조건 오라클 (Pre/Post-condition)

자연어 요구사항을 `(조건, 액션, 기대결과)` 튜플로 분해한 뒤:

- **조건 → 사전조건(precondition) 단정문**
- **기대결과 → 사후조건(postcondition) 단정문**

으로 변환한다. 둘 다 Python 확장 DSL로 표현된다. 그리고 이 오라클이 **세 종류의 의존성**을 포착한다.

| 의존성 | 정의 | 예시 |
|---|---|---|
| **인과 (causal)** | 인접 상태 간, 이전 액션의 직접 효과로 UI 요소가 생성/수정/삭제됨 | 타이핑하면 자동완성 드롭다운이 뜬다 |
| **데이터 (data)** | 한 상태에서 추출한 정보가 다른 상태로 전파·재사용됨 | 상세 페이지의 상품 정보가 장바구니로 흘러감 |
| **시간 (temporal)** | 같은 논리적 페이지의 두 상태를 비교해 증분 변화를 봄 | 담기 전/후 장바구니 내용 비교 |

"상품이 장바구니에 담겼다"를 검증하는 실제 흐름:

```
1. 이전 장바구니 상태를 조회         (temporal)
2. 새로 담긴 상품을 추출              (causal)
3. 현재 장바구니 내용과 비교          (data)
4. 소계가 새 상품 가격만큼 증가했는지 확인
```

이게 **"암묵적 요구사항(implicit requirement)"** 을 검증한다는 말의 의미다. 요구사항에는 "소계가 갱신되어야 한다"고 안 써 있지만, 상식적으로 성립해야 하는 것을 오라클이 추론해서 넣는다.

### 5. 전체 파이프라인

```
[1] Input Parsing
    자연어 요구사항 → (condition, action, expectation) 튜플
    LLM 프롬프팅 + JSON 파싱

[2] Oracle Inference  (2단계 LLM 프롬프팅)
    2-1. 실행 트레이스를 분석해 암묵적 요구사항(의존성) 식별
    2-2. 커스텀 심볼 정의 + DSL 단정문 생성

[3] Oracle Execution
    3-1. 현재 상태에 사전조건 평가
    3-2. 액션 실행  ← GUI grounding + set-of-mark 하이브리드
    3-3. 결과 상태에 사후조건 평가

[4] Page Reidentification
    DOM 트리 편집거리 + LLM 비교로
    논리적으로 같은 페이지에 일관된 ID 부여 → 상태 간 추론 가능
```

액션 실행은 **UI-Venus-7B로 대략적 좌표를 예측 → 잘라낸 스크린샷에 set-of-mark 프롬프팅으로 정밀 선택**하는 2단 구조다. 안정성과 효율의 절충.

### 6. 벤치마크 — 버그를 심어 넣은 실제 대형 앱

기존에 NL→E2E 테스트를 평가할 벤치마크가 없어서 직접 만들었다. **장난감 앱이 아니라 실제 오픈소스 대형 앱**을 쓴 게 특징이다.

| 앱 | 규모(LoC) | 도메인 | 테스트 케이스 |
|---|---|---|---|
| BookStack | 214,819 | 문서 플랫폼 | 27 |
| Indico | 573,316 | 컨퍼런스/이벤트 관리 | 25 |
| InvoiceNinja | 1,513,289 | 청구서 | 25 |
| PrestaShop | 2,234,514 | 이커머스 | 23 |
| **합계** | — | — | **100** |

**버그 주입 방식**: GitHub 이슈 200건 이상을 주제 분석해 도출한 4개 카테고리에서, 요구사항당 인공 버그 1개씩 삽입.

1. UI 요소 누락 (missing UI elements)
2. 데이터 불일치 (data inconsistency)
3. 무동작 (no-op actions)
4. 내비게이션 실패 (navigation failures)

실제 예시: *"첨부파일 삭제 권한이 없는 사용자에게 에러 메시지가 표시되지 않음"* (BookStack #5323)

### 7. 결과

| 지표 | WebTestPilot | 최고 베이스라인 | 차이 |
|---|---|---|---|
| 태스크 완료율 (Task Completion) | **0.99** | 0.64 (LaVague) | +54.7% |
| 올바른 트레이스 (Correct Trace) | **0.99** | 0.77 (LaVague) | +28.6% |
| 버그 탐지 **정밀도** | **0.96** | 0.26 (PinATA) | **+70p** |
| 버그 탐지 **재현율** | **0.96** | 0.69 (PinATA) | +27p |

베이스라인 3종:
- **LaVague** — 멀티 에이전트(World Model + Action Engine), 단계 완료에 초점
- **NaviQAte** — 단일 에이전트, RAG 기반 플래닝
- **PinATA** — 3 에이전트(Orchestrator / Actor / Assertor) + 장기 메모리

가장 눈여겨볼 숫자는 **정밀도 0.26 → 0.96**이다.

#### 이 숫자를 읽을 때 반드시 붙여야 할 조건 (원문 5.3절 확인)

논문의 96%는 **"야생에서 리포트 100건 중 96건이 진짜 버그"라는 뜻이 아니다.** 원문 정의는 이렇다.

- **step-level 지표다.** 버그 주입 상태 `s_bug`에서 단정문이 실패하면 TP, **그 외 모든 상태**에서 실패하면 FP. 한 테스트의 스텝 대부분이 정상 스텝이므로 분모 구성이 통상적인 "버그 리포트 정밀도"와 다르다.
- **요구사항 1개당 버그 1개**가 그 요구사항이 밟는 경로 위에 주입된다. 벤치마크 샘플은 `(앱 W, 요구사항 D, 정답 단정문 A, 버그)` 4-튜플이다. 즉 "버그가 어디 있는지 모르는 채로 수백 개를 돌린다"는 현실 QA와 문제 구조가 다르다.
- **평가에 사람이 들어간다.** 우연히 맞은 spurious TP를 걸러내려고 *모든 단정문의 의미적 정확성을 수동 검증*했다. 측정으로서는 정직하지만, 파이프라인 원출력을 그대로 신뢰한 수치는 아니다.

그럼에도 PinATA 0.26이라는 대비는 유효하다. 오라클 없이/자유형식 메모리로 판정하는 방식이 정상 스텝에서 얼마나 자주 헛단정을 내는지 보여준다.

**실제 버그 재현 실험**: GitHub 이슈에서 가져와 재현한 실제 버그 23건 중 **22건 탐지** (PinATA는 15건). 단, 이건 **이미 알려진 버그를 재현해두고 그 버그를 겨냥한 요구사항으로 잡히는지 본 재현율**이고, **오탐 수치가 아예 보고되지 않는다.** "야생에서 버그의 95%를 잡는다"로 읽으면 안 된다.

### 8. 어블레이션 — 모델 크기와 입력 품질

**Table 5 — 입력 변형별 태스크 완료율(TC)** (DF=원본, AN=노이즈, DO=문장 10% 삭제, RS=문체 변경, SU=요약)

| 모델 | DF | AN | DO | RS | SU | **Total** |
|---|---|---|---|---|---|---|
| GPT-4.1 | 1.00 | 0.93 | 0.70 | 0.70 | 0.70 | 0.81 |
| Qwen2.5-VL-72B | 1.00 | 0.93 | **0.85** | 0.70 | **0.81** | **0.85** |
| Qwen2.5-VL-32B | 0.65 | 0.89 | 0.63 | 0.78 | 0.81 | 0.75 |
| Qwen2.5-VL-7B | 1.00 | 0.74 | 0.70 | 0.70 | 0.63 | 0.72 |
| Qwen2.5-VL-3B | 1.00 | 0.48 | 0.52 | 0.70 | 0.41 | 0.57 |

이 표에서 읽어야 할 것 세 가지:

1. **DF(원본 요구사항)는 3B 모델까지 전부 1.00으로 포화다.** 논문 표현대로 "model performance is generally stable". 벤치마크의 기본 조건에서는 모델을 키워 올릴 자리가 없다. (32B만 0.65로 튀는데 논문은 설명하지 않는다.)
2. **GPT-4.1은 이 표의 1등이 아니다.** Total 기준 Qwen2.5-VL-72B가 TC 0.85 / CT 0.90으로 GPT-4.1(0.81 / 0.86)을 앞선다. 특히 Dropout에서 0.85 vs 0.70으로 15포인트 뒤집힌다.
3. 성능이 무너지는 축은 모델 크기가 아니라 **입력 품질**이다. 전 모델이 DO/RS/SU에서 동반 하락한다.

> ⚠️ 주의: RQ4는 **TC/CT만** 모델별로 측정했다. 버그 탐지 precision/recall(0.96)은 **GPT-4.1 단일 모델 결과뿐**이다. "더 좋은 모델이 96%를 올리는가"는 논문이 답하지 않았다.

**로컬 모델의 단정문 생성 실패 원인 분포**

| 원인 | 비율 |
|---|---|
| 심볼 선언/사용 오류 | 52% |
| DSL 문법 오류 | 39% |
| 런타임 에러 (타입 불일치) | 9% |

작은 모델은 "웹을 못 다뤄서"가 아니라 **"형식 언어를 못 써서"** 실패한다는 게 흥미롭다.

### 9. 실전 케이스 스터디 — China Mobile 노코드 플랫폼

논문에서 가장 상업적으로 의미 있는 부분인데, 벤치마크 숫자에 가려 잘 안 읽히는 절이다.

- 대상: China Mobile의 노코드 플랫폼 위에서 **개발 중이던 창고관리 시스템**
- 입력: PRD 문서 → 개별 요구사항으로 전처리, **56개 테스트 입력** (전처리 6.4분)
- 실행: 전체 **32.7분**, 평균 탐지 시간(MTTD) **4.9분**, 결함밀도 **0.14 bugs/page**
- 결과: **버그 8건 발견** — 데이터 바인딩 5건(62.5%), UI 2건, 내비게이션 1건

발견된 버그의 성격이 인상적이다. "테이블 필수 필드가 비어 있음", "창고 드롭다운 옵션이 실제 테이블 데이터와 바인딩되지 않음", "공급사 드롭다운이 비어 있음" — 전부 **크래시는 안 나지만 데이터가 안 맞는** 종류다. 논문은 PinATA라면 UI/내비게이션 3건만 잡았을 거라고 지적한다.

> 다만 여기서도 **총 몇 건을 리포트해서 8건이 진짜였는지가 안 나온다.** 상용화 가능성을 가르는 건 사실 그 숫자인데.

### 10. 저자가 밝힌 한계

- **내부 타당성**: 같은 기능을 달성하는 경로가 여럿이라 지표가 성능을 **과소평가**할 수 있다.
- **외부 타당성**: 주입된 버그 벤치마크가 현실을 온전히 반영하지 못할 수 있다.
- **가장 큰 가정**: **"요구사항이 자기완결적이고 완전하다"** 고 전제한다. 조건·액션·기대결과가 순서대로 다 명시되어 있어야 한다. 파편적이거나 모호한 명세에는 적용이 어렵다.
- 성능을 좌우하는 건 결국 **입력 파싱 전략과 품질**이다.

## 내가 얻은 인사이트

### E2E QA 관점

1. **오탐률이 곧 자동화의 실효성이다 — 재현율이 아니라**
   - 정밀도 0.26 vs 0.96이라는 대비가 이 논문의 진짜 메시지다. 버그를 잘 찾는 것보다 **헛소리를 안 하는 게** E2E 자동화에서 훨씬 중요하다.
   - 사람이 리포트를 재확인해야 하는 비율이 높다면, 에이전트는 검증 병목을 푸는 게 아니라 **병목을 QA 쪽으로 옮긴 것**뿐이다.
   - 도구를 고를 때 "몇 개나 찾았나"보다 **"리포트 중 진짜 비율이 얼마인가"** 를 먼저 물어야 한다.
   - 그리고 이 논문에 적용하면 부메랑이 된다 — **논문 자체가 야생에서의 오탐률을 끝내 보고하지 않는다.** 주입 버그 벤치마크의 step-level precision과, 실제 배포에서 "리포트 N건 중 8건이 진짜"의 N은 완전히 다른 숫자다. 이게 이 논문의 제일 큰 구멍이다.

2. **"LLM을 판정자로 쓰지 마라"는 원칙의 구체적 구현체**
   - 앞서 QA 논의에서 "게이트는 결정론적으로, LLM은 우선순위 매기기에"라고 정리했는데, 이 논문이 정확히 그 구조다.
   - **LLM은 오라클을 *작성*하고, 실행과 판정은 DSL이 결정론적으로 한다.** LLM이 직접 "맞는 것 같습니다"라고 판정하지 않는다.
   - 확률적 요소를 파이프라인의 **한 지점(오라클 생성)에 가두고**, 나머지를 결정론으로 유지하는 설계는 다른 곳에도 그대로 옮겨 쓸 수 있다. 코드 리뷰 에이전트, 데이터 검증 파이프라인 모두.

3. **심볼화 = "에이전트에게 타입 시스템 주기"**
   - 스크린샷과 DOM은 비교 연산이 정의되지 않은 자료형이다. 그래서 LLM에게 "비교해봐"라고 하면 환각이 나온다.
   - Pydantic 스키마로 바꾸는 순간 `==`, `>`, `in`이 진짜로 계산 가능해진다. **환각을 프롬프트로 줄인 게 아니라, 환각이 발생할 자리를 아예 없앤 것.**
   - 실무 이식 포인트: 우리 서비스에서도 "장바구니", "주문", "잔액" 같은 **핵심 도메인 개념을 화면에서 추출 가능한 스키마로 미리 정의해두면** 어떤 에이전틱 QA 도구를 쓰든 정밀도가 올라갈 것이다. 이건 도구 독립적인 자산이다.

4. **시간(temporal) 의존성이 E2E의 본질이다**
   - "각 상태를 독립적으로 검사하면 이전 맥락에 의존하는 버그를 놓친다"는 지적은, 사실 **왜 유닛 테스트로는 E2E를 대체할 수 없는가**에 대한 정확한 답이기도 하다.
   - 그리고 이게 앞선 멀티 에이전트 논의와 이어진다. 여러 에이전트가 병렬로 만든 변경들이 부딪히는 지점은 대부분 **단일 화면이 아니라 상태 전이**다. 그래서 에이전트 시대의 QA는 유닛보다 E2E 쪽에 더 투자해야 할 가능성이 높다.

### 운영 관점

5. **"요구사항이 자기완결적이어야 한다"는 가정이 실무의 진짜 장벽**
   - 논문이 솔직하게 인정한 이 한계가 도입 시 첫 번째 벽이 될 것이다. 대부분의 조직에서 요구사항은 지라 티켓, 슬랙 스레드, 피그마 코멘트에 흩어져 있다.
   - 뒤집으면 **에이전틱 E2E QA의 선행 투자는 도구 도입이 아니라 "명세를 조건-액션-기대결과 형태로 쓰는 습관"** 이다.
   - 이건 Addy Osmani가 말한 *"모호한 사고는 에이전트를 통해 곱해진다"* 와 정확히 같은 결론이다. 개발이든 QA든, 병목은 결국 명세 품질로 수렴한다.

6. **작은 모델의 병목은 지식이 아니라 형식 준수 능력이다**
   - 로컬 모델(Qwen2.5-VL) 실패 원인 분포가 심볼 선언/사용 오류 52% + DSL 문법 오류 39% = **91%**다. "웹을 못 다뤄서"가 아니라 **"형식 언어를 못 써서"** 실패한다.
   - 다만 크기와 성능이 단조롭게 붙지도 않는다 — 원본 요구사항에서는 3B도 1.00이고, 32B는 오히려 0.65다. 변형 입력을 포함한 Total에서야 72B > 32B > 7B > 3B 순서가 드러난다.
   - 완화책이 있다면 모델을 키우는 게 아니라 **DSL을 단순화하거나 제약 디코딩(constrained decoding)/스키마 강제 출력**을 쓰는 방향일 것이다. 논문의 실패 원인 분포가 그 힌트를 준다.
   - 비용 설계 시: E2E 에이전트는 자주 돌리는 게 아니라 **릴리스 게이트에서 큰 모델로 적게 돌리는** 쪽이 합리적이다. 앞서 본 Slack 사례(회당 $15–30)와도 같은 결론.

7. **"프런티어 모델 쓰면 더 잘하지 않나"에 대한 답 — 이 구조에서는 거의 아니다**
   - 판정 주체가 LLM이 아니라 DSL이므로, **모델을 키워도 precision이 오를 경로가 없다.** 남은 오차는 모델의 추론력이 아니라 GUI 그라운딩(UI-Venus-7B)과 DOM 편집거리 기반 page reidentification 같은 **비-LLM 컴포넌트**에서 나온다.
   - Table 5가 이를 뒷받침한다. 원본 요구사항은 이미 포화(1.00)고, GPT-4.1은 오픈 72B에게 진다.
   - 프런티어 모델이 실제로 효과를 낼 지점은 **오라클 생성이 아니라 그 앞단 — 파편적·모호한 명세를 파싱하고 되묻는 능력**이다. 논문도 Discussion에서 "LLM agents must act as proactive semantic parsers... ask the user clarifying questions"라고 직접 지목한다.
   - 즉 이 아키텍처를 개선하는 길은 모델 교체가 아니라 **앞에 명세 파서 레이어를 하나 더 얹는 것**이다. 리포의 `config.yaml`이 Claude/GPT/Gemini/OpenRouter를 지원하므로 직접 검증도 가능하다 — 단, DF는 이미 1.00이라 RQ3의 Dropout/Summarize 조건으로 돌려야 차이가 보인다.

8. **베이스라인 비교에서 배우는 것 — 에이전트 수를 늘리는 게 답이 아니다**
   - PinATA는 3 에이전트 + 장기 메모리라는 가장 정교한 구조인데 정밀도 0.26이었다. WebTestPilot은 그보다 단순한 파이프라인이지만 0.96이다.
   - **차이를 만든 건 아키텍처의 복잡도가 아니라 "무엇을 결정론적으로 만들었는가"** 였다.
   - 멀티 에이전트를 논할 때 계속 나오는 교훈과 같다. 에이전트를 더 붙이기 전에, **검증 가능한 표현으로 문제를 바꿀 수 있는지**를 먼저 본다.
