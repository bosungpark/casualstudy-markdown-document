## AI 요약

### 1. 이 글이 말하는 "멀티 에이전트 운영"이란?

한 줄로 요약하면 **"에이전트 한 명과 대화하는 일(conductor)에서, 여러 에이전트를 동시에 굴리는 일(orchestrator)로의 전환"** 이다.

| | 지휘자(Conductor) 모드 | 오케스트레이터(Orchestrator) 모드 |
|---|---|---|
| 에이전트 수 | 1개 | 여러 개 |
| 진행 방식 | 동기 (내가 기다림) | 비동기 (나는 계획·검토, 에이전트는 실행) |
| 한계 | 내 컨텍스트 윈도우가 곧 천장 | 에이전트마다 자기 컨텍스트를 가짐 |
| 내가 하는 일 | 프롬프트 작성 → 결과 확인 | 작업 분해 → 위임 → 검증 → 통합 |

저자는 Steve Yegge의 "AI 개발 8단계" 프레임을 빌려, **대부분의 개발자가 3~4단계에 머물러 있고 오케스트레이션은 6단계부터 시작된다**고 말한다. 그리고 5단계까지 오는 데 필요했던 능력과 6단계 이후에 필요한 능력은 완전히 다른 종류라고 강조한다.

### 2. 왜 에이전트 하나로는 부족한가 — 세 가지 제약

원문이 드는 단일 에이전트의 한계는 딱 3가지다.

1. **컨텍스트 과부하 (Context overload)**
   - 코드베이스가 커지면 한 에이전트가 담을 수 있는 정보량을 넘어선다.
2. **전문화 부재 (No specialization)**
   - 만능 제너럴리스트는 특정 도메인에 집중한 스페셜리스트보다 성능이 떨어진다.
3. **협업 부재 (No coordination)**
   - 보조 에이전트를 여러 개 띄워도, 서로 대화하거나 의존성을 관리할 수단이 없다.

그래서 저자는 **집중된 에이전트 3개가, 제너럴리스트 1개가 3배 오래 일한 것보다 낫다**고 정리한다. 병렬성(parallelism)·전문화(specialization)·격리(isolation)·누적 학습(compound learning)이 곱셈으로 작용하기 때문이다.

### 3. 패턴 1 — 서브에이전트 (Subagents)

가장 단순한 형태. 부모 에이전트가 일을 쪼개서 자식에게 브리프를 넘긴다.

```
"북마크 관리자 만들어줘"
        │
        ├─ 서브에이전트 A : Data Layer   (스키마, 마이그레이션)
        ├─ 서브에이전트 B : Business Logic (도메인 규칙)
        └─ 서브에이전트 C : API Routes    (핸들러, 검증)
                │
        부모가 결과를 받아 통합
```

- **장점**: 각자 깨끗한 컨텍스트에서 시작한다. 토큰 비용은 대략 220k 수준으로 **비용 중립적(cost-neutral)** 이다.
- **한계**: 서브에이전트끼리 **직접 메시지를 주고받을 수 없고, 공유 태스크 리스트도 없다.** 의존성 그래프는 사람이 직접 관리해야 한다.
  - 예: B가 A의 스키마를 기다려야 한다면, 그 순서를 내가 짜서 넣어줘야 한다.

### 4. 패턴 2 — 에이전트 팀 (Agent Teams)

서브에이전트의 "대화 불가" 문제를 푼 형태. Claude Code의 실험 기능(`CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1`)으로 소개된다.

```
        ┌───────────────┐
        │   Team Lead   │  ← 계획 승인, 통합 책임
        └───────┬───────┘
                │
        ┌───────▼────────┐
        │ 공유 태스크 리스트 │  ← 의존성 자동 해소
        └───┬────┬───┬───┘
            │    │   │
          팀원A 팀원B 팀원C
            └────┴───┘
          팀원끼리 직접 메시징 (P2P)
```

핵심 차이 두 가지:

1. **의존성 자동 해소** — 공유 태스크 리스트가 "누가 무엇을 기다리는지"를 관리한다. 내가 순서를 손으로 짤 필요가 없다.
2. **팀원 간 직접 통신** — 모든 대화가 리드를 거치지 않는다. 즉 **리드가 병목이 되지 않는다.**

> 적정 규모: **팀원 3~5명이 스위트 스팟.** 그 이상은 조율 비용이 이득을 잡아먹는다.

### 5. 패턴 3 — 스케일 오케스트레이션, 3개 티어

에이전트를 5개, 10개, 20개 이상으로 늘릴 때 도구는 세 계층으로 나뉜다.

| 티어 | 실행 위치 | 대표 도구 | 언제 쓰나 |
|---|---|---|---|
| **Tier 1** | 인프로세스 (내 터미널 세션 하나) | Claude Code 서브에이전트 / Agent Teams | 추가 도구 없이 지금 당장 시작 |
| **Tier 2** | 로컬 오케스트레이터 (worktree별 격리 + 대시보드) | Conductor(Melty Labs), Vibe Kanban, Gastown, OpenClaw + Antfarm | **잘 아는 코드베이스에 에이전트 3~10개** |
| **Tier 3** | 클라우드 비동기 에이전트 (VM에서 실행, 터미널 불필요) | Claude Code Web, GitHub Copilot Coding Agent, Jules(Google), Codex Web(OpenAI), Cursor Cloud Agents | 이슈 던져놓고 PR로 받기 |

Tier 3 도구들의 특징적인 운영 방식:

- **GitHub Copilot Coding Agent**: 이슈를 에이전트에게 할당 → 드래프트 PR 생성 → 자기 검토 루프
- **Jules**: 계획 승인 워크플로, `AGENTS.md` 자동 읽기
- **Codex Web**: 로그·테스트를 인용해 **검증 가능한 증거(verifiable evidence)** 를 함께 제출
- **Conductor**: git worktree 기반 격리 + diff 우선 리뷰 대시보드 (Mac 전용)

### 6. 격리 — git worktree

가장 실용적인 운영 장치. 에이전트마다 **자기 작업 디렉터리**를 준다.

> "Git worktrees give each agent its own working directory. No merge conflicts while they work."
> (에이전트가 작업하는 동안에는 머지 충돌이 발생하지 않는다.)

함께 지켜야 할 규칙: **한 파일에는 한 명의 주인만 (One file, one owner).** 두 에이전트가 같은 파일을 동시에 건드리게 두지 않는다.

### 7. 신뢰를 만드는 품질 게이트 3종

에이전트를 믿고 맡기려면, 믿음이 아니라 **장치**가 필요하다.

1. **계획 승인 (Plan approval)**
   - 팀원은 코딩 전에 계획을 먼저 쓴다. 리드가 접근 방식을 보고 승인/반려한다.
   - 잘못된 방향으로 1시간 달리는 것보다, 계획 단계에서 5분 거절하는 게 싸다.
2. **훅 (Hooks)**
   - 라이프사이클 이벤트에 자동 검사를 건다.
   - 예: `TeammateIdle` 훅이 **테스트 전부 통과해야만** 에이전트가 작업을 끝낼 수 있게 한다.
3. **`AGENTS.md` — 누적 학습 파일**
   - 발견한 패턴, 함정, 스타일 취향을 적어두고 모든 에이전트가 세션 시작 시 읽는다.
   - **중요**: 이 파일은 **사람이 직접 큐레이션해야 한다.**

> 원문이 인용하는 연구 결과: **LLM이 생성한 `AGENTS.md`는 이득이 없고, 오히려 성공률을 평균 ~3% 낮추면서 추론 비용은 20% 이상 늘린다.**

즉 "에이전트한테 AGENTS.md도 알아서 써달라고 하기"는 명확한 안티패턴이다.

### 8. Ralph 루프 — 자기 반복 에이전트

컨텍스트를 계속 쌓지 않고, 태스크 단위로 리셋하며 도는 루프.

```
 ┌──────────────────────────────────────────┐
 │ 1. tasks.json 에서 태스크 하나 집기        │
 │ 2. 변경 구현                              │
 │ 3. 검증 (테스트 / 타입 / 린트)             │
 │ 4. 통과하면 커밋                          │
 │ 5. 컨텍스트 리셋 → 다음 태스크             │
 └──────────────────────────────────────────┘
```

무한 루프가 되지 않게 하는 안전장치:

- 에러 시 자동 재시도
- **3회 이상 같은 자리에서 막히면 강제 종료 (kill)**
- 하드 토큰/시간 한도
- 반드시 피처 브랜치에서, 머지 전에는 PR 필수

컨텍스트를 매번 리셋해도 기억이 유지되는 이유는, 기억을 **모델 안이 아니라 밖의 4개 채널**에 두기 때문이다: **git 히스토리 · 진행 로그 · 태스크 상태 파일 · `AGENTS.md`.**

### 9. 병목이 이동했다 — 이 글의 핵심 문장

> **"Verification is the bottleneck, not generation."**
> (병목은 생성이 아니라 검증이다.)

그리고 가장 인상적인 통찰:

> **"The human bottleneck was a feature, not a bug."**
> 사람 속도로 일할 때는 에러가 천천히 쌓이고, 그 고통이 곧 조기 수정을 강제했다.
> 에이전트 군단을 굴리면 **작은 실수가 내가 잡아낼 수 있는 속도보다 빠르게 복리로 불어난다.**

이게 멀티 에이전트 운영이 "속도 문제"가 아니라 "검증 인프라 문제"인 이유다.

### 10. 팩토리 모델 — 실제 운영 루프

```
Plan → Spawn → Monitor → Verify → Integrate → Retro
계획   생성    모니터링   검증     통합       회고
```

운영 상수(원문이 제시하는 실무 수치):

| 항목 | 값 |
|---|---|
| WIP 제한 | 동시 에이전트 3~5개 |
| 킬 기준 | 같은 자리에서 3회 이상 막힘 |
| 체크인 주기 | 5~10분마다 비동기 확인 |
| 토큰 예산 예시 | 프론트엔드 180k / 백엔드 280k, **85%에서 일시정지** |
| 파일 소유권 | 한 파일 = 한 에이전트 |
| 모델 라우팅 | 계획 → 저렴한 모델 / 구현 → 비싼 모델 / 리뷰 → 보안 특화 |

토큰 예산에 **85% 일시정지**를 거는 게 특히 실용적이다. 컨텍스트가 꽉 차면 에이전트 품질이 급락하는데, 터지기 전에 멈춰서 정리할 기회를 준다.

### 11. 무엇을 위임하고, 무엇을 사람이 쥘 것인가

| 에이전트에게 넘길 것 | 사람이 계속 쥘 것 |
|---|---|
| 명확한 pass/fail 기준이 있는 범위 한정 태스크 | 아키텍처 |
| 보일러플레이트 | **무엇을 만들지 "않을지"** 결정 |
| 마이그레이션 | 전체 맥락을 아는 리뷰 |
| 테스트 스캐폴딩 | 좋은 시스템을 만드는 감각(taste) |

> "에이전트 50개를 병렬로 돌리면, 모호한 사고는 단지 느려지는 게 아니라 **곱해진다.**
> 강한 엔지니어일수록 에이전트에서 더 큰 레버리지를 얻는다. 그 반대가 아니라."

### 12. 오늘부터 할 수 있는 5단계

1. **서브에이전트로 작업 분해** — 오늘 시작 가능, 추가 도구 불필요
2. **에이전트 팀으로 병렬화** — 다음 주쯤
3. **git worktree로 격리**
4. **품질 게이트(계획 승인 + 훅)로 신뢰 확보**
5. **`AGENTS.md`로 학습 누적** — 반드시 사람이 작성

## 내가 얻은 인사이트

### 운영자 관점

1. **"검증이 병목"은 조직 구조 문제로 이어진다**
   - 생성 속도가 3배가 되어도 리뷰 인원이 그대로면 PR 큐만 길어진다.
   - 즉 멀티 에이전트 도입의 실제 선행 조건은 "에이전트 도구"가 아니라 **CI·테스트·린트·타입 체크가 신뢰할 만한가**이다. 자동 검증이 약한 팀은 에이전트를 늘릴수록 손해다.
   - 훅(`TeammateIdle`에서 테스트 강제)이 결국 이 문제를 코드로 푸는 장치다.

2. **"사람 병목은 버그가 아니라 기능이었다"는 관측이 가장 값지다**
   - 기존 개발 프로세스에는 사람의 느림이 만들어주던 **암묵적 에러 감쇠 장치**가 있었다.
   - 그걸 제거하면, 잃어버린 감쇠를 명시적 장치(WIP 제한 3~5, 3회 킬, 토큰 85% 정지)로 **직접 다시 만들어 넣어야 한다.**
   - 이건 소프트웨어 문제가 아니라 **제조업의 WIP 관리 문제**에 가깝다. 칸반의 WIP 제한이 그대로 재발명되는 게 우연이 아니다.

3. **3~5개라는 숫자의 의미**
   - 조율 채널 수는 팀원 n명일 때 n(n-1)/2로 늘어난다. 5명이면 10개, 10명이면 45개.
   - 에이전트 팀이 P2P 메시징을 도입해 리드 병목을 없앤 대가로, **메시징 오버헤드**를 얻었다. 그래서 상한이 생긴다.
   - 더 늘리고 싶으면 채널을 늘리는 게 아니라 **Tier 2(worktree 격리)로 넘어가서 아예 서로 안 만나게** 하는 게 원문이 제시하는 답이다.

### 설계 관점

4. **컨텍스트 리셋이 가능한 이유는 "기억을 밖에 뒀기 때문"**
   - Ralph 루프의 진짜 아이디어는 반복이 아니라, 상태를 **git 히스토리 / 진행 로그 / 태스크 파일 / AGENTS.md** 라는 외부 스토어로 옮긴 것이다.
   - 이건 stateless 서버 + 외부 상태 저장소라는 웹 아키텍처의 기본형과 정확히 같다. 스케일아웃이 되는 이유도 같다.
   - 뒤집어 말하면, **대화 히스토리에만 상태를 쌓는 에이전트 운영은 스케일아웃이 원천적으로 불가능하다.**

5. **LLM이 쓴 `AGENTS.md`가 오히려 해롭다(-3%, +20% 비용)는 결과**
   - 모델이 스스로 만든 요약은 새 정보가 아니라 **이미 모델 안에 있던 것의 재진술**이다. 토큰만 먹고 신호는 없다.
   - 진짜 가치 있는 건 "이 코드베이스에서만 참인 것" — 왜 이 라이브러리를 안 쓰는지, 어떤 함정이 있는지. 그건 **사람만 안다.**
   - 우리 저장소의 `CLAUDE.md`도 같은 기준으로 관리해야 한다는 뜻이다. 자동 생성 유혹을 참을 것.

6. **"한 파일, 한 주인" 규칙은 사실 모듈 경계 테스트다**
   - 이 규칙을 지키기 어려운 코드베이스는, 이미 응집도·결합도가 나쁜 코드베이스다.
   - 즉 멀티 에이전트 도입은 아키텍처 품질에 대한 **리트머스 시험지**로도 쓸 수 있다. 병렬화가 안 되면 에이전트 탓이 아니라 설계 탓일 확률이 높다.

### 개인 실천 관점

7. **당장 바꿀 것은 도구가 아니라 태스크 작성 습관**
   - "명확한 pass/fail 기준이 있는 범위 한정 태스크"가 위임의 최소 단위다.
   - 즉 내가 먼저 연습해야 하는 건 오케스트레이션 도구가 아니라, **검증 기준을 먼저 쓰는 습관**이다. 이게 안 되면 Tier 1에서도 실패한다.
   - 이 저장소의 학습 노트 작성도 같다 — "무엇이 완성인가"를 먼저 정의하는 쪽이 항상 결과가 낫다.
