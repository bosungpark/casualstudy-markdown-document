## AI 요약

### 1. 왜 파인튜닝이 아니라 컨텍스트 엔지니어링인가

저자는 이전 창업에서 오픈 정보 추출 모델을 밑바닥부터 학습시키던 경험을 회고한다. 데이터를 모으고 학습을 돌리고 평가하는 데 몇 주가 걸렸는데, GPT-3와 인컨텍스트 러닝이 등장하면서 그 모델들은 하룻밤 사이에 무의미해졌다.

Manus를 만들 때는 그래서 **엔드투엔드 에이전트 모델을 학습시키는 대신 프론티어 모델의 인컨텍스트 러닝 능력 위에 컨텍스트를 설계하는 길**을 택했다. 개선 주기가 몇 주에서 몇 시간으로 줄었고, 제품이 특정 모델 아키텍처에 묶이지 않는다.

> "If model progress is the rising tide, we want Manus to be the boat, not the pillar stuck to the seabed."
> — 모델 발전이 밀물이라면, Manus는 해저에 박힌 기둥이 아니라 배이고 싶다.

이 원칙 아래 에이전트 프레임워크를 **네 번 다시 만들었고**, 저자는 이 반복 과정을 농담조로 **"Stochastic Graduate Descent"** 라고 부른다. 아래 여섯 가지는 그 과정에서 얻은 국소 최적해들이다.

```
[사용자 입력]
    ↓
 ┌──> 모델이 도구 호출 선택
 │        ↓
 │    환경이 액션 실행 → 관찰(observation) 반환
 │        ↓
 └──── 컨텍스트에 append (평균 ~50회 반복)
          ↓
      [작업 완료]
```

에이전트는 이 루프를 도는 구조여서 매 스텝마다 컨텍스트가 길어진다. 그 결과 **입력:출력 토큰 비율이 평균 100:1** 에 달한다. 이 비대칭이 뒤의 모든 설계를 지배한다.

### 2. 교훈 1 — KV-Cache를 중심으로 설계하라

저자는 프로덕션 에이전트에서 **KV-cache 적중률이 가장 중요한 단일 지표**라고 단언한다. 지연 시간과 비용 양쪽에 직결되기 때문이다.

아티클이 인용한 Claude Sonnet 기준 가격(작성 시점 2025-07):

| 토큰 종류 | 가격 | 배수 |
|---|---|---|
| 캐시 히트 입력 | $0.30 / MTok | 1x |
| 캐시 미스 입력 | $3.00 / MTok | **10x** |

입출력 비율이 100:1인 워크로드에서 10배 차이는 곧 전체 비용의 차이다. 캐시 적중률을 높이기 위한 실천 항목:

- **프롬프트 프리픽스를 안정적으로 유지한다.** 토큰 하나만 달라져도 그 지점 이후 캐시가 전부 무효화된다. 시스템 프롬프트 맨 앞에 초 단위 타임스탬프를 넣는 흔한 실수가 대표적이다.
- **컨텍스트를 append-only로 다룬다.** 이전 액션과 관찰을 나중에 수정하지 않는다.
- **직렬화를 결정적으로 만든다.** 많은 언어의 JSON 객체는 키 순서를 보장하지 않아, 의미가 같아도 바이트가 달라지면서 캐시를 조용히 깨뜨린다.
- **캐시 브레이크포인트를 명시한다.** 자동 증분 프리픽스 캐싱을 지원하지 않는 프레임워크에서는 수동으로 표시해야 하며, 최소한 시스템 프롬프트 끝에는 두는 게 좋다.
- **자체 호스팅(vLLM 등)이라면** 프리픽스 캐싱을 켜고, 세션 ID로 요청을 같은 워커로 라우팅한다.

### 3. 교훈 2 — 도구를 제거하지 말고 마스킹하라

에이전트의 도구가 늘어나면 액션 공간이 비대해지고 모델이 엉뚱한 도구를 고르기 쉬워진다. 그래서 많은 구현이 **동적으로 도구를 넣고 빼는** 방식을 쓰지만, 저자는 이를 권하지 않는다.

1. 도구 정의는 보통 컨텍스트 **앞부분**에 온다. 여기를 건드리면 뒤따르는 모든 액션·관찰의 KV-cache가 무효화된다.
2. 이전 대화에 이미 등장한 도구를 목록에서 없애면 모델이 혼란스러워한다. 제약 디코딩이 없으면 스키마 위반이나 환각 액션으로 이어진다.

대신 Manus는 **컨텍스트 인식 상태 기계로 디코딩 단계에서 토큰 로짓을 마스킹**해 그 스텝에 허용되는 도구만 고르게 한다. 도구 정의 자체는 컨텍스트에 그대로 남는다.

NousResearch의 Hermes 포맷을 예로 든 세 가지 함수 호출 모드:

| 모드 | 의미 | 프리필 |
|---|---|---|
| Auto | 호출해도 되고 안 해도 됨 | `<\|im_start\|>assistant` |
| Required | 반드시 호출, 대상은 자유 | `<\|im_start\|>assistant<tool_call>` |
| Specified | 특정 부분집합에서만 호출 | `<\|im_start\|>assistant<tool_call>{"name": "browser_` |

여기서 실용적인 트릭이 나온다. 액션 이름에 **일관된 접두사**(`browser_`, `shell_`)를 붙여 두면, 프리필 문자열만으로 카테고리 단위 마스킹이 가능해진다. 별도의 상태 저장 로직 없이 액션 공간을 좁힐 수 있다.

### 4. 교훈 3 — 파일 시스템을 컨텍스트로 사용하라

컨텍스트 윈도가 128K를 넘어섰지만 실제 에이전트 시나리오에서는 여전히 부족하거나 해롭다. 저자가 꼽는 세 가지 이유:

1. 웹 페이지나 PDF 같은 비정형 관찰 결과 하나가 컨텍스트 한도를 쉽게 넘긴다.
2. 기술적으로 지원되는 길이라도, 일정 길이를 넘으면 **모델 성능이 떨어진다.**
3. 프리픽스 캐싱을 써도 긴 입력은 여전히 비싸다. 전송해야 할 토큰 값은 지불해야 한다.

여기서 흔히 쓰는 대응이 잘라내기(truncation)와 압축인데, 문제는 **되돌릴 수 없다는 점**이다. 몇 스텝 뒤에야 필요해질 정보를 지금 버릴지 판단하는 것은 원리적으로 불가능하다.

Manus의 답은 **파일 시스템을 궁극의 컨텍스트로 취급하는 것**이다. 크기 제한이 없고, 본질적으로 영속적이며, 에이전트가 직접 조작할 수 있다. 모델은 필요할 때 파일을 쓰고 읽도록 학습되며, 파일 시스템은 저장소가 아니라 **구조화된 외부 메모리**로 쓰인다.

핵심은 **복원 가능한 압축(restorable compression)** 이다.

| 컨텍스트에서 버리는 것 | 대신 남기는 것 | 복원 방법 |
|---|---|---|
| 웹 페이지 본문 | URL | 다시 fetch |
| 문서 전체 내용 | 샌드박스 파일 경로 | 다시 read |

이렇게 하면 정보를 영구히 잃지 않으면서 컨텍스트 길이를 줄일 수 있다.

마지막에 저자는 사변적인 전망을 덧붙인다. **State Space Model(SSM)** 은 Transformer보다 빠르고 효율적이지만 긴 거리 의존성 때문에 에이전트에 쓰기 어려웠다. 그런데 SSM이 컨텍스트 안에 상태를 담는 대신 **파일 기반 메모리를 다루는 법을 익힌다면**, 속도와 효율을 살린 새로운 종류의 에이전트가 가능할지 모른다. 저자는 이것이 Neural Turing Machine이 이루려던 것의 진짜 후계자일 수 있다고 본다.

### 5. 교훈 4 — 낭송(recitation)으로 어텐션을 조작하라

Manus는 복잡한 작업을 시작하면 `todo.md`를 만들고, 진행하면서 항목을 하나씩 지워 나가며 **파일을 다시 컨텍스트 끝에 붙인다.**

이것은 귀여운 습관이 아니라 의도된 어텐션 조작이다. 평균 약 50회의 도구 호출이 이어지는 긴 루프에서는 모델이 주제에서 벗어나거나 초기 목표를 잊는 **lost-in-the-middle** 문제가 생긴다. 목표를 계속 컨텍스트 **끝**으로 다시 써 넣으면, 전역 계획이 모델의 최근 어텐션 범위 안으로 밀려 들어온다.

```
[시스템 프롬프트][도구 정의][...50스텝의 액션/관찰...][todo.md 최신본]
                                                       ↑
                                            목표를 어텐션 근처로 재주입
```

아키텍처 변경도, 특별한 메커니즘도 없다. 자연어를 써서 모델 자신의 어텐션을 편향시키는 방식이다.

---

### 6. 교훈 5 — 틀린 것을 남겨 두어라

에이전트는 실패한다. 환각, 환경 오류, 도구 오작동, 엣지 케이스는 예외가 아니라 루프의 일부다. 흔한 대응은 실패한 액션과 스택 트레이스를 지우고 재시도하거나 상태를 리셋하는 것이다.

저자는 이를 **실수**라고 본다. 실패의 증거를 지우면 모델은 그 증거로부터 배울 기회를 잃는다. 실패한 액션과 그 결과 관찰을 컨텍스트에 남겨 두면, 모델은 암묵적으로 내부 믿음을 갱신해 비슷한 액션에 대한 사전 확률을 낮춘다.

> 실패로부터의 회복(error recovery)은 진짜 에이전트 행동을 보여 주는 가장 명확한 지표 중 하나지만, 학술 벤치마크는 대부분 이상적 조건에서의 성공률만 측정한다.

---

### 7. 교훈 6 — Few-shot에 갇히지 마라

Few-shot 프롬프팅은 LLM에서 표준 기법이지만 에이전트에서는 역효과를 낼 수 있다. 언어 모델은 뛰어난 모방자이기 때문이다.

컨텍스트가 비슷한 액션-관찰 쌍으로 균일하게 채워지면, 모델은 그것이 더 이상 최적이 아닐 때조차 그 패턴을 계속 따라간다. 저자가 든 사례는 20건의 이력서 검토 작업이다. 에이전트는 같은 리듬의 액션을 반복하다가 표류(drift)와 환각, 과잉 일반화로 흘렀다.

해법은 **구조화된 다양성**이다. 직렬화 템플릿을 여러 개 두고, 표현을 바꾸고, 순서나 서식에 약간의 노이즈를 준다. 이 통제된 무작위성이 패턴 의존을 깨고 어텐션을 되돌린다.

> 균일한 컨텍스트는 취약한 에이전트를 만든다.

---

### 8. 정리

| 교훈 | 하지 말 것 | 대신 할 것 |
|---|---|---|
| 1. KV-Cache | 프리픽스에 타임스탬프, 컨텍스트 수정 | append-only + 결정적 직렬화 |
| 2. 액션 공간 | 도구를 동적으로 추가/삭제 | 로짓 마스킹 + 이름 접두사 |
| 3. 컨텍스트 한계 | 되돌릴 수 없는 잘라내기/압축 | 파일 시스템 = 외부 메모리, 복원 가능한 압축 |
| 4. 긴 루프 | 목표가 컨텍스트 중간에 묻히게 두기 | `todo.md` 낭송으로 끝에 재주입 |
| 5. 실패 처리 | 오류 흔적 삭제 후 리셋 | 실패를 컨텍스트에 남겨 사전 확률 갱신 |
| 6. 패턴 | 균일한 few-shot 반복 | 직렬화에 구조화된 다양성 주입 |

저자의 결론:

> "How you shape the context ultimately defines how your agent behaves: how fast it runs, how well it recovers, and how far it scales."
> 모델은 더 강해지고 빨라지고 싸지겠지만, 어떤 원시 능력도 **메모리·환경·피드백**의 필요를 대체하지 못한다.

## 내가 얻은 인사이트

### 아키텍처 관점

1. **"배가 되고 기둥이 되지 마라"는 것이 이 글의 진짜 주제다**
   - 여섯 가지 교훈은 표면상 최적화 팁처럼 보이지만, 전부 하나의 기준으로 수렴한다. *모델이 좋아졌을 때 자동으로 같이 좋아지는가?* 로짓 마스킹은 그렇고, 도구 목록을 동적으로 재구성하는 로직은 그렇지 않다. 파일 시스템 메모리는 그렇고, 학습된 요약 모델은 그렇지 않다.
   - 기술 선택을 할 때 "지금 얼마나 잘 도는가"만 보면 6개월 뒤에 기둥이 된다. 모델 발전과 **직교(orthogonal)** 하는 층에 투자하는지를 같이 물어야 한다.

2. **파일 시스템은 가장 저평가된 에이전트 인프라다**
   - 벡터 DB, 그래프 DB, 별도 메모리 서비스를 붙이기 전에 먼저 물어볼 것: *에이전트가 이미 잘 다루는 도구로 안 되는가?* 모델은 학습 과정에서 파일 시스템 조작을 이미 깊이 익혔다. 새 인터페이스를 배우게 하는 비용이 0이다.
   - "복원 가능한 압축"은 그 자체로 일반화할 수 있는 설계 규칙이다. **컨텍스트에서 무엇을 버리든, 그것을 다시 가져올 핸들(URL·경로·ID)을 반드시 남긴다.** 이 규칙만 지키면 압축 정책이 틀려도 치명적이지 않다.
   - 다만 이 글의 전제는 **샌드박스가 있다**는 것이다. 에이전트가 임의로 파일을 쓰고 읽을 수 있는 격리된 VM이 없으면 3번 교훈은 그대로 적용되지 않는다. 파일 시스템 메모리는 공짜가 아니라 샌드박스 운영 비용과 맞바꾸는 선택이다.

### 비용·운영 관점

3. **입출력 비율 100:1은 에이전트 비용 모델을 완전히 바꾼다**
   - 챗봇 감각으로 비용을 추정하면 크게 틀린다. 에이전트에서 출력 토큰 가격은 거의 무의미하고, **캐시 적중률이 곧 단가**다. KV-cache를 깨는 코드 한 줄(프롬프트 맨 앞 타임스탬프, 정렬되지 않은 JSON 키)이 청구서를 10배로 만들 수 있다는 건 코드 리뷰 체크리스트에 올릴 만한 구체성이다.
   - 실무적으로는 캐시 적중률을 **대시보드 지표로 올려야 한다**는 뜻이기도 하다. 지연 시간이나 성공률만 보고 있으면 캐시가 깨진 걸 비용 청구서를 받고서야 안다.

4. **실패를 남기는 것과 오염되는 것 사이의 경계는 여전히 미해결이다**
   - 교훈 5(틀린 것을 남겨라)와 교훈 6(패턴에 갇히지 마라)은 사실 긴장 관계에 있다. 실패 흔적을 남기면 모델이 배우지만, 그 흔적이 균일하게 쌓이면 그 자체가 모방할 패턴이 된다. 아티클은 이 둘을 나란히 놓기만 하고 경계선을 제시하지 않는다.
   - 나는 이것이 **세션 내 컨텍스트**와 **세션을 넘어 영속되는 메모리**를 구분해야 하는 이유라고 본다. 진행 중인 루프에서 실패는 유용한 신호지만, 그것이 그대로 장기 메모리로 승격되면 잘못된 사실이 이후 모든 세션을 오염시킨다. 어떤 흔적을 승격시킬지 결정하는 게이트는 이 글의 범위 밖이고, 실제로 에이전트 메모리 설계에서 가장 어려운 부분이다.

### 검증 관점

5. **낭송(recitation)은 비용이 거의 없는 개입이다**
   - `todo.md`를 매 스텝 컨텍스트 끝에 다시 붙이는 것은 몇 백 토큰짜리 변경인데, 50스텝짜리 작업의 목표 이탈을 줄인다. 아키텍처를 바꾸지 않고 자연어만으로 어텐션을 편향시키는 이런 개입은 **직접 A/B로 확인해 볼 가치**가 있다.
   - 반대로 아티클은 이 효과를 수치로 제시하지 않는다. "네 번 다시 만들며 찾은 국소 최적해"라는 저자의 표현대로, 여섯 교훈 모두 벤치마크가 아니라 **한 팀의 프로덕션 경험**이다. 우리 워크로드에서도 같은 결론이 나오는지는 별도로 확인해야 한다.
