## AI 요약

### 1. 문제 정의 — 50번의 도구 호출이 컨텍스트를 망친다

Manus의 전형적인 작업 한 건은 **약 50회의 도구 호출**을 소비한다. 컨텍스트 엔지니어링이 없으면 이 결과물이 전부 컨텍스트 윈도에 누적되고, 창이 차오를수록 모델 성능이 떨어진다.

아티클은 이 현상의 근거로 두 가지를 인용한다.

- Chroma의 **context rot** 연구 — 컨텍스트가 길어질수록 성능이 저하된다는 실증
- Anthropic의 설명 — 컨텍스트가 커지면 모델의 **어텐션 예산(attention budget)** 이 고갈된다

그리고 Karpathy의 정의를 기준점으로 삼는다.

> 컨텍스트 엔지니어링은 (에이전트 궤적의) 다음 스텝에 **딱 맞는 정보만으로** 컨텍스트 윈도를 채우는 섬세한 기술이자 과학이다.

### 2. 전제 — 세션마다 전용 가상 컴퓨터

Manus의 모든 전략은 하나의 인프라 전제 위에 서 있다. **세션마다 전용 클라우드 VM**이 붙고, 에이전트는 그 안에서 파일 시스템·탐색 도구·셸 명령 실행을 자유롭게 쓴다.

이 샌드박스 위에서 세 가지 전략이 나온다. 아티클은 이것이 Anthropic이 정리한 접근과 일치한다고 본다.

| 전략 | 한 줄 정의 | 컨텍스트에서 하는 일 |
|---|---|---|
| **Offload** (밖으로 빼기) | 도구 정의와 결과를 샌드박스로 내보낸다 | 애초에 들어오는 양을 줄인다 |
| **Reduce** (줄이기) | 오래된 것을 참조로 바꾸고, 나중엔 요약한다 | 이미 들어온 것을 압축한다 |
| **Isolate** (격리하기) | 서브에이전트에게 별도 컨텍스트를 준다 | 다른 창으로 분리한다 |

### 3. Offload — 레이어드 액션 공간

에이전트에게 많은 일을 시키려면 도구를 많이 붙이면 될 것 같지만, 도구 설명은 토큰을 먹고 **겹치거나 모호한 도구가 많으면 모델이 혼란**에 빠진다.

Manus의 답은 액션 공간을 **두 개 층으로 나누는 것**이다.

```
┌─ 레이어 1: 함수 호출 (컨텍스트에 상주) ─────────┐
│  20개 미만의 원자적 함수                        │
│   · Bash                                       │
│   · 파일 시스템 조작                            │
│   · 코드 실행                                  │
└──────────────────┬─────────────────────────────┘
                   │ Bash로 호출
┌──────────────────▼─────────────────────────────┐
│ 레이어 2: 샌드박스 (컨텍스트 밖)                 │
│   · 각종 유틸리티                               │
│   · MCP 도구 → CLI로 노출                       │
└────────────────────────────────────────────────┘
```

핵심은 **함수 호출 층을 부풀리지 않고 대부분의 액션을 샌드박스 층으로 내려보내는 것**이다. MCP 도구조차 별도 도구로 바인딩하지 않고 CLI로 노출해 에이전트가 Bash로 실행하게 한다.

아티클은 Claude의 **Skills** 기능이 같은 발상이라고 지적한다. 스킬은 바인딩된 도구가 아니라 **파일 시스템에 저장**되고, Claude는 몇 개의 단순한 함수 호출(Bash, 파일 시스템)만으로 필요할 때 점진적으로 발견해 쓴다. 원문이 인용한 **progressive disclosure** 원칙이 그것이다.

도구 결과 역시 같은 방식으로 밖으로 나간다. 파일 시스템에 저장하고, 검색은 인덱싱(벡터스토어) 없이 `glob`과 `grep` 같은 기본 유틸리티로 한다.

### 4. Reduce — 압축(compaction) 다음에 요약(summarization)

Manus의 도구 호출 결과는 **두 가지 표현**을 갖는다.

| 표현 | 내용 | 저장 위치 |
|---|---|---|
| **full** | 도구 호출의 원본 결과 전체 | 샌드박스(파일 시스템) |
| **compact** | full을 가리키는 참조(예: 파일 경로) | 컨텍스트 |

컨텍스트가 차오르면 **오래된(stale) 도구 결과부터 full → compact로 교체**한다. 이미 판단에 사용된 결과이므로 토큰을 회수해도 되고, 필요하면 참조를 따라 다시 가져올 수 있다. 반면 **최신 결과는 full로 유지**한다. 다음 결정을 이끄는 것도, 올바른 도구 사용법의 신선한 few-shot 예시가 되는 것도 최신 결과이기 때문이다.

아티클은 이 전략이 Anthropic의 **context editing** 기능과 유사하다고 본다. 토큰 한도에 근접하면 오래된 도구 호출과 결과를 자동으로 비우되 대화 흐름은 보존하는 방식이다.

압축만으로 수익 체감(diminishing returns)에 도달하면 — 이미 대부분이 참조로 바뀌어 더 줄일 게 없어지면 — 그때 **궤적 전체를 요약**한다. 두 가지가 중요하다.

1. 요약은 컨텍스트에 남은 compact 버전이 아니라 **full 도구 결과를 사용해** 생성한다.
2. 요약 필드를 **스키마로 정의**해, 어떤 궤적이든 일관된 요약 객체가 나오게 한다.

```
컨텍스트 사용량
  ▲
  │      ┌─ compaction ─┐   ┌─ compaction ─┐
  │     ╱               ╲  ╱               ╲
  │    ╱                 ╲╱                 ╲   ← 압축 여지 소진
  │   ╱                                      ╲
  │  ╱                                        ╲─ summarization (full 결과 기반)
  └────────────────────────────────────────────────▶ 스텝
```

### 5. Isolate — 역할이 아니라 컨텍스트로 나눈다

Manus는 멀티 에이전트를 쓰지만 **의인화된 분업을 피한다.** 사람이 디자이너·엔지니어·PM으로 나뉘는 건 사람의 인지 한계 때문이지, LLM이 같은 제약을 공유하지는 않는다는 것이 아티클의 논지다.

그래서 서브에이전트의 **1차 목적은 컨텍스트 격리**다. 할 일이 있으면 자기만의 컨텍스트 윈도를 가진 서브에이전트에 맡긴다.

현재 구성:

| 에이전트 | 역할 |
|---|---|
| **Planner** | 태스크를 나누고 할당 |
| **Knowledge manager** | 대화를 검토해 파일 시스템에 무엇을 남길지 결정 |
| **Executor** | 플래너가 할당한 태스크 수행 |

**여기서 원글(2025-07)의 결론 하나가 뒤집힌다.** Manus는 처음에 `todo.md`로 계획을 관리했지만, **전체 액션의 약 1/3이 todo 리스트를 갱신하는 데 쓰이고 있다**는 것을 발견하고 전용 플래너 에이전트로 전환했다.

멀티 에이전트의 중심 난제는 **플래너와 서브에이전트 사이의 컨텍스트 공유**다. 아티클은 Anthropic의 Erik Schluntz와 Cognition의 Walden Yan도 같은 문제를 지목한다고 언급한다. Manus의 처리 방식은 태스크 복잡도에 따라 둘로 갈린다.

| 상황 | 공유 방식 | 비교 대상 |
|---|---|---|
| 단순 — 플래너가 **결과만** 필요 | 지시문만 만들어 함수 호출로 전달 | Claude Code의 Task 도구 |
| 복잡 — 서브에이전트가 플래너와 **같은 파일에 써야** 함 | 플래너의 **전체 컨텍스트**를 넘김 | — |

두 경우 모두 **플래너가 서브에이전트의 출력 스키마를 정의**한다. 서브에이전트는 `submit results` 도구로 그 스키마를 채워 반환하고, Manus는 **제약 디코딩(constrained decoding)** 으로 스키마 준수를 강제한다.

### 6. 모델 선택 — 단일 모델에 걸지 않는다

Manus는 하나의 모델에 커밋하는 대신 **태스크 단위 라우팅**을 한다. 코딩은 Claude, 멀티모달은 Gemini, 수학·추론은 OpenAI 식이다.

선택 기준은 넓게 보면 비용이고, 그 안에서 **KV 캐시 효율이 중심 역할**을 한다. 시스템 지시문과 오래된 도구 결과 등에 캐싱을 걸어 여러 턴에 걸친 비용과 지연을 줄인다.

여기서 나오는 관찰이 실무적으로 중요하다. Peak는 **분산 KV 캐시 인프라는 오픈소스 모델로 직접 구현하기 어렵지만 프론티어 제공자들은 잘 지원한다**고 말한다. 그 결과 **에이전트 유스케이스에서는 프론티어 모델이 실제로 더 저렴할 수 있다.**

### 7. Bitter Lesson — 하네스가 병목이 되지 않게

마지막 주제는 **The Bitter Lesson**이다. Claude Code를 만든 Boris Cherny가 Claude Code를 의도적으로 **unopinionated**하게 유지한 것도 같은 이유라고 아티클은 전한다.

계속 좋아지는 모델 위에 제품을 올린다는 건 **계속되는 변경을 받아들인다는 뜻**이다. Peak에 따르면 Manus는 3월 출시 이후 **다섯 번 리팩터링**했다.

Peak의 경고는 더 구체적이다. **에이전트의 하네스(harness)가 모델이 발전할수록 오히려 성능을 제한할 수 있다.** 특정 시점의 성능을 올리려고 넣은 구조가, 컴퓨트가 커지면 족쇄가 된다.

이를 막기 위한 실천이 이 글에서 가장 실행 가능한 조언이다.

> **모델 강도를 바꿔 가며 에이전트 평가를 돌려라. 더 강한 모델에서 성능이 올라가지 않으면, 당신의 하네스가 에이전트의 발목을 잡고 있는 것이다.**

Hyung Won Chung의 강연도 같은 요구를 반복한다고 인용한다. *지금의 컴퓨트·데이터 수준에 필요한 구조를 넣되, 나중에는 걷어내라. 그 지름길들이 이후의 개선을 병목시키기 때문이다.*

### 8. 정리

| 전략 | 구체적 실천 |
|---|---|
| **Offload** | 도구 결과를 파일 시스템에 저장하고 `glob`/`grep`으로 온디맨드 접근 |
| | 20개 미만의 원자적 함수만 바인딩, 나머지 유틸·MCP는 샌드박스에서 Bash로 실행 |
| **Reduce** | 오래된 도구 결과를 참조로 교체(compaction), 최신 결과는 full 유지 |
| | 압축이 수익 체감에 도달하면 full 결과 기반 스키마 요약 |
| **Isolate** | 역할 분업이 아니라 **컨텍스트 격리**를 목적으로 서브에이전트 사용 |
| | 단순 태스크는 지시문만, 복잡 태스크는 전체 컨텍스트 공유 |
| **검증** | 모델 강도를 바꿔 가며 평가해 하네스가 병목인지 확인 |

## 내가 얻은 인사이트

### 소규모 팀 관점 — "프론티어 위에 올라타기"의 실제 내용

1. **올라탄다는 것은 "그냥 API를 쓴다"가 아니라 "직교하는 층에만 투자한다"는 뜻이다**
   - 이 글에서 Manus가 만든 것은 모델 능력이 아니라 **샌드박스, 파일 레이아웃, 압축 정책, 플래너-서브에이전트 프로토콜, 출력 스키마**다. 전부 모델이 좋아지면 같이 좋아지는 층이다. 반대로 모델 발전을 흡수하지 못하는 층(자체 파인튜닝, 모델별 하드코딩된 프롬프트 트릭)에는 손대지 않았다.
   - 소규모 팀이 가져갈 판단 기준은 이것이라고 본다. *다음 세대 모델이 나왔을 때 이 코드는 자산인가 부채인가?* 자산이면 만들고, 부채면 사거나 빌린다.

2. **프론티어 API가 자체 서빙보다 싸질 수 있다는 지점이 가장 반직관적이다**
   - 보통 "비용 때문에 오픈소스 모델을 셀프 호스팅한다"고 생각하지만, 이 글은 **분산 KV 캐시**를 근거로 반대 결론을 낸다. 입력이 출력보다 압도적으로 많은 에이전트 워크로드에서는 캐시 히트율이 곧 단가이고, 그 인프라를 직접 만드는 비용이 토큰 단가 차이를 넘어선다는 것이다.
   - 소규모 팀에는 특히 결정적이다. 캐시 인프라는 **팀 규모에 강하게 의존하는 고정비**이고, 그건 프론티어 제공자가 규모의 경제로 이미 지불한 비용이다. 여기서 경쟁하려는 것은 전형적인 기둥 세우기다.
   - 다만 이건 어디까지나 아티클이 전하는 Peak의 관찰이고, 수치 비교는 제시되지 않는다. 자기 워크로드의 캐시 히트율을 먼저 재 보지 않으면 그대로 옮길 수 없는 주장이다.

3. **"모델 강도를 바꿔 가며 평가하라"는 소규모 팀이 당장 도입할 수 있는 유일한 미래 대비책이다**
   - 하네스가 병목인지 아닌지는 논쟁으로 정할 수 없다. 같은 eval을 약한 모델과 강한 모델에서 돌려 **기울기**를 보면 된다. 평평하면 내 구조가 천장이다.
   - 이건 인프라 투자도 조직 변경도 필요 없고, eval 러너에 모델 파라미터 하나를 추가하는 일이다. 비용 대비 효과가 이 글에서 가장 좋다.

### 아키텍처 관점

4. **`todo.md` 폐기는 이 글에서 가장 값진 정보다**
   - 원글(7월)의 교훈 4는 `todo.md` 낭송으로 어텐션을 조작하라는 것이었고, 아키텍처 변경 없이 자연어만으로 되는 저비용 개입이라는 점에서 매력적이었다. 3개월 뒤 같은 팀이 **전체 액션의 1/3이 todo 갱신에 쓰인다**는 이유로 그것을 버렸다.
   - 교훈은 두 가지다. 첫째, **"토큰이 적게 든다"와 "액션이 적게 든다"는 다른 축이다.** 낭송 자체는 몇 백 토큰이지만, 그 파일을 갱신하는 **도구 호출 횟수**가 진짜 비용이었다. 50스텝 예산에서 17스텝을 관리 오버헤드에 쓴 셈이다.
   - 둘째, **유명한 블로그 글의 결론도 3개월이면 뒤집힌다.** 이 저장소에 두 문서를 나란히 두는 것이 정확히 그 이유다. 어떤 프랙티스를 도입할 때 원저자가 지금도 그걸 쓰는지 확인하는 절차가 필요하다.

5. **레이어드 액션 공간은 MCP를 대하는 태도를 바꾼다**
   - MCP 도구를 전부 함수로 바인딩하면 도구 설명이 컨텍스트 프리픽스를 채우고, 서버가 늘수록 선형으로 나빠진다. Manus는 MCP를 **CLI로 노출해 Bash 뒤에 숨겼다.** 함수 호출 층은 20개 미만으로 고정되고, 도구가 100개로 늘어도 컨텍스트는 그대로다.
   - 이 저장소의 [Code Execution with MCP - 토큰 98.7% 절감하는 차세대 에이전트 패턴](Code%20Execution%20with%20MCP%20-%20%ED%86%A0%ED%81%B0%2098.7%25%20%EC%A0%88%EA%B0%90%ED%95%98%EB%8A%94%20%EC%B0%A8%EC%84%B8%EB%8C%80%20%EC%97%90%EC%9D%B4%EC%A0%84%ED%8A%B8%20%ED%8C%A8%ED%84%B4.md) 문서와 정확히 같은 방향이다. 서로 다른 팀이 독립적으로 도달한 결론이라는 점에서 신뢰도가 올라간다.

6. **"압축 → 요약"의 순서와 입력 소스가 설계의 핵심이다**
   - 많은 구현이 컨텍스트가 차면 바로 요약으로 간다. Manus는 **참조 교체를 먼저 소진하고, 그게 한계에 닿을 때만 요약**한다. 압축은 되돌릴 수 있고 요약은 되돌릴 수 없으니, 되돌릴 수 있는 수단을 먼저 쓰는 것이 옳은 순서다.
   - 더 중요한 디테일은 **요약을 compact 버전이 아니라 full 결과로 만든다**는 것이다. 요약할 시점에 컨텍스트에는 이미 참조밖에 없으므로, 파일 시스템에서 원본을 다시 읽어 와야 한다. 이걸 놓치면 "참조를 요약한 요약"이 되어 정보가 이중으로 손실된다. Offload가 없으면 이 순서 자체가 성립하지 않는다.

7. **서브에이전트를 역할이 아니라 컨텍스트 경계로 나누라는 주장은 검증이 필요하다**
   - "LLM은 사람의 인지 한계를 공유하지 않는다"는 논거는 설득력 있고, 실제로 designer/engineer/PM 식 구성은 프롬프트 상의 연극에 가깝다. 다만 아티클은 이 주장을 벤치마크가 아니라 설계 철학으로 제시한다.
   - 그리고 컨텍스트 격리는 공짜가 아니다. **복잡한 태스크에서는 결국 플래너의 전체 컨텍스트를 넘긴다**고 원문이 인정한다. 그 경우 격리로 얻는 토큰 이득은 사라지고, 남는 건 별도 액션 공간과 출력 스키마뿐이다. 즉 서브에이전트의 실제 이득이 "컨텍스트 절약"인지 "구조화된 출력 강제"인지는 태스크마다 다르고, 이 글은 그 경계선을 긋지 않는다.

### 검증 관점

8. **이 글은 웨비나 정리 노트라는 점을 감안해야 한다**
   - 원저자의 1차 기술 문서가 아니라 제3자(Lance Martin)가 대화를 정리한 것이다. 수치(50 tool calls, <20 functions, 1/3 액션, 5회 리팩터링)는 전부 구두 진술이고 재현 가능한 측정 결과가 아니다.
   - 그래서 이 문서에서 가져갈 것은 **숫자가 아니라 설계의 순서와 이유**다. "20개 미만"이 아니라 "함수 층을 고정하고 나머지는 샌드박스로 내린다"가, "1/3"이 아니라 "관리용 도구 호출의 비율을 측정해 봐야 한다"가 실제 교훈이다.
