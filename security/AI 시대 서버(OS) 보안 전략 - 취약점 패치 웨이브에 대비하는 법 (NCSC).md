## AI 요약

### 0. 결론 — AI가 바꾼 것은 위협의 '종류'가 아니라 '속도와 양'이다

AI 위협의 본질은 새로운 공격 기법이 아니다. AI를 쓰는 공격자는 이미 쌓여 있던 오래된 결함(기술 부채)을 **대규모로, 빠르게** 찾아낸다. 그러면 취약점 공개와 보안 업데이트가 한꺼번에 몰리는 **패치 웨이브(patch wave)**가 온다.

그래서 서버 보안 전략의 중심은 새 보안 솔루션이 아니라 **"빠르게, 자주, 대규모로 패치하는 운영 능력"**이다. 패치로 해결되지 않는 부분은 기본 통제로 피해 범위를 줄인다.

| 질문 | 한 줄 답 | 근거 |
| --- | --- | --- |
| AI는 서버에 어떤 위협이 되나 | 묵은 결함을 대규모·고속으로 찾아 악용한다 → 업데이트가 폭주한다 | 1절 |
| 서버 영역의 보안 항목은 | 노출면 · 패치 · 수명주기(EOL) · 기본 통제 · 특권 접근 · 망 분리 · 관측 · 공급망 | 2절 |
| OS 취약점은 어떤 절차로 조치하나 | 노출면 축소 → 우선순위 → 패치 불가면 교체 → 악용 중이면 가속 → 적용 방식 선택 | 3절 |
| 운영 원칙은 | **update by default** — 기본은 즉시 자동 적용, 예외만 따로 관리 | 4절 |

### 1. 위협 모델 — 기술 부채 + AI = 강제 교정

```text
기술 부채 (technical debt)
  단기 이익을 위해 미뤄 둔 결함. 생산자든 운영자든 모든 조직에 있다
        │
        ▼  AI (충분한 실력을 갖춘 사람이 쓸 때)
  이 부채를 대규모(at scale)로, 고속(at pace)으로 찾아내 악용한다
        │
        ▼
강제 교정 (forced correction)
  오픈소스 · 상용 · 독점 소프트웨어 · SaaS 모두에서 취약점 공개가 몰린다
        │
        ▼
패치 웨이브 (patch wave)
  기술 스택 전체에 적용해야 할 업데이트가 쏟아진다
  모든 심각도에 걸쳐 나오고, 그중 상당수는 critical이다
```

서버 엔지니어에게 중요한 점은 두 가지다.

- **예외가 없다.** OS, 미들웨어, 임베디드 장비, SaaS까지 기술 스택 전체가 대상이다.
- **위협은 AI가 만들지만 대응은 사람의 운영 속도가 정한다.** 아래 권고 대부분이 "얼마나 빨리 고치느냐"의 문제다.

### 2. 서버 영역의 보안 항목

서버 쪽 책임 범위로 나누면 아래 8개다.

| # | 항목 | 원문 권고 | 서버에서의 대상 (보충) |
| --- | --- | --- | --- |
| 1 | 노출면 (attack surface) | 인터넷 등 외부에 노출된 부분을 찾아 최소화한다. **경계(perimeter) → 클라우드 → 온프레미스** 순서로 점검한다 | 공인 IP 서버, 열린 포트·서비스, 관리 인터페이스(SSH·RDP·IPMI) |
| 2 | 패치 관리 | 빠르게, 자주, 대규모로 적용한다. 핫패치(서비스를 멈추지 않는 패치) > 자동 업데이트 > 위험 기반 수동 적용 순으로 고른다 (→ 3절) | 커널, OS 패키지, 미들웨어, 펌웨어 |
| 3 | 수명주기 (EOL·레거시) | 지원이 끝난 기술에는 패치가 나오지 않는다. **교체하거나 지원 계약을 다시 맺는다** | 지원 종료(EOL) OS, 지원이 끝난 미들웨어·장비 |
| 4 | 보안 기본 통제 | Cyber Essentials를 전부 이행한다. 필수 서비스 운영 조직은 CAF(Cyber Assessment Framework)를 따른다 | Cyber Essentials 5대 통제: 방화벽, 보안 설정, 보안 업데이트 관리, 사용자 접근 통제, 악성코드 방지 |
| 5 | 특권 접근 | 위협 수준이 높은 조직은 특권 접근 워크스테이션(PAW)을 쓴다 | 서버 관리자 접속 경로를 전용 단말로 분리 |
| 6 | 망 분리 | 위협 수준이 높은 조직은 크로스 도메인(cross-domain) 아키텍처를 쓴다 | 보안 등급이 다른 망 사이의 데이터 이동 통제 |
| 7 | 관측·위협 헌팅 | 위협 수준이 높은 조직은 관측성(observability)과 위협 헌팅으로 회복력을 높인다 | 로그·감사 기록 수집, 이상 행위 탐지 |
| 8 | 공급망 | 큰 조직은 상용·오픈소스 공급망이 패치에 대비하고 있는지 확인한다 | OS 벤더, 패키지 저장소, 장비 벤더 |

벤더에게는 메모리 안전성(memory safety)과 CHERI 같은 격리 기술 도입이 요구된다. 이것은 운영자가 아니라 생산자가 할 일이다.

전부 패치할 여력이 없을 때 어느 항목부터 손댈지는 3절 [2]에 정리했다.

### 3. OS·시스템 레벨 취약점 조치 절차

2절의 권고를 실행 순서대로 엮으면 다음과 같다.

```text
[1] 노출면 식별·최소화
      경계 장비 → 클라우드 인스턴스 → 온프레미스 순으로 점검한다
          │
[2] 패치 대상 우선순위 정하기 (전부 할 여력이 없을 때)
      1순위 외부 노출면 (인터넷에 닿는 서버·장비)
      2순위 핵심 보안 시스템 (critical security systems)
      3순위 나머지 내부 시스템
          │
[3] 업데이트가 나오는가?
      ├─ 아니오 (EOL·지원 종료) ──▶ 교체하거나 지원 계약을 다시 맺는다
      │                              외부에 노출된 시스템이면 가장 먼저
      └─ 예
          │
[4] 실제로 악용되고 있는 critical 취약점인가? (특히 인터넷 노출 서버)
      ├─ 예 ──▶ 가속 경로: 정기 주기를 기다리지 않고 즉시 적용한다
      └─ 아니오
          │
[5] 적용 방식 고르기 (가능한 것 중 위에 있는 것)
      ① 자동·안전한 핫패치(hot patching)   서비스 중단 없이 적용. 가장 먼저 켠다
      ② 자동 업데이트 (임베디드 장비 포함) 운영팀 부담을 줄인다
      ③ 둘 다 불가                        SSVC(아래 표)로 우선순위를 매겨 자주, 대규모로 적용한다
                                          서비스 중단·안전 필수 시스템과의 트레이드오프는
                                          프로세스와 위험 수용 수준에 미리 반영해 둔다
          │
[6] 패치 이후: 기본 통제(2절 4~7)로 침해가 일어나도 피해 범위를 줄인다
```

[4]의 가속 경로는 NCSC의 별도 가이드 'Responding to active exploitation of vulnerabilities'에 자세히 나와 있다.

[5]-③의 **SSVC**(Stakeholder-Specific Vulnerability Categorization)는 CISA가 만든 우선순위 체계다. 원문은 이름만 언급하므로 아래 내용은 CISA 문서를 기준으로 했다.

- **판단 요소 5개**: 악용 상태(Exploitation), 기술적 영향(Technical impact), 자동화 가능성(Automatable), 업무 관련성(Mission prevalence), 공공 영향(Public well-being impact)
- 이 다섯 가지를 보고 아래 네 판정 중 하나를 내린다.

| 판정 | 조치 시점 |
| --- | --- |
| Track | 지금은 조치할 필요 없음. 정기 주기에 처리 |
| Track\* | 정기 주기에 처리하되 상황 변화를 더 면밀히 관찰 |
| Attend | 정기 주기보다 빨리 처리 |
| Act | 가능한 한 즉시 처리 |

### 4. 운영 원칙 — update by default

**업데이트는 가능한 한 빨리, 가능하면 자동으로 적용하는 것을 기본값으로 둔다.** 이 원칙이 업데이트 관리 프로세스의 중심이어야 한다. 예외는 안전 필수(safety-critical) 시스템과 OT(운영 기술) 정도다.

|  | 기존 관행 (내 정리) | update by default |
| --- | --- | --- |
| 기본값 | 정기 점검 주기에 묶어서 적용 | 나오는 대로 즉시, 자동 적용 |
| 증명 책임 | 적용하려면 사유가 필요 | **적용하지 않으려면** 사유(예외)가 필요 |
| 우선순위 기준 | 심각도 점수 순 | 노출면 · 실제 악용 여부 순 |
| 지원 종료 시스템 | 일단 둔다 | 교체하거나 지원 계약을 다시 맺는다 |

시작점은 두 가지다. 모든 조직은 NCSC의 개정된 취약점 관리(Vulnerability Management) 가이드를 읽는다. 큰 조직은 여기에 더해 공급망의 대비 상태를 확인한다.

## 내가 얻은 인사이트

### 서버 운영 관점

1. **패치를 설치했다고 적용된 것은 아니다**
   - 원문은 핫패치를 가장 먼저 켜라고 하지만, 핫패치는 재부팅을 없애는 것이 아니라 **미룬다**.
   - (보충) Windows Server 2025 Hotpatch(Azure Arc 연동)는 분기 첫 달(1·4·7·10월)이 기준선(baseline) 달이다. 이 달에는 누적 업데이트를 설치하고 재시작해야 한다. 재시작 없이 적용되는 것은 나머지 두 달뿐이라 1년에 최대 8회다.
   - (보충) 리눅스 커널 라이브 패치(RHEL kpatch, Ubuntu Livepatch 등)는 커널만 고친다. openssl·glibc 같은 유저랜드 라이브러리는 패키지를 올려도 이미 떠 있는 프로세스가 예전 라이브러리를 메모리에 그대로 들고 있다. 재시작해야 반영되며, `needrestart`(Debian/Ubuntu)나 `dnf needs-restarting -r`(RHEL 계열)로 확인할 수 있다.
   - 따라서 핫패치가 있어도 재부팅 계획은 세워야 한다. 핫패치는 재부팅 횟수를 줄여 줄 뿐이다.

2. **update by default가 가능하려면 무중단 구조가 먼저다**
   - 원문이 말한 "서비스 중단과의 트레이드오프"는 서버 아키텍처의 문제다. 서버가 한 대뿐이면(SPOF) 재시작할 때마다 장애가 되므로 업데이트를 미루게 된다.
   - 이중화와 롤링 재시작이 가능한 구조가 있어야 자동 업데이트를 켤 수 있다. 가용성 설계가 곧 보안 대책이다.

3. **우선순위는 자산 목록이 있어야 매길 수 있다**
   - "외부 노출면 → 핵심 보안 시스템" 순서로 패치하려면 서버마다 `외부 노출 여부`, `보안 시스템 여부`, `OS EOL 날짜`가 기록돼 있어야 한다.
   - 이 정보가 없으면 패치가 몰려올 때 어디부터 할지 정하느라 시간을 쓰게 된다.

### 전략 관점

4. **SSVC가 묻는 것이 정확히 AI가 바꾸는 부분이다** (내 해석)
   - 심각도 점수는 취약점 자체의 위험만 본다. SSVC는 여기에 더해 "지금 악용되고 있는가", "공격을 자동화할 수 있는가"를 묻는다.
   - AI가 키우는 것도 바로 이 두 가지, 악용 속도와 자동화다. 패치 웨이브 속에서는 같은 critical이라도 이 두 질문으로 순서를 가르는 것이 맞다.

5. **EOL 서버는 패치 웨이브의 사각지대다**
   - 업데이트가 쏟아져도 지원이 끝난 OS에는 하나도 오지 않는다. 그래서 "지원 기간 안의 OS 버전을 유지한다"는 것 자체가 보안 항목이 된다.
   - 서버를 도입할 때부터 EOL 날짜를 구매 결정에 넣어야 한다.

6. **AI 위협에 대한 대응은 결국 기본기다**
   - 원문이 권하는 것은 AI 전용 보안 제품이 아니라 Cyber Essentials 수준의 기본 통제다.
   - AI가 바꾸는 것이 공격 기법이 아니라 결함을 찾는 속도라면, 대응도 새 통제를 추가하는 것보다 기존 통제를 **얼마나 빨리, 얼마나 빠짐없이** 이행하느냐에 달려 있다.
