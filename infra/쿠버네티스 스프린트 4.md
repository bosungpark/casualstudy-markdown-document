## 개요

스프린트 4의 1~3부는 **쿠버네티스 클러스터 업그레이드**, 4~5부는 **모니터링 연동과 PromQL 조인**이다. 노드 관점에서 업그레이드는 아래 루프의 반복이다.

```
노드를 비운다(drain) → 노드를 업그레이드한다 → 노드를 다시 연다(uncordon) → 다음 노드
```

노드를 비우면 파드가 다른 노드에 다시 배치된다. 어디에 배치될지, 배치될 곳이 있기는 한지는 **스케줄링 규칙**이 결정한다. 그래서 업그레이드보다 스케줄링 원리를 먼저 다룬다.

4·5부는 모니터링 수업이다. kube-prometheus-stack에 메트릭을 연결하는 과정과, 수집한 메트릭을 라벨로 엮는 PromQL 조인을 다룬다.

| 2부 | 노드 스케줄링 원리 |

## 노드 조인

- 컨트롤 플레인에서 조인 명령을 만들고, 새 노드에서 그 명령을 실행하면 클러스터에 합류한다.
  ```bash
  kubeadm token create --print-join-command   # 컨트롤 플레인에서. 접속 주소 + 토큰 + CA 해시 출력
  kubeadm join ...                             # 새 노드에서 출력된 명령 그대로 실행
  ```
- 합류 직후 노드는 `NotReady`다. CNI가 준비되면 `Ready`로 바뀐다.
- DaemonSet은 조건에 맞는 모든 노드에 파드를 하나씩 둔다. 그래서 새 노드에도 DaemonSet 파드(kube-proxy, CNI 등)가 자동으로 배치된다.

## VM 기반 실습 환경의 네트워크

| 인터페이스 | 용도 | IP 조건 |
|------------|------|---------|
| NAT | 외부 인터넷 접근 (패키지·이미지 다운로드) | 노드 간 통신에 쓰지 않으므로 모든 노드가 같아도 된다 |
| Host-Only | 노드 간 통신, 사용자 접속 | 노드마다 고유해야 한다 |

# 2부. 노드 스케줄링 원리

## 2.1 스케줄러의 결정 과정

스케줄러는 새 파드마다 아래 과정을 거친다.

```
전체 노드
   ↓  ① 필터(Filter): 조건을 하나라도 어기는 노드를 제외한다 (hard)
후보 노드
   ↓  ② 점수(Score): 후보마다 선호도 점수를 매긴다 (soft)
최고점 노드에 바인딩         ※ 후보가 0개면 Pending
```

| 단계 | 관여하는 설정 |
|------|---------------|
| 필터 | `nodeSelector`, required NodeAffinity, required Pod(Anti)Affinity, 톨러레이트하지 못한 `NoSchedule`·`NoExecute` Taint, cordon(스케줄 불가) 표시, requests를 수용할 수 없는 자원 |
| 점수 | preferred NodeAffinity, preferred Pod(Anti)Affinity, `PreferNoSchedule` Taint, 자원 여유 |

- **required는 필터, preferred는 점수**에 들어간다. 이 차이가 "반드시"와 "되도록"의 차이다.
- `nodeName`을 지정하면 스케줄러를 거치지 않고 해당 노드에 바로 할당된다.

## 2.2 자원 여유는 requests로 계산한다

- 노드의 여유 자원 = **할당 가능 자원 − 그 노드에 있는 파드들의 requests 합**
- 실시간 사용량(metrics-server, `kubectl top`)은 기본 스케줄링에 쓰이지 않는다. 사용량은 순간마다 변해 배치 결과를 예측할 수 없기 때문이다. 사용량 기반 스케줄링은 별도 add-on이 필요하다.
- requests를 적지 않은 컨테이너는 필터 단계에서 자원을 0으로 계산한다. limits만 적었으면 requests는 limits와 같은 값이 된다.
- 결론: requests가 실제 필요량을 반영해야 배치가 정확해진다.

## 2.3 스케줄링은 배치 시점에만 평가된다

- 위 조건들은 파드를 **새로 배치할 때만** 평가된다. 필드 이름의 `...IgnoredDuringExecution`이 이 뜻이다. 실행 중에 노드 라벨이 바뀌어도 파드는 그대로 있다.
- 실행 중인 파드를 노드에서 내보내는 수단은 두 가지다.
  - `NoExecute` Taint
  - Eviction(축출) — drain이 쓰는 방식

## 2.4 노드 기준 배치

노드에는 설치 시 붙는 기본 라벨(`kubernetes.io/hostname`, `kubernetes.io/os` 등)과 운영자가 붙인 라벨이 있다. 아래 설정은 모두 **노드 라벨**을 기준으로 한다.

### nodeSelector

```yaml
spec:
  nodeSelector:
    <key>: <value>      # 여러 개면 AND
```

- 라벨이 모두 일치하는 노드만 후보가 된다.
- 후보가 여럿이면 점수 단계에서 결정된다(주로 requests 기준 여유).

### nodeName

- 특정 노드 이름에 직접 할당한다.
- 노드 이름은 재생성 시 바뀔 수 있어 의존하면 안 된다. 특정 노드를 지정해야 하면 기본 라벨 `kubernetes.io/hostname`에 nodeSelector를 쓴다.

### NodeAffinity

```yaml
affinity:
  nodeAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
      nodeSelectorTerms:          # 항목끼리 OR
      - matchExpressions:         # 조건끼리 AND
        - key: <key>
          operator: In            # In, NotIn, Exists, DoesNotExist, Gt, Lt
          values: [<v1>, <v2>]    # 값끼리 OR
    preferredDuringSchedulingIgnoredDuringExecution:
    - weight: <1-100>             # 만족하는 항목의 weight 합이 점수
      preference:
        matchExpressions: [...]
```

- nodeSelector로 표현할 수 없는 OR 조건, 부정 조건, 크기 비교, 선호도를 표현한다.
- 조건이 많아질수록 배치를 예측하기 어렵다. preferred는 의도하지 않은 노드에도 배치될 수 있다.
- 원칙: 기본은 nodeSelector로 하고, NodeAffinity는 꼭 필요한 경우에만 쓴다.

## 2.5 파드 기준 배치 — Pod Affinity / Anti-Affinity

```yaml
affinity:
  podAntiAffinity:                       # 또는 podAffinity
    preferredDuringSchedulingIgnoredDuringExecution:
    - weight: <1-100>
      podAffinityTerm:
        labelSelector:                   # 파드 라벨을 본다
          matchExpressions:
          - key: <pod-label-key>
            operator: In
            values: [<pod-label-value>]
        topologyKey: <node-label-key>    # 도메인 단위
```

### 판단 요소

| 요소 | 의미 |
|------|------|
| `labelSelector` | **파드 라벨**과 매칭한다. 노드 라벨이 아니다 |
| `topologyKey` | 노드 라벨 키. 이 라벨의 **값이 같은 노드들을 하나의 도메인**으로 묶는다 |
| Affinity | selector에 맞는 파드가 있는 도메인으로 배치한다 |
| Anti-Affinity | selector에 맞는 파드가 있는 도메인을 피한다 |

- `topologyKey: kubernetes.io/hostname`이면 노드 하나가 도메인 하나다.
- zone 같은 라벨을 쓰면 같은 값을 가진 노드 묶음이 도메인 하나다.

### 자기 레플리카 분산

- Anti-Affinity의 selector에 **자기 파드 템플릿의 라벨**을 넣으면, 같은 Deployment의 파드끼리 서로 다른 도메인으로 흩어진다.

| 강도 | 동작 | 결과 |
|------|------|------|
| preferred | 매칭 파드가 적은 도메인부터 채운다. 모든 도메인에 이미 있으면 그래도 배치한다 | 레플리카 수 제한 없이 고르게 분산 |
| required | 매칭 파드가 있는 도메인은 후보에서 제외한다 | **레플리카 수 ≤ 도메인 수**. 초과분은 Pending이라 스케일 아웃이 막힌다 |

- 그래서 분산 목적의 Anti-Affinity는 preferred를 쓴다. 대상 노드 범위는 nodeSelector로 따로 한정한다.

### Pod Affinity의 실익이 작은 이유

- 운영 환경은 이중화를 위해 파드를 여러 노드에 분산한다. 모으는 규칙은 이것과 충돌한다.
- 트래픽은 Service가 엔드포인트 전체로 분산한다. 같은 노드에 대상 파드가 있어도 통신이 같은 노드 안에서 일어난다는 보장이 없다.

### 노드 기준 vs 파드 기준

두 축은 독립적이다. "특정 노드 그룹에 배치하면서 레플리카끼리는 흩어 놓기"를 원하면 두 종류를 함께 적용한다.

## 2.6 Taint와 Toleration

### 정의

- **Taint**: 노드 쪽 설정. 톨러레이트하지 않는 파드를 거부한다.
- **Toleration**: 파드 쪽 설정. 특정 Taint의 거부를 면제받는다.

```bash
kubectl taint nodes <node> <key>[=<value>]:<effect>     # 추가
kubectl taint nodes <node> <key>[=<value>]:<effect>-    # 삭제 (끝에 하이픈)
```

```yaml
tolerations:
- key: <key>
  operator: Exists | Equal      # Equal이면 value도 일치해야 한다
  value: <value>                # Equal일 때만
  effect: <effect>              # 생략하면 모든 effect에 매칭
  tolerationSeconds: <N>        # NoExecute에만 의미 있다
```

### Effect

| effect | 새 파드 | 실행 중 파드 |
|--------|---------|--------------|
| `NoSchedule` | 차단 (필터) | 유지 |
| `PreferNoSchedule` | 감점 (점수) | 유지 |
| `NoExecute` | 차단 (필터) | 축출 |

### 매칭 규칙

- 노드의 `NoSchedule`·`NoExecute` Taint를 **모두** 톨러레이트해야 필터를 통과한다. 하나라도 빠지면 그 노드는 후보에서 제외된다.
- `Exists`는 key(와 effect)만 비교한다. `Equal`은 key, value, effect를 모두 비교한다.
- key 없이 `operator: Exists`만 쓰면 모든 Taint에 매칭된다. DaemonSet 파드가 보통 이렇게 되어 있어서 Taint가 있는 노드에도 배치된다.
- **Toleration은 거부를 면제할 뿐, 그 노드로 끌어당기지 않는다.** 특정 노드로 보내려면 nodeSelector나 NodeAffinity를 함께 써야 한다.

### NoExecute와 tolerationSeconds

| 파드의 Toleration | NoExecute Taint가 붙었을 때 |
|-------------------|-----------------------------|
| 없음 | 즉시 축출 |
| 있음, `tolerationSeconds` 없음 | 계속 유지 |
| 있음, `tolerationSeconds: N` | N초 유지한 뒤 축출 |

### Taint가 생기는 경로

| 경로 | 내용 |
|------|------|
| 운영자 설정 | 특정 노드를 특정 워크로드 전용으로 묶어 둘 때 |
| 설치 기본값 | 컨트롤 플레인 노드의 `node-role.kubernetes.io/control-plane:NoSchedule`. 일반 워크로드를 막는다 |
| 노드 상태에 따른 자동 부여 | 노드 수명 주기 컨트롤러가 노드 컨디션을 보고 붙이고, 상태가 회복되면 제거한다 |

**자동 Taint**

| 노드 상태 | Taint 키 | effect |
|-----------|----------|--------|
| Ready=False | `node.kubernetes.io/not-ready` | NoSchedule → NoExecute |
| Ready=Unknown (heartbeat 단절, kubelet 중지 포함) | `node.kubernetes.io/unreachable` | NoSchedule → NoExecute |
| 디스크·메모리·PID 압박 | `node.kubernetes.io/{disk,memory,pid}-pressure` | NoSchedule |
| cordon | `node.kubernetes.io/unschedulable` | NoSchedule |

- not-ready·unreachable은 먼저 `NoSchedule`로 새 파드 유입을 막고, 이어서 `NoExecute`로 기존 파드를 축출한다.

### 기본 Toleration

모든 파드에는 admission 단계에서 아래 Toleration이 자동으로 추가된다.

```yaml
- key: node.kubernetes.io/not-ready
  operator: Exists
  effect: NoExecute
  tolerationSeconds: 300
- key: node.kubernetes.io/unreachable
  operator: Exists
  effect: NoExecute
  tolerationSeconds: 300
```

- 노드 장애가 일시적일 수 있으므로, 즉시 재배치하지 않고 300초를 유예한다.
- 장애에 더 빨리 반응해야 하는 워크로드는 이 Toleration을 직접 명시하고 `tolerationSeconds`를 줄인다.

### kubelet이 멈춘 노드의 파드

| 경로 | 동작 여부 | 이유 |
|------|-----------|------|
| `kubectl logs`, `kubectl exec` | 불가 | API 서버 → kubelet → 컨테이너 경로를 거친다 |
| 파드 IP로 직접 통신 | 가능 | 컨테이너와 네트워크 데이터플레인은 kubelet과 무관하게 동작한다 |

## 2.7 Cordon · Drain · Uncordon

| 명령 | 동작 |
|------|------|
| `kubectl cordon <node>` | 노드를 스케줄 불가로 표시한다(`spec.unschedulable=true` → `unschedulable:NoSchedule` Taint). 기존 파드는 유지된다 |
| `kubectl drain <node>` | cordon + 노드의 파드를 Eviction API로 축출한다 |
| `kubectl uncordon <node>` | 스케줄 불가 표시를 해제한다 |

### Drain의 실제 의미

- drain은 파드를 **옮기지 않는다.** 노드를 막고 파드를 삭제할 뿐이다.
- 파드가 다른 노드에 다시 생기는 것은 컨트롤러가 레플리카 수를 맞추려고 새 파드를 만들고, 스케줄러가 2.1의 규칙대로 배치한 결과다.
- drain은 NoExecute Taint를 쓰지 않는다. 남기는 것은 cordon의 NoSchedule 표시뿐이다. 그래서 되돌리는 명령은 `uncordon`이다.

### 파드 종류별 처리

| 파드 | drain 시 처리 | 필요한 옵션 |
|------|---------------|-------------|
| 컨트롤러(Deployment 등) 소속 | 축출 → 컨트롤러가 다른 노드에 재생성 | 없음 |
| DaemonSet 소속 | 축출 대상에서 제외 (노드마다 하나가 정상 상태) | `--ignore-daemonsets` |
| 컨트롤러 없는 단독 파드 | 삭제되고 재생성되지 않는다 | `--force` |
| emptyDir 사용 파드 | 로컬 데이터가 삭제된다 | `--delete-emptydir-data` |

- Eviction API는 **PodDisruptionBudget(PDB)** 을 지킨다. PDB의 최소 가용 수를 밑돌게 하는 축출은 거부되고, 다른 파드가 준비될 때까지 재시도된다.

### Cordon과 Drain의 용도 차이

| | cordon | drain |
|--|--------|-------|
| 기존 파드 | 유지 | 즉시 축출 |
| 노드가 비는 방식 | 이후 배포·재시작 때 점진적으로 | 즉시 |
| 용도 | 예정된 작업 전에 미리 걸어 둔다 | 바로 작업할 때 |

## 2.8 Drain 전 점검 기준

대상 노드의 각 파드에 대해 아래를 확인한다.

| 질문 | 아니면 |
|------|--------|
| 컨트롤러가 있는가? | 파드가 사라진다 |
| 다른 노드 중 필터를 통과하는 곳이 있는가? (nodeSelector, Affinity, Taint, 자원) | Pending |
| 축출되는 동안 같은 앱의 레플리카가 다른 노드에 남아 있는가? | 서비스 중단 |

**중단을 막는 수단**

| 수단 | 원리 |
|------|------|
| Pod Anti-Affinity (preferred) | 평소에 레플리카를 여러 노드에 분산해 둔다 |
| 사전 수동 분산 | cordon 후 몰린 파드를 하나씩 삭제해 다른 노드에 재생성되게 한다 |
| PodDisruptionBudget | 축출 중에도 최소 가용 파드 수를 보장한다. 관리 요소가 늘어나므로 최소 개수가 중요한 워크로드(DB 등)에 선택적으로 쓴다 |

## 2.9 설계 원칙

- 스케줄링 규칙의 조합 수는 파드와 노드 수에 비례해 늘고, 그만큼 배치 예측이 어려워진다.
- 필요한 것만 쓴다.
  - 노드 지정은 nodeSelector
  - 레플리카 분산은 preferred Anti-Affinity
  - 전용 노드는 Taint + Toleration + nodeSelector
- drain 전에 클러스터에 걸린 Taint, 라벨, Affinity를 파악해 둔다.

```bash
kubectl get nodes --show-labels
kubectl describe node <node> | grep -A5 Taints
kubectl label nodes <node> <key>=<value>     # 추가
kubectl label nodes <node> <key>-            # 삭제
```

# 3부. 업그레이드 원리

## 3.1 릴리즈와 버전 정책

- 마이너 버전은 약 4개월마다 나오고, 각 버전은 약 1년간 패치를 받는다. 그래서 동시에 3개 마이너 버전이 지원된다.
- kubeadm 업그레이드는 **마이너 버전을 한 단계씩만** 올릴 수 있다. 패치 버전은 건너뛸 수 있다.

### 버전 스큐(skew) 정책

| 컴포넌트 | 허용 범위 (kube-apiserver 기준) |
|----------|----------------------------------|
| kubelet, kube-proxy | 같거나 낮아야 한다. 1.28부터 최대 3 마이너 낮아도 된다 (이전 2) |
| kubectl | ±1 마이너 |

- 핵심 규칙: **노드 컴포넌트는 컨트롤 플레인보다 새 버전일 수 없다.** 그래서 항상 컨트롤 플레인을 먼저 올린다.

## 3.2 업그레이드 전략

| 전략 | 방식 | 특성 |
|------|------|------|
| In-place | 기존 클러스터를 한 단계씩 올린다 | 기존 데이터와 설정을 그대로 쓴다. 롤백이 어렵고, 노드가 많을수록 오래 걸린다 |
| 신규 클러스터 전환 | 새 버전 클러스터를 만들고 트래픽을 옮긴다 | 롤백이 쉽다(트래픽을 되돌리면 된다). 리소스가 이중으로 들고, 배포·데이터 이전이 필요하다 |

- 각 전략의 단점을 내 인프라가 감당할 수 있는지를 기준으로 고른다.

## 3.3 사전 검증 항목

개발 환경에서 먼저 검증한다.

| 항목 | 확인 내용 | In-place | 신규 전환 |
|------|-----------|:--------:|:---------:|
| 버전 호환성 | OS, 런타임, add-on, 앱이 대상 버전과 호환되는가 | ✓ | ✓ |
| 배포 파이프라인 | 배포 도구와 매니페스트가 대상 버전에서 동작하는가 | ✓ | ✓ |
| etcd 데이터 | 새 버전이 기존 데이터를 읽는가, 백업이 있는가 | ✓ | |
| 무중단 | 컴포넌트 교체 중 트래픽이 유지되는가 | ✓ | |
| 파드 이동 | drain 절차가 검증되었는가 | ✓ | |

### 버전 호환성

**의존 계층:** 아래층이 위층의 요구사항을 만족해야 한다.

```
커널·OS  ←  컨테이너 런타임  ←  kubeadm·kubelet·kubectl  ←  컨트롤 플레인  ←  add-on·앱
```

| 대상 | 확인 위치 |
|------|-----------|
| OS | 쿠버네티스 문서는 OS 배포판이 아니라 **커널 요구사항**을 명시한다. 배포판의 커널 버전으로 판단한다 |
| 컨테이너 런타임 | 런타임의 릴리즈 문서에 있는 쿠버네티스 지원 표. LTS 라인을 우선한다 |
| CNI, Helm, 대시보드 등 add-on | 각 프로젝트의 지원 매트릭스. "부분 동작" 표시는 미지원으로 본다 |
| 쿠버네티스 API를 쓰는 앱 | 대상 버전에서 제거되는 API 사용 여부 |

### 배포 파이프라인

- kubectl, Helm, Kustomize는 쿠버네티스 버전에 민감하다.
- 버전이 오르면 deprecated API가 제거된다. 자체 매니페스트에서 제거될 API를 쓰고 있는지 확인한다.
  - 외부 Helm 차트는 대개 클러스터 버전을 감지해 맞는 리소스를 렌더링한다.
- 롤백을 고려해 파이프라인이 **이전·이후 두 버전 모두**에서 동작해야 한다. 배포 도구 버전을 빠르게 바꿀 수단을 마련해 둔다.

### etcd 데이터

- etcd 데이터 형식은 상위 버전에서 읽을 수 있도록 하위 호환된다.
- 데이터는 노드 디스크(hostPath)나 별도 볼륨에 있다. 운영 환경은 안전한 볼륨에 두고 **정기 백업**을 한다.

### 무중단

- 컨트롤 플레인이 교체되는 동안 API 서버가 일시 중단된다. 이때 **파드 생성, 스케일링 같은 제어 동작이 멈춘다.** 이미 실행 중인 파드의 트래픽은 데이터플레인이 처리하므로 계속 흐른다. 그래도 부하가 낮은 시간에 진행한다.
- kube-proxy와 CNI는 DaemonSet이다. 교체 중에도 이미 커널에 설정된 네트워크 규칙(iptables 등)은 남아 있어 기존 트래픽이 유지된다. 단, 교체되는 동안에는 Service·엔드포인트 변경이 반영되지 않는다.
- DaemonSet의 기본 업데이트 전략은 RollingUpdate로, 노드를 하나씩 교체한다.

## 3.4 위험 분산

- 변경을 한 번에 몰지 않고 시점별로 나눈다. 문제가 생겼을 때 원인을 하나로 좁힐 수 있다.

| 시점 | 기준 | 대상 |
|------|------|------|
| 업그레이드 전 | 현재 버전과 대상 버전을 **모두** 지원하는 버전이 있는 것 | CNI, Helm |
| 업그레이드 중 | 쿠버네티스 버전에 묶인 것 | OS, 컨테이너 런타임, kubeadm·kubelet·kubectl |
| 업그레이드 후 | 중요도가 낮고 대상 버전만 지원하는 것 | 대시보드 같은 관리 도구 |

## 3.5 업그레이드 순서

### 노드 내부 순서

```
OS → 컨테이너 런타임 → kubeadm 설치 → kubeadm upgrade → kubelet·kubectl 설치 → kubelet 재시작
```

- kubeadm은 **설치 도구**다. kubeadm을 올려도 클러스터 버전은 그대로다.
- kubelet을 kubeadm과 같이 먼저 올리면 kubelet이 컨트롤 플레인보다 새 버전이 되어 스큐 규칙을 어긴다. 그래서 `kubeadm upgrade`로 컨트롤 플레인을 올린 **뒤에** kubelet을 올린다.

### 컨트롤 플레인 vs 워커

| 대상 | 명령 | 하는 일 |
|------|------|---------|
| 첫 컨트롤 플레인 | `kubeadm upgrade plan` → `kubeadm upgrade apply v<ver>` | 컴포넌트 이미지 교체(etcd, apiserver, controller-manager, scheduler 순), 클러스터 설정 갱신 |
| 워커 (및 추가 컨트롤 플레인) | `kubeadm upgrade node` | 노드 로컬 설정(kubelet 설정, 인증서 등)만 갱신 |

- `upgrade plan`은 컴포넌트별 현재·대상 버전, 수동 갱신이 필요한 컴포넌트 설정, 실행할 명령을 보여준다.
- 워커는 교체할 컴포넌트가 없어 컨트롤 플레인보다 훨씬 빨리 끝난다.

### 여러 마이너를 올릴 때의 단계 분할

- 마이너는 한 단계씩만 올릴 수 있다. 워커를 매 단계 따라 올리면 단계마다 drain이 일어나 파드 이동이 잦아진다.
- 그래서 **스큐 허용 범위 안에서 컨트롤 플레인을 먼저 여러 단계 올리고, 워커는 몰아서 올린다.** drain 횟수를 줄이는 것이 목적이다.

```
컨트롤 플레인 N → N+1 → N+2   (워커는 N 유지, 스큐 범위 내)
워커 N → N+1 → N+2            (노드마다 drain 한 번에 여러 단계)
반복
```

### 워커 노드 루프

```
drain (--ignore-daemonsets [--force])
  → OS·런타임 업그레이드, 재부팅
  → kubeadm 설치 → kubeadm upgrade node
  → kubelet·kubectl 설치 → systemctl daemon-reload && systemctl restart kubelet
  → (필요 시 다음 마이너 반복)
  → uncordon
```

- uncordon 직후 그 노드는 비어 있다. 이후 배포와 스케일링을 거치며 점진적으로 다시 채워진다.

## 3.6 패키지 버전 고정

패키지 관리자가 의도하지 않은 버전을 설치하지 않도록 버전을 명시한다.

```bash
# OS: 대상 릴리즈 명시, 컨테이너 런타임 저장소는 제외해서 함께 올라가지 않게 한다
yum update -y --releasever=<os-ver> --disablerepo=<runtime-repo>

# 런타임: 설치 가능한 버전 확인 후 명시 설치
yum list <runtime-pkg> --showduplicates
yum install -y <runtime-pkg>-<ver>

# 쿠버네티스: 저장소 경로를 대상 마이너로 바꾸고, exclude 설정을 일시 해제해 명시 버전 설치
yum list kubeadm --showduplicates --disableexcludes=kubernetes
yum install -y kubeadm-<ver> --disableexcludes=kubernetes
```

- 쿠버네티스 패키지 저장소는 마이너 버전별로 나뉘어 있다. 다음 마이너로 가려면 저장소 경로부터 바꿔야 한다.
- 저장소에 올라와 있는 최신 버전은 시점에 따라 달라진다. 계획 단계에서 버전을 확정하고 실행 직전에 다시 확인한다.

## 3.7 etcd 백업과 복구

### 구조

- kubeadm 클러스터의 etcd는 컨트롤 플레인 노드의 **static pod**다.
- static pod 매니페스트는 `/etc/kubernetes/manifests/`에 있고, kubelet이 이 디렉터리를 감시해 파드를 띄운다. 매니페스트를 고치면 반영된다(kubelet 재시작으로 즉시 반영할 수 있다).
- 데이터는 hostPath 볼륨(`/var/lib/etcd`)에 저장된다.

### 도구

| 도구 | 용도 |
|------|------|
| `etcdctl` | 실행 중인 etcd에 접속해 데이터를 다룬다. 스냅샷 **저장** |
| `etcdutl` | 데이터 파일을 직접 다룬다. 스냅샷 **복원**·상태 조회 (복원은 etcdctl에서 etcdutl로 이관됨) |

- 도구 버전은 실행 중인 etcd 버전에 맞춘다.

### 절차

```bash
# 버전 확인
kubectl exec -n kube-system etcd-<node> -- etcd --version

# 백업
ETCDCTL_API=3 etcdctl --endpoints=https://127.0.0.1:2379 \
  --cacert=/etc/kubernetes/pki/etcd/ca.crt \
  --cert=/etc/kubernetes/pki/etcd/server.crt \
  --key=/etc/kubernetes/pki/etcd/server.key \
  snapshot save <file>
etcdutl snapshot status <file>

# 복원: 새 데이터 디렉터리에 풀기
etcdutl snapshot restore <file> --data-dir <new-dir>
```

1. `/etc/kubernetes/manifests/etcd.yaml`에서 `volumes`의 **hostPath** 경로를 `<new-dir>`로 바꾼다.
2. kubelet을 재시작한다. etcd가 새 데이터로 기동하면 클러스터 상태가 스냅샷 시점으로 돌아간다.

- `volumeMounts.mountPath`는 컨테이너 내부 경로라서 바꾸지 않는다. 바꿀 것은 호스트 쪽 `hostPath`다.
- etcd가 재기동하는 동안에는 API 요청이 실패한다. 기동이 끝난 뒤 작업한다.

## 3.8 Server-Side Apply

| | Client-Side Apply (기본) | Server-Side Apply (`--server-side`) |
|--|--------------------------|--------------------------------------|
| 변경 계산 주체 | kubectl | API 서버 |
| 이전 상태 기록 | `kubectl.kubernetes.io/last-applied-configuration` 어노테이션 | `metadata.managedFields`(필드별 소유자) |
| 충돌 | 감지하지 않는다 | 다른 매니저가 소유한 필드를 바꾸면 충돌로 거부 |

- `--force-conflicts`는 충돌 필드의 소유권을 가져와 덮어쓴다.
- 여러 주체가 같은 리소스를 수정하거나 매니페스트가 큰 경우(CNI 등) 업그레이드에 쓰인다.

## 3.9 대시보드 (Helm 기반 버전)

- 설치 방식이 Helm 차트로 바뀌었다. values 파일로 metrics-server 활성화, Service 타입·포트 등을 지정한다.
  ```bash
  helm repo add kubernetes-dashboard https://kubernetes.github.io/dashboard/
  helm install kubernetes-dashboard kubernetes-dashboard/kubernetes-dashboard \
    --version <chart-ver> -n kubernetes-dashboard --create-namespace -f <values>
  ```
- 로그인 생략(skip) 옵션이 제거되어 **토큰 인증**이 필수다.
  - ServiceAccount 생성
  - ClusterRoleBinding으로 권한 연결
  - `kubernetes.io/service-account-token` 타입 Secret으로 장기 토큰 발급
  - 토큰 조회:
    ```bash
    kubectl get secret <secret> -n kubernetes-dashboard -o jsonpath='{.data.token}' | base64 -d
    ```

## 4.1 한 장 요약 — 설정 경로와 수집 경로를 구분한다

> **Operator는 수집 설정을 만들고, Prometheus가 파드에 직접 HTTP 요청을 보낸다.**

| 용어 | 뜻 |
| --- | --- |
| 메트릭 | 이름·라벨·숫자 값으로 노출하는 관측 데이터 |
| 스크레이프(scrape) | Prometheus가 주기적으로 `/metrics`를 요청하는 동작 |
| ServiceMonitor | 어떤 Service의 어느 포트를 수집할지 선언하는 리소스 |
| Prometheus CR / Operator | 사용할 모니터를 선언한 리소스 / 그 선언을 실제 설정으로 반영하는 컨트롤러 |
| 시리즈·벡터 | 메트릭 이름·라벨 조합 하나의 데이터 / 한 시점에 모은 시리즈와 값들 |
| kube-state-metrics | Kubernetes API의 리소스 상태를 읽어 메트릭으로 내보내는 프로그램 |

![설정은 ServiceMonitor와 Operator로 전달되고 데이터는 파드와 Prometheus 사이에서 수집된다](쿠버네티스%20스프린트%204/images/01-service-overview.svg)

`metrics.enabled=true`는 노출을 켠다. 이 설정만으로 Prometheus의 대상 선택과 실제 수집 성공까지 보장되지는 않는다.

**발표 연결 문장:** “데이터가 ServiceMonitor를 통과하는 것은 아닙니다. 이제 누가 누구를 선택하는지 보겠습니다.”

## 4.2 연결 조건 — 라벨과 namespace를 어느 리소스에 맞추는가?

> **Prometheus는 ServiceMonitor를, ServiceMonitor는 Service를, Service는 파드를 고른다.**

![Prometheus와 ServiceMonitor의 namespace 선택은 각각 다른 리소스를 대상으로 한다](쿠버네티스%20스프린트%204/images/02-service-selectors.svg)

| 확인할 설정 | 선택하는 대상 |
| --- | --- |
| Prometheus `serviceMonitorNamespaceSelector` + `serviceMonitorSelector` | ServiceMonitor의 namespace + 라벨 |
| ServiceMonitor `namespaceSelector` + `selector` | Service의 namespace + 라벨 |
| ServiceMonitor `endpoints.port` | Service 포트 **이름** |
| Service `selector` + `targetPort` | 파드 라벨 + 파드의 숫자 포트 또는 포트 이름 |

강의의 `release: monitoring`은 설치된 Prometheus CR의 셀렉터에 맞춘 예시다. 다른 namespace에 있다는 이유만으로 수집이 불가능한 것은 아니다. **실제 CR의 namespace·라벨 선택 조건을 따로 읽는다.** [(보충 근거·YAML·점검 명령)](<쿠버네티스 스프린트 4/ServiceMonitor.md>)

## 4.3 장애 분류 — 대상 없음, DOWN, UP 이후 빈 패널

> **대상이 없으면 선택·탐색을 보고, DOWN이면 실제 요청의 오류를 본다.**

`up`은 최근 수집 요청의 성공(`1`)·실패(`0`)를 나타내는 자동 생성 메트릭이다. 대상 자체가 없으면 현재 시리즈도 없을 수 있다.

![대상 없음과 수집 실패와 질의 실패는 점검 지점이 다르다](쿠버네티스%20스프린트%204/images/03-service-diagnosis.svg)

| 현재 관찰 | 다음 확인 | PoC |
| --- | --- | --- |
| 현재 활성 대상·`up` 시리즈가 없음 | 모니터 선택 → Service·포트 → EndpointSlice/Endpoints·RBAC·drop | S4~S5 |
| 대상이 있지만 `up=0` | Targets의 `lastError`: 404·timeout·인증·TLS 등 | S2~S3 |
| `up=1`인데 패널이 빔 | 메트릭 이름·라벨·시간·Grafana 변수·데이터소스 | S1은 요청 성공만 검증 |

**(보충·교정)** 종료된 앱을 직접 스크레이프하지 않는 것과 그 파드의 Failed 상태를 관측할 수 없는 것은 다르다. 실행 중인 kube-state-metrics는 API 서버의 파드 상태를 별도 메트릭으로 내보낼 수 있다(S6).

**발표 연결 문장:** “수집이 됐으니 이제 숫자는 있습니다. 그런데 담당 서비스나 노드 이름으로 나누려면 라벨 정보가 더 필요합니다.”

# 5부. PromQL 조인 — 숫자에 업무 정보를 붙이기

이 부의 상세 설명·완성 질의·강의 교정 근거는 [PromQL JOIN 강의 정리](<쿠버네티스 스프린트 4/PromQL 조인.md>)에 있다.

## 5.1 한 장 요약 — 공통 키로 짝짓고, 값은 곱하고, 라벨은 붙인다

> **값 1인 정보 메트릭을 곱하면 측정값은 유지하면서 이름·분류 라벨을 붙일 수 있다.**

| 용어·구문 | 뜻 |
| --- | --- |
| 매칭 키 / `on(vm)` | 두 시리즈를 짝지을 라벨 / `vm` 값으로 짝짓기 |
| 정보 메트릭(info metric) | 이름·OS 등을 라벨로 제공하는 메트릭. 아래 예시는 실제 숫자 값 `1`을 제공 |
| `group_left(os)` | 왼쪽의 키당 여러 시리즈를 허용하고 오른쪽의 `os` 라벨을 가져옴 |
| 집계 / `sum by(...)` | 지정 라벨을 남겨 여러 시리즈의 값을 합산 |

![info 값 1을 곱하면 숫자는 유지되고 OS가 붙지만 짝이 없는 디스크는 제외된다](쿠버네티스%20스프린트%204/images/04-join-overview.svg)

```promql
disk_usage * on(vm) group_left(os) vm_info
```

`*`는 실제 곱셈이다. `+`로 바꾸면 100은 101이 된다. **(보충·교정)** info 메트릭은 “값이 없어서 기본 1”인 것이 아니라 exporter가 값 1을 내보낸다. 짝이 없는 시리즈는 이 산술 조인 결과에서 제외된다(J2·J4·J6).

## 5.2 group_left의 방향 — 오른쪽은 키당 하나

> **`group_left`의 “다”는 왼쪽이다. 전체 개수가 아니라 매칭 키별 시리즈 개수를 센다.**

![디스크를 왼쪽에 두면 정상이고 같은 데이터를 뒤집어 group_left하면 중복 오류가 난다](쿠버네티스%20스프린트%204/images/05-join-cardinality.svg)

| 질의 | 결과 |
| --- | --- |
| `disk_usage * on(vm) group_left(os) vm_info` | 디스크별 값 + OS, 정상 |
| `vm_info * on(vm) group_left(disk) disk_usage` | 오른쪽 vm1에 디스크가 둘이라 오류 |
| `vm_info * on(vm) group_right(os) disk_usage` | 첫 곱셈과 같은 결과 |

**(보충·교정)** 강의의 “group_left에서 기준 벡터가 1”이라는 설명은 방향이 반대다. `group_left`는 오른쪽 중복을 해결하지 않는다. [공식 정의](https://prometheus.io/docs/prometheus/latest/querying/operators/#many-to-one-and-one-to-many-vector-matches)와 PoC E2~E3에서 확인했다.

**청중에게 던질 문제:** “vm1에 디스크가 두 개일 때, 어느 쪽이 ‘다’일까요?” → 디스크 쪽. 남길 디스크 시리즈를 왼쪽에 놓는다.

## 5.3 집계 순서 — 조인할 키를 먼저 없애지 않는다

> **파드를 고른 다음 합한다. 집계 뒤에 조인하려면 `namespace,pod` 키가 남아 있어야 한다.**

![파드별 라벨로 먼저 거르면 150이 나오고 pod 키를 지운 후 조인하면 빈 결과가 나온다](쿠버네티스%20스프린트%204/images/06-join-aggregation.svg)

```promql
sum by(namespace, pod) (
  container_memory_working_set_bytes{container!="", container!="POD"}
  * on(namespace, pod) group_left
  kube_pod_labels{label_component="frontend-server"}
)
```

다른 namespace의 동명 파드를 구별하려면 `pod`만으로 매칭하지 않는다. 합성 데이터에서 team-a/portal의 두 컨테이너 120+30은 150, `pod`를 없앤 뒤 조인한 식은 빈 결과다(J8~J9·E4).

## 5.4 실무 적용 — 어떤 키와 라벨이 필요한가?

> **측정값과 정보 메트릭 양쪽에 실제로 같은 키가 있어야 한다.**

| 원하는 화면 | 정보 메트릭 | 공통 키 | 최종 라벨 |
| --- | --- | --- | --- |
| High/Low Spec 노드 | `kube_node_labels` | `node` | `label_resource` |
| 포탈 담당자용 파드 | `kube_pod_labels` | `namespace,pod` | `label_component`로 필터 |
| IP 대신 노드 이름 | `node_uname_info` | `instance` | `nodename` |

`instance="IP:9100"`과 `node="worker-1"`은 자동으로 같은 키가 되지 않는다. kube-state-metrics에서는 필요한 Kubernetes 라벨을 `metricLabelsAllowlist`로 허용한다. [라벨 허용 설정·완성 질의·Grafana 순서](<쿠버네티스 스프린트 4/PromQL 조인.md>)

<details>
<summary>CPU 계산과 괄호: 발표 뒤 질문에 대비할 두 가지 확인</summary>

CPU 식은 `idle 누적 시간 → rate → 코어 평균 → 1에서 빼기` 순서다.

```promql
(1 - avg by(instance) (rate(node_cpu_seconds_total{mode="idle"}[5m])))
* on(instance) group_left(nodename) node_uname_info
```

1. **rate의 창 경계:** 0·30·60초의 합성 값이 10·20·35일 때, 60초 시점 `[1m]`는 0초 샘플을 제외한다. 샘플 2개로 실제 값은 `0.5/초`; `[61s]`는 3개를 포함해 약 `0.4167/초`다(R1~R3). 강의의 숫자에서 빠진 입력을 역산해 확정하지 않는다.
2. **괄호의 효과:** CPU의 `1 - ...`는 단일 숫자를 빼는 식이라 여기서는 괄호 없이도 같은 결과다(J10~J11). 두 메트릭 벡터의 `total - available * ...`는 뒤 항에만 라벨이 붙어 빈 결과가 될 수 있다(J12~J13). 전체 계산에 라벨을 붙인다는 의도를 보이려면 괄호를 쓴다.

[실제 계산 표·공식 근거](<쿠버네티스 스프린트 4/PromQL 조인.md>)

</details>

## PoC — 직접 조작해서 강의의 기능을 재현하기

> **환경 준비만 자동화하고, ServiceMonitor·라벨·쿼리는 직접 바꿔 화면에서 변화를 확인한다.**

처음에는 [실습서](<쿠버네티스 스프린트 4/실습.md>)를 따라간다. 전용 kind 클러스터에 실제 Operator·Prometheus·Grafana·ingress-nginx·kube-state-metrics·node-exporter를 설치한다.

```bash
cd 'infra/쿠버네티스 스프린트 4'
python3 lab.py setup
python3 lab.py ui
```

| 강의 기능 | 직접 하는 조작 | 확인할 장면 |
| --- | --- | --- |
| ServiceMonitor 선택 | YAML 생성 후 release 라벨 수정 | 객체는 있지만 job은 없음 → job 생성·UP |
| Service 포트·요청 경로 | 포트 이름을 틀리고 복구한 뒤 path를 틀림 | 대상 없음 → DOWN·HTTP 404 → 정상 UP |
| 노드 이름 조인 | Grafana 사본의 쿼리·범례 수정 | IP 범례 → 노드 이름 |
| 담당 컴포넌트 필터 | 실제 파드 메모리에 라벨 조인 | portal·api 전체 → frontend 파드만 |
| 라벨 기반 자동 반영 | Deployment 라벨·레플리카 변경 | 쿼리를 그대로 두고 대상 파드가 바뀜 |
| 노드 스펙 필터 | resource 라벨 변경 | high-spec 패널의 선택 노드가 바뀜 |

처음에는 실습서 1~3단계로 **내가 고친 YAML이 실제 수집 상태를 바꾸는 경험**부터 한다. Grafana는 시작 대시보드를 사본으로 저장한 뒤 직접 편집한다. 실습 환경의 측정값은 고정값이 아니다.

기존 Prometheus 엔진의 **29/29 자동 검증**은 [보조 검증](<쿠버네티스 스프린트 4/자동 검증.md>)으로 남겼다. 실제 기능 실습과 자동 계산 검증의 결과·범위는 [점검 기록](<쿠버네티스 스프린트 4/점검 기록.md>)에서 구분한다.

## 내가 얻은 인사이트 — 발표를 마칠 때 남길 세 문장

1. **(내 해석) 수집 문제는 경계를 따라 좁힌다.** 선택됐는가 → 대상이 있는가 → 요청이 성공하는가 → 질의가 맞는가 순서로 본다.
2. **(내 해석) 조인은 라벨 관리의 가치를 드러낸다.** 파드 이름·IP를 패널마다 등록하는 대신 업무 라벨을 관리하되, 누락·중복도 확인한다.
3. **(내 해석) 빈 결과도 오류의 증거다.** 오른쪽 중복은 에러로 드러나지만, 메타데이터 누락·키 소멸은 조용히 시리즈를 줄인다.

## 정리

| 원리 | 요점 |
|------|------|
| 스케줄링 | 필터(required, Taint, 자원) → 점수(preferred) → 배치. 후보가 없으면 Pending |
| 자원 | requests 합으로 여유를 계산한다. 실사용량은 보지 않는다 |
| 평가 시점 | 배치할 때만. 실행 중인 파드는 NoExecute와 Eviction으로만 내보낸다 |
| Pod (Anti)Affinity | 파드 라벨 × topologyKey 도메인. 분산은 preferred |
| Taint/Toleration | 모든 Taint를 면제받아야 통과한다. 면제는 유인이 아니다 |
| Drain | cordon + eviction. 재배치는 컨트롤러와 스케줄러가 한다 |
| 버전 스큐 | 컨트롤 플레인 먼저. kubelet은 apiserver보다 새 버전일 수 없다 |
| 업그레이드 순서 | OS → 런타임 → kubeadm → upgrade → kubelet. 마이너는 한 단계씩 |
| 위험 분산 | 변경을 업그레이드 전·중·후로 나눈다 |
| etcd | 스냅샷 save/restore, static pod 매니페스트의 hostPath 전환 |
| ServiceMonitor 연동 | 노출·선택·설정 반영·실제 요청을 구분한다. 대상 없음과 DOWN의 원인을 따로 좁힌다 |
| serviceMonitorSelector | Prometheus CR이 사용할 ServiceMonitor를 고른다. namespace 선택 조건·Operator 감시 범위·RBAC도 함께 확인한다 |
| Vector Matching | `on (키)`로 짝짓고 `group_left (라벨)`로 반대쪽 라벨을 붙인다. 결과로 남는 쪽이 "다", 라벨을 빌려주는 쪽은 키당 시리즈 하나 |
| 라벨 조인 | 값이 1인 info·labels 메트릭과 곱해 값은 두고 라벨만 붙인다. `kube_node_labels`·`kube_pod_labels`는 kube-state-metrics 허용 목록이 필요하다 |
