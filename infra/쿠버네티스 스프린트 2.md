# 1부. DevOps 한방 정리

## 왜 역사 얘기는 안 하나

- 컨테이너 한방 정리 때는 히스토리가 의미 있었다 — Kubernetes가 표준이 되기까지 짧은 시간에 변경이 너무 많아서, 인터넷을 중구난방으로 보면 뭐가 맞는 정보인지 헷갈리기 때문.
- 반면 DevOps(2009년 등장)는 이미 안정기에서 **광범위한 영역으로 퍼졌고**, 산업/개발 언어마다 파이프라인 구성이 너무 다양하다. 전체 스토리를 다 설명하면 결국 원론적인 얘기밖에 못 하고, 그건 실무에 도움이 안 된다.
- 그래서 이 강의는 **강사가 경험해 본 실체 있는 내용**만 다룬다. 목표: DevOps가 언제 왜 만들어졌는지는 몰라도, **내가 DevOps를 구성해야 할 때 뭘 해야 할지 전체 그림을 그릴 줄 아는 사람**이 되는 것.

## 시작점 — 지상편 전체 빌드·배포 흐름 (반드시 눈에 익힐 것)

```
[CI/CD 환경]
 빌드 버튼 클릭
   ① GitHub에서 최신 소스 다운로드
   ② 소스 빌드 (Gradle) ─ Maven 저장소에서 라이브러리 다운 → 실행 가능한 jar 생성
   ③ 컨테이너 빌드 (Docker)
        - Docker Hub에서 OpenJDK 베이스 이미지 다운
        - 그 위에 내 jar를 넣어 컨테이너 이미지 생성
        - Docker Hub에 이미지 업로드
   ④ 배포: kubectl 로 파드 생성 명령
[인프라 환경(K8s)]
   ⑤ Kubernetes가 이미지를 Docker Hub에서 다운 → containerd에 컨테이너 생성 요청 → 앱 실행
```

## DevOps에서 가장 중요한 것 — 개발, 빌드, 실행 파일

> 아무리 복잡한 CI/CD 흐름이 있어도, DevOps의 핵심은 **개발하고 → 빌드해서 → 실행 가능한 파일을 만드는 것**이다.

- 개발 환경 = 내 PC. Mac/Windows 위에 IntelliJ, 툴킷은 OpenJDK, 맨바닥 대신 Spring Framework로 금방 앱을 띄운다.
- 코드를 실행 파일로 만들려면 **빌드**: Gradle로 빌드하되 **컴파일은 OpenJDK**가 한다. 만들어진 **jar는 OpenJDK의 JVM 위에서 실행**된다. → **빌드와 실행에는 항상 OpenJDK가 필요하다**는 것만 기억.
- 이 세 가지 동작이 너무 흔해서 중요성을 간과하기 쉽지만, **DevOps 구성의 알맹이**다. 환경별로 필요한 요소가 갈린다:

| 환경 | 필요한 것 |
|------|-----------|
| 개발 환경 | 개발+빌드+실행 전부 (IntelliJ, OpenJDK, Gradle, Spring) |
| 인프라 환경 | 실행 파일 + JVM → **OpenJDK만** 있으면 됨 |
| CI/CD 환경 | 빌드 → **OpenJDK + Gradle** (+ 실행 파일을 인프라로 넘기는 **배포** 과정 추가) |

### 인프라 환경 3종 — 각각의 존재 이유

| 환경 | 목적 | 핵심 포인트 |
|------|------|------------|
| **개발 환경** | 여러 개발자가 같이 쓰며, 내 코드가 **다른 앱과 문제없는지** 편하게 테스트 | 보안 해제, 임시 저장소 사용 등이 흔함 |
| **QA(검증) 환경** | 개발자가 아닌 **전문 테스트 담당자**용 | **최대한 운영과 똑같이** 구성해야 운영 배포 시 문제를 사전에 파악 (개발 환경처럼 보안 해제/임시 저장소 쓰면 안 됨) |
| **운영 환경** | 실제 서비스 | 핵심은 **이중화** |

- 운영 중 서버가 다운될 이유는 너무 많고, 가장 흔하지만 효율적인 대비가 **이중화**다.
- 그래서 운영까지 들어가는 오픈소스를 고를 땐 **이중화 구성이 문제없는지 확인이 필수** — 스펙만 보고 넘기지 말고 **실제로 이중화시켜 앱을 띄우고 테스트**해 볼 것.
- 운영 환경 구성은 프로젝트 일정의 **가장 마지막**인데, 이때 이중화가 안 되면 그동안 수없이 테스트해 온 오픈소스를 이제 와서 바꿔야 하는 상황이 온다 → 구축 일정이 무너진다.

### CI/CD 환경이 필요한 이유

- 혼자 개발하지 않기 때문. 여러 개발자의 코드를 **통합**해야 하고(GitHub로 최신 소스 유지), **Jenkins**가 GitHub에서 소스를 받아 빌드·배포한다. 이런 툴이 설치된 서버가 CI/CD 환경.

### 기존 구성 vs 컨테이너 구성

- **기존(컨테이너 이전)**: Jenkins에 OpenJDK+Gradle 세팅 → 빌드로 jar 생성. 인프라 환경(개발/운영 — OS가 다를 수 있음, 실제로 Red Hat 라이선스 비용 때문에 개발 환경은 무료 OS를 쓰는 경우 많음)에 OS+OpenJDK를 미리 구성 → 배포 = **jar 복사 + 실행 명령** (Jenkins 배포 스크립트의 두 명령).
- **컨테이너 구성**: 소스 빌드 → 컨테이너 빌드 → Docker Hub 업로드 → kubectl 배포 → K8s가 이미지 받아 실행. 컨테이너 안에 OpenJDK와 실행 파일이 들어 있다.
- 빌드·배포가 복잡해졌어도 **"개발하고 빌드해서 실행 파일을 만든다"는 핵심은 항상 존재**한다.

> 💡 처음 보는 기술을 쉽게 쓰는 사람들의 특징: **내가 필요한 게 뭔지 안다.** Docker를 처음 써도 기능을 하나하나 훑지 않고 "OpenJDK 베이스 이미지를 어떻게 얻지? 그 위에 내 jar를 어떻게 올리지?"에만 집중해 원하는 결과물을 만든다. 전체 시스템 흐름을 알고 필요한 것만 잘 알면 새 툴도 빠르게 파이프라인에 연결할 수 있다.

## DevOps 8단계와 단계별 오픈소스

> CI = 통합된 소스로 **빌드·테스트를 자동화**, CD = **배포를 자동화.** → 커밋하는 순간 운영 환경에 자동 배포되는 파이프라인.
> 8단계: **계획 → 개발 → 빌드 → 테스트 → 릴리즈 → 배포 → 운영 → 모니터링.** DevOps계의 OSI 7 레이어 같은 것 — 교과서 같지만, OSI도 "이 트래픽은 헤더를 봐야 하니 L7 로드밸런서가 필요해"처럼 실무에서 쓰인다. 이 8단계도 **대표 오픈소스로** 실무적으로 이해하자.

| 단계 | 대표 도구 | 메모 |
|------|-----------|------|
| **계획** | Jira, Notion (예전엔 Redmine) + 협업 메신저 **Slack** | 일정 공유·이슈 기록. Slack을 쓰는 진짜 이유는 아래에 |
| **개발** | IntelliJ, OpenJDK, Spring + **JUnit**, 코드 분석(FindBugs, PMD) | JUnit: 복잡한 로직은 하루만 지나도 이해가 안 됨 → 입력/결과로 확인하는 **테스트 코드**를 만들어 두면 남이 수정해도 안심. 코드 분석 툴은 코드 패턴의 버그 체크 |
| **빌드** | Gradle(소스), Docker(컨테이너) | 라이브러리 저장소는 Maven 저장소(퍼블릭) / **Nexus**(프라이빗) |
| **테스트** | JUnit(기능), JMeter(성능), Jacoco(커버리지) | 개발 단계에서 돌렸어도 **병합 후 결과가 달라질 수 있어** 빌드 단계에서 JUnit을 한 번 더 자동 실행. Jacoco는 테스트가 전체 로직의 어느 범위를 커버했는지 → 커버리지가 높을수록 신뢰도↑. JMeter는 자동화가 아니라 전문 인력이 날 잡아 수동 진행 |
| **릴리즈** | Dockerfile, K8s YAML → GitHub에 보관 | **배포 가능한 패키지를 만드는 과정.** 이 파일들도 변경 관리가 필요해 GitHub에 올린다. 릴리즈+배포가 Sprint 2의 주요 범위 |
| **배포** | **Kustomize, Helm, Argo CD** | 이전엔 kubectl로 배포했지만 이제 이런 도구로. 모두 이번 강의에서 배움 |
| **운영** | NGINX, Istio(트래픽 관리) 등 | 인프라 환경 안에 설치. 운영자는 이 툴들이 정상 동작하는지 확인 |
| **모니터링** | Grafana, Loki, Prometheus(자원·로그) + Jaeger, Zipkin(트래픽 추적) | MSA가 많아져 **서비스 간 트래픽 흐름 추적**이 중요해짐. 역시 인프라 환경(파드)에 설치 |

- 🔒 기업에서는 GitHub/Docker Hub 같은 **외부(퍼블릭)** 서비스 대신, 내부 데이터의 인터넷 업로드가 제한되는 경우가 많아 **GitLab, Docker Registry** 같은 제품을 **사내에 설치**해 쓴다 (비용이 들어도 많이 씀).
- 💬 **Slack을 쓰는 이유**: DevOps의 중요 포인트를 차지하는 툴들과 **연동**이 되기 때문. 파이프라인에서 발생하는 알람을 개발자/DevOps 엔지니어/운영자 방에 각각 울리도록 설정할 수 있다.
- 이렇게 DevOps가 복잡해졌기 때문에 기업은 **DevOps 엔지니어를 따로 뽑는다.** 단, 한 번에 다 만들 필요는 없다 — kubectl 배포부터 연결해 놓고 **장비 업그레이드하듯 하나씩** 바꿔나가면 된다.

## DevOps에 엮여 있는 IT 직군들 — 연차별 로드맵 (강사 주관)

각 영역엔 담당자가 있지만, **연차가 올라갈수록 영역을 넓혀야 한다.**

### 개발자

| 연차 | 목표 |
|------|------|
| ~2년 | 팀의 개발 환경에 빨리 적응, 주어진 개발 범위를 쳐내는 퍼포먼스 |
| ~4년 | IntelliJ 설정부터 GitHub까지 장애/변경을 **스스로 처리** |
| ~6년 | 개발 환경 몇몇 툴의 **초기 세팅을 주도**, CI의 빌드·테스트 자동화까지 |
| ~8년 | **새 트렌드를 리드** — 컨테이너 전환 프로젝트에서 내 앱을 컨테이너로 만들어 운영 배포·자동화까지 누구보다 먼저 |

- 9년차 이상이 되면 PM/PL/아키텍트/컨설턴트 같은 직책의 기회가 온다. 기회는 누구에게나 오지만 **전체를 모르면 유지를 못 한다.** ("제 상사는 몰라도 잘만 계신데요?" → 여기서 말하는 건 **기술적으로 인정받는** PM/PL 수준. 프리랜서로 치면 월 1,000 이상 계약이 되는 실력.)
- 이 연차쯤 되면 해보고 싶은 아키텍처/방법론을 시도할 **영향력**이 생긴다 — 그때 승승장구하려면 실력을 미리 갖춰야 한다. 영역 확장은 한 번에 안 되므로 **미리 경계를 풀어 둘 것.**

### DevOps 엔지니어

- 예전엔 전체 시스템을 알아야 해서 신입이 힘든 분야였지만, 지금은 고연차 엔지니어들이 기반을 잡아놔서 신입을 키울 수 있는 분위기가 됐다.
- ~2년: 팀의 CI/CD 흐름에 빨리 적응, 비슷한 파이프라인 추가는 스스로. ~4년: 운영 환경 설치 툴 + 개발~GitHub 구간 담당. ~6년: **모니터링 시스템 설치·구성**까지 — 모니터링은 **개발을 알아야** 제대로 구성되는 요소가 많으므로, DevOps로 시작했어도 개발을 꾸준히 알려고 노력할 것.

### 운영자

- ~4년: 만들어진 운영 환경을 모니터링하며 구성 익히기 (기술 스택보다 **담당 시스템 종류가 많아서** 시간을 길게 잡음). ~6년: 릴리즈·배포 구성이 운영에 문제를 일으키지 않는지 파악 + 그걸 모니터링하는 화면 추가. ~8년: **빌드부터 운영 배포까지 다 알고** 운영 편의를 위해 주도적으로 구성을 업데이트 → 이 정도를 **SRE(Site Reliability Engineer)** 라고 부른다 (CI/CD까지 관여하는 운영자).

> 강사 경험: 개발을 오래 하다 보니 어느새 배포까지 다 할 수 있었고, Kubernetes에 관심이 커지며 DevOps 엔지니어로 전직. 운영·모니터링까지 넓히다 보니 아키텍트 자리가 났을 때 쉽게 도전. **내 영역의 경계에만 머물지 말고 조금씩 다른 영역을 시도**하면 누구나 가능하다.

## DevOps 말고 다른 Ops들

> 각각 제대로 알려면 1시간 이상 들어야 하는 주인공들. 직접 해보지 않은 Ops는 강사도 잘 모른다(예: Kubeflow를 질문받고 찾아보니 MLOps의 유명 툴이었던 일화). 다만 **어떤 주제와 목적인지**는 알아두면 유익하다.

| Ops | 목적 | 메모 |
|-----|------|------|
| **GitOps** | 파이프라인을 **Git 하나로 통일** | DevOps 툴이 너무 많아져 선택조차 힘들어짐 → Git에는 이슈/협업/빌드/테스트/배포 기능이 다 있다(예: GitHub Actions는 Jenkins 대체 가능). 도입·유지 비용이 문제일 뿐, 도입하면 GitOps 구성을 많이 한다 |
| **DevSecOps** | **빠른 배포 + 보안**을 동시에 | 배포가 빨라졌는데 보안은 안전한가? → 파이프라인 중간중간 보안 검사를 자동화. 예: 빌드 전 소스 검사(SonarQube), 이미지 업로드 시 취약 라이브러리 검사, K8s 클러스터 보안 툴. 보안 솔루션 업체들이 홍보용으로 많이 쓰는 용어 |
| **MLOps** | 머신러닝/AI 분야의 DevOps | 핵심 인물은 **데이터 분석가**(교수/박사/연구원 — 개발은 잘 모름). 분석→검증→학습→평가로 모델을 만들고 시스템에 반영(**서빙**). DevOps가 개발자↔운영자 소통을 위한 파이프라인이라면, MLOps는 **데이터 분석가↔개발자** 소통을 위한 파이프라인. 전문 툴이 많아 ML 개발 경험자가 MLOps를 하는 게 유리 |
| **LLMOps** | 대규모 언어모델 특화 | 같은 AI라도 다루는 데이터 규모가 방대 → 특화 파이프라인. 현재 MLOps의 끝판왕 위치 |
| **FinOps** | **클라우드 비용 절감** | 클라우드는 좋은데 비용이 생각보다 많이 든다는 문제의식에서 출발. 가장 최근에 나왔고 아직 툴이 별로 없다 — 세미나 등으로 공감대를 만드는 초기 단계 (공감대 이후 툴이 나오며 파이프라인이 만들어지는 게 보통의 순서) |

# 2부. 손쉽게 DevOps 환경 구축 — CI/CD 서버 만들기

## Sprint 2 실습 환경 개요

- Sprint 1에서는 CI/CD 환경이 없어 인프라 환경만 구성했다. 이제 **CI/CD 환경(VM)** 을 추가한다.
- VirtualBox + Vagrant로 게스트 OS 생성 → 스크립트로 필요한 프로그램 일괄 설치 → 내 PC 브라우저에서 **Jenkins 대시보드** 접속.
- 흐름: 빌드 실행 → 강사 GitHub에서 앱 소스(Sprint 1 실습 앱) 다운 → 소스 빌드(jar) → 컨테이너 빌드 → **내 Docker Hub**에 업로드 → 배포 시 **내 GitHub**의 릴리즈 파일(Dockerfile/YAML) 사용.
- ⚠️ **본인 GitHub·Docker Hub 가입이 필수.** 지금까지는 강사 계정(1pro)의 이미지를 썼지만, 이제 이미지 이름에 **본인의 Docker Hub 유저네임**이 들어간다. 배포되는 YAML의 이미지명에 본인 유저네임이 있어야 내 저장소에서 이미지를 가져올 수 있다.

## Vagrant 설치 스크립트에서 일어나는 일

- **자원**: CPU 2코어 / 메모리 2GB / 디스크 30GB (디스크 확장 설정을 안 하면 기본 10GB로 만들어짐). Sprint 2부터는 **인프라 + CI/CD 두 VM을 동시에** 띄워야 하니 PC 자원 확인.
- **네트워크**: host-only 네트워크(VM 간 통신·호스트에서 접속용, IP 중복 불가 — 인프라 30번 / **CI/CD 20번**) + NAT(외부 인터넷용, IP가 같아도 인터넷 전용이라 문제없음).
- **설치 내용**:

| 설치 | 용도 |
|------|------|
| 리눅스 기본 설정 | 인프라 환경 구성 때와 동일 |
| kubectl | Jenkins에서 **배포**할 때 사용 |
| Docker | Jenkins에서 **컨테이너 빌드 + Docker Hub 업로드** |
| OpenJDK **17** + Gradle | **소스 빌드**용 (강사 소스가 17 기반) |
| Git | 소스 코드·릴리즈 파일 가져오기 |
| Jenkins + OpenJDK **11** | Jenkins 자체가 11에서 돌아가서 **설치용 11**을 하나 더 설치 |

- 운영 팁: `vagrant up` 은 최초 생성 때만 쓰고, 이후 켜고 끌 땐 VirtualBox UI 사용 권장 (Vagrant로 올리고 내릴 때 네트워크 인터페이스가 안 내려가 문제가 되는 경우가 있음). 설치 에러 시 `vagrant destroy` 로 전부 지우고 다시 `vagrant up`.

## 설치·설정 절차 (요약 체크리스트)

1. **Vagrant로 CI/CD 서버 생성** — 폴더 생성 → 스크립트 다운 → 플러그인 설치 → `vagrant up`. (PC마다 추가 설정이 필요한 경우는 정리된 자주 발생 문제 참고.)
2. **원격 접속 툴 세팅** — IP `192.168.56.20`, root/vagrant 자격 증명 저장.
3. **Jenkins 초기 세팅** — 초기 어드민 패스워드 확인 → 대시보드 접속 → 권장 플러그인 설치 → 관리자 계정 생성.
4. **전역 툴 설정** — Jenkins 관리 > Tools에서 직접 설치한 **JDK 경로**와 **Gradle 홈** 등록. (Gradle은 자동 설치 목록에 원하는 버전이 없을 수 있어 **수동 경로** 지정 — 이래서 자동 설치 체크를 해제.)
5. **Docker Hub 가입** — 유저네임이 곧 **컨테이너 이미지 이름**에 들어가니 잘 정할 것.
6. **Docker 사용 설정** — ① Jenkins 사용자에게 Docker 사용 **권한 부여**, ② CI/CD 서버에서 내 Docker Hub로 **docker login** (로그인 정보가 저장돼 VM을 껐다 켜도 유지. 단 중요 정보가 디스크에 남는 방식이라, 나중에 파이프라인 플러그인으로 해결 — 실무에서도 초반에 급히 구성할 때만 이렇게).
7. **인증서 복사** — 마스터 노드의 K8s config(인증서)를 SCP로 CI/CD 서버에 복사 → Jenkins가 kubectl로 K8s에 API를 날릴 수 있게 됨. `kubectl get pods` 로 확인.
   - 이 화면이 안 나오면 마스터 노드가 잘 떠 있는지 확인. (강사 팁: 마스터 노드 CPU 렉이 나면 재시작. 이후로는 **CI/CD 서버 먼저 → 마스터 노드** 순으로 기동.)
8. **GitHub 가입 + Fork** — 강사의 릴리즈 파일 리포지토리를 **Fork** → 실습 폴더(일련번호)에 Dockerfile·배포 YAML이 있음 → `deployment.yaml` 의 이미지 부분 `1pro` 를 **본인 Docker Hub 유저네임으로 수정 후 커밋.**
   - 강사가 소스를 수정하면 **Sync fork** 버튼으로 업데이트 (강의 중 파일이 다른 것 같으면 이걸 누르기).

## Jenkins 프로젝트 3종 만들기

### ① 소스 빌드 (Freestyle)

- GitHub project URL = **강사 GitHub**(앱 소스는 그대로 강사 것 사용) → 소스 관리 Git, 브랜치는 `master` → `main` 으로 변경(강사가 브랜치명을 main으로 바꿈).
- Build Step: **Invoke Gradle script** → 전역 설정에서 등록한 Gradle 선택 → Task에 빌드 전 디렉토리를 비우는 명령 포함(clean 후 build).
- 빌드 실행 → Console Output에서 소스 다운로드/Gradle 빌드 로그 확인 → 결과 위치에 **jar 파일** 생성 확인.

### ② 컨테이너 빌드 (Freestyle)

- GitHub project URL·소스 관리 Git 경로에 **본인 GitHub 유저네임**이 들어가야 한다. 브랜치도 main.
- Additional Behaviours > **Sparse Checkout paths**: 리포지토리 전체가 아니라 **해당 실습 폴더만** 다운로드.
- Build Step: **Execute shell** —
  1. 소스 빌드에서 만들어진 **jar를 Dockerfile이 있는 위치로 복사**
  2. `docker build -t <본인유저네임>/...` (⚠️ 태그의 유저네임 수정)
  3. `docker push <본인유저네임>/...` (⚠️ 여기도 수정)
- 실행 후 본인 Docker Hub에 이미지가 올라갔는지 확인.

### Dockerfile 뜯어보기 (별거 없다)

```
FROM  openjdk:17 ...      # Docker Hub에서 OpenJDK 17 기반 이미지 다운
COPY  *.jar  /.../app.jar # 내 jar를 컨테이너 안 지정 위치에 app.jar로 복사
ENTRYPOINT [java, ...]    # 실행 명령 — ConfigMap으로 주입받은 환경변수 3개를
                          #   스프링 시작 시 argument로 전달, app.jar 실행
EXPOSE 8080               # 컨테이너 포트 오픈 (트래픽 수신용)
WORKDIR ...               # 컨테이너 접속 시 홈 디렉토리
```

> 💬 **"쿠버네티스 전에 도커부터 공부해야 하나요?"** (자주 받는 질문) → **전혀 그럴 필요 없다.** 도커가 기초, 쿠버네티스가 심화인 관계가 아니다. K8s를 공부하다 도커가 나오면 **필요한 만큼만** 공부하면 된다 — K8s에서 알아야 할 여러 종목 중 하나가 도커인 것. 주로 컨테이너 빌드에서 쓰이니 개념 정도만 이해하고, 나중에 Dockerfile을 제대로 만들어야 할 상황이 올 때 그때 제대로 공부하는 게 효율적이다.

### ③ 배포 (Freestyle)

- 컨테이너 빌드 프로젝트와 거의 같으므로 새 아이템 생성 시 **Copy from**으로 복사.
- Sparse Checkout 경로만 배포 파일 위치로 변경 + Execute shell을 **다운받은 YAML을 kubectl로 그대로 배포**하는 내용으로 교체.
- 실행하면 K8s 대시보드에서 네임스페이스(anotherclass-212) 아래 Deployment/Service/ConfigMap/Secret/PV 등 리소스 생성 확인.

> 🏋️ **마무리 숙제**: 배포까지 성공해도 **파드는 정상 기동되지 않는 상태**다. 여기까지 왔으면 파이프라인은 잘 만든 것 — 이전 강의(트러블슈팅)를 잘 들었다면 **왜 기동이 안 되는지** 스스로 찾을 수 있다. (힌트: 파드 이벤트 로그부터.)

- 이번 구성은 CI/CD가 흘러가기 위한 **최소한의 기능**이며, 배포 강의가 진행되며 점점 고도화된다. 빨리 완성하려 서두르지 말고 **지금 어느 부분을 세팅 중이고 왜 필요한지** 생각하며 진행할 것.

# 3부. 배포 패키지 매니저 — Helm & Kustomize

## 용어부터 — kubectl은 "배포 툴"이 아니다

- 배포 **툴**(Jenkins, 다음 시간의 Argo CD)이 있고, 그 툴이 Kubernetes로 배포할 때 **패키지 매니저**로 Helm/Kustomize를 쓴다.
- kubectl은 그냥 **CLI**다. `create`/`apply`는 그 CLI 명령 중 하나일 뿐, 배포를 위한 부가 기능은 없다. 실무에서 kubectl은 배포된 자원을 **조회하거나 급하게 수정**할 때 주로 쓰고, **자원 생성은 주로 Helm/Kustomize로** 한다.
- Kube API 서버 입장에선 (예: 6번의 API 호출) 결과가 똑같지만, 작업자는 여러 YAML을 **명령어 한 번**으로 배포할 수 있다. 앱 하나에 YAML이 여러 개 필요하니 **패키지 단위 관리** 니즈에도 맞는다.
- ⚠️ 흔히 이 둘을 "배포 툴"이라 통칭하지만, 처음 접하는 사람은 "Jenkins/Argo CD 없이 이것만 써도 되나?"로 **오해**할 수 있다. 정확한 명칭은 **패키지 매니저**(입에 잘 안 붙어도).

## 공통점

1. **사용 목적** — 배포용 YAML의 **중복 관리를 최소화.** MSA로 앱을 잘게 쪼개 종류가 많아졌고, 예전부터 다양한 환경(dev/QA/운영)에 배포해야 했다. 환경·앱마다 YAML을 따로 만들면 관리가 폭발한다.
2. **다양한 배포 툴에서 지원** — Jenkins/Argo CD 등이 Helm/Kustomize를 더 편히 쓰도록 부가 기능을 준다. 반대로 이 둘이 워낙 대표적이라 **잘 지원하는지가 배포 툴 선택 요인**이 되기도 한다.

## 차이점 (외우지 말 것 — 실습하다 보면 체감됨)

| 항목 | Helm | Kustomize |
|------|------|-----------|
| 배포 편의 기능 | ~200개 (상대적 비교) | ~10개 (상대적 비교) |
| 패키지 활용 목적 | MSA **and** 다중 환경 — **둘 다** 한 패키지로 | 둘 중 **하나만**(OR) 권장 — 둘 다 하면 파일이 급증 |
| 주 사용처 | 내 앱 + **기업 제품/오픈소스** 패키징 | **내 프로젝트 앱** 패키징 |
| 유즈케이스 | 앱 5개 이상, 대형 프로젝트 | 앱 5개 미만, 소규모 프로젝트 |

- 기능이 많다고 Helm이 "더 좋다"는 게 아니다. **닭 잡는 데 소 잡는 칼 필요 없다** — 기능이 적게 필요하고 빨리 구축해야 하면 심플한 Kustomize가 장점.
- 대부분의 오픈소스는 여러 설치 방법을 제공하는데 **Helm이 거의 항상 포함**된다. 설치자마다 환경·구성이 다르니, Helm으로 **각자 환경에 맞게 조절 가능한 패키지**를 만들어 배포하기 때문.

## 최종 의견 (강사 권고)

- Kubernetes를 하면 오픈소스를 반드시 도입하게 되고, 그 대부분이 **Helm으로 배포**된다 → **Helm은 어차피 알아야 한다.** 처음엔 학습이 어렵지만, Helm을 먼저 익히면 Kustomize는 굳이 안 써도 된다.
- 그래도 **Kustomize를 알아야 하는 경우**:
  1. 처음부터 끝까지 **소규모 프로젝트**일 때.
  2. **빨리** 파이프라인을 구축해야 하고 **단계적으로** Helm을 적용해도 될 때 — Helm을 급히 적용하다 사고 치는 것보다, Kustomize로 기본 파이프라인부터 세우고 실력이 오른 뒤 Helm을 안정적으로 얹는 게 낫다(번거로움이 아니라 **안정적·단계적**인 접근).
  3. 이미 누가 **Kustomize로 구축해 놓아** 분석해야 할 때.
- → Helm을 택했더라도 이 강의만큼은 Kustomize도 충분히 이해해 둘 것.

## 설치 구성 비교

- **Kustomize**: 자체 사이트/GitHub 릴리스가 있지만, **kubectl 1.14+에 통합**됐다. 실습 클러스터는 kubectl 1.27이라 이미 포함(버전 확인 시 Kustomize **5.0.1**). 별도 설치 불필요, **`-k` 옵션**(`kubectl ... -k`)으로 사용.
- **Helm**: Helm 사이트/GitHub에서 다운받아 설치. kubectl처럼 **인증서**가 있어야 API 서버와 통신. `helm ...` 명령으로 사용.
- 설치 방식은 달라도 구성은 비슷하다 — 각자 폴더에 구성 방식대로 패키지 파일을 만들면 결국 Kube API로 같은 요청이 나간다.
- 🌐 **Helm은 생태계가 더 크다** — **Artifact Hub**(GitHub/Docker Hub 같은 Helm 패키지 저장소)가 있다. 오픈소스 기업들이 자기 제품을 Helm 패키지로 올려두고, 사용자는 `helm` 명령으로 받아 (기업이 제공하는 설치 가이드대로) 자기 환경에 맞게 수정해 배포한다. 생태계가 크니 Helm이 제공해야 할 기능도 많을 수밖에 없다.

## 사용 방식 — 함수(Helm) vs 오버레이(Kustomize)

- **Helm = 함수 방식.** `templates/` 안의 YAML은 변수 처리된 **템플릿**이다. `helm` 명령으로 **파라미터를 주입**하면 Helm이 변수에 값을 치환해 최종 YAML을 만들어 API로 보낸다. (템플릿 + 입력 파라미터 → 내부 로직 → 결과값. 개발자에게 익숙한 함수 개념.)
- **Kustomize = 오버레이 방식.** `base/`에는 **아무 처리 없는 순수 YAML**(그대로도 배포 가능)이 있고, `-k`로 배포하면 환경별 폴더에 명시한 **달라지는 스펙만** base 위에 덮어쓴다 — 같은 값이면 수정, 없는 값이면 추가.
  - 예: base service에 nodePort가 없어 그대로 배포하면 (필수값 누락으로) 에러날 파일이라도, dev 오버레이가 nodePort를 얹어 재구성해 준다.
- 배포 대상이 늘 때: **Helm은 명령어(파라미터)가 늘고**, **Kustomize는 패키지 내부 파일이 는다** → Kustomize는 사용 목적이 많아질수록 관리가 복잡해진다.

## Helm 실습 — 차트 구조와 4단계 만들기

### 설치
- CI/CD 서버에 **root**로 설치 스크립트 실행. 단 Jenkins가 배포를 실행하므로 **jenkins 유저**로 전환해 `helm`이 뜨는지 확인.
- `helm create <차트명>` 으로 초기 샘플 템플릿 생성(차트명 = 패키지 차트 이름). Helm 패키지를 직접 만들 땐 항상 여기서 시작한다.

### 차트 구조

```
<차트명>/                 # 차트명으로 만들어진 메인 차트 폴더
├── charts/              # 서브 차트(현재 비어 있음) — MSA에서 메인 앱을 보조하는
│                        #   서브 앱들의 YAML을 분리해, 한 번에 함께 배포할 때 사용
├── templates/           # 메인 차트로 배포될 YAML들이 있는 폴더
│   ├── tests/           # 배포 후 통신 확인용(간단 테스트). BusyBox 파드로
│   │                    #   서비스 포트에 wget — 이번 실습에선 삭제
│   ├── _helpers.tpl     # 사용자 정의(전역) 변수 선언 — 기본값을 가공해 전역값 생성
│   ├── deployment.yaml  # 실제 배포될 YAML(변수 처리가 아주 많음)
│   ├── service.yaml
│   └── NOTES.txt        # README 역할 — 배포 후 안내 문구 출력(if/length 등 로직 가능)
├── .helmignore          # 렌더링에서 제외할 파일 경로(.gitignore와 동일 개념)
├── Chart.yaml           # 차트 자체 기본 정보(chart version / appVersion=내 앱 이미지 버전)
└── values.yaml          # ★ 배포 YAML에 들어갈 변수들의 기본값 선언
```

- **values.yaml이 핵심** — 많은 값을 매번 `--set`으로 넘기긴 부담스러우니, 기본값을 파일로 선언해 둔다.
- **.helmignore** — Helm은 폴더 내용 전체로 매니페스트를 **렌더링**하는데(= Helm 차트로 배포할 매니페스트를 만들어 냄), 지금 배포하고 싶지 않은 파일이나 렌더링 중 에러를 유발할 파일을 여기서 걸러낸다.
- **_helpers.tpl** — `define`으로 사용자 정의 변수명을 만들고, 여러 변수를 조합해 값을 만든다. Helm을 쓰다 보면 정말 자주 보는 패턴이라 하나씩 찾아 가며 익히면 된다.

### 4단계로 만들기 (강사 실습 폴더 1~4번)
1. **init** — `helm create`로 만든 차트를 그대로 복사.
2. **deleting** — 당장 불필요한 것 삭제: `charts/`(서브차트), `templates/tests/`.
3. **수정** — 내 YAML에 맞게 `values.yaml` / `deployment.yaml` 손보기.
4. **추가** — ConfigMap/Secret 등 내 리소스 추가.

### 3단계 — values.yaml / deployment.yaml 수정 포인트
- `replicaCount`, `image`(레포/이름), `imagePullPolicy` 설정.
- **tag는 비워도 됨** — 이미지 태그는 `Chart.yaml`의 **appVersion**으로 오버라이딩되므로, 태그는 Chart.yaml에서 관리한다. (⚠️ image에 태그까지 같이 박으면 태그가 **이중**으로 붙는 실수 → 배포 결과에서 이미지가 이상하게 나옴. 강사도 이 실수로 두 번 찍힘.)
- `serviceAccount`, `ingress`, `autoscaling(HPA)`: Sprint 3 등 뒤에서 다룰 것이라 일단 **false**.
- **service**: 타입 NodePort로, port 80 + **nodePort 추가**(기본 템플릿엔 없어 직접 추가).
- **컨테이너 포트**: 기본 템플릿은 service 포트와 컨테이너 포트를 같게 쓰라 제시하지만(그런 경우도 많음), 여기선 컨테이너 포트를 8080으로 썼으므로 그 부분은 무시하고 **8080 하드코딩**.
- `resources`(limits/request): 값을 채우고, 남은 주석/빈 블록은 지워야 문법 에러가 안 난다(어차피 배포 때 에러 나면 그때 고쳐도 됨).
- `nodeSelector`: PV/PVC 강의의 로컬 볼륨 설정 잔재 — 노드가 마스터 하나뿐이라 생략.
- **deployment.yaml 프로브**: readiness/liveness에 **startupProbe** 추가, path/포트(8080) 수정. `periodSeconds`/`failureThreshold` 등은 기본값(10/3)이면 굳이 안 넣어도 됨.

### 4단계 — ConfigMap/Secret 추가 + 들여쓰기
- ConfigMap/Secret YAML은 직접 작성(service를 복사해 `kind`만 바꿔 시작).
- **리소스 이름 규칙**: 모든 리소스 이름엔 **helm install 시 준 배포 인스턴스명**이 들어간다. ConfigMap/Secret은 그 뒤에 **하드코딩 접미사**(예: `-properties`)를 붙여 `{{ 인스턴스명 }}-properties` 형태로 만든다.
- **들여쓰기 함수(`nindent`)**: `nindent 12`는 앞에 공백 12칸을 주라는 뜻 → 상황에 맞게 **2**로 수정. 앞의 하이픈(`{{- ... }}`)은 출력 시 **왼쪽 여백을 모두 없애라**는 지시자. Helm 차트에서 앞 공백을 맞추려고 이런 패턴을 자주 본다.
- deployment에서 `envFrom`으로 ConfigMap 참조(name을 ConfigMap 이름 변수로), Secret은 **volume/volumeMount**로 연결.

### 변수는 어디서 오나 (Helm 변수 체계)

| 출처 | 접근 방식 | 비고 |
|------|-----------|------|
| `helm install <인스턴스명> <경로> -n <ns>` | `.Release.*` | 인스턴스명이 Deployment/Service 이름으로 들어감 |
| `Chart.yaml` | `.Chart.*` | |
| `values.yaml` | `.Values.*` | ⚠️ `.Release`는 **대문자**, `.Values`는 **소문자** 시작 — 혼동 주의 |
| `_helpers.tpl`(사용자 정의) | `{{ include "..." . }}` | |

- Helm 명령·Chart·values는 `templates/`의 **모든 파일**에서 참조 가능, 사용자 정의 변수도 전체에서 사용 가능.

### Jenkinsfile — helm template / upgrade --install
- 이번 실습은 **Helm 배포만** 보므로 소스/컨테이너 빌드·업로드 스텝은 **echo만** 찍고 스킵.
- **`helm template`** — 배포 전에 렌더링될 YAML을 화면에 미리 출력하는 명령. 배포 사고를 막는 사전 확인 단계.
- 💡 **학습 vs 실무**: `helm template` 명령을 아는 건 **학습**이다. 그걸 **배포 직전 이 위치에 배치**하는 게 **실무**다. 실무란 별게 아니라 학습한 걸 **언제·어떤 상황에** 쓰는지 아는 것. 게다가 매번 확인은 번거로우니 **중요한 배포에만** 강제 확인을 넣을 줄 아는 사람이 실무를 잘하는 사람 — 인프라에선 실수로 잘 돌던 걸 내리는 대형 장애가 흔하고, 다급할 때의 실수를 **시스템적으로 차단**하는 장치가 필요하다. (그래서 뭘 배우든 **유즈케이스를 같이** 찾아 두는 습관을 들일 것.)
- **`helm upgrade --install` 관계**:

  | Helm | kubectl 대응 |
  |------|--------------|
  | `helm install` | `create` (최초 배포만) |
  | `helm upgrade` | `patch` (이미 배포된 것 수정) |
  | `helm upgrade --install` | `apply` (없으면 설치, 있으면 업그레이드 — Helm이 알아서 판단) |

- `--create-namespace`: 네임스페이스가 없으면 만들고 거기에 리소스 생성. 자주 쓰는 유용한 옵션.
- 배포 후 **NOTES.txt** 내용이 출력됨 — 내부 로직은 복잡해도 결국 사용자 세팅에 따라 **동적으로 접속 방법을 안내**하는 용도.

## Kustomize 실습 — 패키지 구조와 환경별 배포

### 패키지 구조 (직접 만든다)

```
<메인폴더>/
├── base/                      # 디폴트 포맷 YAML(Helm의 templates 폴더에 매핑되는 위치)
│   ├── deployment.yaml        # 기존 kubectl로 쓰던 YAML 그대로 — 단 labels/selector 없음
│   ├── service.yaml           #   (labels/selector도 없음)
│   └── kustomization.yaml     # ★ resources(배포할 파일 선택) + commonLabels(공통값)
└── overlays/
    ├── dev/
    │   ├── deployment.yaml    # 이 환경에서 달라지는 스펙만(자원 등)
    │   ├── version.yaml       # (예시) 버전만 별도 파일로 관리 — 꼭 나눌 필요는 없음
    │   └── kustomization.yaml # namespace 지정 + commonLabels version override + patches
    └── prod/
        └── ...
```

- Helm은 `helm create`로 자동 생성이지만 **Kustomize는 폴더·하위 구성을 직접** 만든다(가이드에 잘 나와 있음). 대신 **폴더 구조 + kustomization.yaml 기능**만 알면 끝이라 훨씬 심플하다.
- **kustomization.yaml** 핵심 두 기능:
  - `resources`: **배포할 파일을 명시적으로 선택**(YAML이 아무리 많아도 여기 없으면 배포 안 됨). ↔ Helm은 `hpa.yaml` 내부 `if` + values의 true/false로 배포 여부를 제어.
  - `commonLabels`: 여기에 넣으면 **모든 YAML에 labels/selector가 자동 생성**된다. 그래서 base의 deployment/service엔 labels/selector가 없어도 된다. ↔ Helm은 템플릿에 변수를 심고 여러 방식으로 주입.
- **오버레이**: `overlays/<환경>/`마다 그 환경에 맞게 덮어쓸 파일 + `kustomization.yaml`(역할 동일). deployment는 내용이 많아 **수정 대상만 이름 붙인 파일로 쪼개** overlay할 수 있고, 오버레이의 `kustomization.yaml`에서 `patches`로 **실제 overlay할 파일을 별도 지정**해야 한다. 환경별로 자원 크기, `namespace`, `commonLabels`의 version(예: 2.0) 등을 다르게 반영.
- 📁 폴더 이름이 꼭 `base`/`overlays`일 필요는 없다 — `kubectl ... -k <경로>`로 준 폴더 안에 `kustomization.yaml`이 있고, 그 `resources`가 base 파일 경로를 제대로 가리키면 된다.

### 배포
- `kubectl kustomize <경로>`로 렌더링 미리보기(= Helm `template`에 대응).
- 실제 배포: `kubectl apply -f <namespace>` 후 **`kubectl apply -k <overlay 경로>`**.
- dev/prod를 각각 배포하면 자원·버전이 환경별로 반영된다. 실습은 클러스터가 하나라 **네임스페이스로 환경을 구분**했지만, 실무에선 dev/QA 클러스터가 따로라 네임스페이스명에 환경 구분을 굳이 안 넣어도 된다.

### Jenkins 파라미터로 환경 선택
- Jenkinsfile의 `parameters`(choice)로 환경 선택 박스를 만든다. 단, **Jenkins가 Jenkinsfile을 한 번 다운받은 뒤부터** "파라미터와 함께 빌드" 버튼이 생긴다(첫 빌드엔 안 나옴 → 취소·새로고침하면 나타남).
- 선택값은 `params.PROFILE`처럼 **동적으로** 이후 스테이지에서 사용한다. (이전 실습에서 "필수값이지만 지금은 의미 없다"던 입력값이 바로 여기서 쓸모가 생김.)
- 아이템을 **복사**해서 만들면 parameters 설정이 함께 복사되어 처음부터 버튼이 나온다.

## Helm으로 환경별 배포 — values 오버레이 & set

- 환경별로 `values-dev.yaml`, `values-prod.yaml`을 **통째로 하나 더** 만들고, 배포 시 **`-f values-dev.yaml`** 옵션으로 선택.
- **값 우선순위**: `values.yaml`(기본값) → **`-f`로 준 환경별 values(오버레이·덮어쓰기)** → **`--set`(배포 시 동적 주입, 최종 반영)**.
  - 예: 기본 `replicaCount: 2`지만 `values-dev.yaml`에서 1로 두면 dev는 1이 반영된다.
- `--set`은 값이 많으면 명령이 길고 복잡해지니 **정말 동적으로 값을 줘야 할 때만**. 보통은 환경별 values 파일로 관리.
- Helm 배포 시 **`--create-namespace`를 빼고 네임스페이스를 분리**해 배포했다 — **Helm은 네임스페이스에 관여시키지 않는 게 좋다**(자세한 이유는 뒤 강의에서).
- ⚠️ 영상으로 이해됐다고 그냥 넘기지 말고, **언제든 바로 꺼내 쓸 수 있게 코드를 정리**해 둘 것.

# 4부. 배포 파이프라인 구축 후 마주하는 고민들

> 앞 강의에서 "뒤에서 설명한다"며 넘어간 것들 + 실무에서 반드시 마주치는 것들. 지금 다 이해 안 돼도, 실습 코드로 보면 헷갈렸던 게 바로 이해되는 내용들.

## ① 민감 정보 암호화 — docker config.json / kubeconfig

- CI/CD 서버의 Jenkins는 컨테이너 빌드 → **Docker Hub 업로드**(사전 `docker login` 필요) + **Helm 배포**(kubeconfig 인증서 필요)를 한다.
- ⚠️ **문제 1** — `docker login`을 하면 `~/.docker/config.json`에 접속 정보가 저장되고 Docker가 이걸 계속 읽어 재로그인 없이 업로드한다. 그런데 이 파일은 **암호화가 안 되고 Base64 인코딩**뿐이라, K8s Secret처럼 디코딩하면 **Docker Hub 아이디/비번이 그대로 노출**된다.
- ⚠️ **문제 2** — `kubeconfig`는 **관리자 권한 인증서**다. 누가 복사해 가면 관리자 권한으로 클러스터에 API를 날릴 수 있다.
- 즉 CI/CD 서버에 **접속만 하면** Docker Hub·클러스터가 위험 → ①서버 접근 보안 강화, ②**디스크에 암호화 안 된 중요 정보를 남기지 않기**(디스크 교체 시 기존 디스크 복원 위험, 보안팀 점검 툴이 방치된 ID/PW·인증서를 검출).
- **해결 — Jenkins Credential에 등록**(암호화 저장, 등록자도 이후 내용을 못 봄, 권한 있는 사람만 사용):

  | 대상 | Credential 타입 | Jenkinsfile 사용 |
  |------|-----------------|-------------------|
  | Docker Hub 로그인 | Username + Password (id 예: `docker-password`) | 변수로 받아 `docker login` → 업로드 → **`docker logout`**(config.json 접속 정보 삭제) |
  | kubeconfig | Secret file | `kubectl apply --kubeconfig <변수>` — 기본 kubeconfig 대신 이걸 인증서로 사용 |

- 이렇게 하면 CI/CD 서버에 직접 해둔 `docker login`·kubeconfig를 **지워도 된다**(kubeconfig는 파일 이름만 바꿔 놔도 kubectl이 기본 동작 안 함). **서버에 어떤 정보도 남기지 않는 게** 목표.
- 🔒 실무 심화: **Docker Credential Helpers**를 적용하면 config.json을 열어도 비번을 알 수 없게 된다(파일 자체 암호화). 나중에 Public Docker Hub 대신 **Private Docker Registry**를 설치할 때 함께 적용.

## ② CI/CD 서버 이미지 정리

- 빌드를 반복하면 CI/CD 서버에 컨테이너 이미지가 계속 쌓인다 → 디스크가 다 차 **Jenkins가 죽고 나서야** 알게 되는 문제.
- 업로드(push) 직후 **`docker rmi`**로 이미지를 삭제하면 이 사고를 겪지 않는다.

## ③ 네임스페이스는 배포와 분리해서 관리

- Helm으로 앱을 배포할 때 앱마다 NS를 만들지 않고 **그룹 단위**로 묶는 경우가 많다.
- Helm `--create-namespace`로 NS를 만들어도 **`helm uninstall` 시 NS는 삭제되지 않는다** — NS를 지우면 그 안의 **다른 앱까지 삭제**될 수 있어 Helm이 **의도적으로** 안 지운다.
- → NS는 **배포와 별도로 관리**하는 게 좋다: 초반에 `kubectl`로 한 번 만들고 배포 스크립트엔 아예 안 넣거나, **NS 전용 배포 파이프라인**을 따로 둔다. (강의는 실습마다 NS를 새로 만들어 스크립트에 포함했을 뿐, 실무에선 한 번 만들고 건들 일이 적다.)

## ④ Helm 자주 쓰는 부가 기능

- **재배포해도 업그레이드가 안 되는 문제** — Kubernetes는 deployment의 `spec.template` 하위에 **변경이 있어야** 롤아웃(업그레이드)을 시작한다. 소스만 바뀌고 매니페스트 template엔 변경이 없으면, 배포 버튼을 눌러도 파드가 그대로다. (강사 일화: Jenkins 배포 성공만 보고 점심 갔다가 "소스 반영 안 됐다" 전화받고 복귀.)
  - **해결**: `spec.template.metadata.annotations`에 배포마다 **랜덤 값**을 주입 → template에 변경이 생겨 **항상 업그레이드**된다.
- **`--wait` + `--timeout`** — 배포 명령 후 **파드가 실제 정상 기동될 때까지 기다렸다가** 성공을 반환(이전 강의의 while 루프 역할을 Helm이 대신). 반드시 **`--timeout`**(예: 10분)을 함께 준다 — 파드가 `CrashLoopBackOff`로 계속 재시작하면 Helm이 무한 대기하고, **Jenkins의 잡 실행 스레드 수는 제한**이라 스레드를 계속 잡고 있으면 안 되기 때문.

## ⑤ 이미지 태그 전략 (제일 중요·어려움 — 숨 한 번 쉬고)

- 이제부터 버전 앞의 `v`를 뺀다(버전 명명 규칙상 `v` 없는 게 맞음). `latest` = 넘버링과 무관한 **마지막 배포 버전**. 태그를 안 붙이면 `latest`가 받아진다.
- **환경별 태그 + imagePullPolicy 조합**:

  | 환경 | 태그 | imagePullPolicy | 이유 |
  |------|------|-----------------|------|
  | 개발 | `latest` | **Always** | 잦은 배포라 버전 관리 무의미 → 항상 Docker Hub에서 최신을 가져옴. (단점: Docker Hub 연결 안 되면 파드 생성 실패. + latest는 template 변경이 없어 ④의 annotation이 꼭 필요) |
  | 검증/운영 | **명시적 태그** | **IfNotPresent** | 계획된 배포라 버전닝 필수. 노드에 이미지 있으면 그걸 쓰고 없을 때만 Docker Hub → 스케일 인/아웃 시 재다운로드 방지, Docker Hub 장애 시에도 노드에 있으면 파드 생성 가능 |

- ⚠️ **조합을 섞지 말 것**: `latest`에 `IfNotPresent`를 쓰면 노드의 **예전 이미지**를 재사용해 "최신을 받는다"는 latest의 목적이 깨진다.
- 🔧 **롤백 요구에 대응하는 태그 전략**(강사 사례): 개발자는 소스 빌드까지, 컨테이너 빌드·배포는 강사가 담당(소스 빌드 시 자동 컨테이너 배포). 역할이 분리되니 "어제 이미지로 롤백" 요청이 온다 → `latest`만으론 대응 불가. → **개발 환경도 매 배포마다 날짜+시간(또는 시퀀스) 태그** + `IfNotPresent`로 변경. 롤백 요청 시 날짜를 물어 해당 이미지로 되돌린다. 태그가 매번 바뀌니 ④의 Helm 랜덤 값 annotation도 불필요해진다.
- 💡 **latest의 진짜 의미**: 단순 "마지막 배포 버전"은 버그·미실행 가능성이 있다. 하지만 **제3자는 latest를 "최신 안정화 버전"으로 기대**한다(예: Grafana/Prometheus를 latest로 받으면 안정화 버전이 온다). 처음엔 개발 환경에서 latest=마지막 배포 버전으로 써도 되지만, 프로젝트가 커질수록 **latest = 최신 안정화 버전** 의미로 운영하는 게 좋다. 안정화 버전을 남길 땐 `docker tag ... latest` 후 `docker push`.
- 하나를 공부하더라도 **유즈케이스를 찾으며** 익혀야 자신 있게 실무에 적용할 수 있다(이 태그 전략도 그렇게 정립된 것).

## ⑥ Kubernetes 노드 이미지 정리 — Garbage Collector

- 노드에도 이미지가 계속 쌓이지만 **걱정 안 해도 된다** — **kubelet의 Garbage Collector**가 사용하지 않는 이미지를 자동 삭제한다. `kubelet config`로 설정하며, 보통 기본값을 쓰고 굳이 안 건드린다(설정 변경 후 kubelet 재시작 시 반영):

  | 속성 | 의미 |
  |------|------|
  | 이미지 최소 나이 | 생성 후 이 시간(예: 3분, 기본 2분)이 지나야 GC 대상 |
  | HighThresholdPercent | 디스크 **80% 이상**이면 GC 시작 |
  | LowThresholdPercent | 디스크 **70% 이하**로 내려가면 GC 중단 |

## 실습 — 최종 Jenkinsfile에 담긴 것

- Credential로 등록한 **kubeconfig/Docker 인증 정보**를 암호화 상태로 사용.
- **이미지명·태그를 Helm `--set`으로 동적 주입** → deployment의 이미지명이 자동으로 `내Docker유저네임/앱:태그`로 치환된다. 그래서 이제 **deployment.yaml의 이미지명을 직접 수정할 필요가 없다**(Sync fork만 확인).
- 이번엔 소스 빌드를 실제로 수행(이전 실습은 echo만).
- **`post { always { ... } }` 문법** — 스텝이 성공하든 실패하든 **끝난 뒤 항상** 실행(여기선 `docker logout`). `always` 외에 `success`/`failure`도 있다.
- 명령어가 길어 **여러 줄**에 걸쳐 쓸 땐 앞 공백(들여쓰기)에 주의.
- 개발 환경을 선택해 배포하면 `--wait` 덕에 **파드 기동이 완료된 뒤에야** Helm이 결과를 반환한다 → 배포 성공 = 파드 정상 기동으로 판단 가능.

# 5부. Argo CD 빠르게 레벨업

## 배포 파이프라인 레벨 1~4 복기

| 레벨 | 구성 | 얻은 것 | 남은 문제 |
|------|------|---------|-----------|
| **1. Jenkins만** | CI/CD 환경에 최소 **Docker + kubectl** 설치 → Jenkins **UI**로 소스 빌드·컨테이너 빌드·배포 구성 | 가장 쉽고 빠르게 파이프라인이 돈다 | UI로 수정한 구성은 **변경 관리가 안 된다** |
| **2. Jenkins Pipeline** | 파이프라인을 **스크립트(Jenkinsfile)** 로 작성 → **GitHub에서 관리** | 변경 관리 용이 + **복사해서 재사용**, 스크립트에 **로직** 삽입 가능 | 처음 만들 때는 UI보다 시간이 더 든다 |
| **3. Helm / Kustomize** | 배포 *구성*이 아니라 **배포 *파일*** 개선. kubectl로만 배포하면 YAML이 폭증 → **패키지 매니저**로 동적 구성 | YAML **중복 최소화** + **환경별 설정 관리** 편리 | 배포 *방식*은 여전히 K8s 기본 전략뿐 |
| **4. Argo CD** | 다양한 상황에서 안정적으로 배포하기 위한 **배포 전략** | 배포 **편의 기능** + 무엇보다 **블루그린·카나리** 지원 | 새 솔루션 = 유지보수 부담 |

- Kubernetes Deployment가 기본 제공하는 배포 방식은 **Recreate / RollingUpdate 둘뿐**이다.
- 그래서 요즘은 **Jenkins로 빌드까지만 하고, 배포는 Argo CD**로 가는 추세.

### 강사 권고 — 단계적으로, 그리고 과유불급

- 처음 파이프라인을 구성해 보는 사람이 실무에서 **한 번에 레벨 4로** 가려 하면 문제가 **동시다발적으로** 터진다 → **각 단계를 안정화시킨 다음** 넘어갈 것.
- 내 앱을 배포하는 데 **레벨 3으로 충분하다고 판단되면 굳이 다음 단계로 갈 필요 없다.** Argo CD가 없다고 배포를 못 하는 것도 아니고, 새 솔루션 도입은 **그만큼의 유지보수 부담**이 따라온다. 기능을 충분히 파악하고 **꼭 필요하다는 판단이 설 때** 적용해도 된다.
- (이 강의를 잘 들으면 그런 **판단을 내릴 수 있을 정도**로는 레벨업된다.)

## 이번 파트에서 다루는 것

| 영역 | 내용 |
|------|------|
| **① Argo CD 기본** | Argo 제품군 중 **배포를 담당하는 솔루션**이 Argo CD. 다른 Argo 솔루션들이 각각 뭘 하는지 + 설치하면 생기는 **많은 컴포넌트들의 역할·아키텍처** + (Argo 제품 3종) 설치 + 앱 배포에 필요한 **개념 설명과 실습** |
| **② Argo CD Image Updater** | 기본 Argo CD는 **Git에 연결돼 배포 변경 사항을 감지**한다. Image Updater를 설치하면 **Docker Hub에서 이미지 변경을 감지**할 수 있다 → **왜 필요한지**와 실습 |
| **③ Argo Rollouts** | **블루그린 / 카나리** 배포. Argo CD를 쓰는 **가장 큰 이유** |

### 편의 기능 vs 배포 전략 — Argo CD를 써야 하는 진짜 이유

- Argo CD가 주는 **UI와 다양한 배포 편의 기능**은 좋은 이유이긴 하지만 **꼭 써야 할 이유는 아니다.** 말 그대로 편의 기능이고, 처음엔 좋지만 **실력이 올라갈수록 "얘가 내 눈에 안 보이는 어떤 동작을 하고 있는지" 파악해야 하는 불편**도 생긴다.
- 반면 **Rollouts가 제공하는 배포 전략은 우리가 어설프게 직접 만드는 것보다 이걸 쓰는 게 훨씬 낫다.** ← 이게 진짜 이유.

### 🙋 "Argo CD는 안 쓰고 블루그린 배포 기능만 쓸 수 있나요?"

> 강사 경험: Argo CD를 써보기 전, 인터넷 검색으로 "블루그린 배포를 제공해준다"는 걸 알았지만 그 프로젝트에선 Argo CD를 쓸 수 없어 시도를 못 했다. 나중에 직접 써보고 나서야 **"그때 인터넷만 보고 오해했구나"** 를 알게 됐다. 직접 설치해서 써봤으면 쉽게 알 수 있었던 내용. (**답 → 아래 "Argo Rollouts" 영역**)

## 💡 학습 태도 — 직접 설치하고, 정리해 둘 것

- 인터넷 검색도 하지만 **되도록 직접 설치해서 써본다.** 그리고 **한 번 해본 것은 시간이 걸리더라도 잘 정리해 둔다.**
- 정말 쉽고 단순한 방법인데 실제로 하기는 힘들다. 하지만 이게 누적되면 프로젝트에서 **명확하게 확인된 사실들만** 얘기하게 되고 → **내 말에 대한 신뢰가 올라가고** → 그만큼 몸값도 올라간다. (누적된 자료로 강의까지 만들게 된 것.)
- 어쩔 땐 **느린 거북이** 같지만, 뒤돌아보면 정말 많은 걸 해놨다는 게 보인다 → 이번 강의도 **실습과 정리**를 꼭 할 것.

## 【영역 1】 Argo 제품군 — 무엇이 무엇을 하나

| 제품 | 역할 | 메모 |
|------|------|------|
| **Argo CD** | Kubernetes 전용 **배포 툴** | 릴리즈 파일 저장소로 **Git이 반드시 필요** |
| **Argo CD Image Updater** | Argo CD의 **추가 기능** | **Docker Hub에서 컨테이너 이미지 변경을 감지**해 배포하는 파이프라인을 만들 수 있다 |
| **Argo Rollouts** | **고급 배포**(블루그린·카나리) 지원 | |
| **Argo Events** | **Kafka와 같은 역할** — 이벤트 버스 | 이벤트 버스 아키텍처 자체는 여기서 설명하기엔 너무 큰 주제라 따로 검색 권장 |
| **Argo Workflows** | **Airflow / Kubeflow와 같은** Workflow Management 도구 | |

- ⚠️ **"Git 필수"는 생각보다 큰 제약이다.** 변경 관리 저장소가 꼭 Git이어야 한다.
  - 강사 사례: 형상 관리를 **SVN**으로 하던 프로젝트가 있었다. SI 프로젝트는 개발량이 많아 **오픈 때까지 일단 다 돌아가는 게 중요**하고 상대방 코드를 리뷰할 시간이 별로 없다 → Git 문화를 정착시키기보다 **최소한의 기능으로 누구나 빨리 익힐 수 있는 SVN**을 더 선호하게 된다 → 그러면 **Argo CD는 사용할 수 없다.**
- 🔗 **Argo 제품만으로도 하나의 아키텍처가 만들어진다**:

```
[Argo Events]  ← 시스템 간 이벤트를 주고받는 메인 통로
      │  (그중 Workflow로 보내지는 이벤트)
      ▼
[Argo Workflows] ← 받은 이벤트의 값에 따라 어떤 작업을 실행하라는 순서도
      │  (그 결과 중 "배포하라"는 작업이 있으면)
      ▼
[Argo CD] ──▶ [Argo Rollouts] ──▶ 특정 배포 전략으로 Kubernetes 자원 생성
```

## 【영역 2】 Argo CD 아키텍처 — 설치하면 생기는 컴포넌트들

> 기본 구조는 다른 솔루션과 비슷하다. 30000번대 NodePort로 UI에 접근하거나 CLI를 날리면 **Kube API 서버**가 그걸 받아 관련 컴포넌트로 트래픽을 전달한다.

| 컴포넌트 | 역할 |
|----------|------|
| **argocd-server** | **API 서버 + 대시보드**를 동시에 담당. NodePort로 UI 접속, `argocd` 툴을 설치하면 kubectl처럼 **CLI**도 가능 |
| **Repo Server** | **Git에 연결해 YAML 파일들을 가져와서**, Kubernetes에 배포할 **매니페스트를 만들어 놓는** 역할 |
| **Application Controller** | Kubernetes 리소스를 모니터링하면서 **Git에서 받은 내용과 다른 게 있는지 비교** → 다르면 **Git에 있는 내용으로 배포**. Kube API로 리소스 생성 명령을 날림 |
| **Notification** | Argo CD에서 발생하는 **이벤트를 외부로 트리거** |
| **Dex** | **외부 인증(SSO) 관리** |
| **Redis** | 메모리 DB = **캐시** |
| **ApplicationSet Controller** | **멀티 클러스터**를 위한 앱 패키징 관리 |

- **Dex를 왜 쓰나**: Kubernetes를 하다 보면 Grafana를 비롯해 대시보드를 많이 쓰게 되는데, 관리자 입장에서 **UI마다 ID/PW를 만들고 관리하는 게 번거롭다.** → **IAM 솔루션**에 한 번만 로그인하면 연결된 시스템은 별도 로그인 없이 자동 로그인(**Single Sign-On**). Kubernetes에서는 대표적으로 **Keycloak**.
- Notification과 Dex, 이 두 기능은 **웬만한 솔루션에는 다 있는** 기능이라고 보면 된다.
- **Redis가 어디에 쓰이나**: **Git 연동 구간**과 **Kube API 서버 연동 구간**에 캐시로 쓰여 **불필요한 통신을 줄여준다.**
- **ApplicationSet Controller가 필요한 이유**: Argo CD는 **클러스터마다 설치**할 수도 있지만 **하나만 설치해서 여러 클러스터로 배포**할 수도 있다. 그렇게 쓰면 **배포 환경마다 배포 구성을 만들어야 해서 중복**이 생긴다 → **환경별로 다른 부분만 세팅해서 쓸 수 있는 템플릿**을 제공해 준다. (Helm·Kustomize에서 했던 것과 같은 발상.)
- 💡 **전체 구성을 한 번은 훑고 갈 가치**: 내가 Argo CD 기능의 **일부만 쓰고 있더라도, "알지만 안 쓰는 것"이지 몰라서 못 쓰는 게 아니라는 안심**이 생긴다. 실제 필요한 일이 생기면 그때 찾아서 쓰면 된다.

## 【영역 3】 설치 — Artifact Hub → 내 GitHub → Jenkins 잡

### 사전 작업과 실습 시작점

- 이 강의에서 설치할 **Argo 제품 3종(Argo CD / Image Updater / Rollouts)** 은 모두 **Artifact Hub에서 Helm 패키지로** 설치할 수 있다.
- 강사가 미리 해둔 것: Helm이 설치된 서버에서 `helm repo add` → `helm pull <패키지명> --version <버전>` (버전을 주면 그 버전의 패키지가 **압축 파일**로 받아짐) → 압축 해제 → **본인 GitHub에 그대로 업로드** + **실습 환경에 맞는 values 파일 추가**.
- 실습자는 여기서부터: CI/CD 서버에 **Jenkins 잡(`deploy-argo`, Pipeline 타입)** 을 하나 만들고 실행 → 강사 GitHub에서 패키지를 받아 **본인 Kubernetes 클러스터에 설치**된다. (릴리즈 파일을 배포했던 Git 레포지토리와는 **다른 레포지토리**다.)

### Jenkins 잡 파라미터

| 파라미터 | 선택지 |
|----------|--------|
| **Deploy Type** | Namespace Create / Namespace Delete / **Helm Upgrade** / Helm Uninstall |
| **Target Argo** | argo-cd / image-updater / rollouts |

- ⚠️ 파이프라인 잡은 **한 번 빌드해야** "파라미터와 함께 빌드" 버튼이 생긴다(Jenkins가 Jenkinsfile을 한 번 받아와야 하므로).

### values 파일 — 딱 필요한 것만 바꿨다

- Artifact Hub에서 받은 패키지는 **그대로 두고**, `values-dev.yaml` **하나만 추가**했다.
- **Argo CD**: `server.service.type = NodePort` + **32000번대 포트**. 그 외에는 전부 기본값.
- 변경할 수 있는 항목이 엄청나게 많지만 **기본값만으로도 잘 돌아간다.** (지상편은 Kubernetes를 *사용하는* 관점의 강의라 여기까지만 다룬다. 설치 솔루션의 상세 설정은 관리자 관점인 해수편에서.)

### Jenkinsfile에서 배울 점 — Helm 명령어를 변수에 담는 이유

- Helm 명령어를 바로 실행하지 않고 **문자열 변수에 담았다가**, 전용 키워드로 **그 문자열을 그대로 실행**시킨다.
- 왜? **Image Updater를 설치할 때만** `--set` 옵션으로 추가 설정을 줘야 하기 때문에 **`if` 문으로 분기**해야 했다. 이렇게 **설치할 솔루션에 따라 다른 값을 줘야 할 때**는 변수에 담아 필요한 로직을 만들 수 있다.
- 선택한 제품은 `targetArgo` 같은 변수로 들어가서 **`helm/<targetArgo>` 경로의 패키지가 설치**되는 구조.
- 🗑 **삭제할 때 CRD는 별도로 지워야 한다** — Helm으로 설치할 때 만들어지지만 `helm uninstall`로는 **안 지워지는 리소스**라, 스크립트에서 **제품별로 일일이** 지워줬다.

### 첫 로그인

- 초기 admin 비밀번호는 **kubectl로 Secret을 조회**해서 확인 → 유저명 `admin` + 조회한 값으로 로그인 → 로그인 후 **User Info > Update Password**로 변경.

## 【영역 4】 Git 레포지토리는 3개로 분리한다

Kubernetes 관련 레포지토리를 만들다 보면 통상 이렇게 세 개가 생기는데, **각각 분리해 두는 게 좋다.**

| 레포지토리 | 주 담당자 | 연동되는 시스템 |
|-----------|----------|----------------|
| **앱 소스코드 전용** | 개발자 (보통 여러 명이 공유) | **CI/CD 서버**가 소스 빌드를 위해 코드를 모두 다운로드 |
| **앱 릴리즈 전용** | 주로 **DevOps 엔지니어** | **Argo CD**가 배포를 위해 릴리즈 파일을 모두 다운로드 |
| **Add-on 설치 전용** (Argo CD 등) | **운영자**가 관리하게 될 수도 | |

- 릴리즈 레포지토리의 담당은 **정답이 없다** — 프로젝트 상황에 따라 개발자가 본인 앱의 배포를 담당하기도 하고, **DevOps 엔지니어는 관리자 / 개발자는 사용자** 역할로 함께 쓰기도 한다.
- **분리하는 이유**: 레포지토리마다 **사용 담당자와 연동해야 할 시스템이 다르다.** → ① **접근 유저별 권한**을 나눌 수 있어야 하고, ② **연동되는 시스템에 불필요한 코드가 다운로드되는 것을 방지**해야 한다.

## 【영역 5】 Argo CD 핵심 개념

### Application과 Project

- **Application** = **앱 하나를 배포하는 단위.** Jenkins에서 배포 단위별로 프로젝트 잡을 만들었던 것과 **똑같은 개념**이고, 앱별로 여러 개가 만들어진다.
- **Project** = Application들을 **그룹핑**하는 용도. Kubernetes의 네임스페이스처럼 **`default` 프로젝트가 기본으로** 만들어져 있다.

### Application에 넣는 내용

| 항목 | 내용 |
|------|------|
| **Source** | 연동할 **Git 정보** (repo URL / revision / path) |
| **Destination** | 배포할 **Kubernetes 클러스터 주소** + 네임스페이스 |
| **General** | 기본 정보와 배포 시 줄 옵션들 |

- **Sync Policy** ← General에서 주목할 옵션. 리소스 변경이 감지됐을 때 **수동(Manual)** 으로 배포할지 **자동(Automatic)** 으로 배포할지. 자동이면 **3분 이내**에 배포된다.
- **Sync Options**: 배포 상세 옵션 — 예를 들어 **배포 시 네임스페이스 자동 생성**(Auto-Create Namespace).
- **Prune Policy**: 리소스 **삭제** 정책.
- 그 외에도 옵션이 많은데 **강사도 안 쓰는 기능이 많다** — 설명을 다 듣기보다 **한 번 읽어보고 필요할 때 쓰는** 접근이 낫다.
- 📍 **Destination 클러스터 주소** = `https://kubernetes.default.svc`
  - default 네임스페이스에 있는 **`kubernetes` 서비스**이고, 레이블의 component가 **apiserver**로 표시돼 있다.
  - Argo CD가 이 클러스터에 설치돼 있으니 **자기 자신이 속한 클러스터의 API 서버**를 가리키는 것.

### Refresh vs Sync

| 버튼 | 의미 |
|------|------|
| **Refresh** | Git에 연결해 두면 변경이 자동 감지되지만 **약 3분의 체크 인터벌**이 있다 → 누르면 **바로 변경 사항을 체크** |
| **Sync** | **Kubernetes에 배포를 실행** |

### 지원하는 배포 툴 3종

- Argo CD는 **세 가지 방식(Directory / Helm / Kustomize)** 을 지원하므로 이 툴들을 **별도로 설치할 필요가 없다.**
- 내 릴리즈 파일을 다운받으면 **어떤 포맷인지 자동으로 인식**한다. (path 안에 Helm 패키지가 있으면 알아서 **Helm으로 세팅**되고 values 값들도 자동으로 채워진다.)
- Directory 방식은 **그 디렉토리에 있는 YAML 파일 전부를 배포 대상으로 간주**한다.

### ★ Desired Manifest vs Live Manifest — 그리고 Diff의 진짜 의미

| | 정체 | 수정 가능 여부 |
|---|------|---------------|
| **Desired Manifest** | **Git**에 있는 YAML을 다운받은 매니페스트 | **여기서 직접 수정 불가.** Git에서 수정하고 **Refresh**해야 변경된다 |
| **Live Manifest** | **Kubernetes**의 실제 리소스를 조회한 매니페스트 | Kubernetes에서 자원을 직접 수정하면 **바로 반영**되고, 반대로 여기서 수정하면 **Kubernetes 자원이 바로 수정**된다 |

- ⚠️ **Diff 버튼은 Desired ↔ Live의 비교가 아니다.** (강사도 처음엔 그렇게 생각했다.) 만약 그렇다면 **Live만 수정했을 때 Diff가 활성화돼야 하는데 활성화되지 않는다.**
- Diff의 대상은 **"Git의 변경 사항이 반영된 후의 Live"와 "현재 Live"** 다. 즉 **Sync를 눌렀을 때 실제로 바뀔 내용**에 대한 비교다.

  | 상황 | Diff |
  |------|------|
  | **Git에 없는** 내용을 Kubernetes에 새로 추가했다 | Sync해도 그 내용이 삭제되는 게 아니므로 **Diff 없음** |
  | **Git에도 있는** 항목을 Kubernetes에서 수정했다 | Sync하면 Git 내용으로 되돌아가므로 **Diff 활성화** |

- 그래서 "Kubernetes에서 누군가 리소스를 직접 수정하면 다 확인되겠구나"는 **오해**다 — **모두가 체크되지는 않는다.** → **최대한 Kubernetes에서 자원을 직접 수정하지 않는 게 좋다.**

### 상태값 읽는 법

- **App Health / Sync Status**는 쓰다 보면 자연스럽게 알게 되는 내용이라 하나하나 설명하는 게 오히려 더 어렵다(파드 상태값도 마찬가지).
- **초록 = 정상 / 노랑 = 뭔가 할 게 있음 / 빨강 = 문제** 정도만 알아도 충분하다.

## 【영역 6】 실습 ① — kubectl(Directory)와 Helm으로 배포

### Directory 방식

1. **New App** → 이름 입력, **Project = default**, **Sync Policy = Manual**(이번엔 수동), **Sync Options에 Auto-Create Namespace 체크**.
2. **Source**: Git repo URL + revision `main` + path (Jenkins에서 많이 해본 내용이라 익숙하다).
3. **Destination**: 클러스터 주소 `https://kubernetes.default.svc` + 네임스페이스(위에서 auto-create를 켰으니 자동 생성된다).
4. **Create** → Application이 만들어지고, **Git에서 받은 YAML로 배포할 리소스를 미리 만들어 놓은** 상태가 된다.
5. **Sync** → 배포 직전에 **상세 옵션이 한 번 더** 뜨고(생성할 때보다 옵션이 몇 개 더 있다), 실행하면 리소스가 생성된다. Argo CD는 상태를 계속 싱크하고 있어서 **파드가 서비스 가능한 상태가 되면 초록색**으로 바뀐다.

### Desired / Live 직접 확인해 보기

- ConfigMap을 눌러 상세로 들어가면 **Live Manifest = 배포된 리소스**, **Desired Manifest = Git의 YAML** 내용을 볼 수 있다.
- Argo CD에서 Live를 수정 → **Kubernetes에 바로 반영**. 반대로 Kubernetes에서 수정 → **Live에 바로 조회**된다.
- **Git에 없는 내용을 추가**했을 땐 Diff에 "차이 없음"이 뜨고, **Git에도 있는 값을 Kubernetes에서 수정**하면 Diff가 뜬다 → Sync하면 **Git 내용으로 되돌아간다.**
- Git의 ConfigMap을 수정·커밋 → (3분 주기 자동 갱신 또는 **Refresh**) → 변경 감지 → **Diff**에 "Git에서 수정된 내용이 반영될 것"이라고 표시.

### Helm 방식

- New App에서 내용은 거의 동일한데, **path 안에 Helm 패키지가 있으면 Argo CD가 감지해서 자동으로 Helm으로 세팅**하고 **values 값들도 자동으로 채워준다.**
- **Values Files** 항목에 커스텀 values를 추가할 수 있다 → 이건 **Helm의 `-f` 옵션과 같다.** (개발 환경 배포 목적이면 패키지 안의 `values-dev.yaml`을 지정.)
- Create하면 Argo CD가 패키지 내용을 확인해 자원을 만들어 주고, **보기 쉬운 YAML로 렌더링해서** 보여준다 → Sync하면 배포.

## 【영역 7】 Image Updater — 왜 필요한가

### 먼저, 배포가 필요한 상황은 두 가지다

| # | 상황 | 기존(Jenkins) 흐름 |
|---|------|-------------------|
| **①** | **리소스 스펙 변경** (Deployment의 배포 전략 변경, 수동 스케일 업 등) | DevOps 엔지니어가 **YAML 수정 → Git 커밋 → 배포 잡 실행** → Kubernetes 반영 |
| **②** | **앱 버전 업그레이드**(컨테이너 이미지 변경) | 개발자가 **소스 빌드 잡 실행** → jar 생성 → 컨테이너 빌드 → Docker Hub 업로드 → **이어서 배포 실행** |

- 원래 ②에서도 DevOps 엔지니어가 YAML의 **이미지 태그를 수정하고 커밋**해야 하지만, **Helm을 쓰면 배포 명령에 태그를 동적으로 줄 수 있어**(`--set`) YAML을 별도로 수정할 필요 없이 배포된다.
- 👉 **핵심 포인트**: ①은 사람이 YAML을 고치고 배포를 실행하는 작업이 필요하지만, **②는 소스 빌드에 이어 배포까지 자동화시켜 놓을 수 있다.**

### Argo CD를 도입하면 어떻게 바뀌나

| # | 변화 | 평가 |
|---|------|------|
| **①** 리소스 스펙 변경 | YAML 수정·커밋까지는 똑같고, **Argo CD가 변경을 감지해 자동 배포** | **한 스텝 줄었다** ✅ |
| **②** 앱 버전 업그레이드 | 컨테이너 빌드까지는 똑같은데, **배포 자체를 Argo CD가 하다 보니 빌드 이후 자동 배포가 힘들어졌다** | **불편해졌다** ❌ |

- 그래도 자동 배포를 포기할 수 없으니 **Jenkins에서 YAML을 수정해 Git에 업데이트시키는 스크립트**를 만들기도 한다. 하지만 이건 예전에 파드 상태를 확인하려고 **while 문을 돌렸던 것처럼 로직이 복잡해진다** — 그때 `helm --wait` 옵션을 쓰는 게 깔끔했던 것처럼.
- 👉 이 상황을 해결하기 위해 추가된 것이 **Argo CD Image Updater**다.

### Image Updater의 동작과 제약

- Image Updater가 **Docker Hub를 계속 모니터링**하다가 **이미지 업데이트가 감지되면 Argo CD에 배포하라는 명령**을 보낸다.
- ⚠️ **배포 패키지가 Helm 또는 Kustomize일 때만 가능하다** — 내부적으로 그 옵션을 사용하기 때문.
- 설치할 때 **Argo CD 연결 정보 + Docker Hub 연결 정보** 두 곳을 입력해야 하고, **Argo CD의 앱별로 "어떻게 업데이트할지" 태그 규칙**을 추가해야 한다.

> 💬 솔루션 하나를 넣을 때 **그걸 써야 하는 확실한 이유를 아는 것**은 이렇게 길게 설명할 가치가 있을 만큼 중요하다.

## 【영역 8】 실습 ② — Image Updater로 이미지 자동 배포

### 설치 시 values 설정

| 설정 | 값 |
|------|-----|
| **Argo CD 연결** | `argocd-server` **서비스 이름**을 그대로 사용. 80/443 포트가 있으니 **`https://<서비스명>`** 형태로 |
| **Docker Hub 등록** | API URL = **퍼블릭 Docker Hub 도메인**, credentials = **유저네임 / 패스워드** |

- 🔒 **패스워드를 values 파일에 직접 쓰면 노출된다.** 실무에서도 **패스워드는 어딜 보더라도 나오는 곳이 없어야** 한다.
  - → Argo 설치 Jenkinsfile에서 **`if` 문으로 image-updater일 때만** `--set`으로 credentials를 주입하고, 그 값은 **Jenkins Credential**에서 가져온다. 그래서 **어디서도 비밀번호를 알 수 없다.**
  - Docker Hub 접속 방법은 ID/PW 방식 외에도 여러 가지가 있으니 공식 문서 참고.
- 설치 후 로그를 보면 **약 2분 주기**로 Processing result가 갱신된다 — Argo CD에 **이미지 업데이터를 사용한다는 설정이 있는지** 확인하고, 그 설정에 따라 Docker Hub를 체크한 결과가 찍힌다. (설정이 없으면 전부 0.)

### 앱별 자동 배포 설정 — Application의 Annotations

Application > **Details > Annotations**에서 Edit로 추가한다.

| 어노테이션 | 내용 |
|-----------|------|
| `...image-list` | **Docker Hub에서 감시할 이미지 대상**을 지정. 값은 `<alias>=<도커유저명>/<이미지명>` 형식 — 이 이미지에 **alias(별칭)** 를 붙이는 것 |
| `...<alias>.update-strategy` | **업데이트 전략.** 예: **`name`** = 알파벳 순으로 정렬된 목록의 **마지막 태그**로 업데이트 |
| `...<alias>.allow-tags` | **정규식 패턴**으로 감지할 태그를 한정 |

- 이미지는 **여러 개 지정할 수 있고**, 이미지마다 **어떤 상황에 업데이트할지가 다를 수 있어서** alias를 붙여 **각각 전략을 지정**한다.
- 이 강의의 태그 규칙: 정식 버전 `1.1.1` + **빌드할 때마다 일시가 붙는** 패턴 → **그 일시 부분의 변경만** 감지하도록 전략을 `name` + 정규식 패턴으로 줬다. → 그 패턴으로 만들어진 태그만 감지해서 **변경이 생기면 자동 배포.**
- 업데이트 전략은 종류가 있으니 **어떤 방식을 쓸지는 레퍼런스 문서로 공부가 좀 필요하다.**

### Sync Policy를 Automatic으로 바꾸면 나오는 옵션 2개

| 옵션 | 의미 |
|------|------|
| **Prune Resources** | Git에서 리소스(예: ConfigMap)를 삭제해도 **기본적으로 Kubernetes에서는 안 지워진다** — 삭제는 늘 민감해서 기본값이 "안 지움"이다. Enable하면 **Git 삭제 시 실제 자원도 삭제** |
| **Self Heal** | Git의 내용과 Kubernetes 자원 값이 다르면 **무조건 Git 내용으로 적용** |

- ⚠️ **Self Heal 주의**: "항상 Git대로 유지"는 좋아 보이지만, Kubernetes에서 **오토 스케일이 일어나 Deployment의 replica가 늘어나도 이 기능 때문에 다시 줄어든다.** 충분히 감안하고 써야 한다.

### 결과

- 소스 빌드 → 컨테이너 빌드 → Docker Hub 업로드 → **Image Updater가 태그 변경을 감지** → **Argo CD가 자동 배포** → 파드 재생성.
- 정리하면, Argo CD만 쓸 때는 앱 버전 업그레이드 자동화를 위해 **YAML을 업데이트하고 Argo CD가 변경 감지를 해줘야 하는 복잡한 파이프라인**이었는데, Image Updater를 설치하면 **Docker Hub에 직접 연결돼 훨씬 자연스러운 파이프라인**이 된다.

## 【영역 9】 Argo Rollouts — 개념

### ❓ "Argo CD 없이 Rollouts만 쓸 수 있나?" → **쓸 수 있다**

- 인터넷에서 Rollouts의 블루그린 기능을 봤을 때 **"Argo CD가 있어야 쓸 수 있는 기능"이라고 착각**했지만, 막상 설치해 보니 **각각 독립적인 솔루션**이었다.
- Rollouts는 **자체 대시보드가 별도로** 있다. Argo CD가 있으면 **Argo CD 화면에서도 Rollouts를 실행할 수 있는 버튼이 생길 뿐**이다.

### Rollout 컨트롤러의 정체 (CRD + 컨트롤러)

- Rollouts를 설치하면 **`Rollout`이라는 컨트롤러**를 만들 수 있게 된다.
- Kubernetes는 자체 리소스 외에 **CRD(Custom Resource Definition)** 로 누구나 커스텀 리소스를 정의해 추가할 수 있다. 하지만 **리소스만 만드는 건 의미가 없다.**
- Kubernetes는 **Go 언어**로 만들어졌고, Deployment를 만들면 → ReplicaSet이 만들어지고 → ReplicaSet의 replica 수를 보고 파드가 만들어지는 **내부 로직**이 있다. 마찬가지로 CRD를 만든 뒤 **그 리소스가 어떻게 동작할지의 로직(컨트롤러)도 Go로 개발**해야 한다.
- 이때 내가 만든 컨트롤러로 **ReplicaSet이나 파드의 동작을 변형**시킬 수 있는데, **Rollouts가 그걸 다 해놓은 것**이다.

### 블루그린 — 복습과 Rollout의 차이

- 블루그린의 특징(복습): **운영 환경에서만 테스트가 가능한 상황**에 쓰고, **롤백이 빠르다.** RollingUpdate는 배포 중간에 사용자에게 **v1과 v2가 동시에 호출되는 구간**이 있지만 블루그린은 **없다.** 스크립트로 자동화할 수는 있지만 **v2에 과도한 트래픽이 유입되는 문제**를 주의해야 한다.
- Kubernetes 리소스만으로 만든 블루그린: v1 파드가 서비스 중 → **v2 Deployment 생성 + 서비스 붙여 QA 테스트** → 완료되면 **기존 서비스의 selector를 v2로 변경** → 문제없으면 **v1 Deployment 삭제**.
- **Rollout의 블루그린 핵심 설정 = 서비스 2개 지정**

  | 서비스 | 역할 |
  |--------|------|
  | **activeService** | 실제 서비스 사용자가 들어오는 서비스 |
  | **previewService** | 업그레이드 중에 **v2 버전으로만** 들어가 볼 수 있는 서비스 |

- 동작 순서:
  1. Rollout이 **ReplicaSet**을 만들고(Deployment가 만들던 것과 똑같은 K8s 리소스) → 파드 생성. 두 서비스의 selector가 이 파드에 매칭돼 **둘 다 v1으로** 트래픽을 전달.
  2. **태그를 변경하고 Sync**(또는 Argo CD 없이 Kubernetes 자원을 직접 수정)하면 업그레이드 시작 → **v2 ReplicaSet과 파드 생성**. *여기까지는 Deployment와 완전히 동일.*
  3. **여기서부터 다르다** — **activeService는 그대로 v1**을 보고 있지만, **previewService는 v2 파드로 연결이 변경**된다.
  4. QA 담당자가 previewService로 테스트 → 끝나면 **Promote** 명령 → **activeService가 순간적으로 v2로 전환**되고 **v1 파드는 삭제**된다.
- **어떻게 자동으로 연결되나**: 수동 블루그린에서는 v2 Deployment에 레이블 v2를 달고 QA 서비스의 selector도 v2로 줘서 **사람이 직접 연결**했다. Rollout은 **파드에 레이블을 달고, 그 레이블 내용을 서비스의 selector에도 달아서 자동으로 연결**한다.
  - 사실 **똑같은 원리가 Deployment에도 이미 있었다** — ReplicaSet이 만들어질 때 파드와 연결되기 위한 **selector와 레이블이 Kubernetes에 의해 자동 추가**되고, 업그레이드로 새 ReplicaSet이 생기면 **새 이름의 selector/레이블이 붙어 그 둘만 연결되는 관계**가 형성된다.
- ⚠️ 애초에 **평소엔 RollingUpdate로 배포하다가 정말 특수한 경우에 딱 한 번** 블루그린을 하는 것이지, **지속적으로 이렇게 배포 관리를 하는 건 좀 무리**다. 가끔 하더라도 Rollout으로 **클릭 없이 자동 진행**하게 할 수 있으니 → **과도한 트래픽 유입 문제만 없으면 되고**, 급한 배포가 아니면 **새벽 시간에 배포 트리거**를 걸어두면 이런 문제는 확실히 적어진다.

### 카나리 — 복습과 Rollout의 방식

- 카나리의 특징(복습): 트래픽의 **특정 헤더 값에 따라 분기**해 주는 구성이라 **블루그린처럼 서비스를 따로 만들지 않아도 특정 IP·특정 사용자만 v2를 호출**하게 할 수 있다. 트래픽 배분을 조절하며 **서서히 v2에 트래픽을 넣어 콜드 스타트를 방지**하는 용도로도 쓰고, 업그레이드가 아니라 **두 버전을 비교하는 A/B 테스트** 용도로도 쓴다.
- Deployment로 카나리를 하면 **Ingress + Ingress Controller(NGINX)** 가 필요하다(Sprint 3 예정). 업그레이드 시작 → v2 리소스 생성 → **Ingress에 트래픽 가중치 옵션** → NGINX 컨트롤러가 그걸 보고 트래픽 분배 → 작업을 마치면 v1 관련 리소스 삭제.
- ⚠️ **블루그린은 Kubernetes 리소스만으로 (불편해도) 구현이 됐지만, 카나리는 안 된다.** Ingress는 기본 리소스지만 **NGINX는 별도로 설치하는 애드온**이고, 이게 없으면 기본 리소스만으로는 구현이 불가능하다.
- Rollouts도 마찬가지로 **섬세한 트래픽 조절은 NGINX·Istio 같은 애드온이 있어야** 가능하다(Sprint 3에서 테스트). 다만 **그 특징 하나를 못 해보는 것이지, Rollouts 자체는 카나리 방식으로 업그레이드를 해준다.**
- **Rollout의 배포 전략 = `blueGreen` / `canary`** (Deployment에 Recreate/RollingUpdate가 있는 것처럼). 카나리는 **서비스를 하나만** 만들면 된다.
- **`steps` 속성** — `setWeight`와 `pause`를 번갈아 리스트로 준다. 파드가 2개인 상태에서:

  | 스텝 | 동작 |
  |------|------|
  | `setWeight: 33` | **전체 파드에서 카나리가 차지하는 비율이 33%가 되도록** → v2(카나리) 파드 1개 생성 |
  | `pause: {}` (비어 있음) | **Promote 명령이 올 때까지 무한정 대기** → 이때 필요한 테스트 진행 |
  | `setWeight: 66` | v2 비율이 66%가 되도록 조절 → **v1 하나 삭제 + v2 하나 생성.** 테스트가 끝났다고 바로 v2로 전환해 버리면 **v2 파드의 부하가 심해질 수 있어 서서히 전환**하는 것 |
  | `pause: {duration: 2m}` | **2분 대기** → 남은 v1 파드는 2분이 지난 후에 삭제 |

- RollingUpdate도 `maxSurge`/`maxUnavailable`로 생성·삭제 파드 개수를 조절할 수 있었지만 **프로세스 중간에 멈출 수는 없었다.** Rollout은 **이 steps를 준 것만으로 RollingUpdate를 카나리 배포로 바꾼 것**이다.

## 【영역 10】 실습 ③ — Rollouts 블루그린 & 카나리

### 설치

- Jenkins에서 **Deploy Type = Helm Upgrade, Target = Argo Rollouts** → Build.
- 추가한 `values-dev.yaml`:
  - `controller.replicas: 1` — rollout 관련 앱이 기본 **replica 2**로 만들어지는데 굳이 2개가 필요 없어서 1로.
  - **전용 대시보드는 기본적으로 설치되지 않는다** → `dashboard.enabled: true` + 브라우저 접근을 위해 **33000번대 NodePort**.

### 블루그린 실습

- Argo CD에서 **New App → `Edit as YAML`** 버튼을 쓰면 항목을 하나씩 채우지 않고 **YAML로 한 번에** 입력할 수 있다.
- 배포하면 **Deployment 대신 Rollout 컨트롤러가 ReplicaSet을 만들고, ReplicaSet이 파드를 만든다.**
- **서비스 YAML은 이름 뒤에 `-active` / `-preview`가 붙은 것만 다르고**, selector와 포트는 기존과 완전히 똑같다 → **Rollout에 연결된 서비스라고 해서 다르게 준 내용이 하나도 없다.**
- **rollout.yaml**: `apiVersion`에 Argo Rollouts 버전, `kind: Rollout`, 그리고 **`strategy.blueGreen` 부분만 빼면 나머지 스펙은 기존 Deployment와 똑같다.**
  - 심지어 **HPA도 호환된다** — HPA의 타겟에 apiVersion을 Argo 프로젝트로, kind를 `Rollout`으로, 이름을 넣으면 된다. **기존에 Deployment를 넣던 자리에 Rollout을 넣어도 될 만큼** 다른 리소스와 호환이 잘 된다.
  - 👉 **새로 배울 부분은 `strategy.blueGreen` 속성 하나뿐**이라 크게 어렵지 않다.
- `blueGreen` 속성: 앞에서 만든 **activeService / previewService의 이름**을 지정 + **`autoPromotionEnabled`**

  | 값 | 동작 |
  |----|------|
  | `false` (실습에서 사용) | 중간에 멈췄다가 **Promote를 눌러야** 다음으로 진행 |
  | `true` (**기본값**) | 새 그린 파드가 정상 기동되자마자 **자동으로 전환**되고 기존 블루 파드는 삭제 |

  → **야간에 자동으로 블루그린 배포를 돌리고 싶으면 이 속성 자체를 안 넣으면 된다.**
- 진행: Git에서 **이미지 태그를 2로 변경·커밋** → Refresh(변경 감지) → **Sync** → **preview 서비스는 즉시 v2 쪽으로 전환**(파드 기동 전이라 잠시 에러가 나지만 **active는 계속 v1으로 정상 서비스** 중이라 문제 상황이 아니다) → v2 파드가 뜨면 preview에서 v2가 호출된다.
- 🔍 **확인 포인트**: v2 파드의 Live Manifest를 보면 내가 준 레이블 외에 **`rollouts-pod-template-hash`** 라는 **난수 레이블이 Rollout에 의해 추가**돼 있고, **preview 서비스의 selector에도 똑같은 값**이 들어가 있다. ReplicaSet의 selector도 마찬가지이며 **v1/v2의 값이 달라서 서로 다른 파드에 연결**된다. (Kubernetes의 Deployment를 봐도 원리는 똑같다.)
- **Promote** → 트래픽이 **한순간에** v1 → v2로 전환된다(사용자 입장에선 한순간에 변경). 기존 파드는 **30초 뒤 삭제**(속성으로 변경 가능). preview는 여전히 v2를 가리켜 **업그레이드 전의 연결 상황과 똑같아진다.**

### Rollouts 대시보드와 CLI

- Argo CD에 뜨는 Promote 버튼은 **Rollouts를 설치했을 때 Argo CD에 생기는 버튼일 뿐**이고, **Argo CD가 없어도** Rollouts 대시보드 URL로 들어가면 똑같이 할 수 있다.
- 대시보드는 Argo CD와 달리 **기능이 많지 않다** — rollout의 배포 전략, v1 파드(active) / v2 파드(preview) 상태를 보여준다.

  | 버튼 | 동작 |
  |------|------|
  | **Rollback** | preview 파드가 삭제되고 **원래 v1만 있는 상태로** 복귀 |
  | **Restart** | 두 파드를 하나씩 재생성 — **쓰기가 좀 애매하다.** 테스트 중인 새 파드의 ConfigMap을 수정해 다시 적용하려고 재생성할 일은 생기는데, Restart는 **active 파드를 재생성**하는 거라 딱히 누를 일이 없다. 새 파드를 재생성할 땐 **Kubernetes에서 직접 삭제**하면 된다 |
  | **Promote** | **다음 단계로** 진행 |
  | **Promote Full** | **모든 단계를 다** 건너뛰기 |

  → 블루그린은 다음 단계가 한 번뿐이라 **Promote와 Promote Full의 차이가 없다.** 카나리에서 의미가 생긴다.
- **Argo Rollouts CLI**: `kubectl argo rollouts get rollout <이름> -n <네임스페이스>` — kubectl 패턴에서 **중간에 `argo rollouts`만 들어갔을 뿐**이다. **`-w` 옵션**을 주면 한 번만 조회하지 않고 계속 반복 조회돼 **모니터링처럼** 쓸 수 있다(Ctrl+C로 종료).
  - Argo CD도 CLI가 있지만 **대시보드 자체가 Argo CD를 쓰는 큰 이유**라 CLI를 쓸 일이 별로 없었다. 반면 **Rollouts는 대시보드가 별게 없기도 하고, 배포에 익숙해지면 CLI가 더 편하다.**

### 카나리 실습 (Argo CD 없이 kubectl로)

- 마스터에서 **kubectl로 직접 배포**한다. 이번엔 **서비스가 하나**(+ rollout, ConfigMap, Secret).
- 배포 트리거: rollout을 Edit해서 태그를 바꿔도 되지만 **이미지를 바로 변경하는 명령**이 있다.
  - `kubectl argo rollouts set image <rollout명> <컨테이너명>=<이미지>:<태그> -n <네임스페이스>`
  - 컨테이너 이름을 주는 이유는 **파드 안에 여러 컨테이너가 있을 수 있어서**다.
  - 이 명령은 **`argo rollouts`를 `deployment`로만 바꾸면 Deployment의 update 명령과 똑같다.**
- 진행 확인:
  1. 배포 즉시 **카나리 파드 생성** → 기존 2개 + 카나리 1개 = **setWeight 33% 단계 완료** → 다음 스텝이 `pause`라 **멈춰 있는 상태**. 트래픽은 기존 파드 2개와 카나리 1개로 **분산**된다.
  2. **카나리 파드에만 접속하고 싶다면**: `canaryService` / `stableService` 속성을 지정하고 서비스를 하나 더 만들면 된다. 이름만 다를 뿐 블루그린에서 서비스를 썼던 것과 똑같이 동작하며, **카나리에서는 필수값이 아니다.**
  3. **Promote** → 다음 단계 **setWeight 66%** → v2 하나 생성 + v1 하나 삭제.
  4. 다음 스텝 `pause: 2m` → **2분 후** 마지막 v1 파드가 terminating → **v2만 호출**되면서 업그레이드 완료.
- ⚠️ **Promote Full을 누르면 단계가 전부 무시되고 한 번에 배포가 완료**되므로 함부로 누르면 안 된다.
- 콘솔 모니터링(`-w`)보다 **Rollouts 대시보드를 보는 게 가시성이 훨씬 좋다.**

## 한 장 요약

- 🎯 **DevOps의 핵심 = 개발 → 빌드 → 실행 파일.** 아무리 파이프라인이 복잡해져도 이 알맹이는 항상 존재. 빌드/실행엔 늘 OpenJDK. 전체 흐름과 "내가 필요한 것"을 알면 새 툴도 빨리 붙일 수 있다.
- 🏗 **인프라 환경 3종**: 개발(같이 테스트) · QA(운영과 동일하게) · 운영(**이중화가 핵심** — 오픈소스는 실제 이중화 테스트 필수, 일정 마지막에 터지면 답이 없다).
- 🧰 **8단계와 오픈소스**: 계획(Jira/Notion/Slack) · 개발(JUnit/FindBugs/PMD) · 빌드(Gradle/Docker, Nexus) · 테스트(JUnit/Jacoco/JMeter) · 릴리즈(Dockerfile·YAML을 GitHub에) · 배포(Kustomize/Helm/ArgoCD) · 운영(NGINX/Istio) · 모니터링(Grafana/Loki/Prometheus + Jaeger/Zipkin). 기업은 내부용(GitLab/Docker Registry)을 설치해 쓰고, Slack은 파이프라인 **알람 연동** 때문에 쓴다.
- 🧑‍💻 **직군 로드맵**: 개발자/DevOps 엔지니어/운영자 모두 연차에 따라 **영역을 넓혀야** 한다. 빌드~운영 배포까지 아는 운영자 = **SRE**. 9년차+ 직책(PM/PL/아키텍트)은 전체를 알아야 유지된다.
- 🔤 **다른 Ops들**: GitOps(Git으로 통일) · DevSecOps(배포 속도+보안 자동화) · MLOps(데이터 분석가↔개발자 파이프라인) · LLMOps(대규모 특화) · FinOps(클라우드 비용, 아직 초기).
- 🛠 **CI/CD 서버 구축**: Vagrant(2코어/2GB/30GB, IP .20) → kubectl/Docker/OpenJDK 17+Gradle/Git/Jenkins(+JDK 11). 본인 **GitHub Fork + Docker Hub** 필수, deployment.yaml 이미지명을 내 유저네임으로. Jenkins 프로젝트 3종(소스 빌드 → 컨테이너 빌드 → 배포), 마지막 파드 에러는 스스로 트러블슈팅.
- 📦 **Helm vs Kustomize**: 둘 다 **패키지 매니저**(kubectl은 CLI일 뿐). Helm = **함수 방식**(templates + 파라미터 주입, 생태계 큼=Artifact Hub, 오픈소스 대부분 Helm) · Kustomize = **오버레이 방식**(base + overlays, kubectl `-k`에 내장, 심플). **Helm은 어차피 알아야** 하고, 소규모·빠른 구축·기존 분석용으로 Kustomize를 안다.
- 🧩 **Helm 실습**: `helm create` → 차트 구조(`templates`/`values.yaml`★/`Chart.yaml`/`_helpers.tpl`/`.helmignore`/`NOTES.txt`) → 4단계(init→삭제→수정→ConfigMap/Secret 추가). 변수 출처 `.Release`(대문자)/`.Values`(소문자)/`.Chart`/`include`. 배포는 **`helm upgrade --install`**(=kubectl apply), `helm template`로 사전 확인. 태그는 `Chart.yaml`의 appVersion으로.
- 🧱 **환경별 배포**: Kustomize는 `overlays/<env>/`로 base에 오버레이(+Jenkins `parameters`로 환경 선택). Helm은 `values-<env>.yaml`을 **`-f`**로 덮고, 동적 값은 **`--set`**(우선순위: values → `-f` → `--set`). 네임스페이스는 배포와 분리.
- 🧠 **구축 후 고민들**: 민감정보는 **Jenkins Credential**로 암호화(docker config.json/kubeconfig는 평문·Base64라 위험, 배포 후 `docker logout`) · CI/CD·노드 이미지 정리(`docker rmi` / kubelet **GC** 80→70%) · Helm **annotation 랜덤값**(재배포 롤아웃 강제) + **`--wait`/`--timeout`** · **태그 전략**(개발=latest+**Always**, 운영=명시태그+**IfNotPresent**, 롤백 필요 시 날짜/시퀀스 태그, latest는 결국 **최신 안정화 버전** 의미로).
- 🪜 **배포 파이프라인 레벨**: 1) Jenkins UI(변경관리 X) → 2) Jenkins Pipeline(스크립트를 Git으로) → 3) Helm/Kustomize(YAML 중복·환경 관리) → 4) **Argo CD**(배포 전략). **한 번에 4로 가지 말고 단계별 안정화**, **레벨 3으로 충분하면 안 올라가도 된다**(도입 = 유지보수 부담).
- 🐙 **Argo 제품군**: CD(배포, **Git 필수** — SVN 쓰면 못 씀) · **Image Updater**(Docker Hub 이미지 감지) · **Rollouts**(블루그린/카나리) · **Events**(Kafka 격 이벤트 버스) · **Workflows**(Airflow/Kubeflow 격). 컴포넌트: **server**(API+대시보드) · **Repo Server**(Git→매니페스트) · **App Controller**(K8s↔Git 비교·배포) · Notification · **Dex**(SSO, K8s는 Keycloak) · **Redis**(Git·API 구간 캐시) · **ApplicationSet**(멀티 클러스터 템플릿).
- 🗂 **레포지토리 3분리**(앱 소스 / 앱 릴리즈 / Add-on 설치) — 담당자와 연동 시스템이 다르니 **권한 분리 + 불필요한 코드 다운 방지**.
- 🎛 **Argo CD 개념**: **Application**(배포 단위, Jenkins 잡 격) ⊂ **Project**(그룹핑, default 기본). Source(Git)/Destination(`https://kubernetes.default.svc`)/**Sync Policy**(수동·자동, 자동은 3분 내). **Refresh**=즉시 변경 체크(기본 3분 인터벌), **Sync**=배포. Directory/Helm/Kustomize **자동 인식**. **Desired**(Git, 직접 수정 불가) vs **Live**(K8s 실물, 양방향 즉시 반영) — ⚠️ **Diff는 둘의 비교가 아니라 "Sync하면 바뀔 내용"의 비교** → K8s에서 직접 수정하지 말 것.
- 🖼 **Image Updater**: 배포 상황은 ①리소스 스펙 변경 ②앱 버전 업그레이드. Argo CD는 ①을 한 스텝 줄이지만 **②의 자동 배포가 어려워진다** → Docker Hub를 감시해 Argo CD에 배포 명령. **Helm/Kustomize일 때만 가능.** 앱 **Annotations**에 image-list(alias)/update-strategy/allow-tags(정규식). 자동 배포 시 **Prune Resources**(Git 삭제=실물 삭제) · **Self Heal**(⚠️ 오토스케일 replica도 되돌림).
- 🔵🟢 **Rollouts**: **Argo CD 없이도 쓸 수 있다**(독립 솔루션 + 자체 대시보드, Argo CD엔 버튼만 생김). CRD+컨트롤러로 ReplicaSet/파드 동작을 변형. **blueGreen**=active/preview 서비스 2개 + **autoPromotionEnabled**(기본 true) → Promote 시 한순간 전환(구 파드 30초 후 삭제). **canary**=서비스 1개 + **steps**(`setWeight`/`pause`) → **RollingUpdate를 멈출 수 있게 만든 것**. ⚠️ 섬세한 트래픽 조절은 NGINX/Istio 필요(Sprint 3), **Promote Full은 전 단계 스킵**이라 주의. CLI `kubectl argo rollouts get rollout -w`.
