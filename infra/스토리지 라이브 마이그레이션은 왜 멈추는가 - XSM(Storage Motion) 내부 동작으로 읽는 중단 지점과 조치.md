# 스토리지 라이브 마이그레이션은 왜 멈추는가 — XSM(Storage Motion) 내부 동작으로 읽는 중단 지점과 조치

## AI 요약

### 1. XSM(Xapi Storage Migration)이란?

XSM은 **Storage Motion**이라고도 불리며, 원문이 밝히는 기능 범위는 세 가지다.

| 기능 | 설명 |
|---|---|
| 풀 내 이동 | 실행 중인 VM을 **호스트와 스토리지를 동시에** 바꾸며 이동 |
| 풀 간 이동 | 실행 중인 VM을 **다른 풀로** 이동 |
| 디스크만 이동 | 실행 중인 VM에 붙은 디스크를 **다른 SR로** 재배치 |

핵심은 "VM을 멈추지 않은 채로 디스크 데이터를 통째로 옮긴다"는 것이다. 그런데 디스크는 메모리보다 훨씬 크다. 원문은 **디스크 전송이 전체 과정에서 가장 시간이 오래 걸리는 구간**이라고 명시한다. 중단 현상을 이해하려면 이 "가장 긴 구간"에서 무슨 일이 벌어지는지를 봐야 한다.

### 2. 동작 순서 — 원문이 제시하는 5단계

원문의 시퀀스를 그대로 정리하면 다음과 같다.

```
[1] xapi가 소스 디스크의 스냅샷을 만든다
        │
        │  스냅샷 = "지금까지 쓰인 데이터"의 고정된 상태
        ▼
[2] 스냅샷을 목적지로 백그라운드 복사 시작 (오래 걸리는 구간)
        │
        │  동시에 ↓
        ▼
[3] VM ↔ 디스크 데이터패스를 재수립하기 전에,
    xapi가 tapdisk에게 "모든 쓰기를 원격 tapdisk로 미러링하라"고 지시 (NBD 사용)
        │
        ▼
[4] 이 시점부터 VM의 모든 디스크 쓰기는 기존 디스크 + 새 디스크 양쪽에 기록된다
        │
        │  (백그라운드 스냅샷 복사가 끝날 때까지 계속)
        ▼
[5] 스냅샷 복사가 끝나면 → VM 메모리를 전송 →
    목적지 VM이 메모리 이미지를 받으면 기동, 원본은 안전하게 제거
```

여기서 구조적으로 중요한 두 가지가 보인다.

**첫째, 두 개의 데이터 흐름이 동시에 존재한다.**

```
          ┌──────────────────────────────────────────────┐
          │  소스 호스트                                  │
          │                                              │
   VM ────┼──▶ tapdisk ──┬──▶ 로컬 디스크 (기존 VDI)      │
   쓰기   │              │                               │
          │              └──▶ NBD 미러 ──────────────┐   │
          │                                          │   │
          │   스냅샷 ──── sparse 백그라운드 복사 ────┐│   │
          └──────────────────────────────────────────┼┼───┘
                                                     ▼▼
                                          ┌────────────────────┐
                                          │ 목적지 tapdisk/VDI │
                                          └────────────────────┘
```

- **흐름 A (과거 데이터)**: 스냅샷의 백그라운드 복사. 총량이 크고 오래 걸린다.
- **흐름 B (현재 데이터)**: VM이 지금 만들어내는 쓰기의 실시간 미러. 끊기면 안 된다.

**둘째, 흐름 B는 "따라잡기"가 아니라 "동기 이중 쓰기"다.** 원문은 미러 개시 이후 모든 쓰기가 old/new 양쪽에 기록된다고 말한다. 즉 목적지와 네트워크가 소스 VM의 쓰기 속도를 실시간으로 감당해야 한다. 이 조건이 깨지는 순간이 곧 중단 지점이다.

### 3. 왜 "가장 오래 걸리는 구간"이 문제가 되는가

원문의 설계를 그대로 따라가면, 마이그레이션 시간은 대략 이렇게 결정된다.

| 요소 | 영향 |
|---|---|
| 디스크 크기 | 흐름 A(스냅샷 복사)의 총 시간을 결정 |
| VM의 쓰기 속도 | 흐름 B(미러)가 감당해야 할 지속 부하 |
| 네트워크/목적지 SR 성능 | A와 B가 **같은 경로를 공유**하므로 둘 다 좌우 |

흐름 A가 길어질수록, 흐름 B를 유지해야 하는 시간도 그만큼 길어진다. 500GB 디스크를 옮긴다면 미러는 복사가 끝날 때까지 몇 시간이고 계속 유지되어야 한다. **디스크가 클수록 실패 확률이 선형이 아니라 그 이상으로 커지는 구조**다.

또한 [5]단계에서 메모리 전송이 시작되려면 [2]의 백그라운드 복사가 **완료**되어야 한다. 복사가 끝나지 않으면 메모리 전송 단계로 넘어가지 않는다. 진행률이 특정 지점에서 멈춘 것처럼 보이는 현상의 구조적 배경이 여기에 있다.

### 4. 마지막 단계 — 언제 원본을 지우는가

원문은 순서를 분명히 한다. **목적지 VM이 메모리 이미지를 받아 기동한 뒤에야** 원본을 안전하게 제거한다. 즉 원본은 전 과정 내내 살아있는 정본으로 남는다.

이것은 안전한 설계지만, 뒤집어 말하면 **중간에 실패하면 소스와 목적지 양쪽에 흔적이 남는다**는 뜻이기도 하다. 목적지에는 완성되지 않은 VDI가, 소스에는 미러용으로 만든 스냅샷이 남는다. 원문은 정리 실패 시의 처리를 다루지 않는다.

## 내가 얻은 인사이트

> 아래 1~3은 위 원문의 설계에서 직접 도출한 해석이다.
> 4~6은 원문 범위 밖이며, 별도로 표시한 확인 자료에서 정리한 실무 대응이다. 원문의 주장이 아니다.

### 원문에서 도출한 해석

1. **"멈춘 것처럼 보인다"와 "실제로 죽었다"는 다른 현상이다**
   - 원문의 [2]는 대용량 백그라운드 복사다. 진행률이 오래 정체되는 것은 정상 동작일 수 있다.
   - 반면 [3]의 미러가 끊기면 그 순간 실패로 확정된다.
   - **판단 기준은 진행률이 아니라 네트워크 트래픽과 tapdisk 상태여야 한다.** 진행률만 보고 취소를 누르는 것이 상황을 더 나쁘게 만드는 이유다.

2. **미러는 "여유"가 아니라 "실시간 제약"이다**
   - 원문이 말하는 이중 쓰기 구조상, 목적지가 소스의 쓰기를 못 따라가면 실패한다.
   - 따라서 **쓰기가 많은 VM(DB, 로그 수집기, 빌드 서버)은 라이브 스토리지 마이그레이션에 가장 불리하다.**
   - 대응 방향은 "네트워크를 늘린다"보다 **"마이그레이션 중 쓰기를 줄인다"**가 더 확실하다. 야간 창, 백업 잡 정지, 로그 로테이션 억제가 실질적인 사전 조치다.

3. **디스크 크기가 실패 확률을 지배한다 → 문제를 크기 문제로 환원하라**
   - 흐름 A가 길수록 흐름 B의 유지 시간이 길어진다는 구조적 결합 때문이다.
   - 그래서 실무 우선순위는 이렇게 정리된다.
     1. 옮기기 전에 **디스크를 줄인다** (불필요 VDI 분리, 스냅샷 정리)
     2. 옮길 수 없으면 **디스크를 안 옮기는 경로**를 찾는다 (공유 SR을 양쪽에서 보이게 만든 뒤 메모리만 이동)
     3. 그래도 안 되면 **라이브를 포기한다** (warm/오프라인 이동)

### 실무 대응 정리 (원문 범위 밖 — 별도 확인)

> 아래는 XCP-ng 공식 포럼 스레드와 xapi 소스(`storage_migrate.ml`, `storage_smapiv1_migrate.ml`)에서 확인한 내용이다.
> 원문 아티클의 서술이 아니라, 원문의 구조를 실제 실패 사례에 대입해 정리한 것이다.

4. **중단 유형별 1차 분류표**

   | 증상 | 어느 단계 | 실무적 의미 |
   |---|---|---|
   | `MIRROR_FAILED` | [3] 미러 | 쓰기 속도 > 미러 속도. 라이브로는 어렵다는 신호 |
   | `VDI_COPY_FAILED(End_of_file)`, 항상 같은 % 에서 실패 | [2] 복사 | 소스 VHD의 특정 오프셋 손상 의심 |
   | `SR_BACKEND_FAILURE_44` | [1] 스냅샷 | 소스 SR 공간 부족. 스냅샷 자리가 없다 |
   | `SR_BACKEND_FAILURE_47` / "Interrupted operation detected on this VDI" | 이전 실패 잔재 | 앞선 중단이 남긴 상태가 다음 시도를 막는다 |
   | 100%에서 정지 | [5] 전후 | 태스크/툴스택 레벨 문제일 가능성 |

   - `MIRROR_FAILED`와 매우 큰 VM의 조합에 대해 Vates 측이 포럼에서 제시한 답은 **라이브 스토리지 마이그레이션 대신 warm migration을 쓰거나, 새 호스트를 기존 풀에 넣고 공유 스토리지를 유지한 채 일반 라이브 마이그레이션을 한 뒤 옛 호스트를 eject 하라**는 것이었다. 원문의 구조를 알면 이 조언이 왜 나오는지가 바로 이해된다. 흐름 A를 아예 없애버리는 우회다.

5. **손이 먼저 나가면 안 된다 — 취소의 비용**
   - 원문 [5]가 말하듯 원본은 마지막까지 남는다. 하지만 중간 취소는 **목적지의 부분 VDI가 잠긴 채로 남거나, 소스에 미러용 스냅샷이 누수되는** 결과를 만들 수 있다.
   - xapi 소스에도 실패 시 정리 경로(`perform_cleanup_actions`, `mirror_cleanup`)가 있지만, 정리 자체가 중간에 끊기면 `base_mirror` 표시가 붙은 스냅샷이 남는다.
   - 따라서 조치 순서는 **관찰 → 원인 확정 → 정리 → 재시도**이지, **취소 → 재시도**가 아니다.
   - 툴스택 재시작은 마지막 수단이다. 실제로 마이그레이션 중인 VM을 `VM_BAD_POWER_STATE`로 만들어 풀 전체 호스트에서 재시작해야 했던 사례가 보고되어 있다.

6. **중단 발생 시 실제 점검 순서**

   ```bash
   # 1) 태스크가 살아있는지 — 진행률이 아니라 태스크 자체를 본다
   xe task-list

   # 2) 미러가 죽었는지 확인 (소스 호스트)
   grep -i "mirror" /var/log/xensource.log | tail -50
   #    "Tapdisk mirroring has failed" 가 보이면 [3] 단계 실패 확정

   # 3) 스토리지 계층 예외 확인 — 소스/목적지 양쪽 호스트 모두
   tail -f /var/log/SMlog
   #    exception 이 계속 뜨면 SR 또는 특정 VDI 문제

   # 4) 목적지에서 SR을 볼 수 있는지 (풀 간 이동에서 흔한 함정)
   xe pbd-list params=sr-name-label,host-uuid,currently-attached
   #    currently-attached: false 인 호스트로는 애초에 이동 불가

   # 5) 공간 확인 — [1] 스냅샷 실패의 원인
   xe sr-list params=name-label,physical-size,physical-utilisation

   # 6) VHD 체인 무결성 (항상 같은 %에서 실패할 때)
   vhd-util check -n /var/run/sr-mount/<SR-UUID>/<VDI-UUID>.vhd
   ```

   - 4번을 먼저 확인하는 습관이 시간을 가장 많이 아낀다. 이 저장소의 [XCP-ng 구조와 인프라 노트](XCP-ng%20구조와%20인프라%20-%20XOA%20서버,%20XOA%20라이선스.md)에도 정리해 두었듯, PBD가 unplug된 호스트는 그 SR을 보지 못하고 이는 곧 마이그레이션 실패 원인이 된다.
   - 6번에서 `primary footer invalid: invalid cookie` 같은 결과가 나오면 데이터 손상이다. 이 경우 마이그레이션을 반복 시도하는 것은 무의미하며, 복구/재생성 경로로 전환해야 한다.

7. **스토리지 외 마이그레이션에도 같은 구조가 반복된다**

   원문의 XSM 구조를 추상화하면 "① 과거 상태 벌크 복사 → ② 신규 변경분 실시간 미러 → ③ 컷오버"다. 이 패턴은 스토리지 밖에서도 그대로 나타나며, 실패 지점도 같은 자리에 생긴다.

   | 대상 | ① 벌크 | ② 실시간 미러 | 같은 자리에서 나는 문제 |
   |---|---|---|---|
   | DB 마이그레이션 | 초기 덤프/스냅샷 | CDC, binlog/WAL 복제 | 쓰기 속도가 복제 지연을 키워 컷오버 시점을 못 잡음 |
   | 쿠버네티스 PV 이전 | PVC 복사 | 애플리케이션 이중 쓰기 | 벌크 중 앱이 계속 쓰면 정합성 깨짐 |
   | 메시지 큐 이전 | 기존 토픽 미러링 | 프로듀서 이중 발행 | 컨슈머 오프셋 불일치 |

   그래서 마이그레이션 종류를 불문하고 **사전 질문 세 가지**가 동일하다.

   1. ①이 끝나는 데 얼마나 걸리는가? (총량 ÷ 실효 대역폭)
   2. 그 시간 동안 ②가 감당해야 할 변경률은 얼마인가?
   3. ①과 ②가 **같은 자원(네트워크/디스크)을 공유**하는가? 공유한다면 ①이 ②를 굶긴다.

   3번이 대부분의 사고 원인이다. 원문의 XSM에서 스냅샷 복사와 NBD 미러가 같은 네트워크를 쓰는 것과 정확히 같은 구조다. **가능하면 벌크 경로와 미러 경로를 분리하거나, 벌크를 미리 끝내 놓고 미러 구간만 짧게 가져가는 설계**가 답이다.

8. **결론적으로 세운 원칙**
   - 진행률을 보고 판단하지 않는다. 미러 상태와 트래픽을 본다.
   - 큰 디스크 + 쓰기 많은 VM은 라이브를 시도하지 않는다. 처음부터 warm/오프라인으로 계획한다.
   - 취소보다 관찰이 먼저다. 취소는 잔재를 남기고, 잔재는 다음 시도를 막는다.
   - 반복해서 같은 지점에서 실패하면 그것은 성능 문제가 아니라 데이터 손상이다. 접근을 바꾼다.
