# 발표 중 다시 해보는 실습

**약 15분 동안 “설정을 바꾸면 수집과 조회 대상이 어떻게 달라지는가”를 보여준다.** 설치는 발표 전에 끝내고, 발표 중에는 아래 순서만 따른다. 자세한 설명과 포트 생략·노드 분류 실험은 [전체 실습](실습.md)에 있다.

## 발표 전 준비

저장소 루트에서 실행한다. 환경을 지웠을 때만 `setup`을 실행한다. 기존 실습을 이어갈 때는 `ui`만 실행한다.

```bash
cd 'infra/쿠버네티스 스프린트 4'
python3 lab.py setup
python3 lab.py ui
```

이 터미널은 켜 두고, 다른 터미널도 같은 폴더로 이동한다. 브라우저에는 다음 탭을 열어 둔다.

| 화면 | 주소·준비 |
| --- | --- |
| 원시 메트릭 | <http://127.0.0.1:10254/metrics> |
| Prometheus | <http://127.0.0.1:19090> — Query의 Table, Targets |
| Grafana | <http://127.0.0.1:13000> — `admin` / `study-local-only` |

Grafana에서 **Sprint 4 - 직접 바꾸는 모니터링**을 열고 **Save as copy**로 발표용 사본을 만든다. 이전에 조인한 사본 대신 시작 대시보드에서 새 사본을 만든다. 시간 범위는 최근 5분, 새로고침은 5초로 둔다.

### 이전 실습을 했다면 시작 상태로 복구

다음 명령은 앱을 portal 2개·api 1개(backend), worker를 low-spec으로 되돌린다. 기존 Grafana 사본은 유지한다. 수정하던 YAML은 먼저 별도 파일로 보관한다.

```bash
python3 lab.py k apply -f lab/apps.yaml
python3 lab.py k rollout status deployment/portal -n apps
python3 lab.py k rollout status deployment/api -n apps
python3 lab.py k label node sprint4-monitoring-worker resource=low-spec --overwrite
python3 lab.py k delete servicemonitor nginx-metrics -n monitoring --ignore-not-found
cp lab/servicemonitor.yaml .lab/presentation-servicemonitor.yaml
```

`config`에서 job 없음, `targets`에서 활성 대상 0개인지 확인한다. 변경 반영에는 수 초~약 1분 걸릴 수 있다. 이전 수집값이 Query에 잠시 남으면 **현재 Targets와 생성된 설정**을 기준으로 설명한다. 재실습마다 클러스터나 Prometheus 데이터를 지울 필요는 없다.

```bash
python3 lab.py config
python3 lab.py targets
```

## 1. 메트릭 노출과 수집은 별개다 — 2분

```bash
python3 lab.py traffic --count 100
```

원시 메트릭 탭을 새로고침해 `nginx_ingress_controller_requests`를 찾는다. Prometheus의 Targets에는 아직 `nginx-metrics`가 없다.

**말할 내용:** “NGINX가 숫자를 내보내는 것과 Prometheus가 그 숫자를 수집하는 것은 별개입니다. 지금은 내보내기만 하고 있습니다.”

## 2. ServiceMonitor가 있어도 선택되지 않을 수 있다 — 3분

```bash
python3 lab.py k apply -f .lab/presentation-servicemonitor.yaml
python3 lab.py k get servicemonitor nginx-metrics -n monitoring --show-labels
python3 lab.py k get prometheus -n monitoring \
  -o jsonpath='{.items[0].spec.serviceMonitorSelector}'
python3 lab.py config
```

화면에 YAML을 열어 `release: not-selected`와 Prometheus의 선택 조건 `release: monitoring`을 비교한다. **`.lab/presentation-servicemonitor.yaml`의 release만 `monitoring`으로 고친다.**

```bash
python3 lab.py k apply -f .lab/presentation-servicemonitor.yaml
python3 lab.py config
python3 lab.py targets
```

반영될 때까지 새로고침하면 job이 생기고 `:10254/metrics` 대상이 UP이 된다.

**말할 내용:** “ServiceMonitor 객체가 있다는 것만으로 충분하지 않습니다. Prometheus의 선택 조건에 맞으면 Operator가 설정에 반영하고, Prometheus가 직접 수집합니다.”

## 3. 선택됐어도 수집 요청은 실패할 수 있다 — 2분

같은 파일의 `path: /metrics`를 **`path: /not-metrics`**로 바꿔 적용한다.

```bash
python3 lab.py k apply -f .lab/presentation-servicemonitor.yaml
python3 lab.py targets
```

Targets에 대상은 남아 있지만 **DOWN·HTTP 404**가 나온다. `/metrics`로 고쳐 다시 적용한다.

```bash
python3 lab.py k apply -f .lab/presentation-servicemonitor.yaml
python3 lab.py targets
```

**말할 내용:** “대상 없음은 선택 조건부터, DOWN은 대상 URL과 요청 오류부터 봅니다.”

시간이 남으면 `port: metrics`를 `not-a-port`로 바꿔 **job은 있지만 활성 대상이 0개**인 경우도 보여준다. 다음 단계 전에는 `metrics`·`/metrics`로 복구한다.

## 4. 같은 CPU 값에 노드 이름을 붙인다 — 3분

Grafana 사본의 두 번째 CPU 패널을 Edit한다. 기존 IP 범례를 보여준 뒤 질의를 바꾼다.

```promql
(
  1 - avg by(instance) (
    rate(node_cpu_seconds_total{mode="idle"}[1m])
  )
)
* on(instance) group_left(nodename)
node_uname_info
```

Legend를 **`{{nodename}}`**으로 바꾸고 저장한다. CPU 선에 실제 노드 이름이 붙는다. 막 설치한 환경이라면 `rate` 계산을 위한 샘플이 쌓일 시간을 준다.

**말할 내용:** “instance가 같은 노드 정보를 연결했습니다. 오른쪽의 값은 1이어서 CPU 값을 유지하면서 nodename 라벨을 가져옵니다.”

## 5. 쿼리를 두고 라벨만 바꿔 본다 — 5분

Grafana 사본의 세 번째 메모리 패널은 처음에 앱 파드 3개를 보여준다. 아래 식으로 바꿔 frontend 2개만 남긴다.

```promql
sum by(namespace, pod) (
  container_memory_working_set_bytes{
    namespace="apps", container!="", container!="POD",
    job="kubelet", metrics_path="/metrics/cadvisor"
  }
  * on(namespace, pod) group_left
  kube_pod_labels{namespace="apps", label_component="frontend-server"}
)
```

현재 개수를 정확하게 보여줄 때는 이 식을 **Prometheus Table**에도 조회한다. Grafana 그래프에는 이전 파드의 과거 선이 남을 수 있다.

이제 api 파드 템플릿의 분류를 frontend로 바꾼다.

```bash
python3 lab.py k patch deployment api -n apps --type merge \
  -p '{"spec":{"template":{"metadata":{"labels":{"component":"frontend-server"}}}}}'
python3 lab.py k rollout status deployment/api -n apps
python3 lab.py k get pods -n apps -L component
```

새 파드가 수집되면 **같은 질의의 현재 결과가 2개 → 3개**로 바뀐다. 롤아웃 도중에는 이전 파드와 새 파드가 잠시 함께 보일 수 있으므로 완료 뒤 조회한다.

**말할 내용:** “파드 이름을 쿼리에 추가하지 않았습니다. 업무 분류 라벨을 바꾸자 조회 대상이 바뀌었습니다. 라벨을 바꾼 것이 앱의 실제 역할까지 바꾼 것은 아닙니다.”

발표 후 원래 분류로 복구한다.

```bash
python3 lab.py k patch deployment api -n apps --type merge \
  -p '{"spec":{"template":{"metadata":{"labels":{"component":"backend-server"}}}}}'
python3 lab.py k rollout status deployment/api -n apps
```

## 시연이 막혔을 때

| 증상 | 바로 할 일 |
| --- | --- |
| 브라우저 연결 실패 | UI 터미널을 확인하고 `python3 lab.py ui`를 다시 실행 |
| ServiceMonitor를 고쳐도 상태가 그대로 | `config`·`targets`를 다시 조회하며 최대 약 1분 기다림 |
| YAML을 잘못 수정함 | `python3 lab.py k apply -f lab/servicemonitor-working.yaml`로 정상 수집 복구 |
| 그래프가 예상보다 많은 파드를 보여 줌 | 과거 선 대신 Prometheus Table의 현재 결과로 확인 |
| 다시 처음부터 시연하고 싶음 | 위의 “시작 상태로 복구” 명령 실행, Grafana 시작 대시보드에서 새 사본 생성 |

UI 터미널에서 Ctrl+C를 누르면 접속만 종료된다. 다음 발표·연습 때 `python3 lab.py ui`로 다시 연다.
