# 스프린트 4 — 발표 자료 점검 기록

점검일: 2026-10-24. 첨부 전사본 두 편을 끝까지 읽고 기존 `쿠버네티스 스프린트 4.md`의 4·5부와 대조했다. 1~3부는 이번 전사본의 범위에 포함되지 않아 내용 검증 대상으로 삼지 않았다.

## 최초 상태와 판단

**두 강의의 핵심 주제는 대부분 들어 있었다.** 특히 group_left 방향과 Failed 대상 drop의 한계를 교정한 설명도 이미 있었다. 다만 4·5부에는 그림이 없었고, 강의 진행 순서·긴 설정·교정 설명이 이어져 발표자가 핵심을 골라 말해야 했다.

개념 설명에서 실제로 실행할 코드로 이어지는 경로도 부족했다. 기존 `rate` 예시는 전사본에 없는 값을 결과에서 역산했고, CPU 식에 괄호가 반드시 필요하다는 설명은 적용 조건을 구분하지 않았다. 이 둘은 실제 엔진 평가로 다시 확인했다.

## 교정·보완한 설명

| 항목 | 오해 가능성이 있던 설명 | 반영한 설명·증거 |
| --- | --- | --- |
| 데이터 경로 | ServiceMonitor가 메트릭 중계처럼 보임 | 설정 경로와 HTTP 데이터 경로를 나눠 그림 1로 설명 |
| namespace | Prometheus와 다른 namespace이면 탐색 불가 | SM namespace와 Service namespace의 선택 조건을 구분; 실제 CR 확인 |
| release | release는 반드시 Helm 이름과 같아야 함 | 차트가 만든 셀렉터의 값에 맞추는 것; 고정된 프로토콜 규칙이 아님 |
| Operator | 모든 ServiceMonitor를 항상 감지함 | 감시 범위·RBAC·CR 선택 조건을 함께 확인 |
| CRD·CR | 설정 인스턴스와 리소스 종류 정의의 혼용 | Prometheus CR과 CRD를 용어 표에서 구분 |
| DOWN | 인증서 검증 생략이 일반 해결책처럼 보임 | `lastError`에 따라 HTTP·통신·인증·TLS 구분; 클라이언트 인증은 별도 |
| Failed drop | 종료 파드의 상태는 어떤 패널에서도 감지 불가 | 직접 수집 대상 drop과 별도 상태 exporter 분리; S6 |
| info 값 | 강의의 “값이 없어 기본 1” | exporter가 명시적으로 1을 생성; 소스 링크 |
| group_left | 강의의 “기준 쪽이 1” | 왼쪽이 다, 오른쪽이 키당 1; 기존 교정을 전면 그림·J2/E2로 강화 |
| 누락 | 왼쪽을 선택하면 모든 시리즈가 보존되는 듯함 | 산술 매칭에서 짝 없는 disk4 제외, `unless`로 탐지; J6 |
| 집계 | sum이 있으면 무조건 그 안에서만 조인 가능 | 집계 뒤 매칭 키가 남는지가 기준; J8~J9 |
| 파드 식별 | namespace 제거 후 pod 이름만 남겨 집계 | namespace·pod를 함께 보존, 동명 파드 충돌 재현; E4 |

## 검증 기록

- Prometheus/promtool **3.5.0**, macOS arm64에서 **29/29 통과**. 정상·빈 결과 17개, 의도한 오류 4개, 실제 scrape 8개다.
- 공식 바이너리 SHA-256 목록과 다운로드 파일의 해시를 대조했다. [실제 출력·해시](<자동 검증.md>)
- SVG 6개를 XML 파싱하고 `rsvg-convert -w 1350`으로 PNG 렌더링해 각각 직접 확인했다.
- Markdown의 상대 링크·이미지 경로, 접기 태그·코드펜스, Python 문법을 검사했다.
- 기존 1~3부의 본문은 그대로 보존했다. 이번 전사본으로 클러스터 업그레이드 절차의 정확성까지 검증한 것은 아니다.


## 직접 사용하는 기능 실습으로 변경

계산 결과를 맞히는 PoC 대신 [실습.md](실습.md)를 기본 진입점으로 만들었다. 준비만 `lab.py setup`으로 자동화하고, ServiceMonitor 생성·수정, Grafana 쿼리·범례 수정, Deployment·노드 라벨 변경은 사용자가 직접 한다. 기존 29개 검증은 [자동 검증.md](<자동 검증.md>)에 보존했다.

실제 환경은 macOS arm64, Docker Engine 27.4.0, kind 0.30.0의 Kubernetes 1.34.0 두 노드다. kube-prometheus-stack 77.6.0과 ingress-nginx 4.14.4를 설치했다. 사용자의 기존 kubeconfig는 변경하지 않고 전용 `.lab/kubeconfig`를 사용했다.

설치 점검 중 Operator의 webhook TLS 설정과 kubelet EndpointSlice 탐색 설정을 수정했다. 수정한 구성으로 전용 클러스터를 새로 생성해 설치 완료까지 확인했다. 이후 연속 설정 변경 시 reloader의 기본 재확인 간격으로 반영이 늦는 현상을 확인해, 고정한 Operator 버전의 config-reloader에 `--watch-interval=5s`를 적용하고 다시 검증했다. kubelet의 `syncFrequency`도 두 노드 모두 5초로 확인했다. 이는 빠른 반복 실습을 위한 로컬 설정이다. [reloader 공식 소스](https://github.com/prometheus-operator/prometheus-operator/blob/v0.85.0/cmd/prometheus-config-reloader/main.go), [컨테이너 설정 확장 API](https://prometheus-operator.dev/docs/api-reference/api/)

검증 중 원시 NGINX의 `namespace="apps"`가 수집 후 `exported_namespace="apps"`로 바뀌는 실제 라벨 충돌도 확인했다. 시작 요청 패널은 `ingress="portal"`로 선택하도록 수정하고, 실습서에 원시 출력과 수집 후 라벨을 비교하는 항목을 넣었다.

브라우저 자동화 연결을 사용할 수 없어 **Grafana UI를 클릭하며 화면 배치·Save as copy 동작을 검수하지는 못했다.** Grafana의 실제 대시보드·데이터소스와 쿼리 응답은 HTTP API로 확인했다. 노드 두 개는 같은 Docker VM을 공유하므로 실제 서로 다른 하드웨어 사양을 검증한 것은 아니다.


**실제 기능 검증: 22/22 통과.** [시나리오별 실제 관찰 결과](<lab/검증 결과.json>)

| 검증한 조작 | 실제 관찰 |
| --- | --- |
| ServiceMonitor 없음·틀린 release | 원시 요청 카운터 노출, job·활성 대상 없음 |
| 올바른 release | Operator 반영 뒤 실제 `:10254/metrics` 대상 UP |
| 틀린 port / port 생략 | 활성 대상 0개 / 여러 포트 대상과 UP·DOWN 혼재 |
| 틀린 path와 복구 | DOWN·HTTP 404 → UP |
| 틀린 Service namespace와 복구 | 대상 없음 → UP |
| 실제 CPU·노드 정보 조인 | 두 노드의 `nodename` 부착 |
| 실제 kubelet 메모리·KSM 파드 라벨 조인 | 전체 앱 3개 → frontend 2개 |
| api의 component 라벨 변경·복구 | 같은 쿼리에서 frontend 2개 → 3개 → 2개 |
| portal의 레플리카 변경·복구 | 같은 쿼리에서 frontend 2개 → 3개 → 2개 |
| worker의 resource 라벨 변경·복구 | high-spec 노드 1개 → 2개 → 1개 |
| Grafana 대시보드·데이터소스 | 실제 4개 패널 로드, Prometheus 연결 OK |

추가로 Grafana 데이터소스 질의 API를 통해 조인한 두 노드의 프레임 응답(HTTP 200)을 확인했다. 대시보드 사본의 생성·저장·조회도 API로 확인하고 임시 사본은 삭제했다. 이는 브라우저의 버튼 동작·가독성 검수와는 구분한다.

검증 뒤 앱은 portal 2개·api 1개(backend), worker는 low-spec으로 복구하고 `nginx-metrics` ServiceMonitor를 삭제해 1단계부터 시작할 상태로 돌려놓았다. 검증용 이력까지 없애기 위해 전용 실습의 Prometheus 임시 저장소를 새 파드로 초기화했다. 사용자가 이후 실습 중 설정을 바꿀 때는 과거 그래프 데이터가 남으므로 현재 Table·Targets를 기준으로 본다.
