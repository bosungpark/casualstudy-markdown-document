## 실행

저장소 루트에서:

```bash
python3 'infra/쿠버네티스 스프린트 4/run.py' all
```

첫 실행은 [공식 릴리스](https://github.com/prometheus/prometheus/releases/tag/v3.5.0)에서 **Prometheus 3.5.0**을 내려받아 해당 릴리스의 `sha256sums.txt`와 대조한다. 이 버전은 재현을 위한 고정 버전이며 최신 버전을 뜻하지 않는다. macOS·Linux의 arm64·amd64를 지원한다.

바이너리는 Python의 임시 폴더 아래 `sprint4-prometheus/`에 캐시한다. 이미 준비한 파일을 쓰거나 오프라인으로 발표할 때는:

```bash
# prometheus와 promtool 두 실행 파일이 들어 있는 디렉터리
PROM_DIR=/absolute/path/to/prometheus-directory \
  python3 'infra/쿠버네티스 스프린트 4/run.py' all
```

사용자 지정 `PROM_DIR`은 다운로드·체크섬 확인을 건너뛴다. 동일 결과를 재현하려면 공식 3.5.0 바이너리를 사용한다. Python 3.8 이상이 필요하다.

주제별로 실행하려면 마지막 인자를 바꾼다.

```bash
# 수집 서버를 띄우지 않는 결정적 입력 실험: 21개
python3 'infra/쿠버네티스 스프린트 4/run.py' promql

# 실제 HTTP 수집·대상 제외·라벨 충돌 실험: 8개
python3 'infra/쿠버네티스 스프린트 4/run.py' scrape
```

## 실험 구성과 실제 결과

| 시나리오 | 입력·변경 | 실제 확인 | 개수 |
| --- | --- | --- | ---: |
| J1~J7 | 디스크 4개, VM 정보 2개, 중복 VM 정보 | 기본 매칭 빈 결과, 정상 조인은 3개, 덧셈은 +1, 누락 disk4=400, 중복 vm1=2 | 7 |
| J8~J9 | 파드별 컨테이너 120·30, 집계 위치 변경 | 필터 후 합은 150, pod 키 제거 후 조인은 빈 결과 | 2 |
| J10~J13 | CPU 스칼라 뺄셈 / 두 메모리 벡터 뺄셈 | CPU는 괄호 유무와 무관하게 약 0.2; 메모리 뺄셈은 빈 결과 대 600 | 4 |
| R1~R4 | 0·30·60초의 counter 10·20·35, 별도 reset 입력 | 60초 창 샘플 2개, rate 0.5 대 0.4167, reset 보정 0.25 | 4 |
| E1~E4 | group 생략·group 방향 반전·오른쪽 중복·namespace 생략 | 각 질의가 예상한 중복·다중 매칭 오류로 거부됨 | 4 |
| S1~S5 | 정상 HTTP·404·대상 drop·미등록 job | `up=1` / `up=0` / 현재 시리즈 없음, Targets 오류·drop 개수 | 5 |
| S6 | 종료 대상을 제외하면서 다른 exporter는 Failed 상태 제공 | 제외한 대상의 up 없음, `kube_pod_status_phase{phase="Failed"}=1` | 1 |
| S7~S8 | exporter의 pod와 대상의 pod가 충돌 | false는 `exported_pod` 보존, true는 exporter 라벨 사용 | 2 |
| 합계 | 정상·빈 결과·의도한 오류 모두 포함 | **29/29 통과** | **29** |

`promql` 실험은 `promtool test rules`에 고정한 입력과 평가 시각을 전달한다. 성공 질의는 전체 결과 라벨·숫자 값을 비교한다. 오류 질의는 종료 코드가 실패인지, 기대한 오류 문자열이 있는지 확인한다. Python으로 PromQL을 흉내 낸 계산기가 아니다.

`scrape` 실험은 임시 Python HTTP exporter와 Prometheus를 **127.0.0.1의 빈 포트**에 띄운다. 실제 HTTP 요청·시계열 저장·질의를 수행한다. target relabel의 입력은 Kubernetes 메타데이터 대신 `discovered_phase`라는 합성 라벨로 제공한 뒤 제거한다. 실패한 HTTP 요청은 방화벽·TLS 대신 재현이 쉬운 **404 응답**을 사용한다.

실행 후 성공·실패 모두 서버를 종료하고 임시 TSDB를 정리한다. 다운로드 캐시는 남는다. 클러스터 설정을 수정하거나 이미 실행 중인 서비스를 중단하지 않는다.

## 검증한 것과 범위 밖

| 구분 | 범위 |
| --- | --- |
| 실제 엔진으로 실행 | PromQL 매칭·값·결과 라벨·중복 오류·빈 결과·rate·reset, target drop, HTTP 수집 성공·실패, honor_labels |
| 공식 문서·소스로 대조 | ServiceMonitor 선택·namespace·포트 의미, CR과 CRD의 차이, exporter의 info 값 1 |
| 실행하지 않음 | Kubernetes API 탐색, 실제 ServiceMonitor 선택·Operator 재조정·RBAC, Helm 배포, NGINX, kube-state-metrics 프로세스, 실제 TLS·방화벽, Grafana UI |

S6의 `kube_pod_status_phase`는 합성 exporter가 실제 이름·라벨로 내보낸 값이다. 이 실험은 **서로 다른 수집 대상의 분리**를 확인한다. kube-state-metrics가 Kubernetes API를 읽는 동작을 실행한 것은 아니다.

## 발표에서 보여 줄 순서

1. 4부 그림으로 “설정 경로와 데이터 경로가 다름”을 설명한다.
2. `scrape` 출력 S1~S5로 `1 / 0 / 없음`의 차이를 보여 준다.
3. 5부 그림과 `promql` 출력 J2·E2로 group_left의 정상·실패를 비교한다.
4. J8~J9로 집계 뒤 사라진 `pod` 키를 찾는다.
5. 시간이 남으면 R1~R3의 `1m / 61s`를 보여 주고, 창 경계를 질문한다.

오프라인 발표 전에는 바이너리를 한 번 받아 둔다. 로컬 서버 실행이 제한된 환경에서는 `promql`만 실행하고, `scrape`는 아래 검증 기록을 보여 줄 수 있다.
