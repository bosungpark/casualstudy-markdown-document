## 들어가며 — 서비스가 어려운 이유

- 서비스는 **대충 이해하고 쓰기는 쉽다.** 속성값만 제대로 넣으면 알아서 잘 동작한다.
- 문제는 **내가 이해한 대로 동작하지 않을 때 원인을 알기가 정말 어렵다**는 것이다.
- 예를 들어 NodePort 타입 서비스를 만들고 외부에서 호출했는데 파드로 트래픽이 안 들어온다면? 이 기능들은 속성값만 맞으면 정상 동작해야 하므로 대개 원인은 **YAML의 오타**다. 그런데 서비스는 타입과 기능이 여러 갈래라, 단순 오타가 아니라 **각 기능의 옵션 값을 잘못 주는** 실수가 나온다.

### 이번 섹션의 목표

> NodePort 서비스를 만들었을 때, **VM의 그 포트에서 파드까지 이어지는 연결고리를 하나씩 짚어볼 수 있는 능력**을 기르는 것.

인프라 구조를 머릿속에 그려 두고, 뭔가 안 될 때 그 연결고리를 따라가며 문제 지점을 좁혀 나가는 방식. 강사는 이것이 곧 **주니어와 시니어의 문제 해결 방식 차이**라고 본다.

### 같은 내용을 세 번 반복한다

서비스는 영역이 넓고 기능들이 서로 엮여 있어서, 애매하게 끊어 설명하면 오히려 이해가 안 된다. 그래서 소화가 안 되더라도 전체 그림을 한 번 쭉 훑은 뒤, 관점을 바꿔 두 번 더 반복하는 구조로 간다.

| 순서 | 보는 관점 | 이 문서의 위치 |
|------|-----------|----------------|
| ① | 스펙(속성) — 어떤 기능이고 왜 쓰는지 | 1부 |
| ② | 인프라 구성 — 실제로 어떻게 연결돼 동작하는지 | 2부 |
| ③ | 실습 — 눈으로 확인하며 디테일 보강 | 3부 |

1부가 잘 이해되지 않아도 **반복해서 볼 필요는 없다.** 바로 2부로 넘어가면 훨씬 쉽게 잡힌다.

# 1부. 서비스 스펙 — 어떤 기능이 있고 왜 쓰는가

## 셀렉터 뒤에 있는 Endpoint 오브젝트

셀렉터가 파드의 레이블과 매칭되면 그 파드들로 로드밸런싱된다는 것까지는 이미 안다. 한 단계 더 들어가면 `Endpoint`라는 오브젝트가 있다.

| 특징 | 내용 |
|------|------|
| 생성 | 서비스를 만들면 **자동으로** 생성 |
| 이름 | **항상 서비스와 동일한 이름** |
| 핵심 속성 | `subsets.addresses` — 연결된 **파드들의 IP**를 관리 |

> 엔드포인트에 IP가 들어 있어야 서비스로 들어온 트래픽이 파드로 간다. 이게 **서비스 레지스트리** 기능의 정체다.

Kubernetes가 셀렉터에 매칭되는 레이블을 가진 파드를 대상으로, 새 파드가 생기면 IP를 추가하고 삭제되면 제거해 준다.

### 등록 조건은 Readiness Probe다

- 정확히는 파드가 만들어지고 **Readiness Probe가 200 OK를 받았을 때** 엔드포인트에 등록된다. 즉 Kubernetes는 레이블뿐 아니라 **파드의 상태까지 확인한 뒤** IP를 넣는다.
- 등록 이후에도 부하로 Readiness가 실패하면 **IP를 뺐다가, 성공하면 다시 넣어** 준다.
- 반면 **Liveness Probe가 실패하면 파드를 재기동**시켜 버린다.

> 그래서 Probe 설정과 헬스체크 URL을 만들 때 이 차이에 부합하는지 확인해야 한다. 내가 아는 만큼 작업의 디테일이 달라진다.

### 대시보드가 파드 IP를 보여준 이유

대시보드에서 서비스를 조회하면 파드 IP들이 나왔지만, **서비스 속성 자체에는 파드 정보가 없다.** 대시보드가 서비스를 조회한 뒤 같은 이름의 엔드포인트를 추가로 찾아서 파드 IP를 함께 보여준 것이다.

## 타입 ① ClusterIP

타입 속성을 주지 않으면 기본값으로 들어간다.

- `clusterIP` 속성에 **서비스의 IP가 할당**되고, 누군가 이 IP로 트래픽을 보내면 **가지고 있는 엔드포인트 IP로 포워딩**한다.

| 포트 속성 | 의미 |
|-----------|------|
| `port` | 서비스의 포트 |
| `targetPort` | 파드(컨테이너)의 포트 |

- 다른 파드에서는 **서비스 이름만으로도** 호출할 수 있다(포트가 80이면 생략). Kubernetes가 내부 DNS 서버에 서비스 이름과 IP를 자동 등록하기 때문이고, 이걸 **Service Discovery**라고 부른다.
- **Kubernetes 내에서 파드로 통신하기 위한 가장 중요한 타입.**

## 타입 ② NodePort

- 노드 포트를 수동으로 지정할 수 있고, 명시하지 않으면 정해진 대역(`30000~32767`)에서 자동 할당된다.
- 워커노드의 그 포트로 트래픽을 날리면 서비스 IP·포트와 매칭되고, 로드밸런싱되어 파드로 들어간다.
- NodePort로 만들면 워커노드에 새 포트가 생기면서 **ClusterIP 역할도 함께 추가**된다. 그래서 내부 통신용으로도 쓸 수 있다.

실습에서는 정말 많이 썼지만 **실무 운영 환경에서는 거의 쓸 일이 없다.** 정확히는 이 포트가 필요 없다는 게 아니라, **이 포트로 직접 API를 날리지 않는다**는 뜻이다. 대신 로드밸런서를 쓴다.

## 타입 ③ LoadBalancer

- 이 타입으로 만들면 **새로운 IP가 생성**되고 **NodePort의 역할도 포함**한다.
- 이 IP로 호출하면 워커노드 IP의 NodePort로 포워딩되어 결국 파드로 통신이 된다.

> 실무에서 클러스터 외부에서 내부로 트래픽을 보내야 할 때는 **무조건 로드밸런서를 만들고 이 IP로 통신한다**고 보면 된다.

기능만 놓고 보면 NodePort가 더 깔끔해 보일 수도 있다. 왜 로드밸런서를 쓰는지는 2부에서 인프라 구성을 보면 자연스럽게 이해된다.

## 타입 ④ ExternalName

- 이 타입으로 만들면 `externalName` 속성에 **DNS 이름**을 넣는다.
- 파드가 이 서비스를 호출하면 인프라 외부 DNS로 포워딩되어, 그 도메인의 IP 주소를 알아내고 그 주소로 통신하게 해 준다.

다른 타입들은 **파드로 트래픽을 보내기 위한** 용도인데, 이건 **파드에서 밖으로 나가기 위한** 용도다. 방향이 반대다.

### 왜 굳이 서비스를 경유시키나

여러 파드 내부에 `github.com` URL이 박혀 있다면, 코드 저장소가 다른 것으로 바뀌었을 때 파드는 건드리지 않고 **이 서비스만 수정**하면 된다. IT에서 익숙한 패턴이라 유용해 보인다.

### 그런데 HTTPS에서 막힌다

```
파드 → (ext-github 라는 이름으로 DNS 질의) → 서비스 경유 → 공인 DNS → github.com IP 획득
     → 그 IP로 통신 시도
     → HTTPS는 "클라이언트가 보낸 도메인 이름"을 확인함
     → GitHub 입장: 날아온 DNS 명이 ext-github ??? → 변조 의심 → 신뢰 불가
```

- HTTP라면 문제없지만 **HTTPS에서는 이 기능을 쓸 수 없다.** 그리고 외부로 나가는 통신은 통상 HTTPS다.
- 결국 ExternalName은 **의도는 좋지만 실제로 쓸 일이 별로 없다.**

## 타입이 아닌 별도 속성: externalIPs

서비스 스펙에 **워커노드의 IP를 지정**하면, 지정한 IP의 노드를 통해 내부 파드와 통신할 수 있다. 목적(외부 → 내부)은 NodePort와 같지만 차이가 있다.

| | NodePort | externalIPs |
|---|---|---|
| 포트가 열리는 노드 | 클러스터의 **모든 노드** | **내가 선택한 노드만** |
| 포트 범위 | 제한 있음 (`30000~32767`) | **제한 없음** |
| 쓰는 포트 | 별도의 `nodePort` | 서비스에 준 **`port`가 곧 워커노드 포트** → 80/443 가능 |

- **타입과 별개의 속성**이라, 어떤 타입을 선택했더라도 추가로 붙일 수 있다.
- NodePort 대역과 똑같이 줄 수도 있지만 굳이 그럴 필요는 없다.

**언제 쓰나.** NodePort와 마찬가지로 학습·테스트 용도다. 특히 외부에서 내부로 들어오는 연결을 80이나 443으로 해야 할 때. IP를 지정할 수 있다는 점은 메리트가 크지 않은데, 워커노드 IP는 노드가 바뀌면 달라질 수 있고 한 노드로만 트래픽이 들어오는 게 골고루 들어오는 것보다 나을 것도 없기 때문이다. 그래서 **차라리 NodePort를 쓰는 편이 낫다.** 현실적인 용도는 ClusterIP 타입 서비스가 이미 있는데 잠깐 클러스터 밖에서 파드로 통신해야 할 때 이 속성만 추가하는 정도다.

## Headless 서비스 (`clusterIP: None`)

ClusterIP는 자동 생성되니 읽기 전용 속성처럼 보이지만, `None` 값을 직접 넣어서 만들 수 있다. 이렇게 만든 서비스를 **Headless 서비스**라고 부른다. 말 그대로 머리(서비스 IP)가 없다.

| | 일반 ClusterIP | Headless |
|---|---|---|
| 서비스 IP | 생성됨 | **생성 안 됨** |
| 이름으로 DNS 질의하면 | 서비스 IP | **연결된 파드들의 IP 리스트** |
| 통신 경로 | 서비스 IP → 파드 | 클라이언트가 **파드 IP로 직접** |

### 쓰임새 1. 파드 IP 리스트가 필요할 때

마이크로서비스 아키텍처에서는 전체 트래픽을 줄이기 위해 **파드 스스로가 상태 변화 시 수집 서버로 노티**하는 방식이 낫다. (그래서 앱이 자기 IP를 알아내려고 kube-apiserver에 API를 날리는 실습을 했었다.)

그런데 파드가 상태를 못 넘기고 죽을 수도 있으니, 수집 서버 쪽에서도 각 파드 상태를 직접 확인할 필요가 있다. kube-apiserver로 엔드포인트를 조회하면 파드 IP를 알 수는 있지만 통신이 번거롭고, 리소스 조회는 보안 문제로 권한도 따로 줘야 한다.

파드 IP만 알아내는 게 목적이라면 **Headless 서비스를 붙이고 서비스 이름으로 DNS 질의하면 끝**이다. 받은 IP 리스트로 for문을 돌리면 전체를 한 번씩 호출할 수 있다.

다만 수집 서버를 직접 만들 일은 별로 없다. 이건 "Headless를 쓰면 DNS로 파드 IP 리스트를 받는다"는 특징을 설명하기 위한 사례다. 진짜 자주 쓰는 곳은 아래다.

### 쓰임새 2. StatefulSet 데이터베이스

먼저 백엔드 서버와 데이터베이스의 차이부터.

| | 백엔드 서버 | 데이터베이스 |
|---|---|---|
| 성격 | **Stateless** 앱 | **Stateful** 앱 (파드마다 상태가 있음) |
| 컨트롤러 | Deployment | **StatefulSet** |
| 파드 이름 | 난수가 붙음 (쓸 일 없으니 상관없음) | `db-0`, `db-1` **시퀀셜** |
| 트래픽 분산 | 랜덤해도 무방 (모두 같은 역할) | **아무 파드로나 가면 안 됨** |
| 붙이는 서비스 | ClusterIP | **Headless** |

DB는 0번이 읽기·쓰기를 담당할 때 1번은 읽기 전용으로만 동작할 수 있다. 백엔드에서 쓰기를 할 땐 무조건 `db-0`으로 가야 한다. StatefulSet에 `clusterIP: None` 서비스를 붙이면 **파드를 지정해서 DNS를 호출**할 수 있다.

```
<파드이름>.<서비스이름>      예) db-0.db-service, db-1.db-service
```

백엔드 서버에는 이 두 도메인을 DB 연결 대상으로 등록해 두면, **라이브러리가 역할에 맞는 파드로 알아서 연결**한다.

> 여기까지는 기능과 이유만 본 것이라 실체를 몰라 뜬구름 같을 수 있다. 이 상태로 넘어가면 설정대로 동작하지 않을 때 뭘 봐야 할지 막막해진다.

# 2부. 인프라 구성으로 본 서비스의 실체

> 이번 스프린트가 지상편의 마지막이다. 다음 스프린트는 해수편, Kubernetes 관리자를 위한 내용이고 그때는 클러스터를 직접 설치한다.

## 클러스터에 깔려 있는 것들

```
[마스터 노드]  Kubernetes 주요 컴포넌트 (+ CoreDNS)
      │  (워커노드를 join)
[워커 노드들]  ← kube-proxy 처럼 "모든 노드에" 설치되는 컴포넌트가 있음
                ← Calico(CNI)의 프록시 모듈도 모든 워커노드에 존재
```

| 컴포넌트 | 담당 | 실체 |
|----------|------|------|
| **kube-proxy** | 서비스 네트워크 | **리눅스 iptables** |
| **Calico (CNI)** | 파드 네트워크 | 파드 네트워크 대역을 만들고 파드에 IP 할당 |

- 서비스가 만들어지거나 변경될 때마다 Kubernetes는 **kube-proxy를 이용해 각 노드의 iptables를 조작**한다.
- 파드는 Calico가 만든 대역에서 IP를 받고, 파드 간 통신도 이 네트워크 안에서 이뤄진다. 파드가 서로 다른 워커노드에 있어도 Calico 프록시 모듈이 모든 워커노드에 있으므로 잘 전달된다.

## ClusterIP의 실체 — 엔드포인트는 iptables 룰이다

```
서비스 생성 → kube-proxy가 "모든 노드"의 iptables에 룰 등록
              "서비스 IP로 온 트래픽은 → 이 파드 IP들로 보내라"
파드 하나 죽음 → 그 룰에서 해당 파드 IP 삭제
```

- 이 룰은 **엔드포인트의 `addresses` 그대로** 만들어진다. 즉 **엔드포인트의 실체는 iptables에 있는 룰**이고, 이게 서비스 레지스트리다.
- 파드에서 서비스 IP를 호출하면 모든 트래픽은 일단 iptables로 가고, 룰에 따라 파드로 전달된다. 따라서 **로드밸런싱을 하는 주체도 iptables**다.
- iptables의 분배 방식은 **라운드 로빈**이고, iptables를 쓰는 한 이 방식은 바꿀 수 없다. 다만 파드 네트워크를 Calico가 아닌 다른 플러그인으로 교체할 수 있듯, **서비스 네트워크의 구현체도 iptables가 아닌 다른 것으로 바꿀 수는 있다.**

## NodePort의 실체 — kube-proxy + iptables

```
모든 노드에 포트 생성
  → 그 포트로 들어온 트래픽은 각 워커노드의 iptables로 진입
  → 이후는 ClusterIP가 하던 역할 그대로  (그래서 "ClusterIP가 추가됐다"고 표현)
  → 파드가 어느 노드에 있는지는 Kubernetes가 이미 알고 있으므로
    kube-proxy가 해당 노드로 라우팅
```

## LoadBalancer — 원래 인프라에서는 이렇게 만든다

Kubernetes를 잠깐 잊고, 기업 내부 인프라 장비부터 보자.

| 장비 | 역할 |
|------|------|
| **라우터** | 인터넷 외부 사용자가 인프라 안으로 통신할 수 있게 해 주는 장비 |
| **게이트웨이** | 인프라 내부 네트워크를 생성 (대역 설정 → 서버 연결 → 그 대역에서 IP 할당·상호 통신) |

이 상태에서 외부 사용자에게 클러스터 안의 서비스를 오픈하려면:

```
① 라우터에 이 서비스를 위한 "외부 전용 IP"를 하나 생성
② 로드밸런서를 구축하고, 트래픽이 들어올 수 있도록 라우터에 설정
③ 로드밸런서가 모든 워커노드의 NodePort로 연결
→ 모든 노드로 트래픽이 분산되면서 내 파드로 들어옴
```

> **이 구성을 자동으로 만들어지게 하는 것이 LoadBalancer 타입 서비스다.**

### 클러스터 외부 장비를 서비스로 만들 수 있는 이유

NodePort까지는 Kubernetes가 직접 관리하는 영역이지만 로드밸런서는 클러스터 밖에 있다. 어떻게 이게 가능할까? **CNI에 Calico를 끼운 것과 같은 원리**다.

Kubernetes 자체가 모든 기능을 제공하지는 않지만, **외부 플러그인을 연결할 수 있고 그 기능을 쓸 인터페이스(리소스)를 제공**한다. Calico는 파드로 만들어져 있어 클러스터 내부에 있을 뿐이고, 로드밸런서는 밖에 있더라도 `type: LoadBalancer`라는 인터페이스와 Kubernetes 문서의 구현 방법이 있으니 **그대로 만들면 어떤 제품이든 호환**된다. 클라우드 환경이라면 각 CSP가 자사 로드밸런서로 이 구성을 이미 구현해 뒀다.

지금 실습 환경에는 구현체가 없다. 그래서 서비스를 조회하면 **EXTERNAL-IP가 `<pending>`**으로 뜬다. 로드밸런서로 들어오는 흐름은 없지만 **NodePort가 플러스되어 있으므로 그 아래는 정상 생성**된다.

## 퍼블리싱 3종, 언제 무엇을 쓰나

| 방식 | 용도 | 이유 |
|------|------|------|
| **LoadBalancer** | **운영 표준.** 외부 사용자든 인프라 내 다른 내부 서버든, 클러스터 밖에서 안으로 들어오는 통신은 전부 여기로 | 노드 장애·변경과 무관, 워커노드 IP 비공개, 트래픽 골고루 분산 |
| **NodePort 다이렉트** | 테스트용 임시 사용 | 특정 워커노드를 찍어 통신하면 ① 노드 장애 시 통신 불가 ② 노드가 아예 바뀔 수 있음 ③ 워커노드 IP 공개 자체가 보안에 안 좋음 ④ 한 노드로 트래픽 집중 |
| **externalIPs** | 테스트용이되, 포트 제약이 없어 **보안 포트(443)로 접속해야 할 때** 유용 | 결국 임시용. 로드밸런서로도 443을 열 수 있으니 실제 운영 퍼블리싱은 역시 로드밸런서 |

## 문제 해결 방식이 달라진다

로드밸런서 타입 서비스를 만들고 그 IP로 호출했는데 파드로 트래픽이 안 간다면:

```
① 서비스 이름으로 엔드포인트 조회
     → 파드 IP가 안 보인다? → 서비스의 셀렉터를 잘못 넣은 게 아닌지 의심
② 서비스 이름으로 iptables 조회
     → 룰이 제대로 들어갔는지 (여기서 문제 날 일은 거의 없음)
③ 해당 포트로 트래픽 덤프(tcpdump)
     → 데이터가 실제로 흘러들어오고 있는지 확인
④ 여기까지 정상이면 → 로드밸런서 설정을 의심
```

이렇게 **어느 영역에서 문제가 생겼는지 범위를 좁혀 나갈 수 있게 된다.**

이걸 알아야 하는 이유가 하나 더 있다. 앞으로 수많은 오픈소스를 설치하게 되는데, 아무리 구성이 복잡해도 **Kubernetes에서는 이 서비스들이 기본이고 그것들로 다 만들어졌기 때문에** 대부분의 통신 구조를 분석할 수 있다. 강사도 처음 보는 오픈소스라도 통신 구조를 이해하는 데는 부담을 느끼지 않는다고 한다.

## CoreDNS와 그 위의 DNS 계층

Kubernetes 기본 컴포넌트로 **CoreDNS**가 있고, 여기에 서비스 이름과 할당된 IP가 자동 등록된다. 파드는 서비스 이름만 알고 있으므로, 앱이 DNS에 질의해 IP를 확인하고 그 IP로 통신한다. 도메인 통신에서는 자동으로 되는 흐름이라 평소엔 DNS를 신경 쓸 일이 없지만, **Kubernetes에서는 DNS 활용법이 다양해서 알아둘 필요가 있다.**

### ClusterIP 이름 호출 vs Headless 이름 호출

Headless 서비스는 DNS에 서비스 이름으로 **파드 IP 리스트**가 등록된다. 그래서 ClusterIP 서비스 이름으로 호출하든 Headless 서비스 이름으로 호출하든, **결과적으로 두 파드 중 한 곳으로 트래픽이 간다.** 결론은 같아 보여도 **과정의 차이는 엄청나다.**

| | ClusterIP 이름 호출 | Headless 이름 호출 |
|---|---|---|
| DNS가 주는 것 | 서비스 IP 하나 | 파드 IP 리스트 |
| 로드밸런싱 주체 | **iptables가 알아서** | **클라이언트** (받은 IP 중 첫 번째로 날림) |
| 클라이언트 부담 | 없음 | **통신 라이브러리에 그 기능이 있는지 체크해야 함** |

> Headless 서비스의 도메인 이름을 통신용으로 쓰면 안 된다. **도메인 이름으로 통신할 때는 반드시 ClusterIP 타입을 쓴다.**

이런 걸 알고 쓰면, 인프라 환경이 좋아진 만큼 개발은 로직에만 더 집중할 수 있다.

### 그래도 Headless를 꼭 써야 하는 곳

**StatefulSet으로 만든 데이터베이스에는 Headless 서비스를 무조건 붙여야 한다.** 서비스 이름이 `db`라면 연결된 파드 리스트도 똑같이 나오지만, 추가로 **`<파드이름>.<서비스이름>` 도메인에 해당 파드의 IP가 별도로 등록**되기 때문이다. 백엔드 서버는 이 도메인들을 모두 등록해 두고, DB마다 역할이 다르니 연결 라이브러리가 역할에 맞는 도메인을 호출한다.

### ExternalName이 걸리는 지점, 그리고 남는 교훈

```
파드 → CoreDNS: "ext-github 주소 줘"
       CoreDNS: ext-github → github.com 으로 포워딩
                github.com IP는 나도 모름 → 상위(외부) DNS 서버에 질의
```

인프라 관점에서 DNS는 이렇게 계층을 이룬다.

```
[파드] → [CoreDNS] → [사내망 DNS 서버] → [인터넷 공인 DNS 서버]
```

- Kubernetes에는 CoreDNS가 기본 탑재되지만, **기존 인프라의 서버들끼리 도메인으로 통신하려면 사내망에 DNS 서버를 따로 구축**해야 한다. 기업 내부에서 자체 도메인 룰을 정하고 서버 IP를 등록해 쓴다.
- 그 사내 DNS가 **외부 공인 DNS에도 연결돼 있어야** 인터넷 도메인의 IP를 가져올 수 있다.
- 따라서 **Kubernetes를 설치할 때 CoreDNS를 사내 DNS에 연결해 놔야** 파드에서 사내 도메인과 인터넷 도메인을 모두 해석할 수 있다.

ExternalName 자체는 (1부에서 본 대로) HTTPS 도메인 검증에서 막힌다. 사내 내부 서버와 HTTP로 통신한다면 문제없지만, 강사도 유용하게 쓰는 사례는 별로 못 봤다.

> 💡 ExternalName은 "이런 게 있다" 정도만 알면 되고, **이걸 설명하려고 짚은 DNS 서버 간 연결 구성을 아는 게 훨씬 중요하다.**

어디에 써먹나. 프로젝트 초기에는 Kubernetes 설치 담당자가 사내 DNS 연결을 깜빡할 수 있고, 사내 DNS에 내부 서버 도메인이 아직 등록되지 않았는데 인프라 담당자가 바빠 처리가 늦어질 수도 있다. **DNS 구조를 알고 있으면** 파드에서 사내 서버로 DNS 호출이 안 될 때 어느 부분이 문제인지 짚어서 담당자에게 명확히 요청할 수 있다. 나아가 파드에서 직접 DNS를 설정해 임시로 통신되게 만들 수도 있다. 인프라 작업을 기다리지 않고 바로 테스트해서 내 개발 일정을 지키는 것이다.

> 서비스에는 여기서 다루지 않은 기능들이 더 있고 마찬가지로 잘 안 쓰는데, **왜 안 쓰는지가 오히려 중요하다.** 다만 Ingress를 알아야 설명이 되므로 다음 섹션까지 공부한 뒤 맨 마지막에 따로 다룬다.

# 3부. 실습

확인할 것은 네 가지다. 타입별 서비스를 만들고 **특징대로 포트가 만들어졌는지 API를 날려보고**, **엔드포인트에 파드 IP**가 들어 있는지 보고, **iptables에 룰**이 들어갔는지 대조하고, **포트를 모니터링**해 트래픽이 실제로 들어오는지 본다. 이어서 DNS 질의를 네 가지 방식으로 해 보고, 마지막으로 파드부터 공유기까지 DNS 설정을 따라간다.

배포는 Jenkins 파이프라인으로 해도 되고, 이번에는 마스터 서버에서 YAML을 직접 붙여넣어 배포했다.

## 서비스 목록 확인

`kubectl get svc`로 조회하면 타입별로 이름을 준 서비스들이 보인다.

> External IP Service는 **별도의 타입이 아니다.** ClusterIP 타입에 `externalIPs`로 마스터 노드 IP를 추가해 준 것이다.

## 퍼블리싱 — 타입별로 API 날려보기

| 대상 | 확인 결과 |
|------|-----------|
| **NodePort** | YAML에 포트 번호를 직접 넣어준 것. 클러스터 외부에서 `워커노드IP:노드포트`로 API 전송 성공 |
| **LoadBalancer** | 구현체가 없어 EXTERNAL-IP가 `<pending>`. 그래도 **NodePort는 자동 생성**돼 있어 그 포트로 날리면 잘 전달됨 |
| **externalIPs** | 별도의 노드 포트 없이 **서비스의 `port`(여기선 80)를 그대로** 사용. 포트를 아예 생략하거나 `:80`을 줘도 API가 잘 날아감 |

## 엔드포인트와 iptables 룰 대조

```bash
kubectl get endpoints -n <namespace>
```

서비스 4개가 모두 같은 파드에 연결돼 있어 파드 IP가 전부 동일하게 나온다. DB용 서비스만 다른 파드에 연결돼 있어 IP가 다르다.

이 엔드포인트가 정말 iptables에 들어가 있는지 확인한다.

```bash
sudo iptables -t nat -L -n | grep <service-name>
```

출력이 복잡하지만 `TCP to ...` 뒤의 IP들만 보면 된다. **엔드포인트에 있던 파드 IP와 정확히 일치**한다. 서비스를 만들고 파드에 연결될 때마다 kube-proxy가 iptables에 룰을 만들어 주기 때문에 실질적인 물리 통신이 가능한 것이다.

## NodePort는 netstat에 안 잡힌다

그림상으로는 워커노드에 포트가 리스닝돼 있고, 그 포트를 지나 iptables로 가는 것처럼 보인다. 확인해 보면:

```bash
apt install net-tools            # 리스닝 포트 조회용
netstat -anp                     # 리스닝된 모든 포트
netstat -anp | grep <nodePort>   # → 아무것도 안 나옴
```

> ⚠️ 리스닝 포트가 없다고 해서 **NodePort가 안 만들어진 게 아니다.** 예전에는 kube-proxy가 이 포트를 리스닝시켜 줘서 조회가 됐지만, Kubernetes 버전이 올라가면서 **포트 정보가 iptables 안에 포함**되도록 바뀌었다.

```bash
sudo iptables -t nat -L KUBE-NODEPORTS -n | grep <service-name>
```

여기에 포트가 그대로 있다.

## tcpdump로 트래픽 유입 확인

```bash
apt install tcpdump
ip addr                          # 마스터 노드의 인터페이스 확인
                                 # → API를 날릴 IP에 해당하는 인터페이스를 찾는다 (예: eth1)
tcpdump -i eth1 port <포트>       # 모니터링 대기
```

다른 창에서 그 포트로 트래픽을 날리면 날릴 때마다 덤프에 찍힌다. **아무것도 안 찍힌다면 로드밸런서 쪽에 문제가 있는지** 확인하면 된다.

## DNS 질의 ① ClusterIP

구성은 이렇다. Deployment 파드에 ClusterIP 서비스, StatefulSet(`database`) 파드에 Headless 서비스가 붙어 있고 모두 같은 네임스페이스다. 여기에 `init` 파드를 하나 만들어 CoreDNS에 질의한다.

CoreDNS에 실제로 등록되어 있는 이름은 이 형태다.

```
<서비스이름>.<네임스페이스>.svc.cluster.local
                              └ svc = service 의 약어
```

```bash
kubectl exec -it init -n <ns> -- /bin/bash   # nslookup 등 통신 라이브러리가 설치돼 있음
nslookup <service-name>
```

- `Server` — DNS 서버(CoreDNS)의 IP
- `Name` — 위의 풀 도메인 형태
- `Address` — 해당 서비스의 ClusterIP

curl로는 세 가지 형태가 모두 동작한다.

| 형태 | 언제 쓰나 |
|------|-----------|
| `<서비스이름>` | 같은 네임스페이스의 서비스를 호출할 때 |
| `<서비스이름>.<네임스페이스>` | 다른 네임스페이스 호출 시 **필수**, 그리고 이게 **권장** |
| `<서비스이름>.<ns>.svc.cluster.local` | 다른 클러스터의 서비스를 호출할 때 |

- 권장 이유는, 나중에 클러스터에 앱이 많아지면 앱마다 네임스페이스가 달라지기 때문이다. 같은 네임스페이스끼리 호출하더라도 애초에 이 포맷으로 통일하는 게 혼동이 없고 깔끔하다.
- 풀 도메인은 — 다른 클러스터의 서비스를 호출할 땐 보통 그 서비스만 로드밸런서로 오픈하므로 직접 줄 일이 거의 없다. 그래도 장점은 있는데, `ndots` 항목에서 설명한다.

호스트네임을 반환하는 API를 여러 번 날리면 두 파드로 번갈아 응답한다. **iptables가 로드밸런싱**해 준 것이다.

## DNS 질의 ② Headless

```bash
kubectl get svc <headless-svc> -n <ns>
```

타입은 ClusterIP지만 **CLUSTER-IP가 `None`이고 포트도 없다.**

```bash
nslookup <headless-svc>     # 서비스 IP 대신 "파드들의 IP"가 나온다
```

> Headless 도메인으로 curl 할 때는 **포트를 반드시 명시**해야 한다. 헤드리스는 서비스 포트가 없고 파드 IP를 받아 바로 파드로 날리는 것이므로, 여기 주는 포트는 **파드(컨테이너)의 포트**다.

호스트네임 API를 여러 번 날리면 로드밸런싱이 되는 것처럼 보인다. 그런데 curl 자체는 DNS가 IP를 여러 개 줘도 **첫 번째 IP로만** 날린다. `nslookup`을 여러 번 반복해 보면 답이 나온다. **날릴 때마다 CoreDNS가 첫 번째 Address를 다르게 준다.** IP 리스트 순서를 순환시키고 있었던 것이다.

> ⚠️ 이건 DNS 서버 설정에 따라 다르다. IP를 순환해서 주지 않으면 한 IP만 계속 앞에 나와 **그 파드로만 호출**된다. Headless 서비스로 API를 날리는 건 최대한 지양할 것.

## DNS 질의 ③ StatefulSet 파드 지정

```bash
kubectl get pods -n <ns>
# StatefulSet 이름이 database → 파드 이름은 database-0, database-1 (시퀀셜)

nslookup database-0.<headless-svc>   # database-0 파드의 IP만 나옴
nslookup database-1.<headless-svc>   # database-1 파드의 IP만 나옴
```

백엔드 서버에서 DB에 연결할 때는 이 두 DNS 이름을 각각 등록해 주면 된다.

## DNS 질의 ④ ExternalName으로 파드 갈아끼우기

```bash
kubectl get svc <extname-svc> -n <ns> -o yaml
# type: ExternalName, EXTERNAL-IP 자리에 IP가 아닌 "도메인 이름"이 들어간다
```

`externalName`에 `database-0`의 풀 DNS 이름을 넣으면, 파드에서 이 서비스를 호출했을 때 `database-0`으로 포워딩된다. 그리고 **파드는 전혀 수정하지 않고** 서비스의 `externalName`만 `database-1`로 바꾸면, 동일한 API가 다른 파드를 호출하게 된다.

> `externalName`에는 **풀 DNS 이름을 전부 적어야 한다.** 파드에서 curl 날릴 때처럼 `파드이름.서비스이름`으로 축약하면 안 된다. 이유는 바로 다음 항목에 있다.

## resolv.conf — search와 ndots:5

```bash
cat /etc/resolv.conf
```

| 항목 | 의미 |
|------|------|
| `nameserver <IP>` | DNS 쿼리를 보낼 DNS 서버의 IP. 여러 개 등록 가능 |
| `search <list>` | 내가 준 도메인 이름 뒤에 리스트의 이름들을 하나씩 붙여가며 검색 |
| `options ndots:5` | 내가 준 도메인의 점(`.`)이 5개를 넘지 않으면 search 리스트를 붙여서 조회하라 |

search에는 이런 것들이 등록돼 있다.

```
<네임스페이스>.svc.cluster.local
svc.cluster.local
cluster.local
(+ 환경에 따라 공유기 제조사 접미사 등)
```

그래서 입력한 만큼만 쓰면 나머지를 붙여 준다.

| 내가 입력한 것 | search가 붙여 주는 것 |
|---|---|
| `서비스이름` | `.<ns>.svc.cluster.local` |
| `서비스이름.네임스페이스` | `.svc.cluster.local` |
| `서비스이름.ns.svc` | `.cluster.local` |

이 `search` 덕분에 짧게 써도 실제 DNS에 등록된 이름과 매칭되어 IP를 가져올 수 있었던 것이다. 반면 **서비스 오브젝트의 `externalName` 값에는 이런 resolv.conf 설정이 적용되지 않는다.** 그래서 앞에서 풀 DNS 이름으로 명확히 매핑시켜 줘야 했다.

> 💡 **풀 도메인을 쓰면 좋은 이유가 여기 있다.** 점이 5개를 넘지 않으면 search 리스트를 하나씩 붙여가며 DNS에 여러 번 질의한다. 풀 도메인을 쓰면 `ndots` 옵션이 걸리지 않아 search를 여러 번 하지 않으므로, 네트워크 성능을 조금이라도 높일 수 있다. 누가 봐도 거추장스러운 그 긴 도메인을 왜 쓰냐는 질문에 바로 답할 수 있는 지점이다.

## DNS 설정을 끝까지 따라가기

```bash
# 1) resolv.conf의 nameserver IP가 무엇인지 서비스에서 찾기
kubectl get svc -n kube-system      # kube-system 의 "kube-dns" 서비스 IP와 일치

# 2) 실제 파드
kubectl get pods -n kube-system     # coredns 파드가 2개 — 중요 시스템이라 이중화

# 3) CoreDNS 설정
kubectl get cm coredns -n kube-system -o yaml
```

Corefile에서는 `forward` 한 줄만 보면 된다.

```
forward . /etc/resolv.conf     ← VM(마스터 노드)의 이 파일을 참조하겠다는 뜻
```

여기에 IP를 직접 줬다면 그 DNS가 CoreDNS의 상위 DNS 서버가 된다. 현재는 VM의 파일을 참조하도록 돼 있으니, 그 파일을 본다.

```bash
cat /etc/resolv.conf     # 마스터 VM에서
```

- 여기에도 `search`가 있고, **파드에서 봤던 접미사가 그대로 보인다.** 파드의 설정은 이 VM 값을 상속받아 만들어진 것이다.
- `nameserver`의 IP는, 리눅스 설치 시 DNS 서버를 지정하지 않으면 **VirtualBox가 자동으로 내부 서버 IP를 할당**한 것이다.
- 그리고 이 VM은 **호스트 머신의 DNS 설정을 바탕으로** 인터넷 DNS에 연결된다.

```
호스트 PC (Windows)
  네트워크 옵션 → 어댑터 옵션 변경 → 연결된 Wi-Fi 더블클릭 → 자세히
  → "DNS 서버" IP = 실제 외부 DNS (통신사가 제공하므로 각자 다름)
  → 접미사도 여기 값(공유기 제조사명)이 상속되어 Kubernetes까지 타고 들어간 것
```

값 자체에 큰 의미는 없다. **이 흐름을 한 번 따라가 보는 것**이 실습의 목적이다. VM 리눅스에서 DNS가 잘못돼 외부 파일을 못 받는 경우가 많은데, 이렇게 내 서버의 DNS 연결 상태를 확인해 보면 도움이 된다.

## 파드에 DNS를 직접 주는 두 가지 방법

```yaml
spec:
  # ① DNS 서버를 직접 지정
  dnsConfig:
    nameservers:
      - 8.8.8.8
  # ② DNS 호출 없이 IP를 직접 매핑
  hostAliases:
    - ip: "192.168.0.10"
      hostnames:
        - "internal-server.mycompany.com"
```

| 방법 | 효과 |
|------|------|
| `dnsConfig.nameservers` | CoreDNS가 잘못돼 있어도 바로 외부의 원하는 DNS와 연결 |
| `hostAliases` | DNS 서버 연결과 무관하게 그 도메인 이름으로 지정한 IP를 호출 |

강사도 프로젝트를 하면서 종종 이렇게 설정해 쓸 일이 생긴다고 한다.

# 한 장 요약

## 기능과 그 실체

| 기능 | 하는 일 | 실체 |
|------|---------|------|
| 서비스 레지스트리 | 연결된 파드 IP 자동 관리 | **Endpoint 오브젝트 → iptables 룰** (kube-proxy가 조작) |
| 로드밸런싱 | 파드에 트래픽 분산 | **iptables** (라운드 로빈, 변경 불가) |
| Service Discovery | 이름으로 호출 | **CoreDNS**에 서비스 이름·IP 자동 등록 |
| 서비스 퍼블리싱 | 외부 → 내부 파드 | **kube-proxy + iptables** (+ 외부 LB 플러그인) |

## 타입 정리

| 타입 / 속성 | 무엇 | 실무 사용 |
|-------------|------|-----------|
| **ClusterIP** (기본) | 서비스 IP 할당, 내부 파드 통신의 핵심 | 가장 중요 |
| **NodePort** | 모든 노드에 포트(`30000~32767`) + ClusterIP 역할 | 테스트·임시용 |
| **LoadBalancer** | 외부 전용 IP + NodePort 역할 | **운영 표준.** 외부 → 내부는 전부 이걸로 |
| **ExternalName** | 파드에서 밖으로 나가는 DNS 포워딩 | HTTPS 도메인 검증 때문에 사실상 못 씀 |
| `externalIPs` (속성) | 선택한 노드에만, 포트 제한 없음(80/443 가능) | 임시 테스트, 보안 포트가 필요할 때 |
| `clusterIP: None` (**Headless**) | 서비스 IP 없음, DNS가 파드 IP 리스트 반환 | **StatefulSet DB에 필수** |

## 빠지기 쉬운 함정

1. **엔드포인트 등록 조건은 Readiness Probe 200 OK.** Probe 설정과 헬스체크 URL을 그에 맞게 만들 것. (Liveness 실패는 재기동이다)
2. **NodePort는 `netstat`에 리스닝 포트로 안 잡힌다.** 최신 버전은 포트 정보가 iptables 안에 있다. 안 보인다고 잘못된 게 아니다.
3. **Headless 도메인을 통신용으로 쓰지 말 것.** 로드밸런싱 책임이 클라이언트로 넘어오고, DNS가 IP 순서를 섞지 않으면 한 파드로 몰린다.
4. **`externalName`에는 풀 DNS 이름을.** 파드의 `resolv.conf` `search`가 여기엔 적용되지 않는다.
5. **DNS 호출은 `<서비스>.<네임스페이스>` 포맷으로 통일**하고, 성능이 중요하면 풀 도메인(`ndots:5` 회피).

## 트러블슈팅 루틴 (LB → 파드 트래픽 미도달)

```
엔드포인트 조회 (파드 IP 있나? 없으면 셀렉터 오타)
   ↓
iptables 룰 조회 (서비스 이름으로 grep)
   ↓
tcpdump로 해당 포트 덤프 (트래픽이 실제로 들어오나?)
   ↓
전부 정상이면 → 로드밸런서 설정 의심
```
