## 들어가며 — 서비스가 어려운 이유

- 서비스는 **대충 이해하고 쓰기는 쉽다.** 속성값만 제대로 넣으면 알아서 잘 동작한다.
- 문제는 **내가 이해한 대로 동작하지 않을 때 원인을 알기가 정말 어렵다**는 것이다.
- 예를 들어 NodePort 타입 서비스를 만들고 외부에서 호출했는데 파드로 트래픽이 안 들어온다면? 이 기능들은 속성값만 맞으면 정상 동작해야 하므로 대개 원인은 **YAML의 오타**다. 그런데 서비스는 타입과 기능이 여러 갈래라, 단순 오타가 아니라 **각 기능의 옵션 값을 잘못 주는** 실수가 나온다.

### 이번 섹션의 목표

> NodePort 서비스를 만들었을 때, **VM의 그 포트에서 파드까지 이어지는 연결고리를 하나씩 짚어볼 수 있는 능력**을 기르는 것.

인프라 구조를 머릿속에 그려 두고, 뭔가 안 될 때 그 연결고리를 따라가며 문제 지점을 좁혀 나가는 방식. 강사는 이것이 곧 **주니어와 시니어의 문제 해결 방식 차이**라고 본다.

### 같은 내용을 세 번 반복한다

서비스는 영역이 넓고 기능들이 서로 엮여 있어서, 애매하게 끊어 설명하면 오히려 이해가 안 된다. 그래서 소화가 안 되더라도 전체 그림을 한 번 쭉 훑은 뒤, 관점을 바꿔 두 번 더 반복하는 구조로 간다.

| 순서 | 보는 관점 | 이 문서의 위치 |
|------|-----------|----------------|
| ① | 스펙(속성) — 어떤 기능이고 왜 쓰는지 | 1부 |
| ② | 인프라 구성 — 실제로 어떻게 연결돼 동작하는지 | 2부 |
| ③ | 실습 — 눈으로 확인하며 디테일 보강 | 3부 |

1부가 잘 이해되지 않아도 **반복해서 볼 필요는 없다.** 바로 2부로 넘어가면 훨씬 쉽게 잡힌다.

서비스 섹션(1~3부) 다음에는 **인그레스 섹션(4~7부)**과, 서비스 수업에서 미뤄 뒀던 **SessionAffinity·TrafficPolicy(8부)**가 이어진다. 인그레스 섹션도 같은 방식이다. 개념과 오해(4부) → 인프라 구성과 설치 실습(5부) → 운영에서 부딪치는 이슈(6부) → 실습(7부).

# 1부. 서비스 스펙 — 어떤 기능이 있고 왜 쓰는가

## 셀렉터 뒤에 있는 Endpoint 오브젝트

셀렉터가 파드의 레이블과 매칭되면 그 파드들로 로드밸런싱된다는 것까지는 이미 안다. 한 단계 더 들어가면 `Endpoint`라는 오브젝트가 있다.

| 특징 | 내용 |
|------|------|
| 생성 | 서비스를 만들면 **자동으로** 생성 |
| 이름 | **항상 서비스와 동일한 이름** |
| 핵심 속성 | `subsets.addresses` — 연결된 **파드들의 IP**를 관리 |

> 엔드포인트에 IP가 들어 있어야 서비스로 들어온 트래픽이 파드로 간다. 이게 **서비스 레지스트리** 기능의 정체다.

Kubernetes가 셀렉터에 매칭되는 레이블을 가진 파드를 대상으로, 새 파드가 생기면 IP를 추가하고 삭제되면 제거해 준다.

### 등록 조건은 Readiness Probe다

- 정확히는 파드가 만들어지고 **Readiness Probe가 200 OK를 받았을 때** 엔드포인트에 등록된다. 즉 Kubernetes는 레이블뿐 아니라 **파드의 상태까지 확인한 뒤** IP를 넣는다.
- 등록 이후에도 부하로 Readiness가 실패하면 **IP를 뺐다가, 성공하면 다시 넣어** 준다.
- 반면 **Liveness Probe가 실패하면 파드를 재기동**시켜 버린다.

> 그래서 Probe 설정과 헬스체크 URL을 만들 때 이 차이에 부합하는지 확인해야 한다. 내가 아는 만큼 작업의 디테일이 달라진다.

### 대시보드가 파드 IP를 보여준 이유

대시보드에서 서비스를 조회하면 파드 IP들이 나왔지만, **서비스 속성 자체에는 파드 정보가 없다.** 대시보드가 서비스를 조회한 뒤 같은 이름의 엔드포인트를 추가로 찾아서 파드 IP를 함께 보여준 것이다.

## 타입 ① ClusterIP

타입 속성을 주지 않으면 기본값으로 들어간다.

- `clusterIP` 속성에 **서비스의 IP가 할당**되고, 누군가 이 IP로 트래픽을 보내면 **가지고 있는 엔드포인트 IP로 포워딩**한다.

| 포트 속성 | 의미 |
|-----------|------|
| `port` | 서비스의 포트 |
| `targetPort` | 파드(컨테이너)의 포트 |

- 다른 파드에서는 **서비스 이름만으로도** 호출할 수 있다(포트가 80이면 생략). Kubernetes가 내부 DNS 서버에 서비스 이름과 IP를 자동 등록하기 때문이고, 이걸 **Service Discovery**라고 부른다.
- **Kubernetes 내에서 파드로 통신하기 위한 가장 중요한 타입.**

## 타입 ② NodePort

- 노드 포트를 수동으로 지정할 수 있고, 명시하지 않으면 정해진 대역(`30000~32767`)에서 자동 할당된다.
- 워커노드의 그 포트로 트래픽을 날리면 서비스 IP·포트와 매칭되고, 로드밸런싱되어 파드로 들어간다.
- NodePort로 만들면 워커노드에 새 포트가 생기면서 **ClusterIP 역할도 함께 추가**된다. 그래서 내부 통신용으로도 쓸 수 있다.

실습에서는 정말 많이 썼지만 **실무 운영 환경에서는 거의 쓸 일이 없다.** 정확히는 이 포트가 필요 없다는 게 아니라, **이 포트로 직접 API를 날리지 않는다**는 뜻이다. 대신 로드밸런서를 쓴다.

## 타입 ③ LoadBalancer

- 이 타입으로 만들면 **새로운 IP가 생성**되고 **NodePort의 역할도 포함**한다.
- 이 IP로 호출하면 워커노드 IP의 NodePort로 포워딩되어 결국 파드로 통신이 된다.

> 실무에서 클러스터 외부에서 내부로 트래픽을 보내야 할 때는 **무조건 로드밸런서를 만들고 이 IP로 통신한다**고 보면 된다.

기능만 놓고 보면 NodePort가 더 깔끔해 보일 수도 있다. 왜 로드밸런서를 쓰는지는 2부에서 인프라 구성을 보면 자연스럽게 이해된다.

## 타입 ④ ExternalName

- 이 타입으로 만들면 `externalName` 속성에 **DNS 이름**을 넣는다.
- 파드가 이 서비스를 호출하면 인프라 외부 DNS로 포워딩되어, 그 도메인의 IP 주소를 알아내고 그 주소로 통신하게 해 준다.

다른 타입들은 **파드로 트래픽을 보내기 위한** 용도인데, 이건 **파드에서 밖으로 나가기 위한** 용도다. 방향이 반대다.

### 왜 굳이 서비스를 경유시키나

여러 파드 내부에 `github.com` URL이 박혀 있다면, 코드 저장소가 다른 것으로 바뀌었을 때 파드는 건드리지 않고 **이 서비스만 수정**하면 된다. IT에서 익숙한 패턴이라 유용해 보인다.

### 그런데 HTTPS에서 막힌다

```
파드 → (ext-github 라는 이름으로 DNS 질의) → 서비스 경유 → 공인 DNS → github.com IP 획득
     → 그 IP로 통신 시도
     → HTTPS는 "클라이언트가 보낸 도메인 이름"을 확인함
     → GitHub 입장: 날아온 DNS 명이 ext-github ??? → 변조 의심 → 신뢰 불가
```

- HTTP라면 문제없지만 **HTTPS에서는 이 기능을 쓸 수 없다.** 그리고 외부로 나가는 통신은 통상 HTTPS다.
- 결국 ExternalName은 **의도는 좋지만 실제로 쓸 일이 별로 없다.**

## 타입이 아닌 별도 속성: externalIPs

서비스 스펙에 **워커노드의 IP를 지정**하면, 지정한 IP의 노드를 통해 내부 파드와 통신할 수 있다. 목적(외부 → 내부)은 NodePort와 같지만 차이가 있다.

| | NodePort | externalIPs |
|---|---|---|
| 포트가 열리는 노드 | 클러스터의 **모든 노드** | **내가 선택한 노드만** |
| 포트 범위 | 제한 있음 (`30000~32767`) | **제한 없음** |
| 쓰는 포트 | 별도의 `nodePort` | 서비스에 준 **`port`가 곧 워커노드 포트** → 80/443 가능 |

- **타입과 별개의 속성**이라, 어떤 타입을 선택했더라도 추가로 붙일 수 있다.
- NodePort 대역과 똑같이 줄 수도 있지만 굳이 그럴 필요는 없다.

**언제 쓰나.** NodePort와 마찬가지로 학습·테스트 용도다. 특히 외부에서 내부로 들어오는 연결을 80이나 443으로 해야 할 때. IP를 지정할 수 있다는 점은 메리트가 크지 않은데, 워커노드 IP는 노드가 바뀌면 달라질 수 있고 한 노드로만 트래픽이 들어오는 게 골고루 들어오는 것보다 나을 것도 없기 때문이다. 그래서 **차라리 NodePort를 쓰는 편이 낫다.** 현실적인 용도는 ClusterIP 타입 서비스가 이미 있는데 잠깐 클러스터 밖에서 파드로 통신해야 할 때 이 속성만 추가하는 정도다.

## Headless 서비스 (`clusterIP: None`)

ClusterIP는 자동 생성되니 읽기 전용 속성처럼 보이지만, `None` 값을 직접 넣어서 만들 수 있다. 이렇게 만든 서비스를 **Headless 서비스**라고 부른다. 말 그대로 머리(서비스 IP)가 없다.

| | 일반 ClusterIP | Headless |
|---|---|---|
| 서비스 IP | 생성됨 | **생성 안 됨** |
| 이름으로 DNS 질의하면 | 서비스 IP | **연결된 파드들의 IP 리스트** |
| 통신 경로 | 서비스 IP → 파드 | 클라이언트가 **파드 IP로 직접** |

### 쓰임새 1. 파드 IP 리스트가 필요할 때

마이크로서비스 아키텍처에서는 전체 트래픽을 줄이기 위해 **파드 스스로가 상태 변화 시 수집 서버로 노티**하는 방식이 낫다. (그래서 앱이 자기 IP를 알아내려고 kube-apiserver에 API를 날리는 실습을 했었다.)

그런데 파드가 상태를 못 넘기고 죽을 수도 있으니, 수집 서버 쪽에서도 각 파드 상태를 직접 확인할 필요가 있다. kube-apiserver로 엔드포인트를 조회하면 파드 IP를 알 수는 있지만 통신이 번거롭고, 리소스 조회는 보안 문제로 권한도 따로 줘야 한다.

파드 IP만 알아내는 게 목적이라면 **Headless 서비스를 붙이고 서비스 이름으로 DNS 질의하면 끝**이다. 받은 IP 리스트로 for문을 돌리면 전체를 한 번씩 호출할 수 있다.

다만 수집 서버를 직접 만들 일은 별로 없다. 이건 "Headless를 쓰면 DNS로 파드 IP 리스트를 받는다"는 특징을 설명하기 위한 사례다. 진짜 자주 쓰는 곳은 아래다.

### 쓰임새 2. StatefulSet 데이터베이스

먼저 백엔드 서버와 데이터베이스의 차이부터.

| | 백엔드 서버 | 데이터베이스 |
|---|---|---|
| 성격 | **Stateless** 앱 | **Stateful** 앱 (파드마다 상태가 있음) |
| 컨트롤러 | Deployment | **StatefulSet** |
| 파드 이름 | 난수가 붙음 (쓸 일 없으니 상관없음) | `db-0`, `db-1` **시퀀셜** |
| 트래픽 분산 | 랜덤해도 무방 (모두 같은 역할) | **아무 파드로나 가면 안 됨** |
| 붙이는 서비스 | ClusterIP | **Headless** |

DB는 0번이 읽기·쓰기를 담당할 때 1번은 읽기 전용으로만 동작할 수 있다. 백엔드에서 쓰기를 할 땐 무조건 `db-0`으로 가야 한다. StatefulSet에 `clusterIP: None` 서비스를 붙이면 **파드를 지정해서 DNS를 호출**할 수 있다.

```
<파드이름>.<서비스이름>      예) db-0.db-service, db-1.db-service
```

백엔드 서버에는 이 두 도메인을 DB 연결 대상으로 등록해 두면, **라이브러리가 역할에 맞는 파드로 알아서 연결**한다.

> 여기까지는 기능과 이유만 본 것이라 실체를 몰라 뜬구름 같을 수 있다. 이 상태로 넘어가면 설정대로 동작하지 않을 때 뭘 봐야 할지 막막해진다.

# 2부. 인프라 구성으로 본 서비스의 실체

> 이번 스프린트가 지상편의 마지막이다. 다음 스프린트는 해수편, Kubernetes 관리자를 위한 내용이고 그때는 클러스터를 직접 설치한다.

## 클러스터에 깔려 있는 것들

```
[마스터 노드]  Kubernetes 주요 컴포넌트 (+ CoreDNS)
      │  (워커노드를 join)
[워커 노드들]  ← kube-proxy 처럼 "모든 노드에" 설치되는 컴포넌트가 있음
                ← Calico(CNI)의 프록시 모듈도 모든 워커노드에 존재
```

| 컴포넌트 | 담당 | 실체 |
|----------|------|------|
| **kube-proxy** | 서비스 네트워크 | **리눅스 iptables** |
| **Calico (CNI)** | 파드 네트워크 | 파드 네트워크 대역을 만들고 파드에 IP 할당 |

- 서비스가 만들어지거나 변경될 때마다 Kubernetes는 **kube-proxy를 이용해 각 노드의 iptables를 조작**한다.
- 파드는 Calico가 만든 대역에서 IP를 받고, 파드 간 통신도 이 네트워크 안에서 이뤄진다. 파드가 서로 다른 워커노드에 있어도 Calico 프록시 모듈이 모든 워커노드에 있으므로 잘 전달된다.

## ClusterIP의 실체 — 엔드포인트는 iptables 룰이다

```
서비스 생성 → kube-proxy가 "모든 노드"의 iptables에 룰 등록
              "서비스 IP로 온 트래픽은 → 이 파드 IP들로 보내라"
파드 하나 죽음 → 그 룰에서 해당 파드 IP 삭제
```

- 이 룰은 **엔드포인트의 `addresses` 그대로** 만들어진다. 즉 **엔드포인트의 실체는 iptables에 있는 룰**이고, 이게 서비스 레지스트리다.
- 파드에서 서비스 IP를 호출하면 모든 트래픽은 일단 iptables로 가고, 룰에 따라 파드로 전달된다. 따라서 **로드밸런싱을 하는 주체도 iptables**다.
- iptables의 분배 방식은 **라운드 로빈**이고, iptables를 쓰는 한 이 방식은 바꿀 수 없다. 다만 파드 네트워크를 Calico가 아닌 다른 플러그인으로 교체할 수 있듯, **서비스 네트워크의 구현체도 iptables가 아닌 다른 것으로 바꿀 수는 있다.**

## NodePort의 실체 — kube-proxy + iptables

```
모든 노드에 포트 생성
  → 그 포트로 들어온 트래픽은 각 워커노드의 iptables로 진입
  → 이후는 ClusterIP가 하던 역할 그대로  (그래서 "ClusterIP가 추가됐다"고 표현)
  → 파드가 어느 노드에 있는지는 Kubernetes가 이미 알고 있으므로
    kube-proxy가 해당 노드로 라우팅
```

## LoadBalancer — 원래 인프라에서는 이렇게 만든다

Kubernetes를 잠깐 잊고, 기업 내부 인프라 장비부터 보자.

| 장비 | 역할 |
|------|------|
| **라우터** | 인터넷 외부 사용자가 인프라 안으로 통신할 수 있게 해 주는 장비 |
| **게이트웨이** | 인프라 내부 네트워크를 생성 (대역 설정 → 서버 연결 → 그 대역에서 IP 할당·상호 통신) |

이 상태에서 외부 사용자에게 클러스터 안의 서비스를 오픈하려면:

```
① 라우터에 이 서비스를 위한 "외부 전용 IP"를 하나 생성
② 로드밸런서를 구축하고, 트래픽이 들어올 수 있도록 라우터에 설정
③ 로드밸런서가 모든 워커노드의 NodePort로 연결
→ 모든 노드로 트래픽이 분산되면서 내 파드로 들어옴
```

> **이 구성을 자동으로 만들어지게 하는 것이 LoadBalancer 타입 서비스다.**

### 클러스터 외부 장비를 서비스로 만들 수 있는 이유

NodePort까지는 Kubernetes가 직접 관리하는 영역이지만 로드밸런서는 클러스터 밖에 있다. 어떻게 이게 가능할까? **CNI에 Calico를 끼운 것과 같은 원리**다.

Kubernetes 자체가 모든 기능을 제공하지는 않지만, **외부 플러그인을 연결할 수 있고 그 기능을 쓸 인터페이스(리소스)를 제공**한다. Calico는 파드로 만들어져 있어 클러스터 내부에 있을 뿐이고, 로드밸런서는 밖에 있더라도 `type: LoadBalancer`라는 인터페이스와 Kubernetes 문서의 구현 방법이 있으니 **그대로 만들면 어떤 제품이든 호환**된다. 클라우드 환경이라면 각 CSP가 자사 로드밸런서로 이 구성을 이미 구현해 뒀다.

지금 실습 환경에는 구현체가 없다. 그래서 서비스를 조회하면 **EXTERNAL-IP가 `<pending>`**으로 뜬다. 로드밸런서로 들어오는 흐름은 없지만 **NodePort가 플러스되어 있으므로 그 아래는 정상 생성**된다.

## 퍼블리싱 3종, 언제 무엇을 쓰나

| 방식 | 용도 | 이유 |
|------|------|------|
| **LoadBalancer** | **운영 표준.** 외부 사용자든 인프라 내 다른 내부 서버든, 클러스터 밖에서 안으로 들어오는 통신은 전부 여기로 | 노드 장애·변경과 무관, 워커노드 IP 비공개, 트래픽 골고루 분산 |
| **NodePort 다이렉트** | 테스트용 임시 사용 | 특정 워커노드를 찍어 통신하면 ① 노드 장애 시 통신 불가 ② 노드가 아예 바뀔 수 있음 ③ 워커노드 IP 공개 자체가 보안에 안 좋음 ④ 한 노드로 트래픽 집중 |
| **externalIPs** | 테스트용이되, 포트 제약이 없어 **보안 포트(443)로 접속해야 할 때** 유용 | 결국 임시용. 로드밸런서로도 443을 열 수 있으니 실제 운영 퍼블리싱은 역시 로드밸런서 |

## 문제 해결 방식이 달라진다

로드밸런서 타입 서비스를 만들고 그 IP로 호출했는데 파드로 트래픽이 안 간다면:

```
① 서비스 이름으로 엔드포인트 조회
     → 파드 IP가 안 보인다? → 서비스의 셀렉터를 잘못 넣은 게 아닌지 의심
② 서비스 이름으로 iptables 조회
     → 룰이 제대로 들어갔는지 (여기서 문제 날 일은 거의 없음)
③ 해당 포트로 트래픽 덤프(tcpdump)
     → 데이터가 실제로 흘러들어오고 있는지 확인
④ 여기까지 정상이면 → 로드밸런서 설정을 의심
```

이렇게 **어느 영역에서 문제가 생겼는지 범위를 좁혀 나갈 수 있게 된다.**

이걸 알아야 하는 이유가 하나 더 있다. 앞으로 수많은 오픈소스를 설치하게 되는데, 아무리 구성이 복잡해도 **Kubernetes에서는 이 서비스들이 기본이고 그것들로 다 만들어졌기 때문에** 대부분의 통신 구조를 분석할 수 있다. 강사도 처음 보는 오픈소스라도 통신 구조를 이해하는 데는 부담을 느끼지 않는다고 한다.

## CoreDNS와 그 위의 DNS 계층

Kubernetes 기본 컴포넌트로 **CoreDNS**가 있고, 여기에 서비스 이름과 할당된 IP가 자동 등록된다. 파드는 서비스 이름만 알고 있으므로, 앱이 DNS에 질의해 IP를 확인하고 그 IP로 통신한다. 도메인 통신에서는 자동으로 되는 흐름이라 평소엔 DNS를 신경 쓸 일이 없지만, **Kubernetes에서는 DNS 활용법이 다양해서 알아둘 필요가 있다.**

### ClusterIP 이름 호출 vs Headless 이름 호출

Headless 서비스는 DNS에 서비스 이름으로 **파드 IP 리스트**가 등록된다. 그래서 ClusterIP 서비스 이름으로 호출하든 Headless 서비스 이름으로 호출하든, **결과적으로 두 파드 중 한 곳으로 트래픽이 간다.** 결론은 같아 보여도 **과정의 차이는 엄청나다.**

| | ClusterIP 이름 호출 | Headless 이름 호출 |
|---|---|---|
| DNS가 주는 것 | 서비스 IP 하나 | 파드 IP 리스트 |
| 로드밸런싱 주체 | **iptables가 알아서** | **클라이언트** (받은 IP 중 첫 번째로 날림) |
| 클라이언트 부담 | 없음 | **통신 라이브러리에 그 기능이 있는지 체크해야 함** |

> Headless 서비스의 도메인 이름을 통신용으로 쓰면 안 된다. **도메인 이름으로 통신할 때는 반드시 ClusterIP 타입을 쓴다.**

이런 걸 알고 쓰면, 인프라 환경이 좋아진 만큼 개발은 로직에만 더 집중할 수 있다.

### 그래도 Headless를 꼭 써야 하는 곳

**StatefulSet으로 만든 데이터베이스에는 Headless 서비스를 무조건 붙여야 한다.** 서비스 이름이 `db`라면 연결된 파드 리스트도 똑같이 나오지만, 추가로 **`<파드이름>.<서비스이름>` 도메인에 해당 파드의 IP가 별도로 등록**되기 때문이다. 백엔드 서버는 이 도메인들을 모두 등록해 두고, DB마다 역할이 다르니 연결 라이브러리가 역할에 맞는 도메인을 호출한다.

### ExternalName이 걸리는 지점, 그리고 남는 교훈

```
파드 → CoreDNS: "ext-github 주소 줘"
       CoreDNS: ext-github → github.com 으로 포워딩
                github.com IP는 나도 모름 → 상위(외부) DNS 서버에 질의
```

인프라 관점에서 DNS는 이렇게 계층을 이룬다.

```
[파드] → [CoreDNS] → [사내망 DNS 서버] → [인터넷 공인 DNS 서버]
```

- Kubernetes에는 CoreDNS가 기본 탑재되지만, **기존 인프라의 서버들끼리 도메인으로 통신하려면 사내망에 DNS 서버를 따로 구축**해야 한다. 기업 내부에서 자체 도메인 룰을 정하고 서버 IP를 등록해 쓴다.
- 그 사내 DNS가 **외부 공인 DNS에도 연결돼 있어야** 인터넷 도메인의 IP를 가져올 수 있다.
- 따라서 **Kubernetes를 설치할 때 CoreDNS를 사내 DNS에 연결해 놔야** 파드에서 사내 도메인과 인터넷 도메인을 모두 해석할 수 있다.

ExternalName 자체는 (1부에서 본 대로) HTTPS 도메인 검증에서 막힌다. 사내 내부 서버와 HTTP로 통신한다면 문제없지만, 강사도 유용하게 쓰는 사례는 별로 못 봤다.

> 💡 ExternalName은 "이런 게 있다" 정도만 알면 되고, **이걸 설명하려고 짚은 DNS 서버 간 연결 구성을 아는 게 훨씬 중요하다.**

어디에 써먹나. 프로젝트 초기에는 Kubernetes 설치 담당자가 사내 DNS 연결을 깜빡할 수 있고, 사내 DNS에 내부 서버 도메인이 아직 등록되지 않았는데 인프라 담당자가 바빠 처리가 늦어질 수도 있다. **DNS 구조를 알고 있으면** 파드에서 사내 서버로 DNS 호출이 안 될 때 어느 부분이 문제인지 짚어서 담당자에게 명확히 요청할 수 있다. 나아가 파드에서 직접 DNS를 설정해 임시로 통신되게 만들 수도 있다. 인프라 작업을 기다리지 않고 바로 테스트해서 내 개발 일정을 지키는 것이다.

> 서비스에는 여기서 다루지 않은 기능들이 더 있고 마찬가지로 잘 안 쓰는데, **왜 안 쓰는지가 오히려 중요하다.** 다만 Ingress를 알아야 설명이 되므로 다음 섹션까지 공부한 뒤 맨 마지막에 따로 다룬다.

# 3부. 실습

확인할 것은 네 가지다. 타입별 서비스를 만들고 **특징대로 포트가 만들어졌는지 API를 날려보고**, **엔드포인트에 파드 IP**가 들어 있는지 보고, **iptables에 룰**이 들어갔는지 대조하고, **포트를 모니터링**해 트래픽이 실제로 들어오는지 본다. 이어서 DNS 질의를 네 가지 방식으로 해 보고, 마지막으로 파드부터 공유기까지 DNS 설정을 따라간다.

배포는 Jenkins 파이프라인으로 해도 되고, 이번에는 마스터 서버에서 YAML을 직접 붙여넣어 배포했다.

## 서비스 목록 확인

`kubectl get svc`로 조회하면 타입별로 이름을 준 서비스들이 보인다.

> External IP Service는 **별도의 타입이 아니다.** ClusterIP 타입에 `externalIPs`로 마스터 노드 IP를 추가해 준 것이다.

## 퍼블리싱 — 타입별로 API 날려보기

| 대상 | 확인 결과 |
|------|-----------|
| **NodePort** | YAML에 포트 번호를 직접 넣어준 것. 클러스터 외부에서 `워커노드IP:노드포트`로 API 전송 성공 |
| **LoadBalancer** | 구현체가 없어 EXTERNAL-IP가 `<pending>`. 그래도 **NodePort는 자동 생성**돼 있어 그 포트로 날리면 잘 전달됨 |
| **externalIPs** | 별도의 노드 포트 없이 **서비스의 `port`(여기선 80)를 그대로** 사용. 포트를 아예 생략하거나 `:80`을 줘도 API가 잘 날아감 |

## 엔드포인트와 iptables 룰 대조

```bash
kubectl get endpoints -n <namespace>
```

서비스 4개가 모두 같은 파드에 연결돼 있어 파드 IP가 전부 동일하게 나온다. DB용 서비스만 다른 파드에 연결돼 있어 IP가 다르다.

이 엔드포인트가 정말 iptables에 들어가 있는지 확인한다.

```bash
sudo iptables -t nat -L -n | grep <service-name>
```

출력이 복잡하지만 `TCP to ...` 뒤의 IP들만 보면 된다. **엔드포인트에 있던 파드 IP와 정확히 일치**한다. 서비스를 만들고 파드에 연결될 때마다 kube-proxy가 iptables에 룰을 만들어 주기 때문에 실질적인 물리 통신이 가능한 것이다.

## NodePort는 netstat에 안 잡힌다

그림상으로는 워커노드에 포트가 리스닝돼 있고, 그 포트를 지나 iptables로 가는 것처럼 보인다. 확인해 보면:

```bash
apt install net-tools            # 리스닝 포트 조회용
netstat -anp                     # 리스닝된 모든 포트
netstat -anp | grep <nodePort>   # → 아무것도 안 나옴
```

> ⚠️ 리스닝 포트가 없다고 해서 **NodePort가 안 만들어진 게 아니다.** 예전에는 kube-proxy가 이 포트를 리스닝시켜 줘서 조회가 됐지만, Kubernetes 버전이 올라가면서 **포트 정보가 iptables 안에 포함**되도록 바뀌었다.

```bash
sudo iptables -t nat -L KUBE-NODEPORTS -n | grep <service-name>
```

여기에 포트가 그대로 있다.

## tcpdump로 트래픽 유입 확인

```bash
apt install tcpdump
ip addr                          # 마스터 노드의 인터페이스 확인
                                 # → API를 날릴 IP에 해당하는 인터페이스를 찾는다 (예: eth1)
tcpdump -i eth1 port <포트>       # 모니터링 대기
```

다른 창에서 그 포트로 트래픽을 날리면 날릴 때마다 덤프에 찍힌다. **아무것도 안 찍힌다면 로드밸런서 쪽에 문제가 있는지** 확인하면 된다.

## DNS 질의 ① ClusterIP

구성은 이렇다. Deployment 파드에 ClusterIP 서비스, StatefulSet(`database`) 파드에 Headless 서비스가 붙어 있고 모두 같은 네임스페이스다. 여기에 `init` 파드를 하나 만들어 CoreDNS에 질의한다.

CoreDNS에 실제로 등록되어 있는 이름은 이 형태다.

```
<서비스이름>.<네임스페이스>.svc.cluster.local
                              └ svc = service 의 약어
```

```bash
kubectl exec -it init -n <ns> -- /bin/bash   # nslookup 등 통신 라이브러리가 설치돼 있음
nslookup <service-name>
```

- `Server` — DNS 서버(CoreDNS)의 IP
- `Name` — 위의 풀 도메인 형태
- `Address` — 해당 서비스의 ClusterIP

curl로는 세 가지 형태가 모두 동작한다.

| 형태 | 언제 쓰나 |
|------|-----------|
| `<서비스이름>` | 같은 네임스페이스의 서비스를 호출할 때 |
| `<서비스이름>.<네임스페이스>` | 다른 네임스페이스 호출 시 **필수**, 그리고 이게 **권장** |
| `<서비스이름>.<ns>.svc.cluster.local` | 다른 클러스터의 서비스를 호출할 때 |

- 권장 이유는, 나중에 클러스터에 앱이 많아지면 앱마다 네임스페이스가 달라지기 때문이다. 같은 네임스페이스끼리 호출하더라도 애초에 이 포맷으로 통일하는 게 혼동이 없고 깔끔하다.
- 풀 도메인은 — 다른 클러스터의 서비스를 호출할 땐 보통 그 서비스만 로드밸런서로 오픈하므로 직접 줄 일이 거의 없다. 그래도 장점은 있는데, `ndots` 항목에서 설명한다.

호스트네임을 반환하는 API를 여러 번 날리면 두 파드로 번갈아 응답한다. **iptables가 로드밸런싱**해 준 것이다.

## DNS 질의 ② Headless

```bash
kubectl get svc <headless-svc> -n <ns>
```

타입은 ClusterIP지만 **CLUSTER-IP가 `None`이고 포트도 없다.**

```bash
nslookup <headless-svc>     # 서비스 IP 대신 "파드들의 IP"가 나온다
```

> Headless 도메인으로 curl 할 때는 **포트를 반드시 명시**해야 한다. 헤드리스는 서비스 포트가 없고 파드 IP를 받아 바로 파드로 날리는 것이므로, 여기 주는 포트는 **파드(컨테이너)의 포트**다.

호스트네임 API를 여러 번 날리면 로드밸런싱이 되는 것처럼 보인다. 그런데 curl 자체는 DNS가 IP를 여러 개 줘도 **첫 번째 IP로만** 날린다. `nslookup`을 여러 번 반복해 보면 답이 나온다. **날릴 때마다 CoreDNS가 첫 번째 Address를 다르게 준다.** IP 리스트 순서를 순환시키고 있었던 것이다.

> ⚠️ 이건 DNS 서버 설정에 따라 다르다. IP를 순환해서 주지 않으면 한 IP만 계속 앞에 나와 **그 파드로만 호출**된다. Headless 서비스로 API를 날리는 건 최대한 지양할 것.

## DNS 질의 ③ StatefulSet 파드 지정

```bash
kubectl get pods -n <ns>
# StatefulSet 이름이 database → 파드 이름은 database-0, database-1 (시퀀셜)

nslookup database-0.<headless-svc>   # database-0 파드의 IP만 나옴
nslookup database-1.<headless-svc>   # database-1 파드의 IP만 나옴
```

백엔드 서버에서 DB에 연결할 때는 이 두 DNS 이름을 각각 등록해 주면 된다.

## DNS 질의 ④ ExternalName으로 파드 갈아끼우기

```bash
kubectl get svc <extname-svc> -n <ns> -o yaml
# type: ExternalName, EXTERNAL-IP 자리에 IP가 아닌 "도메인 이름"이 들어간다
```

`externalName`에 `database-0`의 풀 DNS 이름을 넣으면, 파드에서 이 서비스를 호출했을 때 `database-0`으로 포워딩된다. 그리고 **파드는 전혀 수정하지 않고** 서비스의 `externalName`만 `database-1`로 바꾸면, 동일한 API가 다른 파드를 호출하게 된다.

> `externalName`에는 **풀 DNS 이름을 전부 적어야 한다.** 파드에서 curl 날릴 때처럼 `파드이름.서비스이름`으로 축약하면 안 된다. 이유는 바로 다음 항목에 있다.

## resolv.conf — search와 ndots:5

```bash
cat /etc/resolv.conf
```

| 항목 | 의미 |
|------|------|
| `nameserver <IP>` | DNS 쿼리를 보낼 DNS 서버의 IP. 여러 개 등록 가능 |
| `search <list>` | 내가 준 도메인 이름 뒤에 리스트의 이름들을 하나씩 붙여가며 검색 |
| `options ndots:5` | 내가 준 도메인의 점(`.`)이 5개를 넘지 않으면 search 리스트를 붙여서 조회하라 |

search에는 이런 것들이 등록돼 있다.

```
<네임스페이스>.svc.cluster.local
svc.cluster.local
cluster.local
(+ 환경에 따라 공유기 제조사 접미사 등)
```

그래서 입력한 만큼만 쓰면 나머지를 붙여 준다.

| 내가 입력한 것 | search가 붙여 주는 것 |
|---|---|
| `서비스이름` | `.<ns>.svc.cluster.local` |
| `서비스이름.네임스페이스` | `.svc.cluster.local` |
| `서비스이름.ns.svc` | `.cluster.local` |

이 `search` 덕분에 짧게 써도 실제 DNS에 등록된 이름과 매칭되어 IP를 가져올 수 있었던 것이다. 반면 **서비스 오브젝트의 `externalName` 값에는 이런 resolv.conf 설정이 적용되지 않는다.** 그래서 앞에서 풀 DNS 이름으로 명확히 매핑시켜 줘야 했다.

> 💡 **풀 도메인을 쓰면 좋은 이유가 여기 있다.** 점이 5개를 넘지 않으면 search 리스트를 하나씩 붙여가며 DNS에 여러 번 질의한다. 풀 도메인을 쓰면 `ndots` 옵션이 걸리지 않아 search를 여러 번 하지 않으므로, 네트워크 성능을 조금이라도 높일 수 있다. 누가 봐도 거추장스러운 그 긴 도메인을 왜 쓰냐는 질문에 바로 답할 수 있는 지점이다.

## DNS 설정을 끝까지 따라가기

```bash
# 1) resolv.conf의 nameserver IP가 무엇인지 서비스에서 찾기
kubectl get svc -n kube-system      # kube-system 의 "kube-dns" 서비스 IP와 일치

# 2) 실제 파드
kubectl get pods -n kube-system     # coredns 파드가 2개 — 중요 시스템이라 이중화

# 3) CoreDNS 설정
kubectl get cm coredns -n kube-system -o yaml
```

Corefile에서는 `forward` 한 줄만 보면 된다.

```
forward . /etc/resolv.conf     ← VM(마스터 노드)의 이 파일을 참조하겠다는 뜻
```

여기에 IP를 직접 줬다면 그 DNS가 CoreDNS의 상위 DNS 서버가 된다. 현재는 VM의 파일을 참조하도록 돼 있으니, 그 파일을 본다.

```bash
cat /etc/resolv.conf     # 마스터 VM에서
```

- 여기에도 `search`가 있고, **파드에서 봤던 접미사가 그대로 보인다.** 파드의 설정은 이 VM 값을 상속받아 만들어진 것이다.
- `nameserver`의 IP는, 리눅스 설치 시 DNS 서버를 지정하지 않으면 **VirtualBox가 자동으로 내부 서버 IP를 할당**한 것이다.
- 그리고 이 VM은 **호스트 머신의 DNS 설정을 바탕으로** 인터넷 DNS에 연결된다.

```
호스트 PC (Windows)
  네트워크 옵션 → 어댑터 옵션 변경 → 연결된 Wi-Fi 더블클릭 → 자세히
  → "DNS 서버" IP = 실제 외부 DNS (통신사가 제공하므로 각자 다름)
  → 접미사도 여기 값(공유기 제조사명)이 상속되어 Kubernetes까지 타고 들어간 것
```

값 자체에 큰 의미는 없다. **이 흐름을 한 번 따라가 보는 것**이 실습의 목적이다. VM 리눅스에서 DNS가 잘못돼 외부 파일을 못 받는 경우가 많은데, 이렇게 내 서버의 DNS 연결 상태를 확인해 보면 도움이 된다.

## 파드에 DNS를 직접 주는 두 가지 방법

```yaml
spec:
  # ① DNS 서버를 직접 지정
  dnsConfig:
    nameservers:
      - 8.8.8.8
  # ② DNS 호출 없이 IP를 직접 매핑
  hostAliases:
    - ip: "192.168.0.10"
      hostnames:
        - "internal-server.mycompany.com"
```

| 방법 | 효과 |
|------|------|
| `dnsConfig.nameservers` | CoreDNS가 잘못돼 있어도 바로 외부의 원하는 DNS와 연결 |
| `hostAliases` | DNS 서버 연결과 무관하게 그 도메인 이름으로 지정한 IP를 호출 |

강사도 프로젝트를 하면서 종종 이렇게 설정해 쓸 일이 생긴다고 한다.

# 4부. 인그레스 — 개념과 인프라 구성

## 들어가며 — 인그레스가 가장 설명하기 어려운 이유

강사가 현업 분들에게 Kubernetes를 교육할 때 **가장 설명하기 힘들고, 설명해도 가장 이해하기 어려워하는 리소스**가 인그레스였다고 한다.

속성만 보면 단순하다.

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: portal
spec:
  ingressClassName: nginx
  rules:
    - host: portal.com            # 이 도메인으로 호출이 오면
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: portal      # 이 서비스로 보내라
                port:
                  number: 80
  tls:
    - hosts: [portal.com]
      secretName: portal-tls      # TLS 타입 시크릿에 인증서를 넣으면 HTTPS 통신
```

- `rules` — 외부에서 이 도메인을 호출하면 그 트래픽은 이 서비스로 가라.
- `tls` — 시크릿을 TLS 타입으로 만들어 인증서를 넣으면 이 도메인은 HTTPS로 통신된다. **앱에 직접 인증서를 넣지 않아도 인그레스가 그 역할을 대신**한다.

여기까지는 잘 이해된다. 그냥 이렇게 알고 쓰면 잘 동작한다. 문제는 "Kubernetes에서 **어떻게** 이렇게 동작할 수 있는 거지?" 하고 한 단계 더 들어가는 순간 혼란이 온다는 것이다.

### 오해 ① 인그레스를 만들면 구현체가 생긴다?

파드를 만들면 실체인 컨테이너가 만들어지듯, 인그레스를 만들 때마다 룰을 수용하는 어떤 구현체가 만들어지지 않을까 오해하기 쉽다. **아니다.** 인그레스는 **인그레스 컨트롤러(NGINX)를 반드시 설치해야 동작하는 리소스**다.

서비스와 같은 개념이라고 보면 된다.

| 리소스 | 리소스 자체는 | 실제로 동작시키는 실체 |
|--------|---------------|------------------------|
| 서비스 | 포트를 넣고 IP는 자동 부여되는 **연결 정보** | kube-proxy + iptables |
| 인그레스 | 도메인 → 서비스 **트래픽 룰** | **NGINX 파드**가 인그레스를 읽고 룰대로 트래픽 관리 |

> Calico를 안 깔면 파드 네트워크가 안 만들어지고, 로드밸런서를 연결 안 하면 LoadBalancer 타입 서비스가 제대로 동작 안 하듯이, **NGINX를 안 깔면 인그레스를 만들어도 동작하지 않는다.**

이렇게 알고 보면 **Kubernetes 스스로 할 수 있는 게 별로 없어 보인다.** NGINX 말고도 인그레스 컨트롤러 역할을 하는 오픈소스는 많다. Kubernetes는 "이렇게 사용하라"는 **표준을 제시**하고, 어떤 오픈소스든 그 표준만 맞추면 Kubernetes 안에서 쓸 수 있게 해주는 역할을 한다.

> 처음 공부할 때는 "Kubernetes가 제공하는 리소스만 잘 알면 되겠지"라고 시작하지만, 막상 공부해 보면 **이 섹션 내용의 반은 NGINX 사용법**이다. 다음 강의(해수편)부터가 본격적인 오픈소스의 세계다.

### 오해 ② 기존처럼 서비스로 트래픽을 날리면 되나?

그렇지 않다. 이제 **모든 트래픽은 NGINX를 통해서** 들어간다. NGINX에 LoadBalancer 타입 서비스를 만들고, 외부에서 도메인으로 호출하면 그게 결국 파드까지 간다.

### 오해 ③ NGINX가 인그레스 룰에 적힌 서비스로 트래픽을 보낸다?

연결고리를 따라 "NGINX → 서비스 → 파드"로 흐를 것 같지만 아니다. **NGINX가 알아서 인그레스를 조회하고, 관련 정보를 통해 해당 파드로 직접 트래픽을 보낸다.** (아래 인프라 구성에서 상세히)

### 왜 스스로 공부하면 잘 받아들여지지 않나

지금까지 배운 오브젝트는 **셀렉터와 레이블**로 관계가 명확히 연결됐고, 각 오브젝트에 연결되는 속성이 명시적이라 전체 구조를 파악하기 쉬웠다. 그런데 인그레스는

- 트래픽을 보내기 위한 **중간 연결고리가 많아지고**,
- NGINX와 인그레스 사이의 연결이 복잡하며,
- 그 중간고리 역할을 하는 **IngressClass**라는 오브젝트까지 있다.

Ingress, Ingress Controller, NGINX, IngressClass — 생소한 용어가 한꺼번에 나오니 혼란스러울 수밖에 없다. 하지만 서비스 수업처럼 **인프라 관점에서 보면 전체 구성이 당연하게 느껴진다.**

### 이번 섹션의 두 가지 목표

1. 가장 오해하기 쉬운 **인그레스를 제대로 이해**한다.
2. 실무에서 인그레스 구성은 한 번 잡아 놓으면 크게 바꿀 일이 없다. **가장 많이 손대는 곳은 NGINX 설정**이다. NGINX는 많은 인그레스 룰을 가지고 여러 파드로 트래픽을 분배하는데, 트래픽 관리에는 정말 많은 이슈가 있고 그걸 해결하는 기능이 NGINX에 있다. **설치하고 바로 부딪치는 이슈들을 NGINX 기능으로 해결하면서, 시작 단계에서 어떤 설정을 건드리게 되는지** 안다.

## 인프라 구성 — 서비스 수업의 배경 위에 그리기

서비스 수업에서 그렸던 배경 그대로다. 프론트엔드 **포탈**과 백엔드 **코어** 두 앱이 있고, 두 파드에 연결된 서비스는 ClusterIP 타입이며 모두 한 네임스페이스에 있다.

### 포탈을 NodePort나 LoadBalancer로 열지 않는다

포탈은 외부에서 접속해야 하니 앞에서 배운 NodePort나 LoadBalancer를 붙여야 하나 싶지만, **실무에서는 포탈을 그렇게 오픈하지 않는다.** NGINX를 통해서 트래픽을 받는다. NGINX가 인증서, 트래픽 관리 등 도와주는 게 많고, 그만큼 **포탈 자체에서는 신경 쓸 게 적어지기** 때문이다.

### NGINX 쪽 구성

```
[외부 사용자] --portal.com--> DNS --> [LoadBalancer 서비스] --> [NGINX 파드 (Deployment)]
[사내 서버]  --k8s-core---> 사내 DNS -----------------------^
                                   (ingress-nginx 네임스페이스)
```

- NGINX는 Deployment로 만들어진 파드다. (ReplicaSet은 생략)
- 모든 외부 트래픽을 NGINX가 받으니 **NGINX에 LoadBalancer 타입 서비스를 연결**한다.
- NGINX 관련 리소스는 모두 **`ingress-nginx` 네임스페이스** 안에 만들어진다.
- 사용자는 도메인을 입력 → DNS 질의 → 트래픽이 들어온다. 포탈이 코어를 호출하기도 하지만, **내부에서 코어로 직접 API를 보내는 경우도 많아서** 사내 DNS 서버에 `k8s-core` 같은 도메인을 등록해 트래픽이 들어오기도 한다.

이 트래픽들이 각각의 파드로 잘 들어가게 하려고 인그레스를 작성한다.

| 인그레스 속성 | 의미 |
|---------------|------|
| `rules[].host` | 이 호스트 이름으로 호출이 오면 |
| `backend.service.name` / `port` | 이 이름의 서비스와 80 포트로 전달 |
| `path: /` | 이 도메인으로 들어오는 **모든 하위 패스**를 그 서비스로. 패스별로 분기하려면 여기에 분기할 패스를 추가 |
| `ingressClassName` | 아래 IngressClass 항목에서 |

## 내가 인그레스를 만들면 NGINX는 무엇을 하나

```
NGINX 파드
  │ ① ClusterRoleBinding으로 강력한 ClusterRole 보유
  ├─→ kube-apiserver: 네임스페이스에 상관없이 모든 Ingress 조회
  │ ② 인그레스에서 트래픽을 보낼 "서비스 이름" 확인
  ├─→ kube-apiserver: 그 서비스 이름으로 EndpointSlice 조회
  │ ③ EndpointSlice 안의 파드 IP 확인
  └─→ 파드로 직접 트래픽 전달
```

1. NGINX를 설치할 때 **ClusterRole**이 **ClusterRoleBinding**으로 연결된다. 그래서 kube-apiserver로 **네임스페이스에 상관없이 모든 인그레스를 조회**할 수 있다.
2. NGINX는 인그레스 내용을 보고 트래픽을 보낼 **서비스의 이름**을 확인한다. 서비스로 트래픽을 보내기 위해서가 아니다. **서비스 이름으로 알 수 있는 EndpointSlice 오브젝트를 찾기 위해서**다.
3. EndpointSlice 안에 파드 IP가 있다. 여기서 IP를 확인하고 **직접 파드로 트래픽을 전달**한다.

> 이전엔 Endpoint 오브젝트에서 IP를 찾았지만, 최근 Kubernetes에는 Endpoint에 속성이 더 확장된 **EndpointSlice**가 추가됐고 NGINX도 이 오브젝트를 확인하는 걸로 바뀌었다.

이렇게 외부의 호출 정보에 따라 해당 파드로 트래픽을 분산시키는 역할을 **인그레스 컨트롤러**라고 하고, 그 역할을 하는 오픈소스 중 하나가 NGINX다.

> **이 구성에서 트래픽 분산은 더 이상 서비스의 iptables가 아니라 NGINX가 한다.**

## IngressClass — NGINX와 인그레스의 중간 고리

- NGINX를 설치할 때 **IngressClass**라는 리소스가 만들어지고, 이름은 `nginx`다.
- 이 IngressClass는 NGINX를 설치할 때 NGINX에 지정해 준다.
- 그러면 NGINX는 **`nginx`라는 클래스 이름이 붙은 인그레스들의 룰만 적용**한다. 다른 이름의 클래스가 붙어 있으면 조회하지 않는다.

이걸 보면 "NGINX가 여러 개 설치될 수도 있겠구나" 하는 생각이 든다. 맞다.

### NGINX를 여러 개 두는 경우

서비스가 클 경우 **로드밸런서에 장애가 나거나 NGINX 설정을 건드렸을 때 여길 지나는 모든 서비스에 영향**이 간다. 그래서 서비스별로 트래픽을 분리하려고 **새 로드밸런서에 새 NGINX를 연결**해야 할 때가 있다.

```
LB 1 → NGINX (class: nginx)  → ingressClassName: nginx  인그레스들만 반영
LB 2 → NGINX (class: nginx2) → ingressClassName: nginx2 인그레스들만 반영
```

IngressClass도 새 이름으로 만들고 새 NGINX에 적용하면, 그 클래스 이름의 인그레스들은 그 NGINX에서만 룰이 반영된다.

### 클래스를 안 주면?

IngressClass를 여러 개 만들 때 **딱 하나에만 default IngressClass 옵션**을 줄 수 있다. 클래스를 안 준 인그레스들은 default로 선언된 IngressClass가 적용된다. 굳이 안 줄 필요는 없고, 알고만 있으면 된다.

> 인그레스는 **NGINX의 동작 방식을 알아야 제대로 이해할 수 있는 개념**이었다.

# 5부. NGINX 설치와 인그레스 기본 실습

## 커뮤니티용과 상용 — 반드시 구분해서 들어갈 것

NGINX 인그레스 컨트롤러는 **커뮤니티용**과 **상용 제품**이 있다. 상용에는 더 많은 고급 기능이 있기 때문에, 커뮤니티용을 설치해 놓고 실수로 상용 문서를 보며 설정하면 안 된다. 그런데 이름이 서로 뒤집혀 있어서 정말 헷갈린다.

| | 커뮤니티용 (Kubernetes 프로젝트) | 상용 (NGINX Inc.) |
|---|---|---|
| GitHub | `kubernetes/ingress-nginx` | `nginxinc/kubernetes-ingress` |
| Artifact Hub 경로 | `ingress-nginx/ingress-nginx` | `nginx/nginx-ingress` |
| 가이드 문서 | kubernetes.github.io/ingress-nginx | docs.nginx.com — NGINX Ingress Controller |
| 설치 후 네임스페이스 | `ingress-nginx` | `nginx-ingress` |

- 구글에서 "nginx"로 문서나 GitHub를 검색하면 어느 게 커뮤니티용이고 상용인지 구별이 안 된다. 커뮤니티용과 상용이 있다는 걸 모르면 커뮤니티용을 깔아 놓고 상용 문서를 보고 있기 십상이다.
- Artifact Hub에서 "nginx"를 치면 NGINX가 잔뜩 나와서 골라 설치하기도 까다롭다. 강사도 잘못 설치한 적이 종종 있다.

> **NGINX는 꼭 링크를 정리해 두고 그 링크로 들어가라.** 강사가 강력하게 권하는 부분.

## Helm으로 설치

이번 실습도 마스터 서버에서 한다. 먼저 Helm을 설치하고(맥은 별도 명령), 커뮤니티용 NGINX를 받아 배포한다.

```bash
# 커뮤니티용 Helm 레포지토리 추가 후 차트 다운로드
helm repo add ingress-nginx https://kubernetes.github.io/ingress-nginx
helm pull ingress-nginx/ingress-nginx
tar -xf ingress-nginx-*.tgz && cd ingress-nginx
ls                                # Helm 패키지 파일들

# 강의 자료실(강사 GitHub)의 values 파일을 추가로 다운로드

helm install ingress-nginx . -f values.yaml -n ingress-nginx --create-namespace
helm list -n ingress-nginx        # STATUS deployed 확인
```

### values 파일에서 봐야 할 것

| 설정 | 내용 | 이유 |
|------|------|------|
| `controller.allowSnippetAnnotations: true` | NGINX의 **snippet** 기능 허용 | 다음 수업(리다이렉션 포트 변경)에서 필요. 기본 기능이 아니라 켜야 함 |
| `controller.service.type: LoadBalancer` + `nodePorts.http: 31080`, `https: 31443` | LoadBalancer 타입 서비스를 만들고 NodePort도 지정 | HTTP는 이번 실습, HTTPS는 다음 수업 TLS 실습에서 사용 |
| `controller.ingressClassResource.name: nginx`, `default: true` | IngressClass를 `nginx`라는 이름으로 만들고 **default IngressClass**로 선언 | 클래스가 여러 개일 때 클래스 없는 인그레스가 여기로 |
| `controller.ingressClass: nginx` | 생성한 IngressClass를 NGINX에 적용 | NGINX가 기동되면서 이 값을 파라미터로 가져감 (아래에서 확인) |
| `rbac.create: true` | ClusterRole과 ClusterRoleBinding을 생성해 NGINX에 할당 | 모든 네임스페이스의 인그레스 조회 권한 |

## 설치된 구성 확인

```bash
kubectl get ns ingress-nginx
kubectl get all -n ingress-nginx
```

- 네임스페이스 `ingress-nginx`가 만들어졌다.
- 서비스는 **LoadBalancer 타입**으로, 지정한 NodePort로 잘 생성됐다.
- NGINX는 `ingress-nginx-controller`라는 **Deployment**로 생성됐고 파드가 떠 있다.

> 지금은 테스트라 파드 하나지만, 실무에서는 **NGINX가 모든 트래픽의 중심**이므로 **최소 3개 이상** 만들어 두는 게 좋다.

### IngressClass

```bash
kubectl get ingressclass nginx -o yaml
```

```yaml
metadata:
  annotations:
    ingressclass.kubernetes.io/is-default-class: "true"   # default 선언은 annotation으로 들어간다
  name: nginx
spec:
  controller: k8s.io/ingress-nginx
```

`spec.controller` 값은 뭔가 잘 생각해서 넣어야 할 것 같지만 **특별한 기준은 없다.** NGINX의 공식 식별자 값일 뿐이다. IngressClass 이름처럼, **IngressClass마다 고유한 값**을 주면 된다.

### NGINX에 주입된 IngressClass

```bash
kubectl get pod -n ingress-nginx <ingress-nginx-controller-파드> -o yaml
```

```yaml
containers:
  - args:
      - --ingress-class=nginx                  # NGINX가 볼 IngressClass 이름
      - --controller-class=k8s.io/ingress-nginx  # 그 식별자
```

NGINX를 기동시킬 때 추가로 주는 옵션이다. NGINX마다 이렇게 IngressClass를 지정하는데, **새 로드밸런서에 새 NGINX를 설치할 때는 이 값들이 다르게 들어가 있는지 꼭 확인**해야 한다.

### ClusterRole / ClusterRoleBinding

```bash
kubectl get clusterrole ingress-nginx -o yaml          # 내용이 엄청 많다
kubectl get clusterrolebinding ingress-nginx -o yaml
```

- ClusterRole에는 여러 리소스를 조회할 수 있는 권한이 있다. NGINX가 알아서 하는 영역이니 꼼꼼히 볼 필요는 없고, **`endpointslices`를 조회할 수 있는 권한이 있다**는 것만 확인한다.
- ClusterRoleBinding에는 이 ClusterRole과, NGINX 설치 시 만들어진 **ServiceAccount**가 연결돼 있다. 이 바인딩 덕분에 NGINX가 kube-apiserver로 **모든 네임스페이스의 인그레스를 조회**할 수 있다.

## 인그레스 생성과 도메인별 트래픽 분리 테스트

포탈과 코어를 위한 서비스, 파드, 그리고 인그레스들을 배포한다.

```bash
kubectl get svc,ingress -n <ns>
```

- 포탈 서비스는 **ClusterIP 타입**이다.
- 인그레스에는 `portal.com`이라는 host로 트래픽이 들어오면 포탈 서비스 이름과 포트로 보내라는 내용이 있고, `ingressClassName: nginx`도 잘 들어가 있다.

### 서비스 이름으로 파드 IP 찾기 — Endpoint와 EndpointSlice

```bash
kubectl get endpoints -n <ns>                  # 서비스와 같은 이름
kubectl get endpointslices -n <ns>             # 서비스이름-<난수>  (탭 자동완성으로 찾기)
kubectl get endpointslices <이름> -n <ns> -o yaml
```

| | Endpoint | EndpointSlice |
|---|---|---|
| 이름 | 서비스와 동일 | **서비스 이름 + 난수** |
| 서비스와의 연결 | 이름으로 | `metadata.ownerReferences`에 **서비스 정보** → NGINX가 이걸로 찾는다 |
| 파드 IP | `subsets.addresses` | `endpoints[].addresses` |
| 추가 속성 | — | `conditions` 등 Endpoint에는 없는 속성들 |

### /etc/hosts로 DNS 서버 없이 도메인 테스트

```bash
# 마스터 노드 (강의 IP는 192.168.56.30, 자료 오타는 56으로 수정)
vi /etc/hosts
192.168.56.30  k8s-core

# Windows: C:\Windows\System32\drivers\etc\hosts (관리자 권한 에디터로)
192.168.56.30  portal.com
```

`/etc/hosts`에 IP와 도메인을 등록해 두면 DNS 서버 없이도 그 도메인이 그 IP로 간다.

```bash
# 마스터에서 내부 서버 시나리오
curl http://k8s-core:31080/hostname        # → 코어 파드 응답

# 크롬에서 외부 사용자 시나리오
http://portal.com:31080/hostname           # → 포탈 파드 응답
```

각 인그레스 룰에 따라 트래픽이 잘 분배된다.

### NGINX 로그

```bash
kubectl logs -n ingress-nginx <ingress-nginx-controller-파드> --tail 10 -f
```

포탈에서 트래픽을 날리면 로그가 찍히고, **어떤 서비스로 가는지**에 대한 정보도 있다. NGINX만 보면 외부에서 어디로 호출하는지 **트래픽 흐름을 한눈에** 볼 수 있다.

# 6부. NGINX를 쓰기 시작하면 바로 마주치는 이슈와 설정

## TLS — 인증서를 어디에 심을 것인가

### 배경

| 호출 | 기본 포트 | 암호화 |
|------|-----------|--------|
| `http://` | 80 | 없음. 중간에서 트래픽을 까보면 내용이 보인다 |
| `https://` | 443 | **TLS 암호화.** 까봐도 내용을 알 수 없다 |

인터넷을 지나는 통신에 대해 TLS 암호화는 **기업 보안의 필수**다. 암호화를 하려면 인증서가 필요하다.

| 인증서 | 브라우저 표시 | 비용 | 용도 |
|--------|---------------|------|------|
| 공인인증서 | 신뢰된 사이트 | 있음 | 운영 |
| 사설인증서 | "신뢰되지 않는 기관" 경고 (암호화 자체는 잘 동작) | 없음 | 테스트 |

TLS 메커니즘 자체는 해수편에서 다루고, 여기서는 **통신에는 무조건 TLS를 적용한다는 가정**으로 간다.

### 심을 수 있는 위치 네 곳

기존엔 애플리케이션에 직접 TLS를 적용했다. 앱이 많아질수록 일일이 인증서를 관리하기 불편하다. Kubernetes 환경에서는 선택지가 더 있다.

| 위치 | 적용 범위 | 언제 쓰나 |
|------|-----------|-----------|
| **앱 직접** | 그 앱만 | 예전 방식. 앱이 늘수록 관리 부담 |
| **인그레스 `tls`** | 지정된 서비스에 연결된 **모든 파드**에 동일 인증서 | **공인인증서를 앱 도메인 이름으로 샀을 때.** 접속 도메인과 인증서의 DNS 이름이 맞아야 하므로 그 서비스의 인그레스에 넣어야 한다 |
| **NGINX 자체** | NGINX를 지나는 **모든 통신** | 설치 시 기본 세팅되어 있다. **사설 인증서·테스트**는 인그레스에 안 넣어도 이걸로 TLS 통신 가능. 공인인증서라면 여러 앱에 적용할 수 있는 도메인을 사야 하니 **비용이 더 든다** |
| **로드밸런서** | **외부 사용자 ↔ LB 구간만** | 사용자는 443으로 들어오지만 LB 뒤로는 80으로 연결돼 내부는 HTTP. LB까지 들어오면 기업 내부망이니 보안상 큰 문제 없음 |

- 인그레스에 TLS가 있으면 "인증서를 두 번 타나?" 싶지만, **TLS가 적용된 인그레스를 쓸 때는 NGINX 인증서가 미적용**된다. 인그레스의 인증서만 적용된다.
- 정리하면 **사설 인증서는 NGINX에 있는 걸 쓰면 되고, 공인인증서는 DNS 이름을 어떻게 샀느냐에 따라 설치 위치가 달라진다.**

### 로드밸런서에만 심을 때의 주의점

워커노드들이 **서로 다른 지역**에 있을 수 있다. 특히 클라우드는 센터 장애에 대비해 워커노드를 지역별로 분산시키기도 한다. 이 경우 내부 통신이라도 **트래픽이 사실상 외부망으로 나가기 때문에** 로드밸런서에만 인증서를 적용하면 안 된다.

> Kubernetes 위에는 또 기존 인프라가 있다. **항상 전체적으로 생각하는 시각**이 필요하다. 이미 상위단에서 인증서를 적용하고 있는데 Kubernetes 내부에 또 적용하면 **성능이 느려진다.** 어떤 인증서가 있고, 내 상황에서 어디에 설치할지, 그 장단점이 무엇인지 알고 있어야 한다.

## 내부 호출도 NGINX를 탄다 — path 분기와 rewrite-target

비즈니스 로직에 코어 외에 **커스트**(customer의 약어, 이름은 중요하지 않다)도 있다고 하자. 두 앱에는 많은 API가 있고, 포탈은 메뉴나 페이지에 따라 두 앱으로 API를 호출한다. 이때 **외부에서만 NGINX를 통해 파드로 가는 게 아니라, 클러스터 내부 파드에서 타 앱을 호출할 때도 NGINX를 사용**한다.

인그레스에 패스별로 서비스를 다르게 줄 수 있다고 했으니 서비스별로 패스를 만들면 될 것 같지만, **두 앱에 똑같은 API가 있으면 문제**가 된다. 그래서 이렇게 한다.

```
포탈에서 호출하는 URL:
  http://ingress-nginx-controller.ingress-nginx/core/hostname
        └─ NGINX 서비스이름.네임스페이스 (CoreDNS 질의) ─┘ └─ 대상 서비스 이름을 패스 맨 앞에
```

```yaml
metadata:
  annotations:
    nginx.ingress.kubernetes.io/use-regex: "true"
    nginx.ingress.kubernetes.io/rewrite-target: /$2     # 슬래시 기준 두 번째 이후 패스만 사용
spec:
  rules:
    - http:
        paths:
          - path: /core(/|$)(.*)     # core로 시작하면 뒤에 어떤 패스가 오건 매칭
            pathType: ImplementationSpecific
            backend:
              service:
                name: core
                port:
                  number: 80
```

- 포탈은 서비스와 네임스페이스를 붙인 도메인 이름으로 NGINX를 호출한다. (서비스 수업의 CoreDNS 질의)
- 도메인 뒤에 **호출할 대상 서비스의 이름을 패스의 가장 앞에** 붙인다.
- 인그레스 `path`는 포탈에서 분기한 패스로 시작하고 뒤에 정규식이 붙는다.
- **`rewrite-target`이 중요하다.** 이 API는 `/core...` 패스의 인그레스에 매칭되지만, 서비스로 나갈 때는 **`core` 부분을 뺀 `/hostname`만** 파드로 전달된다.

## HTTP로 들어온 사용자를 HTTPS로 보내기

사용자는 HTTPS로 들어오면 되는데 간혹 HTTP를 친다. **80 포트는 통상 막아 놓기 때문에** "페이지를 찾을 수 없다"는 화면을 본다. 그런데 알아서 HTTPS로 리다이렉션되는 경험을 해봤을 텐데, 그건 **서버 측에서 이 기능을 설정해 줬기 때문**이다.

```yaml
metadata:
  annotations:
    nginx.ingress.kubernetes.io/ssl-redirect: "true"     # HTTP → HTTPS, 기본 443 포트로
```

우리는 로드밸런서가 없고 NodePort로 보내야 하므로 **31080 → 31443**으로 리다이렉션돼야 한다. 포트를 바꾸려면 `configuration-snippet`을 쓴다.

```yaml
metadata:
  annotations:
    nginx.ingress.kubernetes.io/configuration-snippet: |
      if ($scheme = http) {
        return 308 https://$host:31443$request_uri;    # 리다이렉션할 포트만 원하는 값으로
      }
```

> 이 기능은 기본 기능이 아니라 **snippet 기능이 활성화**돼 있어야 한다. 그래서 설치할 때 `allowSnippetAnnotations`를 true로 바꿔 뒀던 것.

## 파드에 부하가 걸렸을 때 — 로드밸런싱 알고리즘

코어 앱의 두 파드 중 하나에 갑자기 부하가 생겨 트래픽을 처리할 수 없는 상황이라고 하자.

| 경로 | 분배 방식 | 부하 파드 처리 |
|------|-----------|----------------|
| NGINX 없이 **서비스로** | iptables **라운드로빈**, 규칙 변경 불가 | Readiness Probe가 실패해 엔드포인트에서 빠지지 않는 한 부하 상태를 모르고 **계속 보낸다** |
| **NGINX 통해서** | 기본은 라운드로빈이지만 **룰을 바꿀 수 있다** | **EWMA**로 바꾸면 응답 시간이 길어진 파드에 부하가 있다고 판단해 **트래픽을 덜 보낸다** |

지금까지는 인그레스로 설정했지만 이번엔 **ConfigMap**으로 NGINX 설정을 바꾼다.

```yaml
# kubectl edit configmap ingress-nginx-controller -n ingress-nginx
data:
  load-balance: ewma        # 기본값 round_robin
```

> 파드 입장에서는 부하가 생기면 트래픽이 덜 오니 **현재 부하를 처리하는 데 집중**할 수 있다.

### ConfigMap을 바꿔도 NGINX는 재기동하지 않는다

일반적으로 ConfigMap을 수정하면 파드를 재기동해야 반영된다. 하지만 NGINX는 환경변수를 읽어서 기동하는 방식이 아니라, **떠 있는 상태에서 kube-apiserver로 계속 API를 날려 ConfigMap을 조회하고, 변경이 있으면 바로 설정에 반영**한다. NGINX는 모든 트래픽을 관장하므로 **웬만해선 재기동되지 않도록 설계**돼 있다.

### 인그레스 설정과 ConfigMap 설정의 차이

| 설정 위치 | 영향 범위 |
|-----------|-----------|
| 인그레스 annotation | **그 인그레스를 통해 보내지는 서비스**만 |
| ConfigMap | **NGINX 자체 설정** → NGINX를 지나는 **모든 트래픽** |

## 로그 포맷과 타임존

- **로그 포맷** — 앞 수업에서 본 NGINX 로그는 처음 보는 사람은 이해하기 힘들다. ConfigMap으로 **내가 이해할 수 있는 내용으로 필요한 것만** 포맷을 바꿀 수 있다.
- **타임존** — 기본은 UTC다. 오픈소스는 대개 UTC를 쓴다.
  - 글로벌 프로젝트는 **모든 시스템의 타임존을 UTC로 맞추고 웹단에서 지역별 시간을 계산**한다. 개발자는 로그 볼 때마다 시간을 계산하거나 별도의 로그 조회 스크립트를 만든다. 어쩔 수 없는 부분.
  - 순수 국내 프로젝트는 굳이 UTC로 할 필요 없고 **Asia/Seoul**로 바꾼다. 이건 **파드의 env**로 설정한다.

> NGINX를 컨트롤하는 설정 방법이 참 많다(인그레스 annotation, ConfigMap, 파드 env, Helm values). 구글링과 NGINX 문서를 많이 볼 수밖에 없고, 한 번에 모든 기능을 알기는 불가능할 정도로 많다. **실무에서 이슈를 하나씩 부딪쳐 보면서 배워 나가면 된다.**

# 7부. NGINX 실습 — TLS, 리다이렉션, rewrite, EWMA, 로그, 타임존

## TLS ① NGINX 자체 인증서 확인

브라우저에서 `https://portal.com:31443/hostname`을 호출한다.

- 사설 인증서라 경고가 나오지만 "고급 → 이동"으로 들어가면 응답이 온다.
- 인증서를 열어 보면 **"Kubernetes Ingress Controller Fake Certificate"** — 인그레스 컨트롤러가 만든 인증서다. NGINX로 오는 **모든 HTTPS 통신에 공통 적용**되는 인증서이며, 인그레스에 전용 인증서를 만들면 이건 타지 않게 된다.

## TLS ② 인그레스 전용 시크릿 만들기

```bash
mkdir tls && cd tls

# 개인 키 생성
openssl genrsa -out portal.key 2048

# 키로 인증서 서명 요청(CSR)을 만들고 자체 서명 — 기간 10년, 도메인 이름 포함
openssl req -x509 -new -key portal.key -days 3650 -out portal.crt -subj "/CN=portal.com"

# TLS 타입 시크릿 생성
kubectl create secret tls portal-tls --cert=portal.crt --key=portal.key -n <ns>
kubectl get secret portal-tls -n <ns> -o yaml      # data.tls.crt / data.tls.key 확인
```

인증서 생성은 간단한 방법만 다루고 자세한 내용은 관리자를 위한 해수편에서.

포탈 인그레스에 TLS를 추가한다.

```bash
kubectl edit ingress portal -n <ns>
```

```yaml
spec:
  # ... rules ...
  tls:                      # status 위에 추가
    - hosts:
        - portal.com
      secretName: portal-tls
```

> 같은 브라우저에서 다시 호출하면 **캐시 때문에 아까의 NGINX 인증서가 그대로** 적용된다. **다른 브라우저**로 열어야 한다.

다른 브라우저로 호출하면 응답이 오고, 인증서를 보면 **방금 만든 인증서**가 적용돼 있다. **인그레스에 TLS를 주면 NGINX 인증서보다 우선 적용**된다.

## 리다이렉션 — 인그레스에 TLS를 넣는 순간 기본값이 바뀐다

아직 NGINX에 아무 설정도 안 준 상태에서 HTTP로 호출해 본다.

| 호출 | 결과 |
|------|------|
| `http://portal.com:31080/hostname` | "사이트에 연결할 수 없음". 주소창을 보면 **`https://portal.com/hostname`으로 바뀌고 포트가 사라졌다** |
| `http://k8s-core:31080/hostname` | 내가 보낸 포트 그대로 응답이 잘 온다 |

왜 결과가 다른가. 포탈 인그레스에는 TLS가 적용돼 있고, 코어 인그레스에는 없다.

> **인그레스에 TLS가 적용되면 `ssl-redirect`가 기본값 `true`로 적용된다.** 그래서 포탈은 자동으로 HTTPS + 기본 포트 443으로 리다이렉션됐고, 코어는 TLS가 없어 준 포트 그대로 들어갔다.

즉 인그레스에 TLS를 적용했는데 HTTP와 HTTPS를 **모두** 쓰고 싶다면 오히려 이 값을 **`false`로 바꿔야** 한다.

### configuration-snippet으로 리다이렉션 포트 바꾸기

```bash
kubectl edit ingress portal -n <ns>
```

```yaml
metadata:
  annotations:
    nginx.ingress.kubernetes.io/configuration-snippet: |
      if ($scheme = http) {
        return 308 https://$host:31443$request_uri;
      }
```

`$host`에는 `portal.com`이 그대로, `$request_uri`에는 `/hostname`이 그대로 들어가고 **포트만 31443으로** 바뀐다. 다시 새 창에서 `http://portal.com:31080/hostname`을 호출하면 바로 HTTPS로 변경되고 포트도 지정한 포트로 전환된다.

> NGINX 문서에는 annotation으로 줄 수 있는 설정도, ConfigMap으로 줄 수 있는 설정도 정말 많다. 미리 다 해보는 건 비효율적이고 재미도 없다. **실무에서 필요한 기능이 생겼을 때 키워드로 검색해서 읽어 보고 적용해 보며 익히고, 한 번 적용한 기능은 잘 정리해 둔다.** 이렇게 정리한 내용을 쌓아 나가면서 실력을 높이면 된다. 부담 갖지 말 것.

## 내부 호출 — pathType과 rewrite-target

커스트 앱과, 포탈에서 커스트·코어로 내부 호출하기 위한 인그레스 두 개(`...-internal`)를 새로 배포한다.

### pathType 세 가지

| pathType | 매칭 규칙 | `path: /core`일 때 |
|----------|-----------|--------------------|
| **Prefix** | 패스의 **시작 부분만 일치**하면 | `/core`, `/core-abc`, `/core/hosts` 모두 매칭 |
| **Exact** | 패스가 **정확히 일치**해야 | `/core`만 매칭 |
| **ImplementationSpecific** | **인그레스 컨트롤러 구현에 따라** | 우리는 NGINX를 쓰니 **NGINX가 패스 룰을 컨트롤**한다. 이번 실습이 이 방식 |

Kubernetes 문서에 각 타입의 예시가 여러 개 있으니 참고할 것.

### internal 인그레스 내용

```bash
kubectl get ingress core-internal -n <ns> -o yaml
```

- `pathType: ImplementationSpecific`
- `path: /core(/|$)(.*)` — core로 시작하지만 뒤에 정규식
- annotation `use-regex: "true"` — NGINX 정규식 사용
- annotation `rewrite-target: /$2` — **중요**

> 강사도 이런 정규식은 한 번 공부한 다음 써먹고 까먹는다. 이해하려고 노력하지 않는다. NGINX 문서의 rewrite 예제를 찾아서 **내가 쓸 예제를 고른 다음 바로 테스트**한다.

문서의 예시 (`path: /something(/|$)(.*)`, `rewrite-target: /$2`):

| 요청 | 파드로 가는 패스 |
|------|------------------|
| `/something` | `/` |
| `/something/` | `/` |
| `/something/new` | `/new` ← 우리가 하려는 것 |

### 포탈 파드에서 호출

```bash
kubectl exec -it <portal-파드> -n <ns> -- bash      # 탭 자동완성으로 파드 이름, 두 개 중 하나

curl http://ingress-nginx-controller.ingress-nginx/core/hostname    # → 코어 파드
curl http://ingress-nginx-controller.ingress-nginx/cust/hostname    # → 커스트 파드
```

도메인은 NGINX 컨트롤러의 **서비스이름.네임스페이스**이고, 경로 맨 앞이 `core`냐 `cust`냐에 따라 각각의 인그레스가 잘 먹혔다.

### 인그레스가 여러 개일 때 어느 것이 적용되나

방금 만든 internal 인그레스에는 **host를 안 줬기 때문에 host가 `*`**로 들어간다. 어떤 호스트 이름이 들어와도 이 룰에 걸린다는 뜻이다. 그럼 기존 `k8s-core` host 인그레스에는 문제가 없을까. 코어로 가는 인그레스가 두 개이니 **꼭 확인**해야 한다.

| 외부 호출 | 결과 | 적용된 인그레스 |
|-----------|------|-----------------|
| `http://k8s-core:31080/hostname` | 정상 응답 | 기존 host 인그레스 |
| `http://k8s-core:31080/core/hostname` | **에러** — 코어에 `/core/hostname` API가 없다 | 역시 기존 host 인그레스 (rewrite가 안 됨) |
| 기존 host 인그레스 삭제 후 `http://k8s-core:31080/core/hostname` | 정상 응답 — `core`가 제거되어 `/hostname`으로 호출됨 | `*` internal 인그레스 |

> **`*`보다 호스트 이름이 매칭된 인그레스가 우선 적용된다.** 인그레스가 여러 개 있어도 **딱 하나만 적용**되므로, 헷갈리면 이것저것 테스트해 보며 감을 익힐 것.

## 로드밸런싱 — EWMA 적용 전후 비교

실습 구성: 포탈에서 코어로 실시간 트래픽을 날리면서, 코어 파드 하나에 부하를 준다.

```bash
# 창 1 — 포탈 파드에서 0.5초마다 코어 호출
kubectl exec -it <portal-파드> -n <ns> -- bash
while true; do curl -s http://ingress-nginx-controller.ingress-nginx/core/hostname; echo; sleep 0.5; done

# 창 2 — 코어 파드 두 개 중 하나로 들어가서 부하 생성 API 호출
kubectl exec -it <core-파드> -n <ns> -- bash
curl localhost:8080/cpu-load      # (앱에서 제공하는 부하 API)
```

- **라운드로빈(기본)**: 부하가 들어갔지만 두 파드로 계속 균등하게 간다. 실무에서 무거운 트래픽이었다면 부하 파드에서 간혹 에러가 났겠지만, 지금 API는 hostname을 부르는 가벼운 로직이라 바로 응답이 와서 **파드에 부하가 있는지도 모른다.**

```bash
kubectl edit configmap ingress-nginx-controller -n ingress-nginx
```

```yaml
data:
  load-balance: ewma      # 저장하면 NGINX가 바로 적용
```

- **EWMA**: 다시 호출을 돌리고 부하를 주면, **부하가 있는 파드로는 트래픽이 확연히 덜 가고** 다른 파드로만 간다. 부하가 풀리자마자 다시 그 파드로도 트래픽이 간다. 한쪽으로 쭉 몰리기도 하지만, 부하가 있을 때는 덜한 쪽으로 더 주기 때문에 **부하 파드는 처리할 시간을 충분히 벌고 전체 서비스가 안정화**된다.

> 강사가 **정말 강력하게 추천**하는 기능. 특히 부하 테스트를 해보면 얼마나 좋은 기능인지 느끼게 된다.

## 로그 포맷 변경

```bash
kubectl logs -n ingress-nginx <ingress-nginx-controller-파드> --tail 10
```

기본 로그에는 시간, 어떤 API가 들어왔는지, 어떤 서비스로 갔는지는 대략 짐작되지만 뒤에 붙는 수치들은 처음엔 무슨 뜻인지 모른다. NGINX 문서의 **log-format** 설명을 보고, 모르는 값은 하나씩 찍어 보며 테스트한다. 강사가 만든 포맷은 각 값 앞에 **무슨 값인지 알 수 있는 문자**를 붙인 형태다.

```yaml
# kubectl edit configmap ingress-nginx-controller -n ingress-nginx
data:
  log-format-upstream: '$time_local | remote:$remote_addr | service:$service_name | pod:$upstream_addr | request:"$request" | type:$content_type | status:$status | sent:$body_bytes_sent | received:$request_length | time:$request_time'
```

포탈에서 트래픽을 날리고 다시 로그를 보면 지정한 포맷대로 찍힌다.

| 항목 | 의미 |
|------|------|
| time | 트래픽을 보낸 시간 |
| remote | 포탈의 IP (curl을 날린 곳) |
| service | 보내진 서비스 이름 |
| pod | 실제 호출된 파드의 IP |
| request | 날린 API |
| status | 200 OK |
| sent / received | 보낸·받은 패킷의 길이 |
| time | 응답 시간 (예: 0.002초) |

## 타임존 변경

현재 NGINX 로그의 시간이 PC 시간보다 **9시간 앞선다**(UTC). Asia/Seoul로 맞추려면 **Helm values를 수정하고 재배포**한다.

```yaml
# ingress-nginx/values.yaml
controller:
  extraEnvs:
    - name: TZ
      value: Asia/Seoul
```

```bash
helm upgrade ingress-nginx . -f values.yaml -n ingress-nginx
```

재배포됐으니 NGINX 파드 이름이 바뀐다. 다시 탭으로 파드를 찾아 트래픽을 날리고 로그를 보면 PC 시간과 맞는다.

> 실습이 많았다. 다음 수업(볼륨)은 바로 들으면 부담될 수 있으니 **여유를 두고 머릿속이 리프레시된 뒤** 편한 마음으로.

# 8부. 서비스 속성 — SessionAffinity와 TrafficPolicy

서비스 수업에서 "이 속성들은 거의 안 쓴다"고 했고, 그 이유를 인그레스 섹션이 끝난 뒤 설명하겠다고 했던 부분이다. 통신에 대한 여러 상식을 알게 되니 가벼운 마음으로.

## 세션이란

| 기능 | 내용 |
|------|------|
| **로그인 유지** | 로그인 후 인증 정보를 세션에 넣어 사용자에게 보내면, 이후 사용자는 이 세션 정보로 접근하고 서버는 그걸 확인해 로그인 없이 서비스를 쓰게 한다. **앱 개발 시 무조건 구현**해야 하는 기능 |
| **환경설정 유지** | 언어, 테마, 타임존을 한 번 세팅하면 세션에 담아 계속 유지 |
| **임시 저장** | 글을 쓸 때 자동 임시 저장되는 것도 세션 활용 |

활용 범위는 무궁무진하고, 서비스를 만든다면 꼭 알아야 하는 개념.

## 이중화된 앱에서 세션을 관리하는 네 가지 방법

사용자가 앱 1로 로그인해 세션이 만들어졌는데, 다음 메뉴 조회 트래픽이 앱 2로 갈 수 있다. 앱 2가 또 로그인하라고 하면 쓸 수 없는 서비스다.

| 방법 | 어떻게 | 문제 | 현재 위상 |
|------|--------|------|-----------|
| **① 쿠키** | 세션 관련 정보를 모두 **브라우저에 보관** → 어느 서버로 가든 통신 가능 | 브라우저의 쿠키에 접근하기는 어렵지 않아 악성 소프트웨어가 깔리면 **세션 정보를 쉽게 털린다** | 로그인 같은 중요 정보는 **절대 담으면 안 됨.** 언어·테마·시간처럼 문제없는 정보에는 사용 |
| **② 스티키 세션** | 로드밸런서가 **사용자 IP 기준으로 한 번 앱 1로 보냈으면 로그아웃까지 계속 앱 1로** | 앱 1이 죽으면 문제. 한 서버로 사용자가 몰려 **트래픽 분배가 비효율적** | 초기 구축에서 급할 때나 쓴다. 시스템이 커질수록 불편. **서비스의 `sessionAffinity`가 바로 이것** |
| **③ 세션 복제** | 앱들 간에 세션이 바뀔 때마다 서로 공유 | 마이크로서비스화로 앱이 많아지며 **동기화 부하**가 서버·네트워크에 커짐 | 예전엔 많이 썼지만 점점 안 씀 |
| **④ 세션 저장소 (Redis 등)** | 세션 정보를 **메모리 캐시 시스템**에 저장, 모든 앱이 연결 | — | **현재 표준.** 보안 처리 추가 가능, 특정 앱 장애에도 OK, 메모리라 성능 좋음, 앱이 확장돼도 수용 |

> `sessionAffinity`는 스티키 세션이고 현재 잘 쓰이지 않는 방식이라 **속성도 크게 중요하지 않다**고 했던 것. 그래도 Kubernetes에서 이 기능을 한 번쯤 이해하고 넘어가는 건 나쁘지 않다.

## SessionAffinity 사용법

```yaml
spec:
  sessionAffinity: ClientIP          # 스티키 세션 활성화
  sessionAffinityConfig:
    clientIP:
      timeoutSeconds: 600            # 10분 동안만 동일 파드 유지
```

포탈에서 코어 서비스로 API를 보내면 **같은 클라이언트 IP일 경우 계속 같은 파드**를 호출한다. 개념만 알면 사용법은 정말 간단하다.

## internalTrafficPolicy

ClusterIP 타입의 코어 서비스가 있고 파드는 워커노드 두 곳에 분산돼 있다. 호출하는 포탈 파드는 워커노드 1에 있다.

| 값 | 동작 |
|----|------|
| `Cluster` (기본) | 대상 파드가 어느 노드에 있건 클러스터 내에 있으면 호출 |
| `Local` | **같은 워커노드 내의 파드와만** 통신. 다른 노드의 파드와는 통신 안 됨 |

굳이 Local을 쓸 일이 있을까. 포탈과 코어를 항상 같은 워커노드에 올라가게 설정하면 **워커노드 간 트래픽 이동 낭비를 없애 네트워크 성능**을 좋게 만들 수 있다. 하지만

- 강사는 이렇게까지 해서 성능을 개선해야 할 일이 없었고, 얼마나 개선되는지도 말하기 어렵다.
- 그림에선 포탈과 코어가 1:1로 보이지만 실무에서는 **포탈 하나에 10개 이상의 다른 종류의 파드**가 연결된다. 특정 관계의 앱들끼리 같은 노드에 넣는 게 불가능하고, 스케일링도 생각해야 한다.

> 성능을 떠나 **스케줄링 면에서 Local은 쓰기 어렵다.** 이런 기능이 있다 정도만.

## externalTrafficPolicy

외부에서 들어오는 통신과 내부 통신은 트래픽 라우팅 방식이 다르기 때문에 속성도 나눠져 있다. **NodePort나 LoadBalancer 타입 서비스를 쓸 때는 반드시 external 쪽**을 봐야 한다. 값은 똑같이 Cluster와 Local이지만, 보내는 주체가 외부라서 생각할 부분이 있다.

로드밸런서는 워커노드의 모든 NodePort로 트래픽을 골고루 분산시킨다.

| 값 | 동작 |
|----|------|
| `Cluster` (기본) | 어느 노드로 들어오건 **실제 파드가 있는 노드로 트래픽이 이동한 뒤** 파드 호출 |
| `Local` | 파드가 없는 워커노드 2로 트래픽이 들어오면 **서비스를 찾을 수 없다는 에러** |

Local이 매우 위험해 보이지만, **의외로 이렇게 쓰는 케이스를 종종 본다.** NGINX가 그 예다.

### NGINX + DaemonSet + externalTrafficPolicy: Local

**DaemonSet**은 모든 워커노드에 파드를 **딱 하나씩** 만들어 주는 컨트롤러다. NGINX를 DaemonSet으로 설치하면 모든 노드에 NGINX가 있으니 로드밸런서에서 어느 노드로 들어오건 에러가 나지 않는다. 실제로 NGINX Helm 설치에는 **Deployment로 할지 DaemonSet으로 할지 선택 옵션**이 있다.

| 구성 | 트래픽 경로 |
|------|-------------|
| **Deployment + Cluster** (지금까지 쓴 방식) | 노드 1로 들어옴 → NGINX가 없으면 노드 2로 이동 → NGINX → 호출할 파드가 그 노드에 없으면 또 이동. **노드 간 이동이 많다** |
| **DaemonSet + Local** | 어느 노드로 들어오건 바로 그 노드의 NGINX → 운 좋으면 같은 노드의 파드, 아니어도 **노드를 한 번만** 지나면 도달 |

> 기억할 것 두 가지. **로드밸런서를 쓸 때는 `externalTrafficPolicy`를 Local로 설정한다**는 것과, **DaemonSet으로 모든 워커노드에 앱을 배포하면 트래픽 효율이 좋아진다**는 것. 이 케이스를 위해 TrafficPolicy는 알아 둘 필요가 있다.

이것으로 서비스에 대한 모든 강의를 마쳤다. 다음 섹션은 Sprint 3의 마지막인 **볼륨**이다.

# 한 장 요약

## 기능과 그 실체

| 기능 | 하는 일 | 실체 |
|------|---------|------|
| 서비스 레지스트리 | 연결된 파드 IP 자동 관리 | **Endpoint 오브젝트 → iptables 룰** (kube-proxy가 조작) |
| 로드밸런싱 | 파드에 트래픽 분산 | **iptables** (라운드 로빈, 변경 불가) |
| Service Discovery | 이름으로 호출 | **CoreDNS**에 서비스 이름·IP 자동 등록 |
| 서비스 퍼블리싱 | 외부 → 내부 파드 | **kube-proxy + iptables** (+ 외부 LB 플러그인) |

## 타입 정리

| 타입 / 속성 | 무엇 | 실무 사용 |
|-------------|------|-----------|
| **ClusterIP** (기본) | 서비스 IP 할당, 내부 파드 통신의 핵심 | 가장 중요 |
| **NodePort** | 모든 노드에 포트(`30000~32767`) + ClusterIP 역할 | 테스트·임시용 |
| **LoadBalancer** | 외부 전용 IP + NodePort 역할 | **운영 표준.** 외부 → 내부는 전부 이걸로 |
| **ExternalName** | 파드에서 밖으로 나가는 DNS 포워딩 | HTTPS 도메인 검증 때문에 사실상 못 씀 |
| `externalIPs` (속성) | 선택한 노드에만, 포트 제한 없음(80/443 가능) | 임시 테스트, 보안 포트가 필요할 때 |
| `clusterIP: None` (**Headless**) | 서비스 IP 없음, DNS가 파드 IP 리스트 반환 | **StatefulSet DB에 필수** |

## 빠지기 쉬운 함정

1. **엔드포인트 등록 조건은 Readiness Probe 200 OK.** Probe 설정과 헬스체크 URL을 그에 맞게 만들 것. (Liveness 실패는 재기동이다)
2. **NodePort는 `netstat`에 리스닝 포트로 안 잡힌다.** 최신 버전은 포트 정보가 iptables 안에 있다. 안 보인다고 잘못된 게 아니다.
3. **Headless 도메인을 통신용으로 쓰지 말 것.** 로드밸런싱 책임이 클라이언트로 넘어오고, DNS가 IP 순서를 섞지 않으면 한 파드로 몰린다.
4. **`externalName`에는 풀 DNS 이름을.** 파드의 `resolv.conf` `search`가 여기엔 적용되지 않는다.
5. **DNS 호출은 `<서비스>.<네임스페이스>` 포맷으로 통일**하고, 성능이 중요하면 풀 도메인(`ndots:5` 회피).

## 트러블슈팅 루틴 (LB → 파드 트래픽 미도달)

```
엔드포인트 조회 (파드 IP 있나? 없으면 셀렉터 오타)
   ↓
iptables 룰 조회 (서비스 이름으로 grep)
   ↓
tcpdump로 해당 포트 덤프 (트래픽이 실제로 들어오나?)
   ↓
전부 정상이면 → 로드밸런서 설정 의심
```

## 인그레스 — 실체는 NGINX다

| 오해 | 실제 |
|------|------|
| 인그레스를 만들면 구현체가 생긴다 | 인그레스는 룰일 뿐. **인그레스 컨트롤러(NGINX)를 설치해야** 동작한다 (서비스 ↔ kube-proxy와 같은 관계) |
| 기존처럼 서비스로 트래픽을 보내면 된다 | **모든 트래픽은 NGINX(LoadBalancer 서비스)를 통해** 들어간다. 포탈도 직접 오픈하지 않는다 |
| NGINX가 인그레스의 서비스로 보낸다 | NGINX는 서비스 이름으로 **EndpointSlice**를 찾아 **파드 IP로 직접** 보낸다. 분산은 iptables가 아니라 NGINX가 한다 |

```
NGINX (ClusterRole로 전 네임스페이스 Ingress 조회)
  → ingressClassName이 자기 클래스(nginx)인 인그레스만 반영
  → 서비스 이름 → EndpointSlice(ownerReferences=서비스) → 파드 IP → 직접 전달
```

## NGINX 설정은 어디에 주나

| 위치 | 영향 범위 | 예 |
|------|-----------|-----|
| 인그레스 annotation | 그 인그레스로 가는 서비스만 | `ssl-redirect`, `rewrite-target`, `use-regex`, `configuration-snippet` |
| ConfigMap `ingress-nginx-controller` | NGINX 전체 (재기동 없이 즉시 반영) | `load-balance: ewma`, `log-format-upstream` |
| Helm values (재배포) | 설치 구성 | `allowSnippetAnnotations`, NodePort, IngressClass, `extraEnvs`(TZ), Deployment/DaemonSet |
| 인그레스 `tls` / NGINX 기본 인증서 / LB | 인증서 적용 구간 | 인그레스 TLS가 있으면 NGINX 인증서는 미적용 |

## 인그레스·NGINX에서 빠지기 쉬운 함정

1. **커뮤니티용(`kubernetes/ingress-nginx`, ns `ingress-nginx`)과 상용(`nginxinc/kubernetes-ingress`, ns `nginx-ingress`)이 이름이 뒤집혀 있다.** 링크를 정리해 두고 들어갈 것.
2. **인그레스에 TLS를 넣는 순간 `ssl-redirect`가 기본 true.** HTTP도 같이 쓰려면 명시적으로 false.
3. **인그레스가 여러 개 매칭돼도 하나만 적용된다.** host 없는 인그레스는 `*`이고, 호스트 이름이 매칭된 인그레스가 우선.
4. **인그레스 TLS 확인은 다른 브라우저로.** 같은 브라우저는 캐시된 이전 인증서를 보여준다.
5. **NGINX를 하나 더 설치할 때는 `--ingress-class`, `--controller-class` 값이 다른지 확인.**
6. **LB에만 인증서를 심을 때 워커노드가 지역 분산돼 있으면 내부 구간이 외부망을 탄다.** 반대로 상위단에 이미 있는데 내부에 또 심으면 성능 저하.
7. **`externalTrafficPolicy: Local`은 파드 없는 노드로 들어오면 에러.** NGINX를 DaemonSet으로 깔 때만 Local 조합을 쓴다.
8. **운영에서 NGINX 파드는 최소 3개.** 모든 트래픽의 중심이다.
