## AI 요약

### 0. 한 장 요약 — Istio는 파드 사이 트래픽을 맡고, 설치 전에 세 가지를 정한다

![LB와 Ingress는 들어오는 트래픽만, Istio는 파드 사이 트래픽까지 다룬다](쿠버네티스%20스프린트%205/images/01-istio-scope.svg)

> **LB(L4)와 Ingress(L7)는 클러스터로 들어오는 트래픽을 다룬다. 그 뒤의 파드 사이 호출을 보고 제어하는 것이 Istio다. 이 선택은 모든 파드에 영향을 주므로 설치 전에 방식을 정한다.**

| 용어 | 뜻 |
| --- | --- |
| 서비스 메시 | 앱 코드를 바꾸지 않고 프록시로 서비스 사이 통신을 관측·제어·보호하는 계층. Istio가 그 구현이다 |
| 사이드카 (istio-proxy) | 앱 파드 안에 함께 뜨는 Envoy 프록시. 파드의 들고 나는 트래픽을 대신 처리한다 |
| istiod | Istio의 컨트롤 플레인. 사용자가 만든 설정을 읽어 게이트웨이·사이드카에 넣어 준다 |
| CNI | 파드에 네트워크(IP·경로)를 붙이는 플러그인. Calico·kindnet 등 |
| Kiali | Istio 트래픽을 그래프로 보여 주는 화면. 데이터는 Prometheus에서 가져온다 |

| 질문 | 한 줄 답 | 근거 |
| --- | --- | --- |
| LB와 Ingress가 있는데 왜 Istio인가? | 둘은 들어오는 길목만 본다. 파드 사이 호출은 보이지도, 제어되지도 않는다 | 0절 |
| 설치 전에 무엇을 정하나? | 설정 API, 트래픽 가로채기 방식, 데이터 플레인 모드 | 1~5절 |
| 설치했는데 왜 Kiali가 비어 있나? | Kiali→Prometheus 주소, Prometheus→사이드카 수집 라벨, 트래픽·조회 기간 | 7절, PoC 4·5단계 |

| 설치 전에 정할 것 (강의 4) | 선택지 | 다룬 절 |
| --- | --- | --- |
| 트래픽 설정 API | Istio API / Gateway API | 1절 |
| 트래픽 가로채기 | istio-init 컨테이너 / Istio CNI 노드 에이전트 | 4절 |
| 데이터 플레인 | 사이드카 모드 / Ambient 모드 | 5절 |

강의는 "설치는 5분이지만 문제가 생기면 결국 설치 문서로 돌아온다"고 말한다. 블로그에서 최신 기능의 장점만 보고 들였다가 기본값으로 되돌아가는 일도 경계한다.

### 1. 세 가지 API — 같은 트래픽, 다른 설정 리소스

![세 API는 트래픽 흐름은 같고 설정을 담는 리소스가 다르다](쿠버네티스%20스프린트%205/images/02-three-apis.svg)

> **사용자가 받는 결과는 같다. 설정을 담는 리소스, 확장 방식, 설정이 게이트웨이에 닿는 경로가 다르다.**

| | Ingress API | Istio API | Gateway API |
| --- | --- | --- | --- |
| 리소스 | IngressClass, Ingress | Gateway, VirtualService, DestinationRule | GatewayClass, Gateway, HTTPRoute |
| 소속 | K8s 기본 (구 표준) | Istio와 함께 설치되는 CRD | K8s 차세대 표준 (CRD) |
| 세부 제어 | 어노테이션 키-값. 구현체마다 다르다 | VirtualService의 전용 필드 | 표준 필드(`weight` 등). 구현체가 바뀌어도 그대로 |
| 설정 반영 | Nginx 파드가 직접 조회 | istiod가 게이트웨이에 넣어 준다 | istiod가 넣어 주고, Gateway마다 파드를 만든다 |
| 맞는 곳 | 작은 클러스터. 배우기 쉽다 | 규모·관리 인력이 있고 세밀한 제어가 필요할 때 | 구현체를 바꿀 가능성이 있을 때. 아직 Istio API 기능을 다 담지 못한다 |

강의는 Istio API를 주로 쓰고 Gateway API는 일부만 함께 써 본다. 새 서비스에서 둘 중 무엇을 고를지는 각자 기준을 세워야 한다고 말한다.

- **(보충)** DestinationRule이 Service를 대신하지는 않는다. 대상은 여전히 Service이고, DestinationRule은 그 Service의 버전 묶음(subset)과 연결 정책을 정한다.
- **(보충)** Istio의 Gateway는 이미 배포된 게이트웨이를 *설정*한다. Gateway API의 Gateway는 게이트웨이를 *설정하고 배포*한다. [Gateway API 작업](https://istio.io/latest/docs/tasks/traffic-management/ingress/gateway-api/)
- **(보충)** 공식 시작 가이드는 이제 Bookinfo를 Gateway API로 연다. 강의가 쓴 ingress-nginx는 2026년 3월에 종료됐다. [종료 공지](https://kubernetes.io/blog/2025/11/11/ingress-nginx-retirement/)

### 2. 미러링 — 카나리와 무엇이 다른가

![카나리는 실제 사용자를 v2로 보내고 미러링은 복사본만 보낸다](쿠버네티스%20스프린트%205/images/03-canary-vs-mirror.svg)

> **카나리는 실제 사용자 일부를 v2로 보낸다. 미러링은 요청을 복사해 v2에 보내고, v2의 응답은 버린다.**

강의의 비교 예시다. v2 로직을 운영 환경에서 미리 확인하고 싶을 때, Nginx 10% 카나리는 v2에 문제가 있으면 사용자 10%가 오류를 받는다. Istio 미러링은 v2의 로그로 검증하고, 사용자는 오류를 받지 않는다. **(보충)** 복사 요청은 응답을 기다리지 않고 버린다(fire and forget). [미러링](https://istio.io/latest/docs/tasks/traffic-management/mirroring/)

다만 강의 15는 미러링을 실무에서 쓰기 어렵다고 본다. 쓰기 요청도 복사되므로 v2가 DB에 쓰면 데이터가 망가지고, 응답이 없어 결과를 로그로만 확인해야 하기 때문이다(12절).

### 3. 요청 경로 — 앱 사이에 사이드카 두 개

![앱 사이에 사이드카 두 개가 끼고 받는 앱은 사이드카를 본다](쿠버네티스%20스프린트%205/images/04-request-path.svg)

> **앱은 평소처럼 보낸다. 파드 안의 iptables 규칙이 나가는 TCP는 15001로, 들어오는 TCP는 15006으로 돌려 사이드카를 거치게 한다.**

강의는 여기서 개발자가 놓치기 쉬운 점을 짚는다. 받는 앱이 Remote Address로 호출자를 보면, 보낸 파드가 아니라 **자기 사이드카**가 나온다. PoC에서 사이드카가 있는 httpbin은 `127.0.0.6`을 받았고, 사이드카가 없는 httpbin은 curl 파드의 실제 IP를 받았다.

**(보충)** 호출자의 신원은 `X-Forwarded-Client-Cert` 헤더에 들어 있었다. 여기에는 IP가 아니라 서비스 계정 기반 신원(`spiffe://cluster.local/ns/default/sa/curl`)이 담긴다. `X-Forwarded-For`는 붙지 않았다.

**(보충·교정)** 강의는 "8080 포트에서 나가는 트래픽"을 예로 들었다. 실제 규칙은 포트를 고르지 않고 **모든 TCP**를 돌린다. 사이드카 자신(UID 1337)과 Istio가 쓰는 포트(15008·15020·15021·15090)만 제외한다.

### 4. istio-init과 Istio CNI — 같은 핵심 규칙, 다른 설치자

![istio-init은 파드마다 권한이 필요하고 Istio CNI는 노드 에이전트 하나가 규칙을 넣는다](쿠버네티스%20스프린트%205/images/05-init-vs-cni.svg)

> **핵심 규칙은 같다. 파드마다 권한 있는 init 컨테이너가 넣느냐, 노드마다 하나인 CNI 에이전트가 넣느냐가 다르다.**

| | istio-init (기본값) | Istio CNI (실습에서 전환) |
| --- | --- | --- |
| 규칙을 넣는 주체 | 파드마다 init 컨테이너 | 노드마다 DaemonSet 파드 1개 |
| 앱 파드의 init 컨테이너 | `istio-init`: NET_ADMIN·NET_RAW, root, 쓰기 가능 | `istio-validation`: 추가 권한 없음, UID 1337, 읽기 전용. 확인만 한다 |
| 강의가 든 단점 | 대량 업그레이드 때 동시에 자원 사용. 일반 앱 파드에 관리자 권한 → 보안 솔루션이 막으면 파드가 안 뜬다 | 권한을 DaemonSet 한곳에서 관리한다 |
| 기본 CNI(Calico 등) | 필요 | 여전히 필요. Istio CNI는 파드 IP를 주지 않는다 |

- **(보충·교정)** 실측한 istio-init은 `privileged: false`였다. 컨테이너 전체 특권이 아니라 NET_ADMIN·NET_RAW capability 두 개를 더한다. [Istio CNI](https://istio.io/latest/docs/setup/additional-setup/cni/)
- **(보충·교정)** 강의는 CNI 파드가 "자기 노드의 iptables"를 설정한다고 말한다. 실제로는 **체인 CNI 플러그인**이 파드를 만들 때 **그 파드의 네트워크 네임스페이스**에 규칙을 넣는다. 노드 기본 네임스페이스의 ISTIO 규칙은 0개였다.
- **(보충)** 두 방식의 규칙을 비교하면, CNI 쪽에 OUTPUT 체인의 15020(TCP·UDP) 예외 2줄이 더 있다(18개 대 20개). 그 이유는 확인하지 않았다.

### 5. 사이드카와 Ambient — 프록시를 파드마다 둘까, 노드마다 둘까

![사이드카는 파드마다 L4와 L7 프록시를 두고 Ambient는 노드마다 L4, 필요할 때 L7을 둔다](쿠버네티스%20스프린트%205/images/06-sidecar-vs-ambient.svg)

> **Ambient는 노드마다 L4 프록시(ztunnel)를 두고, L7 기능은 필요한 곳에만 waypoint를 둔다.**

| 관점 | 강의의 설명 | 공식 문서 (보충) |
| --- | --- | --- |
| 자원 | Ambient가 적게 쓴다. 탄생 배경이다 | 같다. 평균 자원 비용 Large vs Small |
| 지연 | 노드 파드가 모든 트래픽을 처리해 성능이 떨어진다 | 비교표의 p90/p99: 사이드카 0.63~0.88ms, ztunnel 0.16~0.20ms, waypoint 0.40~0.50ms |
| L7 기능 | ztunnel이 사이드카 역할을 대신한다 | ztunnel은 L4(mTLS·L4 정책·TCP 지표)만 한다. L7은 waypoint가 필요하다 |
| 운영 준비 | 아직 운영 환경 검증이 더 필요하다 | 1.22부터 단일 클러스터 운영 가능(production-ready) |
| 장애 범위 | ztunnel이 죽으면 그 노드의 파드가 모두 장애 | 이 PoC에서 확인하지 않았다 |

[데이터 플레인 비교표](https://istio.io/latest/docs/overview/dataplane-modes/) · [Ambient 데이터 플레인](https://istio.io/latest/docs/ambient/architecture/data-plane/)

강의의 결론은 "새 기술이 낫다"가 아니다. 각 방식의 장단점을 알고, 어떤 결정을 하든 그 단점을 어떻게 보완할지 정해 두라는 것이다.

### 7. Kiali가 비는 지점 — 주소, 라벨, 기간

![Kiali 그래프가 비는 세 지점](쿠버네티스%20스프린트%205/images/08-kiali-empty.svg)

> **Kiali는 트래픽을 직접 보지 않고 Prometheus에 묻는다. Prometheus가 Istio 메트릭을 수집하지 않거나 Kiali가 Prometheus를 못 찾으면 그래프가 빈다.**

| 막힌 곳 | PoC에서 본 증상 | 고친 방법 |
| --- | --- | --- |
| Kiali → Prometheus | 로그: `prometheus.istio-system … no such host` | Kiali 설정에 `url` 한 줄 추가 |
| Prometheus → 사이드카 | 샘플 모니터의 `release: istio`를 스프린트 4 Prometheus(`release: monitoring`만 선택)가 고르지 않음 | 라벨을 `release: monitoring`으로 변경 |
| 그래프 조회 | 트래픽이 없거나 조회 기간 밖 | 트래픽을 보내고 기간을 늘림 |

두 번째는 [스프린트 4의 ServiceMonitor 선택 조건](<쿠버네티스 스프린트 4.md>)과 같은 문제다. Istio 공식 샘플을 그대로 적용해도 우리 Prometheus의 선택 조건과는 맞지 않는다. 강의는 Kiali 기본 조회 기간이 최근 1분이라고 말한다(화면으로는 확인하지 않았다).

### 8. VirtualService와 DestinationRule — 흐름 규칙과 연결 대상 (강의 9)

> **VirtualService는 "어디로 보낼지"를, DestinationRule은 "보낼 대상 묶음(subset)"을 정한다. 둘은 `host`(도메인)와 subset 이름으로 이어진다.**

| VirtualService의 용도 | 예 |
| --- | --- |
| 외부 → 내부 | Gateway에 붙어 `/productpage` 등을 productpage:9080으로 보낸다 (PoC 3단계) |
| 내부 서비스 사이의 정책 | 헤더 `end-user: admin`이면 reviews v2, 나머지는 v1. QA 환경 대신 운영 환경에서 v2를 시험한다 |
| 한 도메인 안에서 경로별 분기 | `backend` 도메인 하나에서 경로마다 다른 subset으로. 연결 대상을 코드에 박지 않아 다시 배포하지 않고 바꾼다 |

```yaml
kind: VirtualService
spec:
  hosts: [reviews]                    # 이 도메인으로 가는 트래픽에 규칙 적용
  http:
  - match:
    - headers:
        end-user: {exact: admin}      # exact / prefix / regex
    route:
    - destination: {host: reviews, subset: v2}
  - route:
    - destination: {host: reviews, subset: v1}
---
kind: DestinationRule
spec:
  host: reviews                       # VirtualService의 destination.host와 같은 값
  subsets:
  - {name: v1, labels: {version: v1}} # 파드 라벨과 AND 조건으로 매칭
  - {name: v2, labels: {version: v2}}
```

`host`는 Service 이름이 아니라 **도메인**이다. 쿠버네티스에서는 Service 이름이 곧 도메인이고 FQDN도 쓸 수 있다. 내부 규칙에 `*`를 쓰는 일은 거의 없다. 매치 조건은 문서의 `HTTPMatchRequest`에 헤더·URI·메서드 등으로 정리돼 있고, 복잡한 건 예제를 보는 편이 빠르다.

| 강사가 던진 질문 | 강의의 답 |
| --- | --- |
| 왜 VirtualService가 파드를 바로 고르지 않고 DestinationRule을 거치나? | 관심사 분리다. VirtualService는 규칙만, DestinationRule은 대상만 맡는다. subset 이름을 blue/green처럼 추상화하면 대상 파드를 바꿀 때 DestinationRule만 고친다 |
| 왜 DestinationRule 이름이 아니라 `host`로 잇나? | 같은 host로 DestinationRule을 여러 개 둘 수 있어서 |
| 왜 `selector`가 아니라 `labels`인가? | (강사 의견) 키-값 AND 매칭만 하므로, 문법이 더 많은 selector와 헷갈리지 않게 |

**(보충·교정)** 강의는 green subset에 v3도 넣으려면 "같은 host에 같은 subset 이름(green)의 DestinationRule을 하나 더 만들면 된다"고 한다. Istio 1.31.4 소스는 같은 host의 DestinationRule을 합칠 때 **이미 있는 이름의 subset은 버리고** "Duplicate subset" 지표만 남긴다. 그러면 green은 v2만 가리킨다. 이름이 다른 subset을 여러 DestinationRule에 나누는 병합은 공식 문서상 된다. v2·v3를 한 subset으로 묶으려면 두 파드에 공통 라벨을 붙여 그 라벨로 고르는 편이 맞다(내 해석, 실습으로 확인하지 않음). [트래픽 관리 모범 사례](https://istio.io/latest/docs/ops/best-practices/traffic-management/) · [병합 소스](https://github.com/istio/istio/blob/1.31.4/pilot/pkg/model/destination_rule.go)

### 9. Request Routing 실습 — 접근 로그와 Kiali로 확인하기 (강의 10)

> **admin으로 로그인하면 항상 reviews v2(검은 별)가 나온다. 규칙이 실제로 적용됐는지는 사이드카 접근 로그와 Kiali로 확인한다.**

공식 예제(Request Routing)는 사용자 `jason`을 쓰고, 강의는 `admin`으로 바꿨다. Bookinfo 로그인은 비밀번호를 확인하지 않는다. 로그아웃하거나 다른 이름으로 로그인하면 v1(별 없음)이다.

사이드카는 기본으로 요청 로그를 남기지 않는다. IstioOperator의 `meshConfig`에 접근 로그(JSON 형식)를 켜야 `kubectl logs <파드> -c istio-proxy`에 요청이 찍힌다.

| productpage 사이드카 로그에서 본 것 | 뜻 |
| --- | --- |
| 게이트웨이에서 들어온 요청에 `end-user` 없음 | 브라우저가 보낸 헤더가 아니다. productpage 앱이 로그인 정보로 나가는 요청에 헤더를 붙인다 |
| reviews로 나간 요청의 upstream에 `v2` | 규칙이 고른 subset 이름이 클러스터 이름에 들어간다. 규칙이 없는 요청은 비어 있다 |
| CSS·이미지 요청이 304 | 브라우저 캐시(수정 시각 비교) 응답이다. Istio와 관계없다 |

Kiali 그래프는 app(라벨 `app` 기준), service, **versioned app**(`app`과 `version`, 가장 많이 본다), workload(Deployment 등) 네 종류다. 엣지 라벨은 이렇게 읽는다.

| 엣지 라벨 | 뜻 |
| --- | --- |
| 응답 시간: 평균 / 중앙값 / p95 / p99 | 평균은 극단값 하나에 끌려간다. 사용자 체감은 중앙값, 성능을 말할 때는 p95("대부분 260ms 안"), 게임·스트리밍처럼 엄격하면 p99 |
| 처리량 (bps) | 초당 데이터량. **(교정)** 강의는 Kbps를 "초당 킬로바이트"라고 했지만 킬로비트다 |
| 트래픽 분배 (%) | 갈래별 비율. 블루그린·카나리 때 본다 |
| 트래픽 비율 (rps) | 초당 요청 수. 부하 테스트 목표(예: 1000 rps)와 스케일 아웃 기준이 된다 |

**Gateway API로 같은 규칙:** HTTPRoute를 `reviews` **Service에 붙이고**(`parentRefs`), 대상은 버전별 Service(`reviews-v1`, `reviews-v2`)로 지정한다. 그래서 버전별 Service를 따로 만든다(DestinationRule subset의 역할). 요청이 Istio API 게이트웨이로 들어와도 이 규칙은 적용된다. 파드 사이 라우팅은 productpage의 사이드카가 하고, istiod가 두 API를 모두 사이드카 설정으로 바꿔 넣기 때문이다.

### 10. Fault Injection — 운영 환경에서 장애를 안전하게 재현하기 (강의 11·12)

> **지연이나 에러를 특정 사용자(admin)에게만 넣어, 운영 환경에서 예외 처리 코드와 타임아웃을 확인한다.**

재시도·타임아웃 같은 예외 처리 코드는 운영 전에 시험하기 어렵다. 그래서 "상상 코딩"으로 남다가 장애가 난 뒤에야 고친다. 장애를 코드로 재현하는 것도 번거롭고, 운영 데이터가 있어야 나는 장애는 검증 환경에서 재현할 수조차 없다. Istio는 Request Routing과 함께 써서 admin에게만 장애를 넣는다.

강의는 팀 A(productpage)·B(reviews)·C(ratings)와 인프라 운영자가 따로 있는 상황을 두고, 운영자의 수준별로 같은 장애를 추적한다(강의 11 대본은 레벨 2 도입부에서 끊겨 있어 실습 내용으로 채웠다).

| 운영자 수준 | 보는 것 | 강의 12 실습 결과 |
| --- | --- | --- |
| 레벨 1 | 대시보드, 앱 로그 | 앱 로그 세 개에 에러가 없다. 팀 사이를 오가며 원인 앱을 찾는다 |
| 레벨 2 | 사이드카 로그 (`-c istio-proxy`) | productpage → reviews가 두 번, 둘 다 응답 코드 0(응답 없음). reviews → ratings는 200 |
| 레벨 3 | 로그 형식에 `DURATION` 추가, 지연값을 바꿔 가며 시험 | 구간마다 타임아웃을 역산한다 |

| ratings 지연 (admin만) | 관찰 | 결론 |
| --- | --- | --- |
| 2초 | 모두 200, 약 2초 | 타임아웃에 걸리지 않음 |
| 4초 | productpage → reviews가 3초에 끊김 × 2번, 사용자는 6초 | productpage 타임아웃 3초, 재시도 1번 |
| 11초 | reviews → ratings가 10초에 끊김(코드 0), 사용자는 6초 | reviews(v2) 타임아웃 10초, 재시도 없음 |

소스 코드로도 맞춰 봤다. productpage(Python)는 `timeout=3`에 2회 for 루프, reviews(Java)는 별 색이 black(v2)이면 10초, 아니면(v3) 2.5초다.

**Abort:** admin의 ratings 요청에 100% HTTP 500을 넣으면 별점 자리만 에러 문구로 바뀐다. reviews가 예외를 처리해 productpage에는 성공으로 돌려주기 때문이다. Kiali는 에러 구간을 바로 보여 주지만 개별 요청의 원인은 알려 주지 않아서, 원인 분석은 사이드카 로그가 낫다. Gateway API에는 Fault Injection이 없다.

- 공식 예제는 사용자 `jason`과 7초 지연을 쓴다. 강의는 `admin`과 2·4·11초로 바꿨다.
- (확인 필요) 강의는 Kiali에서 응답 코드 0을 "NR"로 분류한다고 한다. Envoy 응답 플래그에서 NR은 "라우트 없음"이고, 클라이언트가 먼저 끊은 경우는 보통 DC다. 접근 로그의 `response_flags`로 가릴 수 있다.

### 11. Traffic Shifting — Argo Rollouts와 Istio로 카나리 자동화 (강의 13·14)

> **비율 자체는 VirtualService의 `weight`로 쉽게 나눈다. 버전마다 subset과 비율을 바꾸는 반복 작업을 Argo Rollouts가 자동화한다.**

| 배포 방식 (스프린트 2 복습) | 장점 | 한계 |
| --- | --- | --- |
| Recreate / RollingUpdate | Deployment 설정만으로 동작 | 중단되거나 두 버전이 함께 호출됨. 중간에 멈출 수 없고 롤백만 가능 |
| 블루그린 (기본 리소스로 가능) | 중단 없음, 중간에 멈춰 확인 가능 | 리소스 추가·수작업, 비율 조절 불가 |
| 카나리 (오픈소스 필요) | 비율을 조절하며 전환 | 가장 어렵다 |

**Argo Rollouts만 쓰면** 비율을 파드 수로 맞춘다. 파드가 2개면 33%·66%만 되고, 5%로 설정해도 카나리 파드 1개가 생겨 33%를 받는다. 막 뜬 파드에 트래픽이 몰리는 콜드 스타트도 막지 못한다.

**Istio와 연동하면** `setWeight`가 VirtualService의 weight를 바꾸고, 파드 수는 비율에 맞춰 따로 정한다(5%면 1개, 90%면 2개처럼 설정한 최대치 안에서). 강의가 다룬 방식은 subset 수준 분할이다. 도메인이 바뀌는 host 수준 분할은 잘 쓰지 않는다.

```
Rollout (trafficRouting.istio: VirtualService·DestinationRule 이름, stableSubset, canarySubset)
  └ Argo Rollouts 오퍼레이터가
      · DestinationRule의 stable·canary subset에 rollouts-pod-template-hash 라벨을 넣고
      · 이미지를 바꾸면 canary의 hash를 새 ReplicaSet 것으로, weight를 100/0 → 5 → 50 → 100으로 바꾸고
      · 끝나면 두 subset 모두 새 hash, stable 100 (새 버전이 다시 stable)
```

실습(강의 14)은 Istio만으로 95/5를 먼저 걸고 Kiali의 분배 비율로 확인한다. 그다음 Argo Rollouts를 설치하고, reviews Deployment를 지운 뒤 Rollout(replicas 2)으로 만든다. 라벨과 이미지를 v2로 바꾸면 카나리 파드 1개에 5%가 가고, Promote하면 50% → 1분 뒤 100%가 되며 v1 파드가 삭제된다.

- Rollout의 `selector`는 바꾸지 않는다. 바꾸면 처음부터 다시 시작한다. 라벨은 template 쪽만 바꾼다.
- `stableSubset`·`canarySubset` 이름이 실제 DestinationRule과 맞지 않으면 ReplicaSet부터 생기지 않는다.
- 강의에서는 Kiali가 카나리 비율을 제대로 그리지 못해서, productpage 사이드카 로그에서 stable/canary 요청 수를 세어 5%를 확인했다(강의는 Kiali가 Argo Rollouts를 완전히 지원하지 않아서라고 설명한다. 확인하지 않았다).
- 강의는 Gateway API 리소스가 Argo Rollouts와 연동되지 않는다고 한다. **(보충)** Argo Rollouts는 Gateway API를 별도 플러그인(rollouts-plugin-trafficrouter-gatewayapi)으로 지원한다. "내장 지원은 없다"로 읽으면 된다.

### 12. Circuit Breaking ① — TrafficPolicy와 커넥션 풀 (강의 15·16)

> **VirtualService가 "흐름 규칙"이라면 DestinationRule의 trafficPolicy는 "연결 규칙"이다. 연결을 어떻게 맺고(connectionPool), 어떻게 나누고(loadBalancer), 문제 있는 파드를 언제 빼는지(outlierDetection) 정한다.**

배경은 이렇다. VM 시절에는 클라이언트 코드가 서버 수에 맞춰 연결 설정을 직접 했다. 쿠버네티스는 파드 발견과 로드밸런싱까지만 해 주고, 서킷 브레이킹이나 클라이언트 연결 설정의 자동화는 하지 않는다. 그 빈자리를 Istio가 채운다.

**먼저 실무에서 쓰기 어려운 두 기능 (강의 15):**

| 기능 | 강의가 든 이유 |
| --- | --- |
| 미러링 | v2가 DB에 쓰면 데이터가 망가진다. 조회 기능만 시험할 수 있고, 응답이 없어 결과를 로그로만 확인한다 |
| Request Timeout (VirtualService) | 타임아웃·재시도는 업무 로직과 엮여 있다(일반 API는 짧게, 배치는 길게). 인프라가 기본값을 주면 장애 분석이 복잡해지고, 기본값을 넘어야 하는 예외를 허용하지 못한다 |

trafficPolicy는 DestinationRule의 host 수준(모든 subset 공통)과 subset 수준에 둘 수 있고, 둘 다 있으면 subset 쪽이 이긴다. 클러스터 공통값은 와일드카드 host의 DestinationRule이나 Istio 전역 설정으로 준다.

**배경 지식 — HTTP 버전과 연결 (강의 16):**

| | 연결과 요청 | 분산 환경에서의 문제 |
| --- | --- | --- |
| HTTP/1.0 | 요청마다 TCP 연결을 맺고 끊는다 | 연결 비용이 크다 |
| HTTP/1.1 | Keep-Alive로 한 연결에 요청을 순차로 보낸다 | 동시 요청에는 연결이 많이 필요한데 연결 수는 OS 자원이다 |
| HTTP/2 | 한 연결에 요청을 병렬로 보낸다(멀티플렉싱) | 연결 1~2개로 충분해서, 서버가 연결 수보다 많아지면 새 서버로 분산되지 않는다. DNS 결과도 캐시해서 새 서버를 늦게 안다 |

Istio에서는 앱과 자기 사이드카가 1:1로 붙고, 나가는 쪽 사이드카가 대상 파드를 바로 감지해 연결을 관리한다. 그래서 HTTP/2의 분산 문제가 사라진다. 받는 쪽 사이드카에서 앱까지는 파드 안이라 따로 연결이 필요 없다.

강의 17 실습이 이걸 보여 준다. 연결 풀이 2로 고정된 core 앱이 custom 앱을 부르는 구성이다.

| 구성 | custom 파드를 3개로 늘린 뒤 |
| --- | --- |
| 사이드카 없음 | 계속 파드 하나로만 간다. 그 파드를 죽여도 다시 한 파드로만 간다 |
| `istio-injection` 후 파드 재생성 | 고르게 분산된다. 앱의 연결 2개는 자기 사이드카까지만 쓰이고, 사이드카가 대상을 감지해 나눈다 |

Istio를 쓰는데 개발 팀이 앱의 커넥션 풀 튜닝에 공을 들이고 있다면 이 구조를 알려 줘야 한다.

- **(보충·교정)** 강의는 `maxConnections`를 "파드마다의 최대 연결 수라서 파드가 늘면 자동으로 늘어난다"고 설명한다. 공식 API 정의는 "목적지 호스트로의 최대 HTTP1/TCP 연결 수"다. 파드마다의 값으로 단정하지 않는다. [DestinationRule API](https://istio.io/latest/docs/reference/config/networking/destination-rule/)

### 13. Circuit Breaking ② — 로드밸런서와 Outlier Detection (강의 16·17)

> **loadBalancer는 LEAST_REQUEST와 warmup이면 대부분 충분하다. outlierDetection은 부하로 잠깐 튀는 파드 하나를 빼는 기능이지, 서킷 브레이킹의 전부가 아니다.**

| loadBalancer 설정 | 동작 | 강의의 평가 |
| --- | --- | --- |
| `simple: ROUND_ROBIN` | 길게 보면 균등하다. 한 파드에 연달아 갈 수도 있다 | 강의는 기본값이라고 설명 |
| `simple: LEAST_REQUEST` | **이 클라이언트가 보낸** 활성 요청이 가장 적은 파드로 보낸다 | 서버 전체 부하를 보는 건 아니지만, 그나마 상태를 반영한다 |
| `simple: RANDOM` / `PASSTHROUGH` | 무작위 / Istio 분산을 끄고 클라이언트 연결 그대로 | 잘 안 쓴다 (PASSTHROUGH면 12절의 분산 문제가 돌아온다) |
| `consistentHash` | 해시로 고정 분배 (세션 고정) | MSA는 세션을 메모리 DB에 둬서 잘 안 쓴다 |
| `localityLbSetting` | 이중화 환경 사이의 비율(distribute)과 장애 전환(failover) | 고가용성 구성에서 |
| `warmup` (duration, minimumPercent, aggression) | 새 파드에 트래픽을 조금씩 늘린다 | 콜드 스타트 방지. 무조건 쓰면 좋다. aggression 1은 일정하게, 1보다 작으면 처음엔 천천히, 크면 처음에 빠르게 늘린다 |

**(보충)** 공식 API 설명은 ROUND_ROBIN이 많은 경우 엔드포인트에 부담을 줄 수 있다며 LEAST_REQUEST를 대신 쓰라고 권한다. 알고리즘을 정하지 않으면 Istio가 적절한 기본값을 고른다. 강의가 실무에서 가장 선호한다고 한 "평균 응답 시간 기반 분배"는 이 목록에 없다.

실습에서 LEAST_REQUEST를 걸고 한 파드에 sleep 요청을 물려 활성 요청을 붙잡아 두면, 다른 파드로 요청이 더 많이 간다. warmup(최소 5%, 2분, 일정 속도)에서는 새 파드가 10초마다 2 → 3 → 4 → 5개로 늘다가 2분 뒤 다른 파드와 비슷해진다.

| outlierDetection 설정 | 뜻 | 기본값 | 강의의 권장 |
| --- | --- | --- | --- |
| `consecutive5xxErrors` | 연속 5xx 횟수를 넘으면 제외 | 5 | 0 (끔). 앱 로직 에러는 모든 파드에서 함께 나 전체가 제외될 수 있고, 메모리 누수는 liveness probe가 재시작으로 처리한다 |
| `consecutiveGatewayErrors` | 연속 502·503·504 | 0 (끔) | 5 이상. 부하로 특정 파드가 버거울 때 나는 에러다 |
| `splitExternalLocalOriginErrors` / `consecutiveLocalOriginFailures` | 연결 타임아웃·리셋 같은 로컬 에러를 따로 센다 | false / 5 | false로 둬도 된다 |
| `interval` / `baseEjectionTime` | 판정 주기 / 제외 시간 | 10s / 30s | 기본값. 무거운 로직이 많으면 늘린다 |
| `maxEjectionPercent` | 동시에 제외할 수 있는 비율 | 10% | 20 정도. 너무 많이 빼면 남은 파드에 연쇄 부하가 온다 |
| `minHealthPercent` | 건강한 파드가 이 비율 아래면 기능을 끈다 | 0% | `maxEjectionPercent`만으로 충분하다 |

**(보충·교정)** 강의는 `consecutive5xxErrors`가 서버 앱의 에러만 센다고 설명한다. 공식 정의에서는 `consecutiveGatewayErrors`가 세는 502·503·504도 `consecutive5xxErrors`에 들어간다. 그래서 gateway 값이 5xx 값 이상이면 gateway 설정은 효과가 없다. 강의의 권장(5xx는 0, gateway는 5)은 5xx를 껐으므로 그대로 성립한다. 연속 횟수 대신 실패 비율로 판단하는 `failurePercentageThreshold`도 있다.

실습에서는 custom 파드를 5개로 늘리고 503을 반복해서 보냈다. 그러자 `istioctl proxy-config endpoint <core 파드>`의 OUTLIER CHECK에서 한 파드만 FAILED가 되고, 30초 뒤 OK로 돌아오면 다른 파드가 FAILED가 됐다. `maxEjectionPercent`가 20이라 한 번에 하나만 빠진다. 파드가 3개일 때는 20%가 1개에 못 미쳐 제외가 일어나지 않는다. **(보충)** Envoy는 `always_eject_one_host`를 켰을 때만 비율과 상관없이 최소 1개를 제외한다.

강의의 결론은 기대치를 낮추라는 것이다. 서킷 브레이킹은 큰 개념이고 outlierDetection은 그중 하나일 뿐이다. 잘못 설정하면 오히려 큰 장애가 나므로, 자주 나는 문제를 이 설정으로 안정시킬 수 있다고 판단될 때 다시 고민한다. trafficPolicy의 TLS 설정은 보안 섹션에서 다룬다.

#### 1단계. 설치

```bash
python3 lab.py istioctl install --set profile=default -y
python3 lab.py k get deploy -n istio-system
python3 lab.py k get crd | grep istio.io
```

`istiod`와 `istio-ingressgateway`가 생기고, `*.istio.io` CRD는 15개다.

#### 2단계. 사이드카 주입과 권한

```bash
python3 lab.py k label namespace default istio-injection=enabled
python3 lab.py k apply -f .lab/istio/samples/bookinfo/platform/kube/bookinfo.yaml
python3 lab.py k get pods -w
```

처음에는 이미지 다운로드로 2분쯤 걸린다. 6개가 모두 `2/2 Running`이면 Ctrl+C. 컨테이너 구성, istio-init의 권한, 파드 안 규칙을 본다.

```bash
python3 lab.py k get pod -l app=productpage -o jsonpath='{range .items[0].spec.initContainers[*]}{.name}{" restartPolicy="}{.restartPolicy}{"\n"}{end}{range .items[0].spec.containers[*]}{.name}{"\n"}{end}'
python3 lab.py k get pod -l app=productpage -o jsonpath='{.items[0].spec.initContainers[0].securityContext}'
python3 lab.py rules productpage
```

istio-init, istio-proxy(`restartPolicy=Always`), productpage 세 개다. istio-init은 `NET_ADMIN`·`NET_RAW`, `runAsUser: 0`, `privileged: false`다. `rules`는 파드 안의 `REDIRECT --to-ports 15006`(들어옴)·`15001`(나감)과 노드의 ISTIO 규칙 0개를 보여 준다. 사이드카는 CPU 100m·메모리 128Mi를 예약한다.

#### 3단계. 두 게이트웨이

Istio API: 예제 Gateway(`selector: istio: ingressgateway`, 포트 8080, hosts `*`)와 VirtualService(`match` → `productpage:9080`)를 적용하고, 80 포트의 NodePort를 30011로 바꾼다.

```bash
python3 lab.py k apply -f .lab/istio/samples/bookinfo/networking/bookinfo-gateway.yaml
curl -s -o /dev/null -w '%{http_code}\n' --max-time 3 http://127.0.0.1:30011/productpage
python3 lab.py k patch svc istio-ingressgateway -n istio-system -p '{"spec":{"ports":[{"port":80,"nodePort":30011}]}}'
curl -s http://127.0.0.1:30011/productpage | grep -o '<title>.*</title>'
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:30011/
```

변경 전 `000`, 변경 후 `Simple Bookstore App`. `/`는 VirtualService의 `match`에 없어 404다. match가 Ingress의 path 역할을 한다.

Gateway API: CRD가 없는 상태부터 확인하고 설치한다.

```bash
python3 lab.py k get gatewayclass
python3 lab.py k apply --server-side -f .lab/gateway-api-v1.6.0.yaml
python3 lab.py k get gatewayclass
python3 lab.py k apply -f .lab/istio/samples/bookinfo/gateway-api/bookinfo-gateway.yaml
python3 lab.py k get deploy,svc -l gateway.networking.k8s.io/gateway-name=bookinfo-gateway
python3 lab.py k patch svc bookinfo-gateway-istio -p '{"spec":{"ports":[{"port":80,"nodePort":30012}]}}'
curl -s http://127.0.0.1:30012/productpage | grep -o '<title>.*</title>'
python3 lab.py k get gw,gtw
```

처음에는 `gatewayclass` 리소스가 없다는 오류가 난다. CRD를 설치하면 Istio가 `istio`·`istio-remote` GatewayClass를 만든다. Gateway를 만들면 `bookinfo-gateway-istio` Deployment와 Service가 새로 생기고, 30012도 같은 화면이다. `gw`는 Istio, `gtw`는 Gateway API 쪽 Gateway다.

<details>
<summary>gtw의 PROGRAMMED가 False인 이유</summary>

`AddressNotAssigned`다. kind에는 LoadBalancer가 없어 주소가 배정되지 않는다. 접속과는 무관하다. 주석으로 Service 타입을 NodePort로 바꾸면 `True`가 되고, 바꿔 둔 30012는 유지된다.

```bash
python3 lab.py k annotate gtw bookinfo-gateway networking.istio.io/service-type=NodePort --overwrite
python3 lab.py k get gtw
```

</details>

양쪽에 요청을 보낸 뒤 브라우저에서 productpage를 새로고침한다. reviews는 v1(별점 없음)과 v2·v3(ratings를 불러 별점 표시)가 번갈아 나온다.

```bash
python3 lab.py traffic --count 50
```

#### 4단계. Kiali — Prometheus 주소

```bash
python3 lab.py k apply -f .lab/istio/samples/addons/kiali.yaml
python3 lab.py k patch svc kiali -n istio-system -p '{"spec":{"type":"NodePort","ports":[{"port":20001,"nodePort":30020}]}}'
python3 lab.py k rollout status deploy/kiali -n istio-system
python3 lab.py k logs deploy/kiali -n istio-system --tail=100 | grep -i prometheus
```

Kiali는 열리지만 그래프가 비고, 로그에 `prometheus.istio-system … no such host`가 반복된다. 사본을 만들어 `external_services.prometheus` 아래에 `url` **한 줄**을 넣는다.

```bash
cp .lab/istio/samples/addons/kiali.yaml .lab/my-kiali.yaml
```

```yaml
      prometheus:
        enabled: true
        url: http://monitoring-prometheus.monitoring:9090
```

```bash
python3 lab.py k apply -f .lab/my-kiali.yaml
python3 lab.py k rollout restart deploy/kiali -n istio-system
python3 lab.py k rollout status deploy/kiali -n istio-system
python3 lab.py k logs deploy/kiali -n istio-system --tail=100 | grep -i prometheus
```

`Prometheus connected`가 나온다. **그래도 그래프는 비어 있다.** Prometheus가 아직 Istio 메트릭을 수집하지 않기 때문이다.

#### 5단계. 메트릭 수집 — release 라벨

Istio 예제의 PodMonitor(사이드카 `:15020`)와 ServiceMonitor(istiod `:15014`)를 **그대로** 적용하고, 라벨을 Prometheus의 선택 조건과 비교한다.

```bash
python3 lab.py k apply -f .lab/istio/samples/addons/extras/prometheus-operator.yaml
python3 lab.py k get podmonitor,servicemonitor -n istio-system --show-labels
python3 lab.py k get prometheus -n monitoring -o jsonpath='{.items[0].spec.podMonitorSelector}'
```

Targets에서 `envoy`로 검색하면 대상이 없다. 모니터는 `release=istio`, Prometheus는 `release: monitoring`만 고른다. 사본을 만든다.

```bash
cp .lab/istio/samples/addons/extras/prometheus-operator.yaml .lab/my-monitors.yaml
```

에디터로 `.lab/my-monitors.yaml`을 열어 **두 곳**의 `release: istio`를 `release: monitoring`으로 바꾸고 저장한 뒤 적용한다.

```bash
grep -n 'release:' .lab/my-monitors.yaml    # 두 줄 모두 monitoring인지 확인
python3 lab.py k apply -f .lab/my-monitors.yaml
python3 lab.py traffic --count 60
python3 lab.py query 'sum by (source_workload, destination_workload) (istio_requests_total{reporter="destination"})'
```

30초쯤 뒤 Targets에 사이드카 8개(Bookinfo 6 + 게이트웨이 2)와 istiod가 UP이다. 질의와 Kiali 그래프에 두 게이트웨이 → productpage → details·reviews v1/v2/v3, reviews v2·v3 → ratings가 나온다(노드 9개·엣지 8개).

#### 6단계. Istio CNI 전환

강의처럼 앱을 먼저 지운다. 이미 떠 있는 파드에는 새 방식이 적용되지 않는다.

```bash
python3 lab.py k delete -f .lab/istio/samples/bookinfo/platform/kube/bookinfo.yaml
python3 lab.py istioctl install -f lab/istio-cni.yaml -y
python3 lab.py k get pods -n istio-system -l k8s-app=istio-cni-node -o wide
python3 lab.py k apply -f .lab/istio/samples/bookinfo/platform/kube/bookinfo.yaml
python3 lab.py k wait --for=condition=Ready pod -l 'app in (productpage,details,ratings,reviews)' --timeout=300s
python3 lab.py k get pod -l app=productpage -o jsonpath='{.items[0].spec.initContainers[0].name}{"\n"}{.items[0].spec.initContainers[0].securityContext}{"\n"}'
python3 lab.py rules productpage
```

`istio-cni-node`가 노드마다 하나씩 3개(control-plane 포함) 뜬다. 다시 설치해도 NodePort 30011은 유지된다. init 컨테이너는 `istio-validation`(`--run-validation --skip-rule-apply`)이 되고, 추가 권한 없이 UID 1337·읽기 전용으로 실행된다. 파드 안의 핵심 규칙은 2단계와 같고, 30011·30012 모두 200이다.

전환 직후 Kiali에는 게이트웨이 → productpage 선만 남을 수 있다. 앱 파드가 새로 생겨 요청 카운터가 0부터 다시 시작했고, 새 시계열은 샘플이 두 개 쌓여야 증가량이 계산되기 때문이다. `python3 lab.py traffic --count 60`을 보내고 1분쯤 뒤 다시 보면 엣지 8개가 돌아온다.

<details>
<summary>더 해보기 A — 받는 앱이 보는 호출자 주소</summary>

같은 httpbin을 사이드카가 있는 `default`와 없는 `no-mesh`에 하나씩 둔다.

```bash
python3 lab.py k create namespace no-mesh
python3 lab.py k apply -f .lab/istio/samples/curl/curl.yaml
python3 lab.py k apply -f .lab/istio/samples/httpbin/httpbin.yaml

python3 lab.py k exec deploy/curl -- curl -s httpbin.default:8000/ip
python3 lab.py k exec deploy/curl -- curl -s httpbin.no-mesh:8000/ip
python3 lab.py k exec deploy/curl -- curl -s httpbin.default:8000/headers
```

사이드카가 있는 쪽은 `127.0.0.6:…`, 없는 쪽은 curl 파드의 IP를 본다. `/headers`의 `X-Forwarded-Client-Cert`에 `URI=spiffe://cluster.local/ns/default/sa/curl`이 있다. 정리: `python3 lab.py k delete namespace no-mesh` 후 curl·httpbin 파일을 `delete -f`.

</details>

**검증하지 않은 것:** 브라우저 화면(Kiali·Prometheus UI)은 API 응답으로만 확인했다. Ambient 모드, Calico, 실제 LoadBalancer는 실행하지 않았다. 첫 자동 실행은 17/19였다. 이전 실습의 Prometheus 이력이 Kiali 그래프에 잡힌 것과 "두 방식의 규칙이 완전히 같다"는 내 가정이 원인이었다. `reset`이 Prometheus 이력까지 지우게 하고 규칙 비교를 실측대로 고친 뒤 다시 실행했다.

## 내가 얻은 인사이트

1. **(내 해석) 설치 옵션은 "나중에 바꾸기 비싼 선택"이다.** API, 가로채기 방식, 데이터 플레인은 모든 파드에 영향을 준다. 처음에 정하고 그 이유를 남긴다.
2. **(내 해석) 사이드카는 앱이 보는 네트워크를 바꾼다.** 호출자 주소가 `127.0.0.6`이 되는 것처럼 로그·접근 제어 로직이 영향을 받는다. 도입 전에 개발자에게 알린다.
3. **(내 해석) 연동은 라벨 한 줄에서 끊긴다.** 공식 샘플도 우리 Prometheus의 선택 조건과는 다르다. 설치 성공과 수집 성공을 따로 확인한다.
4. **(내 해석) 권한은 사라지지 않고 옮겨 간다.** CNI는 앱 파드의 네트워크 권한을 노드 DaemonSet 하나로 모은다. 그 DaemonSet이 새로운 보호 대상이 된다.
5. **(내 해석) 업무 로직과 겹치는 설정은 앱에 남긴다.** 타임아웃·재시도·미러링은 업무를 아는 개발자가 정하고, 연결 관리·분산·배포 비율·장애 주입은 사이드카에 맡길 때 Istio의 값이 가장 크다.
