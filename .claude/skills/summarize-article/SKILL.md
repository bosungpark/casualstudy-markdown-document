# Summarize Technical Article

기술 주제를 다루는 아티클 한 편을 선정해 한국어 학습 문서로 정리한다. 문서는 **단순 명료한 글과 직접 그린 SVG 그림**으로 만든다. 이 주제를 처음 보는 동료가 발표 자료로 읽어도 그림만 넘겨 보면 흐름이 잡혀야 한다. 사용자가 요청하면 같은 위치에 재현 가능한 PoC도 만든다.

## 입력

- 명시적 호출의 인자 또는 현재 요청에서 기술 주제를 가져온다.
- 주제가 불명확할 때만 짧게 질문한다.

## 작업 순서

1. 저장소 루트의 `CLAUDE.md`, `AGENTS.md` 등 적용 가능한 작성 규칙을 먼저 확인한다.
2. 인터넷에서 `[주제] architecture deep dive internals`와 같이 검색한다.
3. 공식 문서, 원저자 기술 블로그, 논문 등 가장 깊이 있고 신뢰할 수 있는 **아티클 한 편**을 선택해 원문을 끝까지 읽는다.
   - 웹 요약 도구의 결과만 믿지 않는다. 요약 모델은 수치나 고유명사를 바꾸기도 한다(예: "330개 도시"를 "330개 데이터센터"로). 가능하면 원문 HTML을 받아 본문 텍스트를 뽑아 직접 읽는다.
4. 선택한 아티클을 중심으로 핵심 구조, 동작 순서, 트레이드오프를 정리한다.
   - 제목을 질문형·증상형으로 지었다면(`왜 ~인가`, `~하면 무슨 일이 생기는가`) **요약 첫 절에서 그 질문에 직접 답한다.** 원문 목차 순서를 그대로 옮기면 제목과 본문이 따로 논다.
   - 나머지 절은 그 답의 근거가 되도록 배치한다. 답 먼저, 근거 나중.
5. 그림을 계획한다. 그림이 필요한 지점을 3~6개 고른다 (→ 시각화).
6. 기존 카테고리 중 가장 가까운 위치를 선택한다.
   - 인프라·클라우드·운영: `infra/`
   - 시스템·분산 시스템: `system_design/`
   - 네트워크·프로토콜: `network/`
   - 데이터베이스: `database/`
   - AI·ML: `ai/`
   - 보안: `security/`
7. `[카테고리]/[주제 제목]/` 디렉터리를 만들고 그 안에 둔다.
   - 문서: `[주제 제목].md`
   - 그림: `images/NN-kebab-case.svg`
   - PoC를 만들면 `README.md`와 실행 파일도 같은 디렉터리에 둔다. 별도의 범용 `pocs/` 디렉터리를 만들지 않는다.
8. 링크, 명령어, 코드 문법, 그림 렌더링을 검사한다(→ 시각화 / 검증). PoC를 포함했다면 안전한 격리 환경에서 실제 실행해 핵심 주장을 검증한다.

## 단일 출처 원칙

- 한 문서의 `출처`에는 아티클·논문·챕터 하나만 둔다.
- 여러 아티클의 내용을 하나의 요약처럼 섞지 않는다.
- 보조 자료로 사실을 검증하더라도 선택한 원문의 주장과 자신의 해석을 구분한다. 보조 자료에서 가져온 사실은 **(보충)**으로 표시하고, 출처 노트에 그 자료를 밝힌다.
- 여러 자료를 각각 정리해야 한다면 문서를 분리한다.

## 글쓰기 — 단순 명료하게

- **한 절에 메시지 하나.** 그 절의 핵심을 `>` 인용 한 줄로 둔다.
- **문장은 짧게.** 한 문단이 3~4문장을 넘으면 표나 목록으로 바꾼다.
- **비유보다 정의와 사실.** 용어는 처음 나올 때 `용어 | 뜻` 표로 정의한다.
- **비교는 표로.** before/after, A vs B는 표에 나란히 둔다. 결론은 `10.2초 / exit 137 → 0.1초 / exit 143`처럼 비교 가능한 값으로 닫는다.
- **본문에는 핵심만 남긴다.** 상세 타임라인, 긴 명령어, 부가 설정은 `<details><summary>…</summary>…</details>`로 접는다.
- **인사이트는 3~5개, 각 1~2줄.**
- 취약점·공격 기법을 다루는 아티클은 원인·영향·수정·방어에 집중한다. 단계별 공격 절차나 exploit의 세부 값은 옮기지 않는다.
- 전체 설명은 한국어로 쓰고 필요한 기술 용어는 영어를 병기한다.
- 원문 요약과 직접 실험 결과를 명확히 구분한다. 내 해석은 `(내 해석)`으로 표시한다.
- 시간에 따라 변할 수 있는 버전, 명령어, 지원 상태는 현재 공식 자료에서 확인한다.
- 긴 원문 인용 대신 간결한 의역을 사용한다.
- 출처에 없는 사실을 원문의 주장처럼 쓰지 않는다.
- `원문은 여기서 한 걸음 더 들어간다`, `원문이 지적하는 문제는`, `원문의 결론은 단순하다` 같은 메타 서술을 반복하지 않는다. 주장을 직접 쓰고, 원문과 내 해석을 구분해야 하는 자리에서만 출처를 밝힌다.

## 시각화 — SVG 그림

### 무엇을 그리나

- **그림 하나에 주장 하나.** 문장으로 더 빨리 전달되면 그리지 않는다.
- **이름이 아니라 메커니즘을 그린다.** 흐름, 경계, 두 선택지의 차이, 상태 변화처럼 글로 조립해야 하는 것을 그린다. 이름만 적힌 박스 나열은 그림이 아니다.
- 0절에는 **한 장 요약 그림**을 반드시 둔다. 나머지는 필요한 절에만 둔다.

| 유형 | 언제 쓰나 | 예 |
| --- | --- | --- |
| 한 장 요약 | 0절. 전체를 한눈에 | 대응 타임라인, 전체 요청 흐름 |
| 원인 구조 | 왜 그런 일이 생겼나 | 수정이 LTS로 백포트되지 않은 틈 |
| 대응 지도 | 요소끼리 짝을 지을 때 | 공격 단계 × 방어 수단 |
| 비교 | 두 선택지의 차이 | 모듈 제거 vs bpf-lsm. 같은 레이아웃의 두 패널에서 다른 점만 다르게 |
| 함정 | 직관과 어긋나는 지점 | 롤링 재부팅에서 이미 지나간 서버 |

### 어떻게 그리나

- **손으로 쓴 SVG**만 쓴다(`rect`, `line`, `path`, `polygon`, `text`). 외부 이미지, `<script>`, `<foreignObject>`는 쓰지 않는다.
- **크기**: `viewBox` 너비 900을 기준으로 하고 높이는 내용에 맞춘다. `width`, `height` 속성도 같은 값으로 둔다.
- **배경 카드**: 첫 요소로 흰 배경 `rect`(`rx="14"`, 연회색 테두리 `#E5E7EB`)를 깐다. 그래야 다크 테마 미리보기에서도 읽힌다.
- **글꼴**: `'Apple SD Gothic Neo', 'Noto Sans KR', 'Malgun Gothic', sans-serif`. 그림 제목은 19px 굵게 "주제 — 핵심 주장" 형식으로 쓴다. 본문은 13~15px, 주석은 12px을 쓴다.
- **색은 의미에 묶고 문서 전체에서 고정한다.**

  | 색 | 의미 | fill / stroke |
  | --- | --- | --- |
  | 빨강 | 위험, 실패, 공격 | `#FEE2E2` / `#DC2626` |
  | 초록 | 정상, 해결 | `#DCFCE7` / `#16A34A` |
  | 파랑 | 권장, 예방, 선택한 쪽 | `#DBEAFE` / `#2563EB` |
  | 주황 | 탐지, 주의 | `#FEF3C7` / `#D97706` |
  | 회색 | 범위 밖, 중립 | `#F3F4F6` / `#9CA3AF` |

- **화살표에는 라벨을 단다**(`백포트 필요`, `끊음`, `감지`). 범례는 같은 표현(색, 점선)이 반복될 때만 둔다. 점선은 예정, 가정, 끊긴 경로를 뜻한다.
- **맨 아래 한 줄 주석**으로 읽는 법이나 한계를 밝힌다(예: "시간 간격은 실제 비율이 아니다").
- **접근성**: `<svg role="img" aria-label="그림이 말하는 주장">`으로 쓴다.
- 함정 두 가지를 피한다.
  - 짧은 선(20px 안팎)에 `marker`를 달면 화살촉이 뭉개진다. 작은 `polygon`으로 그린다.
  - `<style>`의 class 규칙은 `text-anchor` 같은 속성보다 우선한다. 정렬이 다른 텍스트에는 class를 따로 만든다.
- **문서에서의 배치**
  - 이미지는 `![그림이 말하는 것](images/01-overview.svg)` 형식으로 넣는다.
  - 그림 바로 아래에는 2~4줄 설명이나 표를 둔다. 그림이 보여 주는 내용을 글로 다시 길게 쓰지 않는다.
  - 출처 노트에 "그림은 원문 내용을 바탕으로 직접 그린 것"이라고 밝힌다.

### 검증

- 그림마다 `rsvg-convert -w 1350 X.svg -o [scratchpad]/X.png`로 렌더하고 이미지를 직접 본다. 다음 결함이 있으면 고친다.
  - 겹치거나 잘린 글자
  - 글자나 박스를 가로지르는 화살표
  - 박스에서 떨어져 시작하는 화살표
- 모든 SVG가 XML로 파싱되는지, md의 이미지 경로와 상대 링크가 실제 파일을 가리키는지 스크립트로 확인한다.

## 자가 점검

문서를 저장하기 전에 아래를 확인한다. 실제로 이 저장소에서 나왔던 결함들이다.

- **제목의 질문에 요약이 답하는가.** 답이 PoC 절에만 흩어져 있고 요약은 원문 목차만 따라가는 경우가 많다.
- **그림만 넘겨 봐도 흐름이 잡히는가.** 0절 그림과 각 그림의 제목만 이어 읽어도 이야기가 되는지 본다.
- **그림과 글이 같은 말을 반복하지 않는가.** 그림이 보여 주는 내용은 글에서 한 줄로 줄인다.
- **본문에 핵심만 남았는가.** 세부는 `<details>`로 접었는지, 문단이 길어져 표로 바꿔야 할 곳은 없는지 본다.
- **그림을 렌더링해서 눈으로 확인했는가.**
- **교차 참조가 문서 안을 가리키는가.** `→ 2절`, `→ PoC C`처럼 이 문서의 번호로 쓴다. 원문의 영문 소제목을 참조 열에 두면 독자가 원문으로 튕겨 나가고 요약과의 연결이 끊긴다. 원문 대응표가 필요하면 각주 한 줄로 내린다.
- **용어를 쓰기 전에 정의했는가.** 뒤 절에서 설명할 용어를 앞 절 도식이나 0절 그림에 먼저 쓰지 않는다. 0절 그림에 꼭 필요하면 그림 아래에 한 줄로 정의한다.
- **도구·이름이 하나로 통일됐는가.** 원문의 도구를 현대 대체물로 바꿔 검증했다면 본문은 검증에 쓴 쪽으로 통일하고, 전환은 한 문장으로 한 번만 밝힌다. 둘을 번갈아 쓰면 독자는 도구가 몇 개인지부터 헷갈린다.
- **숫자에 근거가 있는가.** 원문, 문서에 붙인 출력, 검증 스크립트에 없는 수치를 쓰지 않는다. 원문 안에서 수치가 서로 다르면 어느 쪽을 따랐는지 한 줄로 밝힌다.
- **개수를 말한 헤딩이 항목 수와 맞는가.** `두 가지 예외` 아래 세 항목이 있으면 둘 중 하나가 틀린 것이다.
- **같은 그림을 두 번 그리지 않았는가.** 요약 절은 원리, PoC는 실측값, 인사이트는 판단으로 역할을 나눈다. 같은 흐름이 두 그림에 나오면 한쪽을 지운다.
- **검증하지 않은 주장이 검증된 것처럼 보이지 않는가.** PoC로 확인하지 않은 절은 그렇게 밝힌다. 검증한 절과 나란히 두면 전부 실측처럼 읽힌다.
