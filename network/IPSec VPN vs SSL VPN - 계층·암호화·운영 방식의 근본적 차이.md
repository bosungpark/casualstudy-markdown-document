## AI 요약

### 1. 두 VPN은 무엇이 다른가?

IPSec와 SSL VPN은 "터널을 만들어 트래픽을 암호화한다"는 목적은 같지만, **OSI 어느 계층에서 동작하느냐**가 다르고 그 하나의 차이가 암호화·클라이언트·접근제어·운영 방식을 모두 갈라놓는다.

| 구분 | IPSec VPN | SSL VPN |
|------|-----------|---------|
| 동작 계층 | 네트워크 계층 (L3) | 전송~응용 계층 (L4~L7) |
| 암호화 대상 | IP 패킷 전체 | 애플리케이션/웹 세션 |
| 클라이언트 | 전용 클라이언트 SW 필요 | 웹 브라우저 (Clientless) |
| 인증 단위 | 디바이스(단말) 기반 | 사용자(User) 기반 |
| 주 용도 | Site-to-Site, 풀 네트워크 접근 | 원격 사용자, 특정 앱 접근 |
| 방화벽/NAT | NAT-T 필요, 통과 까다로움 | 443(HTTPS) 사용, 통과 용이 |

핵심 한 줄: **IPSec은 "네트워크를 통째로 연결"하고, SSL VPN은 "필요한 애플리케이션만 골라 연결"한다.**

### 2. 동작 계층 — 모든 차이의 근원

```
             OSI 계층                VPN 동작 위치
   ┌─────────────────────────┐
   │ 7  Application          │◄── SSL VPN
   │ 6  Presentation         │    (TLS 핸드셰이크 / 웹 세션 암호화)
   │ 5  Session              │◄── SSL VPN
   ├─────────────────────────┤
   │ 4  Transport (TCP/UDP)  │
   ├─────────────────────────┤
   │ 3  Network (IP)         │◄── IPSec
   │                         │    (IP 패킷 자체를 암·복호화)
   │ 2  Data Link            │
   │ 1  Physical             │
   └─────────────────────────┘
```

- **IPSec (L3)**: IP 위에서 직접 동작하여 라우팅되는 IP 패킷 자체를 보호한다. 애플리케이션은 VPN의 존재를 모른 채 그대로 통신한다 → **모든 트래픽이 투명하게 보호됨**.
- **SSL VPN (L4~L7)**: HTTPS(TLS)와 동일한 메커니즘으로 애플리케이션 데이터 스트림을 보호한다 → **특정 세션/앱 단위로 선택적 보호**.

---

### 3. 암호화 방식

#### IPSec — 프로토콜 스위트

IPSec은 단일 프로토콜이 아니라 여러 구성요소의 묶음이다.

```
   [ IKE ]  키 교환·SA 협상 (IKEv1/IKEv2 + Diffie-Hellman)
      │
      ├── [ ESP ]  Encapsulating Security Payload → 암호화 + 무결성
      └── [ AH  ]  Authentication Header → 무결성/인증만 (암호화 X)

   암호 알고리즘: AES, 3DES 등
   무결성:       HMAC-SHA
```

**동작 모드 2가지**

```
Transport 모드 (호스트↔호스트)
  [IP헤더][ ESP로 암호화된 페이로드 ]
   └ 원본 IP 헤더는 그대로 노출

Tunnel 모드 (게이트웨이↔게이트웨이, 가장 흔함)
  [새 IP헤더][ ESP로 암호화된 (원본 IP헤더 + 페이로드) ]
   └ 원본 헤더까지 통째로 캡슐화 → Site-to-Site 표준
```

#### SSL VPN — TLS 핸드셰이크

- 현재는 사실상 **TLS 1.2 / 1.3** 사용 (SSL은 이름만 남은 레거시 용어).
- **인증서(X.509)** 기반으로 서버를 인증하고 세션 키를 협상 → 이후 AES-GCM, ChaCha20 등으로 대칭 암호화.
- 웹 브라우저의 HTTPS와 동일 → 별도 클라이언트 없이 브라우저만으로 성립.

---

### 4. 운영 / 접속 방식

| 항목 | IPSec VPN | SSL VPN |
|------|-----------|---------|
| **클라이언트** | 전용 클라이언트 설치 필수 | 브라우저만으로 접속(Clientless) 또는 경량 에이전트 |
| **접속 형태** | 네트워크 전체 연결(풀 터널) | 특정 애플리케이션/웹 자원 단위 |
| **인증** | 디바이스 기반, 엄격 | 사용자 기반, 간편 (대신 세밀한 접근제어 관리 필요) |
| **배포/유지보수** | 설정 복잡, 유지보수 부담 | 배포 간편, 클라이언트 관리 최소화 |
| **방화벽/NAT 통과** | ESP 차단·NAT 이슈 → NAT-T 필요 | 443 포트 사용 → 대부분 환경 통과 |
| **성능** | 원시 처리 성능 우수 | TLS·브라우저 오버헤드로 상대적으로 느릴 수 있음 |

---

### 5. 접근 제어 관점 — 보안 경계의 넓이

```
IPSec: 연결되면 내부망에 "네트워크 레벨"로 광범위 접근
   [원격 단말] ══터널══> [게이트웨이] ──> 내부망 전체 도달 가능
        강력하지만 보안 경계가 넓어짐 (측면이동 위험 ↑)

SSL VPN: "애플리케이션 단위"로 세밀하게 접근
   [원격 사용자] ══TLS══> [게이트웨이] ──> 허용된 웹앱 A만
                                    └─X─> 앱 B, 앱 C 차단
        최소 권한(Least Privilege) 구현에 유리
```

- **IPSec**: 단말을 신뢰해 내부망 전체를 여는 모델 → 고정된 관리 단말 환경에 적합.
- **SSL VPN**: 자원별로 문을 여는 모델 → **제로트러스트(Zero Trust)**와 궁합이 좋음.

---

### 6. 언제 무엇을 쓰나

**IPSec VPN을 선택**
- 본사–지사 간 고정된 **Site-to-Site** 연결
- 모든 트래픽을 상시 투명하게 터널링해야 할 때
- 관리 서버가 통제하는 고정 단말 환경, 최고 처리 성능이 필요할 때

**SSL VPN을 선택**
- 다양한 기기로 접속하는 **원격 근무자·모바일 사용자**
- 클라이언트 설치가 어렵거나 방화벽 제약이 많은 환경
- 특정 웹 앱/자원만 선택적으로 열어주고 싶을 때

> Palo Alto의 결론: **어느 쪽도 절대적으로 우월하지 않다.** "보안의 깊이(IPSec)" vs "배포의 단순함(SSL)" 사이에서 조직 요구사항에 맞춰 선택하는 문제다.

## 내가 얻은 인사이트

### 아키텍처 관점

1. **"어느 계층에서 암호화하는가"가 제품 특성을 결정한다**
   - IPSec이 클라이언트를 요구하고 NAT에서 애를 먹는 이유, SSL VPN이 브라우저만으로 되고 방화벽을 잘 통과하는 이유는 전부 L3 vs L7이라는 단 하나의 설계 결정에서 파생된다. 스펙 표를 외우기보다 이 근원을 잡으면 나머지는 유도할 수 있다.
   - L3 암호화는 애플리케이션에 투명(transparent)하다는 것이 장점이자 단점이다. 앱을 수정할 필요가 없어 편하지만, 그만큼 "무엇이 열렸는지"가 불투명해 접근 경계가 넓어진다.

2. **SSL VPN이 443을 쓴다는 건 "웹 인프라에 무임승차"한다는 뜻**
   - 전 세계 방화벽이 이미 HTTPS(443)를 허용하도록 설정돼 있으므로, 같은 포트를 재사용하는 SSL VPN은 별도 통과 정책이 필요 없다. 반면 IPSec은 ESP/IKE라는 고유 프로토콜을 쓰기 때문에 NAT-T 같은 우회 기법이 필요하다. **기존 표준에 얹는 설계가 배포 마찰을 얼마나 줄이는지** 보여주는 좋은 사례.

### 보안 설계 관점

3. **트렌드가 IPSec(디바이스 신뢰) → SSL VPN(자원별 신뢰)으로 이동한 이유**
   - 전통적 IPSec은 "단말이 붙으면 내부망을 믿고 연다"는 성곽(castle-and-moat) 모델이다. 원격근무 확대와 측면이동(lateral movement) 위협으로 이 전제가 깨지면서, 자원 단위로 최소 권한을 부여하는 SSL VPN / 제로트러스트가 부상했다.
   - 다만 SSL VPN도 "사용자 기반 인증"이라 계정 탈취 시 위험이 사용자 권한만큼 열린다. 계층이 낮다고 안전, 높다고 위험이 아니라 **각자 다른 위협 모델**을 가진다는 점이 실무적 통찰.

### 실무 트레이드오프 관점

4. **성능 vs 유연성은 상시연결 vs 임시접속과 겹친다**
   - IPSec의 원시 성능 우위는 "상시 켜두는 Site-to-Site 백본"에서 값어치를 하고, SSL VPN의 유연성은 "제약 많은 환경에서 잠깐 붙는 원격 사용자"에서 값어치를 한다. 성능 수치만 비교하면 IPSec 승리처럼 보이지만, 실제 선택은 **연결의 수명과 주체**가 좌우한다.
   - 현실에서는 둘 중 하나가 아니라 병행 운영이 흔하다: 지사 연결은 IPSec, 재택 인력 접속은 SSL VPN. "대결"이 아니라 "용도별 배치"로 보는 것이 맞다.
