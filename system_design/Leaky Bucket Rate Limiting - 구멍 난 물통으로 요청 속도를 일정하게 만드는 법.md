## AI 요약

### 1. Leaky Bucket이란?

바닥에 작은 구멍이 난 물통을 떠올리면 된다.

- 요청(request)은 **물통에 붓는 물**이다. 언제, 얼마나 몰려올지 알 수 없다.
- 구멍으로는 **항상 일정한 속도**로 물이 빠져나간다. 이것이 "처리 속도"다.
- 물통에는 **용량(capacity)**이 있다. 붓는 속도가 빠져나가는 속도보다 빠르면 물이 차오르고, 가득 찬 상태에서 더 부으면 넘친다. 넘친 물이 **거부된 요청**이다.

핵심은 한 문장이다. **들어오는 속도가 아무리 들쭉날쭉해도, 나가는 속도는 항상 일정하다.** 원문은 이를 Token Bucket과 대비시킨다. Token Bucket은 토큰을 모아 두었다가 한꺼번에 쓰는 "버스트(burst)"를 허용하지만, Leaky Bucket은 출력 속도를 일정하게 유지하는 데만 집중한다.

```
   요청 A B C D E ...  (불규칙하게 도착)
        │ │ │ │ │
        ▼ ▼ ▼ ▼ ▼
     ┌───────────┐
     │ ~~~~~~~~~ │  ← 용량(capacity)까지 차면 넘침 = 거부(429)
     │ ~~~~~~~~~ │
     │ ~~~~~~~~~ │
     └─────┬─────┘
           │  ← 일정한 속도로 누수(leak) = 처리
           ▼
       서버 / 다운스트림
```

### 2. 그림으로 보는 동작 (초당 1건 누수, 용량 2)

원문 Figure 1의 시나리오를 시간순으로 풀면 다음과 같다.

| 시각 | 요청 | 물통 상태 (처리 전) | 결과 | 이유 |
|------|------|--------------------|------|------|
| 0초 | A | 비어 있음 (0/2) | 수락 | 빈 물통에 들어감 |
| 0초 | B | 1/2 | 수락 | 한 칸 남아 있어 가득 참 |
| 0초 | C | 2/2 | **거부** | 가득 찼고 아직 누수가 없음 |
| 1초 | D | 1/2 (A가 빠짐) | 수락 | 1초 지나 한 칸 비었음 |
| 3초 | E | 0/2 (B, D 빠짐) | 수락 | 누수가 이어져 물통이 비었음 |

몰려온 C는 거부되지만, 시간이 흐르며 물이 빠지면 D, E는 정상 수락된다. 구멍의 크기(누수 속도)가 서버가 감당할 수 있는 처리량이고, 물통의 크기(용량)가 "잠깐 참아줄 수 있는 밀림의 양"이다.

### 3. 구현 방식 1: 순수(pure) Leaky Bucket, 큐 없이 "수위"만 센다

원문이 먼저 보여주는 구현은 큐를 쓰지 않는다. 물통의 **수위(water level)**를 숫자 하나로 기억하고, 요청이 올 때마다 "그동안 얼마나 빠졌는지"를 계산해 수위를 낮춘 뒤, 자리가 있으면 수위를 1 올리고 통과시킨다.

설정값은 세 가지다.

| 설정 | 의미 |
|------|------|
| `capacity` | 물통이 동시에 "담고 있을 수 있는" 최대 요청 수 |
| `period` | 누수를 평가하는 시간 단위 |
| `leaksPerPeriod` | `period`마다 빠져나가는(처리되는) 요청 수 |

동작 흐름은 다음과 같다.

```
요청 도착
  │
  ▼
사용자별 물통 조회 (없으면 수위 0으로 생성)
  │
  ▼
leak(): 마지막 누수 시각 이후 지난 period 수 × leaksPerPeriod 만큼 수위 감소 (0 미만 불가)
  │
  ▼
수위 < capacity ?
  ├─ 예 → 수위 += 1, 요청 통과 (true)
  └─ 아니오 → 요청 거부 (false)
```

원문의 Java 구현 핵심부를 의역하면 이렇다.

```java
public boolean allowed(String userId) {
  LeakyBucket bucket = userLeakyBucket.computeIfAbsent(userId,
      k -> new LeakyBucket(clock.millis(), 0));   // Map<String, LeakyBucket>
  bucket.leak();          // 지난 시간만큼 물을 빼고
  return bucket.processed(); // 자리가 있으면 수위 +1 후 통과
}

void leak() {
  long now = clock.millis();
  long elapsedPeriods = (now - leakTimestamp) / period.toMillis();
  long leaks = elapsedPeriods * leaksPerPeriod;
  if (leaks > 0) {
    waterLevel = Math.max(0, waterLevel - leaks);
    leakTimestamp = now;
  }
}

boolean processed() {
  if (waterLevel < capacity) { ++waterLevel; return true; }
  return false;
}
```

눈여겨볼 점은 **백그라운드 타이머가 없다**는 것이다. 물이 "실제로" 빠지는 게 아니라, 요청이 들어온 순간에 경과 시간으로 누수를 소급 계산한다. 그래서 상태는 사용자당 숫자 두 개(마지막 누수 시각, 수위)면 충분하다.

원문의 테스트는 `capacity=1, period=2초, leaksPerPeriod=1`로 Bob과 Alice 두 사용자를 시뮬레이션한다. Bob의 첫 요청(0ms)은 통과, 999ms와 1000ms의 요청은 아직 2초가 지나지 않아 거부, 2001ms의 요청은 한 번 누수가 일어나 통과한다. Alice는 Bob과 독립된 물통을 가지므로 1000ms에 첫 요청이 바로 통과한다. 이 테스트가 보여주는 것은 두 가지다. **사용자별로 물통이 분리된다**는 것과, **`period`가 지나기 전까지는 물이 한 방울도 빠지지 않는다**는 것(정수 나눗셈이므로 누수는 `period` 단위로 계단식으로 일어난다).

### 4. 구현 방식 2: 큐 기반(queue-based) Leaky Bucket

원문이 소개하는 두 번째 방식은 이름 그대로 **고정 용량 FIFO 큐**를 쓴다.

1. 큐가 들어오는 요청의 버퍼 역할을 한다.
2. 요청이 도착하면 큐의 뒤에 붙인다.
3. 별도의 "누수" 프로세스가 설정된 속도로 큐의 앞에서 요청을 꺼내 처리한다.
4. 요청이 도착했을 때 큐가 가득 차 있으면 그 요청은 거부한다.

두 방식의 차이는 "물통이 가득 찼을 때 무엇을 하느냐"가 아니라, **수락된 요청을 언제 처리하느냐**에 있다.

| | 순수(pure) 방식 | 큐 기반 방식 |
|---|---|---|
| 수락된 요청의 처리 시점 | 즉시 처리. 수위는 "최근에 얼마나 썼는지"의 회계 장부 | 큐에서 차례가 올 때 처리. 대기 지연이 생김 |
| 상태 | 숫자 2개 (시각, 수위) | 실제 요청 객체가 큐에 쌓임 |
| 출력 형태 | 일정 시간당 허용 건수를 보장 | 처리 자체가 일정 간격으로 나감 (진짜 트래픽 셰이핑) |
| 원문의 권장 상황 | 엄격하고 보장된 rate limit이 우선일 때 | 버스트를 흡수하면서 평균 속도를 유지하고 싶을 때 |

원문은 둘 다 유효한 Leaky Bucket 구현이며, 요구사항에 따라 고르라고 정리한다.

### 5. 트레이드오프

**장점**
- **단순함**: 개념이 직관적이고 구현이 쉽다. 복잡도를 줄여야 하는 곳에 알맞다.
- **일정한 흐름**: 들어오는 버스트와 무관하게 출력 속도가 고정된다. 서버 과부하 방지나 DoS 완화처럼 "예측 가능한 흐름"이 중요한 상황에 맞다.
- **메모리 효율**: 큐 크기가 고정이라 추가 메모리가 거의 필요 없다.

**단점**
- **버스트에 약함**: 물통 용량을 넘는 순간적 폭주는 그대로 거부된다. 가끔 트래픽이 튀는 서비스에는 불리하다.
- **공정성 문제**: 갑작스러운 유입이 물통을 순식간에 채우면 그 뒤에 오는 새 요청은 굶는다(starvation). 수락된 요청도 언제 처리될지 불확실해진다.
- **저활용**: 트래픽이 적을 때도 정해진 속도로만 처리하므로 여유 자원을 놀린다.

### 6. 실제 쓰임

- 원문은 네트워크 트래픽 관리(영상 스트리밍, 통신)처럼 **일정한 데이터 흐름**이 중요한 곳을 대표 사례로 든다.
- API rate limit에도 쓰인다. 원문이 직접 언급한 예는 **Shopify의 API rate limit**과 **nginx의 `ngx_http_limit_req_module`**이다. 둘 다 Leaky Bucket 방식이다.

## 내가 얻은 인사이트

### 개념 정리

1. **"쉽게 설명"의 핵심은 두 개의 손잡이다.**
   - 구멍 크기(누수 속도) = 다운스트림이 실제로 감당 가능한 처리량, 물통 크기(용량) = 잠깐 밀리는 걸 얼마나 참아줄지. 설정을 고민할 때 이 두 질문으로 환원하면 대부분 정리된다.
   - 원문의 Figure 1(초당 1건, 용량 2)을 직접 파이썬으로 재현해 보니 A, B 수락, C 거부, D, E 수락으로 원문과 동일했다. 테스트 시나리오(Bob/Alice)도 원문의 기대값과 모두 일치했다. (원문 요약이 아니라 내 재현 결과다.)

2. **순수 방식은 사실상 Token Bucket의 거울상이다. (내 해석, 원문 주장 아님)**
   - 원문은 Leaky Bucket을 Token Bucket과 대비시키지만, 큐 없이 수위만 세는 순수 방식은 "토큰을 채운다"를 "물을 뺀다"로 뒤집은 것과 같다. 용량 N, 누수 속도 r인 순수 Leaky Bucket과 용량 N, 충전 속도 r인 Token Bucket은 같은 요청 열에 같은 판정을 내린다.
   - 따라서 "Leaky Bucket은 버스트를 못 받는다"는 말은 **큐 기반 방식**에만 정확히 들어맞는다. 순수 방식은 용량만큼의 버스트를 허용한다. 두 방식을 뭉뚱그려 부르는 데서 오는 혼란을 원문이 잘 분리해 준다.

### 실무 관점

3. **큐 기반의 진짜 비용은 거부가 아니라 지연이다.**
   - 큐에 들어간 요청은 "수락"되었지만 처리는 나중이다. 용량을 크게 잡을수록 거부율은 낮아지지만 뒤쪽 요청의 대기 시간은 용량 ÷ 누수 속도만큼 늘어난다. 사용자 응답을 기다리는 API라면 빨리 429를 주는 순수 방식이 오히려 친절할 수 있다.
   - 큐 기반이 빛나는 곳은 원문이 말하듯 "평균 속도를 지키면서 폭주를 흡수"해야 하는 다운스트림 보호다. 예를 들어 초당 처리량이 고정된 외부 결제 API나 파트너 쿼터를 향한 아웃바운드 호출을 셰이핑할 때다.

4. **원문 구현은 단일 프로세스 전제다.**
   - `HashMap`은 동시성을 고려하지 않았고, 인스턴스마다 물통이 따로 생기므로 여러 파드에 배포하면 사용자는 파드 수만큼 한도를 곱해 쓸 수 있다. 실제 서비스에서는 Redis 같은 공유 저장소에 (마지막 누수 시각, 수위) 두 값을 두고 원자적으로 갱신해야 한다. 순수 방식의 상태가 숫자 두 개뿐이라는 점이 여기서 장점이 된다.

5. **누수 계산의 계단 현상을 알고 설정해야 한다.**
   - 경과 시간을 `period`로 정수 나눗셈하므로 `period`가 길면 그 안에서는 한 방울도 빠지지 않는다. 원문 테스트에서 999ms, 1000ms 요청이 모두 거부된 이유다. 부드러운 누수를 원하면 `period`를 짧게 잡고 `leaksPerPeriod`를 그에 맞춰 줄이거나, 밀리초 단위 실수 계산으로 바꾸는 편이 낫다.
