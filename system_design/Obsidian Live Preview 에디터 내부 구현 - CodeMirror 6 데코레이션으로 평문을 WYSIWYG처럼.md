## AI 요약

### 1. 풀어야 할 문제 — "데이터는 평문, 화면은 리치하게"

Obsidian의 가장 중요한 제약은 **저장 데이터는 끝까지 순수 마크다운(.md)이어야 한다**는 것이다. 그런데 사용자는 `**굵게**`라는 별표가 항상 보이는 걸 원하지 않는다. 굵은 글씨로 **보이길** 원한다.

전통적 마크다운 앱은 이걸 **창을 둘로 쪼개서** 해결했다.

```
┌─────────────────┬─────────────────┐
│  편집 패널        │  미리보기 패널    │
│  (원문 텍스트)    │  (렌더링된 HTML)  │
│                 │                 │
│  # 제목          │   제목 (큰 글씨)  │
│  **굵게**        │   굵게 (볼드)     │
└─────────────────┴─────────────────┘
   ↑ 같은 내용을 두 번 본다 = 시선 분산
```

Obsidian의 **Live Preview**는 이 분리를 없앤다. **한 화면에서**, 커서가 없는 곳은 렌더링된 모습으로, 커서가 닿은 줄만 원문으로 보여준다. 핵심은:

> **문서(document)는 절대 건드리지 않는다. 오직 '보이는 방식'만 바꾼다.**

이걸 가능하게 하는 게 CodeMirror 6의 **Decoration** 시스템이다.

| 요구사항 | 구현 메커니즘 |
|---------|-------------|
| 저장 데이터는 평문 유지 | Document는 불변, 시각 효과는 view-only decoration |
| `**굵게**`를 **굵게**로 보이기 | 별표 토큰을 숨기고(hide), 본문에 볼드 스타일 적용(mark) |
| 커서가 닿으면 원문 노출 | 커서 위치를 decoration 범위와 비교해 활성 줄만 reveal |
| 거대 문서도 빠르게 | Viewport 가상화 — 보이는 영역 + α만 렌더 |
| 복붙/저장이 원문과 1바이트도 안 틀림 | decoration은 DOM에만 존재, 텍스트엔 없음 |

### 2. CodeMirror 6의 핵심 3요소 — State / View / Decoration

Live Preview를 이해하려면 CM6의 아키텍처를 알아야 한다. CM6는 **상태(State)와 뷰(View)를 엄격히 분리**한다.

```
┌───────────────────────────────────────────────┐
│                 EditorState                     │
│  (불변 immutable - 문서 내용 + 커서/선택 영역)    │
│   "이것이 진실의 원천(source of truth)"          │
└──────────────────────┬────────────────────────┘
                       │ Transaction (변경 = 새 State 생성)
                       ▼
┌───────────────────────────────────────────────┐
│                  EditorView                     │
│  (State를 받아 실제 DOM을 그림 / 사용자 입력 수신) │
│                                                 │
│   ┌─────────────────────────────────────────┐  │
│   │  Decorations  ← 여기가 Live Preview 핵심  │  │
│   │  "텍스트는 그대로, 보이는 모습만 덧칠"      │  │
│   └─────────────────────────────────────────┘  │
└───────────────────────────────────────────────┘
```

**Decoration의 4가지 타입** (Live Preview가 모두 활용한다):

| 타입 | 역할 | Live Preview에서의 용도 |
|------|------|----------------------|
| `Decoration.mark()` | 텍스트 구간에 CSS 클래스 입힘 | `**굵게**`의 본문에 볼드 스타일 |
| `Decoration.replace()` | 구간을 위젯으로 치환(또는 숨김) | `**` 별표 토큰 자체를 안 보이게 |
| `Decoration.widget()` | 특정 지점에 DOM 삽입 | 렌더된 이미지·수식·임베드 |
| `Decoration.line()` | 줄 전체에 속성 부여 | 헤딩 줄, 인용문 줄 스타일 |

### 3. 렌더링 파이프라인 — syntaxTree에서 DecorationSet으로

Live Preview는 매 변경마다 다음 흐름을 돈다.

```
   문서 변경 / 커서 이동
          │
          ▼
  ┌────────────────┐   Lezer 파서가 마크다운을
  │  syntaxTree     │   증분 파싱(incremental parse)
  │  (Lezer 파스트리)│   → 헤딩/강조/링크/코드블록 노드
  └───────┬────────┘
          │  viewport 범위만 순회 (보이는 영역 + α)
          ▼
  ┌────────────────┐   각 노드 타입별로:
  │  Decoration     │   - 마크업 토큰(`**`,`#`) → replace(숨김)
  │  빌더            │   - 본문 → mark(스타일 클래스)
  │                 │   - 블록(이미지/수식) → widget(렌더)
  └───────┬────────┘
          │  단, 커서가 노드 안에 있으면 → 데코 건너뜀(원문 노출)
          ▼
  ┌────────────────┐
  │  DecorationSet  │ → EditorView.decorations facet으로 제공
  └───────┬────────┘
          │
          ▼
   CM6가 텍스트 위에 데코를 입혀 DOM 렌더
```

**구현의 핵심 포인트 3가지:**

**(a) syntaxTree 기반 정밀 타겟팅**
정규식으로 `**...**`를 찾지 않는다. Lezer 파서가 만든 **구문 트리**를 순회하며 노드 타입(`StrongEmphasis`, `ATXHeading`, `Link`...)으로 정확히 식별한다. 중첩(`**굵게 _기울임_**`)이나 코드블록 안의 별표 같은 엣지 케이스가 자동으로 올바르게 처리된다.

**(b) Viewport 가상화 — 수백만 줄도 버틴다**
CM6 에디터는 **보이는 영역(viewport)과 그 주변만 DOM으로 렌더**한다. Decoration도 전체 문서가 아니라 viewport 범위만 빌드한다. 그래서 10만 줄짜리 노트를 열어도 화면에 보이는 ~50줄에 대해서만 파싱·데코 작업이 일어난다.

```
전체 문서 (예: 100,000줄)
┌─────────────────────────┐
│   ... (렌더 안 함) ...    │
├─────────────────────────┤ ← viewport 시작
│  실제 DOM + decoration   │   ← 여기 ~50줄 + 위아래 여유분만
│  이 영역만 처리           │      파싱하고 데코를 만든다
├─────────────────────────┤ ← viewport 끝
│   ... (렌더 안 함) ...    │
└─────────────────────────┘
```

**(c) ViewPlugin vs StateField — 어디에 데코를 둘 것인가**
CM6에서 decoration을 제공하는 방법은 두 가지이며, Live Preview는 둘을 용도별로 나눠 쓴다.

| 제공 방식 | 특징 | 쓰임새 |
|----------|------|--------|
| `ViewPlugin` | viewport·뷰 변화에 반응, 화면 기준 | 대부분의 인라인 데코(강조/링크 숨김) |
| `StateField` | State 트랜잭션에 반응, 문서 기준 | 위치가 문서 전체에 걸쳐 유지돼야 하는 데코 |

> 공식 마이그레이션 가이드의 변화: "plugin fields는 사라졌고, 이제 데코는 `EditorView.decorations` **facet에 함수를 제공**하는 방식으로 준다." (`atomicRanges`, `scrollMargins`도 facet으로 전환)

### 4. 마법의 핵심 — "커서가 닿으면 원문이 돌아온다"

Live Preview를 Live Preview답게 만드는 단 하나의 동작. 구현 원리는 의외로 단순하다.

```
데코를 만들기 직전, 각 마크업 노드마다 물어본다:
  "지금 커서(또는 선택 영역)가 이 노드 범위와 겹치는가?"

  ┌──────────────────────────────────────┐
  │  **굵게**   ← 커서가 다른 줄에 있음     │
  │   → 별표 숨김 + 볼드 적용 = 굵게        │
  ├──────────────────────────────────────┤
  │  **굵게**|  ← 커서가 이 줄에 들어옴     │
  │   → 데코 건너뜀 = 별표 다시 보임 = **굵게** │
  └──────────────────────────────────────┘
```

즉 **"커서가 겹치는 노드는 decoration을 만들지 않는다"**는 조건 하나로 "타이핑할 땐 원문, 비활성일 땐 렌더"가 구현된다. 커서가 이동할 때마다 viewport 데코가 재계산되므로, 별표는 커서가 떠나는 순간 다시 사라진다(tuck away).

이 비교가 빠른 이유 역시 **데코를 viewport 범위만 만들기 때문**이다. 커서 한 번 움직일 때 100줄만 재평가하면 된다.

### 5. 토큰을 "어떻게" 숨기는가 — display:none의 함정

마크업 토큰(`**`, `#`, `[[ ]]`)을 안 보이게 하는 건 생각보다 까다롭다. 순진하게 `display: none`을 쓰면 **커서가 그 자리에 갈 수 없어** 편집이 깨진다.

CodeMirror 진영이 실제로 거쳐온 접근들:

| 접근 | 방법 | 문제 |
|------|------|------|
| `display: none` (순진) | 토큰 DOM을 숨김 | 커서 배치가 깨짐 ❌ |
| CSS 트릭 (CM5 시절) | `font-size:1px; letter-spacing:-1ch; color:transparent` | 작동하나 해킹에 가까움 |
| **zero-width 처리 (CM6)** | 비활성 토큰을 **너비 0**으로 만들어 replace | 레이아웃 안정 + 커서 정상 ✅ |

> nothingislost의 관찰: "Live Preview 에디터의 DOM은 Source 모드와 거의 같되, **비활성 마크다운 토큰이 zero-width로 대체**된다는 점이 다르다." → 줄의 높이·구조는 그대로 유지되므로 커서가 들어오면 자연스럽게 토큰이 펼쳐진다.

**레이아웃 안정성(no layout shift)**: 토큰을 숨겨도 줄 높이는 변하지 않게 설계한다. 그래서 커서가 줄을 드나들 때 텍스트가 위아래로 출렁이지(reflow) 않는다 — 에디터에서 흔한 CLS(Cumulative Layout Shift) 문제를 회피.

### 6. 블록 렌더링 — 이미지·수식·임베드는 Widget으로

인라인 스타일(굵게/링크)과 달리, **이미지·LaTeX 수식·노트 임베드(`![[note]]`)·코드블록 결과**는 텍스트 스타일링으로 안 된다. 별도의 DOM 덩어리를 끼워 넣어야 한다. 여기서 `Decoration.widget()` / `replace({widget})`이 쓰인다.

```
원문(평문 유지):           화면(위젯 주입):
┌────────────────┐        ┌────────────────┐
│ ![[diagram.png]]│  →     │  ┌──────────┐  │
│                │        │  │ [실제 이미지]│  │ ← widget DOM
│ $E = mc^2$     │  →     │  └──────────┘  │
│                │        │   E = mc²       │ ← 렌더된 수식 widget
└────────────────┘        └────────────────┘
   (.md 파일엔                (위젯은 DOM에만,
    이 텍스트만)               파일엔 안 들어감)
```

주의점: 위젯이 CM6 에디터 DOM 안에 **새 DOM 노드를 추가**하므로, viewport 높이 계산·스크롤 위치 보정이 함께 일어나야 한다. (그래서 `lineBlockAtHeight` 같은 height 측정 API가 중요)

### 7. 전체를 한 장으로 — Live Preview 동작 요약

```
[사용자가 타이핑 / 커서 이동]
        │
        ▼
 EditorState 갱신 (불변, 새 State)
        │
        ▼
 ViewPlugin.update() 호출
        │
        ├─ syntaxTree(state) 로 viewport 구간 파싱
        │
        ├─ 각 마크업 노드마다:
        │     커서가 겹치나? ── 예 ──▶ 데코 안 만듦 (원문 노출)
        │             │
        │             └─ 아니오 ──▶ 토큰 replace(숨김) + 본문 mark(스타일)
        │                          블록이면 widget(렌더)
        │
        ▼
 DecorationSet 완성 → EditorView.decorations facet
        │
        ▼
 CM6가 텍스트 위에 데코 입혀 DOM 패치 (변경분만)
        │
        ▼
[화면: WYSIWYG처럼 보이지만 문서는 여전히 순수 .md]
```

## 내가 얻은 인사이트

### 아키텍처 관점

1. **"렌더링을 데이터가 아니라 뷰의 책임으로"라는 분리의 일관성**
   - 이전 개요 문서에서 본 큰 원칙 — *"원본은 단순하게, 부가 기능은 파생물로"* — 이 에디터 레이어에서도 똑같이 반복된다. 백링크가 in-memory 인덱스의 파생물이듯, **굵게/제목/이미지 미리보기는 전부 DecorationSet이라는 view-only 파생물**이다. 문서(EditorState의 doc)는 끝까지 순수 텍스트.
   - 한 제품이 서로 다른 레이어(인덱싱 / 에디터)에서 **같은 설계 철학**을 관철하면, 기능 간 충돌이 줄고 추론이 쉬워진다. "데이터는 단순하게, 똑똑함은 파생 레이어에"가 Obsidian 전체를 관통하는 한 문장이다.

2. **State와 View의 엄격한 분리가 Live Preview를 가능하게 한다**
   - CM6가 "State는 불변, View는 State를 그리는 함수"로 못 박았기 때문에, "같은 텍스트를 커서 위치에 따라 다르게 그린다"가 깔끔하게 성립한다. 만약 에디터가 텍스트와 화면을 한 덩어리로 다뤘다면(예: contentEditable에 직접 HTML), 평문 보존과 리치 렌더를 동시에 잡기 어려웠을 것이다.
   - **교훈**: "보여지는 것(view)"을 "진실(state)"에서 떼어내면, 같은 진실에 대해 여러 표현(Source/Live Preview/Reading)을 비용 없이 추가할 수 있다.

### 설계 트레이드오프 관점

3. **정규식이 아니라 구문 트리를 쓰는 이유 = 정확성의 비용을 미리 지불**
   - `**...**`를 정규식으로 잡으면 중첩·코드블록 예외에서 무너진다. Lezer 증분 파서를 깔아 syntaxTree를 유지하는 건 초기 복잡도 비용이 크지만, **엣지 케이스를 구조적으로 제거**한다.
   - 이건 "싼 임시방편(정규식) vs 비싼 정공법(파서)"의 전형적 선택이고, 매 키 입력마다 돌아야 하는 핫패스에서는 정공법이 결국 이긴다. **자주 실행되는 경로일수록 정확한 자료구조에 투자하라.**

4. **성능의 비밀은 알고리즘이 아니라 '범위 한정(viewport)'이다**
   - "10만 줄도 빠르다"의 답은 더 빠른 파싱이 아니라, **애초에 보이는 ~50줄만 처리**한다는 범위 한정이다. 커서 비교도, 데코 빌드도, DOM 패치도 전부 viewport 스코프.
   - **실무 적용**: 무거운 작업을 만났을 때 "어떻게 빠르게 할까"보다 "**어떻게 일을 안 할까(보이는 것만)**"를 먼저 물어라. 가상화(virtualization)는 리스트·테이블·맵 등 큰 UI 전반에 재사용되는 가장 가성비 높은 패턴이다.

5. **`display:none`의 함정 — UI는 '안 보이게'와 '없는 것'이 다르다**
   - 토큰을 단순히 숨기면 커서가 그 자리에 못 가서 편집이 깨진다. "보이지 않지만 커서는 갈 수 있어야 한다"는 요구는 zero-width 처리라는 정교한 해법을 강제했다.
   - **교훈**: 에디터·접근성 영역에서 "숨김"은 시각적 숨김 / 레이아웃 제거 / 포커스 제거 / 스크린리더 제거가 전부 다른 축이다. 한 축만 생각하고 `display:none`을 쓰면 다른 축이 깨진다.

### 실무 적용 관점

6. **"한 화면 안의 모드 전환"이라는 UX 패턴**
   - Live Preview의 본질은 "편집 모드 / 보기 모드를 토글"이 아니라, **커서 위치를 신호로 줄 단위에서 자동 전환**하는 것이다. 사용자는 모드를 의식하지 않는다.
   - 이 "컨텍스트(커서/포커스)에 따라 같은 요소가 편집형↔표시형으로 바뀌는" 패턴은 인라인 편집 UI(노션식 슬래시 메뉴, 인플레이스 편집 필드, 코드 셀)에 두루 적용할 수 있는 일반 패턴이다. 핵심 질문은 "**전환을 트리거하는 신호를 무엇으로 잡을 것인가**(커서 겹침? 호버? 더블클릭?)".

7. **오픈소스 재현 구현(atomic-editor)이 곧 최고의 사양서**
   - Obsidian 본체는 클로즈드 소스라 내부를 직접 못 본다. 하지만 동일 동작을 CM6로 재현한 작은 오픈소스(atomic-editor)가 "데코로 토큰 숨기기 / 커서 기반 노출 / syntaxTree 타겟팅"이라는 **핵심 메커니즘을 투명하게** 보여준다.
   - **교훈**: 블랙박스 제품의 내부가 궁금할 때, "이걸 똑같이 만들려면 무엇이 필요한가"를 구현한 미니 클론이 종종 공식 문서보다 정확한 사양서가 된다.
