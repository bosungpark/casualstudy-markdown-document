## AI 요약

### 1. 프로세스란?

**프로세스(process)의 정의는 놀랄 만큼 단순하다: "실행 중인 프로그램(a running program)"이다.**

디스크에 놓인 프로그램 자체는 생명이 없는 물건(lifeless thing)이다. 그냥 명령어 더미와 약간의 정적 데이터가 디스크에 앉아 있을 뿐이다. 이 바이트 덩어리를 실행 상태로 바꿔 쓸모 있게 만드는 주체가 OS다.

| 구분 | Program | Process |
|---|---|---|
| 위치 | 디스크(또는 SSD) | 메모리 |
| 상태 | 정적, 수동적 | 동적, 실행 중 |
| 구성 | 코드 + 정적 데이터 | 코드 + 정적 데이터 + 스택 + 힙 + 레지스터 + I/O 정보 |
| 개수 | 1개의 실행 파일 | 같은 프로그램에서 N개 생성 가능 |

#### 이 챕터가 던지는 질문 (The Crux)

> **어떻게 "CPU가 많이 있다"는 환상을 만들 것인가?**
> 물리 CPU는 몇 개뿐인데, OS는 어떻게 거의 무한한 CPU가 있는 것 같은 환상을 제공하는가?

일반적인 시스템은 수십~수백 개의 프로세스를 동시에 실행하는 것처럼 보인다. 사용자는 "지금 CPU가 비어 있나?"를 신경 쓸 필요 없이 그냥 프로그램을 실행한다. 이 환상의 정체가 **CPU 가상화(virtualizing the CPU)** 다.

**동작 원리는 무식할 정도로 단순하다.** 하나를 잠깐 실행하고, 멈추고, 다른 것을 실행하고, 다시 멈추고를 반복한다. 이것이 **시분할(time sharing)** 이다. 대가는 성능이다. CPU를 나눠 쓰면 각 프로세스는 그만큼 느리게 돈다.

```
  물리 CPU 1개                          사용자가 보는 환상
  ┌──────────────┐                    ┌────┐ ┌────┐ ┌────┐
  │ P0 P1 P2 P0  │   ──── 시분할 ───▶  │vCPU│ │vCPU│ │vCPU│
  │ P1 P2 P0 P1  │                    │ P0 │ │ P1 │ │ P2 │
  └──────────────┘                    └────┘ └────┘ └────┘
   시간축으로 잘게 쪼개 번갈아 실행        "각자 CPU를 하나씩 가진 것 같다"
```

> **시분할(time sharing)과 공간분할(space sharing)**
> 시분할은 자원을 *시간*으로 나눠 쓴다(CPU, 네트워크 링크). 반대편에 있는 공간분할은 자원을 *공간*으로 나눈다. 디스크 공간이 대표적이다. 한 블록이 어떤 파일에 할당되면, 그 파일이 지워지기 전까지 다른 파일에 할당되지 않는다.

### 2. 메커니즘과 정책의 분리

CPU 가상화를 "잘" 구현하려면 저수준 기계 장치와 고수준 지능이 둘 다 필요하다. OSTEP은 이를 명시적으로 두 층으로 가른다.

| 구분 | 질문 | 의미 | 예시 |
|---|---|---|---|
| **메커니즘 (mechanism)** | **How?** | 기능을 실제로 구현하는 저수준 프로토콜 | 컨텍스트 스위치는 *어떻게* 하는가 |
| **정책 (policy)** | **Which?** | 결정을 내리는 알고리즘 | *어떤* 프로세스를 지금 실행할 것인가 |

정책은 과거 이력(최근 1분간 누가 많이 돌았나), 워크로드 지식(어떤 종류의 프로그램인가), 성능 지표(대화형 응답성 우선인가, 처리량 우선인가)를 근거로 판단한다.

**둘을 분리하면 메커니즘을 다시 설계하지 않고 정책만 갈아끼울 수 있다.** 소프트웨어 설계의 모듈화 원칙이 OS에 적용된 형태다.

### 3. 프로세스의 machine state — 무엇이 프로세스를 구성하는가

프로세스를 이해하려면 그 **machine state**, 즉 "이 프로그램이 실행 중일 때 읽거나 쓸 수 있는 것"이 무엇인지 알아야 한다. OSTEP은 세 가지를 꼽는다.

| 구성요소 | 내용 | 왜 프로세스의 일부인가 |
|---|---|---|
| **메모리 (주소 공간, address space)** | 코드, 정적 데이터, 힙, 스택 | 명령어도 메모리에 있고, 읽고 쓰는 데이터도 메모리에 있다 |
| **레지스터 (registers)** | 범용 레지스터 + 특수 레지스터 | 수많은 명령어가 레지스터를 명시적으로 읽고 쓴다 |
| **I/O 정보** | 현재 열려 있는 파일 목록 등 | 프로그램은 영속 저장장치에도 접근한다 |

특히 중요한 특수 레지스터들:

| 레지스터 | 역할 |
|---|---|
| **PC (Program Counter)** = IP (Instruction Pointer) | 다음에 실행할 명령어가 어디인지 |
| **Stack Pointer** | 스택의 현재 꼭대기 |
| **Frame Pointer** | 현재 함수 스택 프레임의 기준점 |

스택 포인터와 프레임 포인터는 **함수 인자, 지역 변수, 반환 주소**를 담는 스택을 관리하는 데 쓰인다.

### 4. Process API — 어떤 OS든 반드시 제공하는 인터페이스

실제 API(`fork()`, `exec()` 등)는 다음 챕터의 몫이고, 여기서는 "어떤 현대 OS든 어떤 형태로든 제공하는" 다섯 가지 기능만 짚는다.

| API | 하는 일 | 사용자 관점 예시 |
|---|---|---|
| **Create** | 새 프로세스 생성 | 셸에 명령을 입력하거나 앱 아이콘을 더블클릭할 때 |
| **Destroy** | 프로세스를 강제로 종료 | 폭주하는 프로세스를 kill |
| **Wait** | 프로세스가 끝날 때까지 대기 | 부모가 자식 종료를 기다림 |
| **Miscellaneous Control** | 일시 중지(suspend)와 재개(resume) | 잠깐 멈췄다 다시 실행 |
| **Status** | 상태 정보 조회 | 얼마나 오래 실행됐는지, 지금 어떤 상태인지 |

### 5. 프로그램은 어떻게 프로세스가 되는가 (Process Creation)

디스크의 실행 파일이 살아 움직이는 프로세스로 바뀌는 과정은 다음과 같다.

```
        Disk                          Memory (프로세스의 주소 공간)
   ┌─────────────┐                    ┌──────────────┐
   │ code        │ ──── ① Loading ──▶ │ code         │
   │ static data │                    │ static data  │
   └─────────────┘                    ├──────────────┤
     (Program)                        │ heap         │ ◀── ③ 힙 할당
                                      │      ↓       │
                                      │              │
                                      │      ↑       │
                                      │ stack        │ ◀── ② 스택 할당
                                      └──────────────┘     (argc, argv 채움)
                                            │
                                   ④ I/O 초기화 (fd 0,1,2)
                                            │
                                   ⑤ main()으로 점프 ──▶ 실행 시작
```

| 단계 | 작업 | 세부 내용 |
|---|---|---|
| **① 로딩** | 코드와 정적 데이터를 디스크에서 메모리(주소 공간)로 적재 | 실행 파일 포맷을 읽어 메모리에 배치 |
| **② 스택 할당** | 런타임 스택 메모리를 할당 | C 프로그램은 지역 변수·함수 인자·반환 주소에 스택을 씀. OS가 `main()`의 인자인 **`argc`와 `argv` 배열**을 스택에 채워 넣는다 |
| **③ 힙 할당** | 동적 할당용 힙 초기화 | 처음엔 작게 시작. `malloc()` 요청이 늘면 OS가 개입해 메모리를 더 준다. 연결 리스트·해시 테이블·트리 등에 필요 |
| **④ I/O 초기화** | 기본 파일 디스크립터 설정 | UNIX에서는 기본으로 **stdin / stdout / stderr 3개의 fd**가 열린 채 시작 |
| **⑤ 진입점으로 점프** | `main()`으로 제어를 넘김 | CPU 제어권이 새 프로세스로 이전되고 실행이 시작된다 |

#### Eager vs Lazy Loading

| 방식 | 동작 | 채택 |
|---|---|---|
| **Eager (즉시)** | 실행 전에 프로그램 전체를 한 번에 메모리로 적재 | 초기/단순한 OS |
| **Lazy (지연)** | 실행 중 필요한 코드·데이터 조각만 그때그때 적재 | 현대 OS |

지연 로딩이 실제로 어떻게 동작하는지는 **페이징(paging)과 스와핑(swapping)** 을 알아야 이해할 수 있고, 그건 메모리 가상화 파트의 주제다. 지금은 "실행 전에 OS가 디스크에서 메모리로 뭔가를 옮기는 일을 반드시 한다"만 기억하면 된다.

### 6. 프로세스 상태 (Process States)

단순화하면 프로세스는 세 가지 상태 중 하나에 있다.

| 상태 | 의미 |
|---|---|
| **Running** | 프로세서 위에서 실제로 명령어를 실행 중 |
| **Ready** | 실행할 준비는 됐지만, OS가 지금은 실행하지 않기로 선택한 상태 |
| **Blocked** | 어떤 연산을 수행한 결과, 다른 사건이 일어나기 전까지는 실행할 수 없는 상태 (예: 디스크 I/O 요청) |

```
                     Descheduled
        ┌─────────┐ ───────────▶ ┌─────────┐
        │ Running │              │  Ready  │
        └─────────┘ ◀─────────── └─────────┘
             │        Scheduled       ▲
             │                        │
   I/O: initiate                 I/O: done
             │                        │
             ▼                        │
        ┌─────────┐                   │
        │ Blocked │ ──────────────────┘
        └─────────┘
```

- Ready → Running: **스케줄됨(scheduled)**
- Running → Ready: **디스케줄됨(descheduled)**
- Running → Blocked: I/O를 시작하면 진입. 사건(I/O 완료)이 생길 때까지 OS가 붙잡아 둔다
- Blocked → Ready: I/O가 끝나면 다시 실행 가능 상태로. OS 판단에 따라 곧바로 Running이 될 수도 있다

#### 상태 추적 예시 1 — CPU만 쓰는 두 프로세스

| Time | Process0 | Process1 | Notes |
|---|---|---|---|
| 1~3 | Running | Ready | |
| 4 | Running | Ready | Process0 완료 |
| 5~7 | – | Running | |
| 8 | – | Running | Process1 완료 |

#### 상태 추적 예시 2 — I/O가 끼어들 때

| Time | Process0 | Process1 | Notes |
|---|---|---|---|
| 1~2 | Running | Ready | |
| 3 | Running | Ready | Process0가 I/O 시작 |
| 4 | **Blocked** | Running | Process0가 블록되어 Process1이 실행 |
| 5~6 | Blocked | Running | |
| 7 | **Ready** | Running | I/O 완료 |
| 8 | Ready | Running | Process1 완료 |
| 9~10 | Running | – | Process0 완료 |

**이 짧은 예시에도 OS의 정책적 결정이 두 번 들어 있다.**

1. Process0가 I/O를 걸었을 때 **Process1을 실행하기로 한 결정** → CPU를 놀리지 않으므로 자원 활용도가 올라간다
2. I/O가 끝난 시점(time 7)에 **Process0로 즉시 되돌아가지 않은 결정** → 이게 좋은 판단인지는 자명하지 않다

이런 결정을 내리는 주체가 **OS 스케줄러**이고, 별도의 챕터에서 다룬다.

### 7. OS가 프로세스를 추적하는 자료구조

OS도 결국 하나의 프로그램이고, 따라서 정보를 추적할 자료구조를 가진다.

- **프로세스 리스트(process list)** = **태스크 리스트(task list)**: ready 상태의 모든 프로세스 목록 + 지금 어떤 게 실행 중인지
- blocked 프로세스도 추적해야 한다. I/O가 완료되면 **정확히 그 프로세스를 깨워서** ready로 만들어야 하기 때문이다
- 프로세스 하나의 정보를 담는 개별 구조체를 **PCB(Process Control Block)** 또는 **프로세스 디스크립터(process descriptor)** 라 부른다

#### xv6 커널의 실제 구조체

```c
// 프로세스를 멈췄다 다시 시작하기 위해 xv6가 저장/복원하는 레지스터들
struct context {
  int eip;  int esp;  int ebx;  int ecx;
  int edx;  int esi;  int edi;  int ebp;
};

// 프로세스가 가질 수 있는 상태들
enum proc_state { UNUSED, EMBRYO, SLEEPING,
                  RUNNABLE, RUNNING, ZOMBIE };

// xv6가 각 프로세스에 대해 추적하는 정보
struct proc {
  char *mem;                  // 프로세스 메모리 시작 주소
  uint sz;                    // 프로세스 메모리 크기
  char *kstack;               // 이 프로세스용 커널 스택 바닥
  enum proc_state state;      // 프로세스 상태
  int pid;                    // 프로세스 ID
  struct proc *parent;        // 부모 프로세스
  void *chan;                 // 0이 아니면 chan에서 sleeping 중
  int killed;                 // 0이 아니면 kill된 상태
  struct file *ofile[NOFILE]; // 열린 파일들
  struct inode *cwd;          // 현재 디렉터리
  struct context context;     // 이 프로세스를 실행하려면 여기로 switch
  struct trapframe *tf;       // 현재 인터럽트의 트랩 프레임
};
```

**레지스터 컨텍스트(register context)** 가 핵심이다. 프로세스가 멈추면 레지스터 값들이 이 메모리 위치에 저장되고, 다시 실행할 때 이 값들을 실제 물리 레지스터로 되돌려 놓으면 프로세스가 하던 일을 이어서 한다. 이 기법이 **컨텍스트 스위치(context switch)** 다.

#### Running / Ready / Blocked 외의 상태들

| 추가 상태 | 설명 |
|---|---|
| **Initial (초기)** | 생성 중인 프로세스가 거쳐가는 상태 (xv6의 `EMBRYO`) |
| **Final / Zombie (좀비)** | **종료됐지만 아직 정리되지 않은 상태** |

**좀비 상태는 왜 필요한가?** 다른 프로세스(보통 부모)가 방금 끝난 자식의 **반환 코드(return code)** 를 확인할 수 있게 하기 위해서다. UNIX 계열에서 프로그램은 성공하면 0, 실패하면 0이 아닌 값을 반환한다. 확인이 끝나면 부모가 `wait()` 같은 호출을 해서 자식의 완료를 기다리고, **동시에 OS에게 "이제 이 프로세스 관련 자료구조를 정리해도 된다"고 알린다.**

### 8. 한 장 요약

| 개념 | 핵심 |
|---|---|
| **프로세스** | 실행 중인 프로그램. OS의 가장 기본적인 추상화 |
| **machine state** | 주소 공간의 메모리 내용 + CPU 레지스터(PC, SP 포함) + I/O 정보(열린 파일) |
| **CPU 가상화** | 시분할로 물리 CPU 몇 개를 "무한한 CPU"처럼 보이게 하는 환상 |
| **메커니즘 vs 정책** | How(컨텍스트 스위치) vs Which(어떤 프로세스를 실행) |
| **Process API** | create, destroy, wait, misc control, status |
| **프로세스 상태** | running / ready / blocked (+ initial, zombie) |
| **프로세스 리스트** | 모든 프로세스 정보. 각 항목이 PCB |

### 운영 관점

1. **`ps`의 상태 코드는 이 챕터의 상태 다이어그램 그대로다**
   - Linux에서 `ps aux`의 STAT 컬럼(`R` running/runnable, `S` sleeping, `D` uninterruptible sleep, `Z` zombie)은 OSTEP의 running/ready/blocked/zombie와 거의 1:1로 대응한다.
   - 특히 **`D` 상태는 "I/O: initiate"로 blocked에 들어간 프로세스**다. `D` 상태 프로세스가 쌓이고 load average만 치솟는데 CPU는 한가한 장애 패턴은, "blocked는 CPU를 쓰지 않는다"는 이 챕터의 정의를 알면 바로 스토리지/네트워크 쪽으로 진단 방향을 좁힐 수 있다.

2. **컨테이너의 좀비 프로세스 문제는 "왜 zombie 상태가 존재하는가"를 알아야 풀린다**
   - 원문은 좀비 상태의 존재 이유를 "부모가 자식의 반환 코드를 확인하고, OS에 정리를 지시하기 위해"라고 설명한다. 뒤집으면 **부모가 `wait()`을 하지 않으면 자식은 영원히 좀비로 남는다.**
   - 컨테이너에서 PID 1로 뜬 애플리케이션이 reaping을 하지 않아 좀비가 쌓이는 흔한 문제, 그리고 `tini`/`dumb-init` 같은 init 프로세스를 넣는 관행이 정확히 이 지점에서 나온다. 원문이 던진 개념의 실무적 귀결이다.

3. **"메커니즘과 정책의 분리"는 Kubernetes 설계에도 그대로 있다**
   - kube-scheduler는 "어떤 노드에 파드를 둘 것인가"라는 **정책(which)** 만 담당하고, kubelet + 컨테이너 런타임이 "실제로 어떻게 띄울 것인가"라는 **메커니즘(how)** 을 담당한다.
   - 그래서 스케줄러를 커스텀 스케줄러로 교체해도 런타임 계층을 손대지 않는다. OS가 50년 전에 정립한 모듈화 원칙이 오케스트레이터 계층에서 반복된다.

### 학습 관점

4. **"프로세스 = 실행 중인 프로그램"이라는 한 줄이 실제로는 6개 항목의 체크리스트다**
   - 주소 공간(코드/정적데이터/힙/스택), 레지스터(PC/SP/FP), 열린 파일. 이 목록이 곧 **컨텍스트 스위치에서 저장·복원해야 할 것들의 목록**이고, 나중에 "컨텍스트 스위치 비용"을 논할 때 그 비용의 구성 요소가 된다.
   - xv6의 `struct context`가 레지스터 8개뿐인 걸 보면, 컨텍스트 스위치의 직접 비용이 왜 "생각보다 싸고", 진짜 비용은 캐시/TLB 무효화 같은 간접 비용인지 감이 잡힌다. (후자는 이 챕터 범위 밖이며 내 추론이다.)

5. **lazy loading 언급이 "컨테이너 콜드 스타트"의 이론적 배경이다**
   - 원문은 현대 OS가 실행 전 전체를 적재하지 않고 필요한 조각만 적재한다고만 짧게 말하고 페이징 챕터로 넘긴다.
   - 이미지 lazy pulling(eStargz, SOCI 등)이 컨테이너 기동 시간을 줄이는 원리가 결국 같은 아이디어의 한 계층 위 버전이다. **"전부 준비될 때까지 기다리지 말고, 실제 접근이 일어날 때 가져와라."**
